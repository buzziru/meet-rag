# 노트북 작성 규약

`notebooks/` 아래 `.ipynb` 작성 기준이다.

## 1. 파일명과 분리 단위

- `NN_단계명.ipynb`
- 한 단계가 여러 작업으로 나뉘면 `NN_MM_작업명.ipynb`. 예: `04_01_전처리.ipynb`, `04_02_인덱싱.ipynb`, `04_03_평가.ipynb`
- 노트북 하나 = 목적 하나. 길어지면 `MM`으로 쪼갠다.

## 2. 셀 구조

| 순서 | 내용 |
| --- | --- |
| 1 | import 전부 |
| 2 | config (경로, 파라미터). 값만 (§6) |
| 3 | 헬퍼 함수. 있을 때만 (§2.2) |
| 4 | 시드 고정. 필요할 때만 (§5) |

- 작업 중 아래쪽에 추가한 import는 커밋 전에 1번 셀로 올린다.
- **코드 셀 하나 = 목적 하나, 논리 하나.** 성격이 다른 것을 한 셀에 넣지 않는다.
- 안정화된 코드는 함수로 묶고, 검증이 끝나면 `src/rag/`로 옮긴다 (§9).

### 2.1 config 셀에는 값만 둔다

함수 정의를 config 셀에 섞지 않는다. config는 "무엇을 쓸지"이고 함수는 "어떻게 할지"다.
같은 셀에 있으면 값 하나를 고치려고 함수 정의까지 다시 실행하게 되고, 셀의 목적이 흐려진다.

### 2.2 헬퍼 함수는 별도 셀에

노트북 전체에서 재사용하는 함수는 config 다음 셀에 모은다. 한 군데서만 쓰는 함수는
쓰는 자리 근처에 둔다. 함수가 없으면 이 셀 자체를 두지 않는다.

## 3. 마크다운

- 워크플로우 단계(데이터 로딩 / 전처리 / 인덱싱 / 검색 / 평가 등)를 `##` 헤더로 구분해 목차가 잡히게 한다.
- 노트북 최상단에 목적 한 줄을 적는다. 파일명만으로 구분되지 않는 `NN_MM` 분할일수록 필요하다.

## 4. 과정의 확인

- 탐색 단계에서는 **중간 결과를 출력으로 확인하며 진행한다.** 한 셀이 무엇을 만들었는지 다음 셀로 넘어가기 전에 눈으로 본다.
- 이 출력은 부산물이 아니라 노트북의 본문이다. 독자가 로직을 따라오는 근거이자, 작성 과정 자체의 기록이다.
- 확인 방식은 데이터 모양에 맞춘다. DataFrame은 `.shape` / `.head()` / `.dtypes`, 리스트·딕셔너리는 길이와 앞부분 몇 건, 텍스트는 샘플 한두 건, 필터링·조인은 처리 전후 건수.
- **최종 정리 단계에서 중간 출력을 걷어낼지는 사용자가 판단한다.** Claude가 임의로 확인 셀을 지우거나 여러 확인을 한 셀로 합치지 않는다.

## 5. 시드

- **무작위성이 재현성에 영향을 주는 노트북에서만** 고정한다. 데이터 분할, 표본 추출, 학습이 여기 해당한다.
- 무작위성이 없는 노트북에 시드 셀을 두지 않는다. 효과 없는 시드 셀은 재현성이 확보됐다는 착시를 준다.
- 고정할 때는 사용하는 라이브러리 전부에 건다 (`random`, `numpy`, 필요 시 `torch`).
- 표본을 추출했다면 시드와 별개로 **추출 결과 ID 목록을 파일로 남긴다.** 라이브러리 버전이 바뀌면 시드는 같은 표본을 보장하지 못하지만 목록은 깨지지 않는다.

## 6. 설정

- 목표 형태는 `configs/*.yaml`이다. 노트북 config 셀은 yaml을 로드하는 자리다.
- 탐색 중이라 값이 확정되지 않은 동안은 노트북 셀에 상수로 둔다.
- `src/rag/`로 이관하는 코드와 SLICE·EXP 실행에 쓰는 값은 `configs/`로 옮긴다. 코드에 직접 쓰지 않는다.
- 경로 기준도 config 셀에 모은다. 노트북은 `notebooks/`에서 실행되므로 `ROOT = Path.cwd().parent`.

### 6.1 무엇을 대문자로 올릴 것인가

PEP 8은 상수의 표기(ALL_CAPS)와 위치(최상단)만 정하고 **개수 상한을 두지 않는다.**
개수는 기준이 아니다. 기준은 "대문자가 가리키는 것이 일관된가"다.

노트북은 모듈이 아니라 셀 간에 전역 네임스페이스를 공유하는 세션이다. 그래서 이름만 보고
**위에서 정해진 값인지, 이 셀이 만들어낸 중간 결과인지** 구분되어야 한다. 세 줄이면 된다.

1. **대문자는 실행 전에 값이 정해지는 것에만.** 파일시스템을 읽은 결과나 데이터에서 뽑아낸 값은
   상수처럼 보여도 소문자로 둔다. `SRC_ZIPS = sorted(DATA.rglob(...))`, `FIELDS = list(rec)` 같은 것이 여기 해당한다
2. **한 셀에서만 쓰는 값은 그 셀에 소문자로 둔다.** 상단에 올리는 근거는 "여러 셀이 공유한다"이지 "중요하다"가 아니다
3. 이 둘을 지켰으면 **나머지는 개수를 세지 않는다**

관련 상수를 dict로 묶는 것은 이름 수를 줄이려는 목적이라면 하지 않는다. 접근만 한 단계 깊어진다.

## 7. 출력과 커밋

- **셀 출력을 남긴 채 커밋한다.** 검증 결과가 기록의 일부다.
- 출력 제거 자동화(`nbstripout` 등)를 쓰지 않는다. 개인 프로젝트이고, 작성 중에는 커밋하지 않고 노트북이 완료된 시점에 커밋하므로 출력으로 인한 diff 잡음이 생기지 않는다.
- 국회 회의록 발언 원문은 공개 자료이므로 출력에 남겨도 된다.
- 다만 `data/` 아래 파일 자체는 어떤 형태로도 커밋하지 않는다 (AI Hub 재배포 제한). 노트북에서 만든 중간 산출물을 저장할 때 경로를 확인한다.
- 용량 관리는 사용자가 필요한 시점에 직접 clear output으로 한다.

## 8. 재현성

- 커널은 `.venv`를 선택한다. Jupyter 서버 패키지는 설치하지 않고 에디터(VS Code, Cursor) 안에서 연다.
- 재현의 기준은 코드와 설정이다. 시드(§5)를 고정하고 설정값을 `configs/`에서 받으면(§6) 같은 입력에서 같은 결과가 나온다.
- **실행 순서와 `execution_count`는 규약으로 강제하지 않는다.** 셀을 오가며 실행한 흔적이 남아도 커밋을 막지 않는다. 노트북이 맞게 돌았는지는 작성자가 출력을 보고 판단한다.

## 9. 패키지 이관

- 노트북은 검증 장소다. 파이프라인 로직을 영구히 두지 않는다.
- SLICE의 완료 기준은 노트북이 아니라 `src/rag/` 코드와 명령으로 확인한다.
- 검증이 끝난 코드는 `src/rag/`로 옮기고, 옮길 때 타입힌트와 Google 스타일 독스트링(`Args:` / `Returns:` / `Raises:`)을 붙인다.
- 이관 후 노트북에는 함수 호출과 결과 확인만 남긴다.
