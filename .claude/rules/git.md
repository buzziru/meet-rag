# 브랜치·커밋·PR 규약

## 기본 규칙

1. `main`에 직접 커밋하지 않는다. 예외는 아래 "핸드오프" 절차의 `docs/STATUS.md` 하나뿐이다.
2. 모든 작업은 최신 `main`에서 딴 브랜치에서 시작한다.
3. 브랜치 하나에는 목적 하나만 둔다.
4. 작업이 끝나면 PR을 만든다.
5. 사용자는 PR 화면에서 diff를 한 번 읽는다.
6. 테스트와 린트가 통과한 뒤 병합한다.
7. 병합 후 브랜치를 삭제한다. 원격 브랜치는 사용자가 병합하며 지우고, 로컬 브랜치는 Claude가 아래 "main 맞추기"에서 지운다.

## 세션 시작

- `git branch --show-current`로 현재 브랜치를 확인한다.
- `main`이면 코드나 문서를 고치기 전에 브랜치를 만든다.
- Orca가 만든 worktree는 `buzziru/<이름>` 브랜치로 시작한다. 아래 "브랜치" 절의 접두사가 없는 이름이므로, 작업 전에 최신 `main`에서 규약 이름의 브랜치를 새로 만들어 옮긴다(예: `git switch -c chore/<이름> origin/main`, 접두사는 작업 종류에 맞춘다). Orca가 붙인 브랜치는 worktree를 지울 때 함께 정리한다(main 맞추기 6, ADR-0064).
- 다른 목적의 브랜치에 있으면 사용자에게 알리고 정리한 뒤 진행한다.
- `main`에 있거나 지금 브랜치의 PR이 병합됐으면 아래 "main 맞추기"를 한다. PR 병합을 확인할 때와 핸드오프 1단계에서도 한다.

## main 맞추기

main을 원격과 맞출 때마다 병합된 로컬 브랜치도 함께 지운다. 사용자가 병합하며 원격 브랜치만 지우므로, 로컬 브랜치는 따로 지우지 않으면 쌓인다(2026-10-12 세션 시작 때 병합된 로컬 브랜치 12개).

1. `git status --short --untracked-files=no`가 비어 있는지 본다(추적하지 않는 파일은 switch해도 그대로 남는다). 커밋하지 않은 변경이 있으면 switch하지 않고 사용자에게 알린다
2. `git switch main`, `git fetch --prune`, `git pull --ff-only`
3. `git branch --merged main -vv`에 나온 브랜치(`main` 제외)를 `git branch -d`로 지운다. `-D`는 쓰지 않는다. 그중 원격 브랜치가 남아 있던(upstream이 있고 `gone`이 아닌) 브랜치는 지운 뒤 사용자에게 알린다. 원격 삭제는 사용자 몫이다
4. `git branch --no-merged main -vv`에서 원격이 `gone`인 브랜치는 지우지 않고 사용자에게 알린다. 병합하지 않고 닫은 PR일 수 있다. 원격이 있거나 아직 올리지 않은 작업 브랜치는 알리지 않는다
5. 병합을 확인한 PR마다 사용자 코멘트(`gh pr view N --comments`, `gh api repos/{owner}/{repo}/pulls/N/comments`)를 점검한다. 대상은 2에서 받아 온 병합 커밋(`git log --merges --format=%s ORIG_HEAD..HEAD`의 `Merge pull request #N`)과 이 세션에서 병합을 확인한 PR이다. 로컬 브랜치로 찾지 않는다. 로컬 브랜치는 원격이 지워진 뒤에도 여러 이유로 남거나 처음부터 없을 수 있다. 답글이나 반영 커밋이 없는 코멘트는 바로 반영한다. 진행 중인 작업과 구별되는 일이면 처리 방법(하위 세션을 만들어 처리, STATUS "다음 행동"에 기록 등)을 사용자에게 묻고 그 결정을 따른다. 사용자는 병합 직전에 단 코멘트를 후속 PR에서 반영할 것으로 보고 병합한다(사용자 설명 2026-10-20, PR #116 코멘트). 이 점검이 없으면 코멘트가 빠진다(PR #92 코멘트가 병합 뒤 반영되지 않음)
6. `git worktree list`에서 병합된 커밋에 머문 worktree(하위 세션이 쓰던 `.claude/worktrees/<이름>` 등)를 정리한다. 커밋하지 않은 변경이 없고 안에 링크(junction·심볼릭 링크)가 없는지 먼저 보고, 링크가 있으면 링크만 지운 뒤(`(Get-Item <링크>).Delete()`) `git worktree remove`, `git worktree prune`을 한다. `_workspace/` 진행 기록은 메인 `_workspace/`로 옮기고(`mv`. `cp`면 원본이 남아 훅이 계속 막는다), 옮긴 것을 확인한 다음 명령에서 지운다. `_workspace/`는 .gitignore 대상이라 `git worktree remove`가 경고 없이 함께 지운다. 확인과 삭제를 한 명령에 묶으면 옮기지 않은 기록이 지워진다(2026-10-26 하위 세션 진행 기록 1개). 파일이 남아 있으면 `data_delete_guard` 훅이 삭제를 막는다(ADR-0062). Orca가 만든 worktree(위치 `.claude/worktrees/<이름>`, 브랜치 `buzziru/<이름>`. Orca 설정 Worktree Location `.claude/worktrees`, Nest Workspaces 끔, 사용자 설정 2026-10-27)는 미커밋 변경 확인, 링크 확인과 링크만 삭제, `_workspace/` 기록 `mv`와 옮긴 것 확인을 모두 마친 뒤 다른 명령에서 `git worktree remove` 대신 `orca worktree rm --worktree path:<경로> --json`으로 지운다. 이 명령은 `data_delete_guard` 훅이 링크·`_workspace/`를 검사하지 않으므로 이 확인이 유일한 보호다. 폴더와 브랜치를 함께 지우고 몇 초 뒤 `git worktree list`에 반영된다. 지운 뒤 Orca가 붙인 `buzziru/<이름>` 브랜치가 남아 있으면 `git branch -d`로 지운다(ADR-0064). 진행 중인 세션의 worktree는 건드리지 않는다. 브랜치만 지우고 worktree를 두면 폴더가 쌓인다(S21 worktree가 PR #136 병합 뒤에도 남음, 2026-10-22). 링크째 지우면 원본 `data/`가 지워진다(ADR-0058)

## 브랜치

- 접두사: `feat/`(SLICE), `exp/`(EXP), `docs/`, `fix/`, `chore/`
- SLICE·EXP 번호를 넣는다. 예: `feat/s01-data`, `exp/exp001-hybrid`
- 영문 소문자, 숫자, 하이픈만 쓴다. 한글은 git이 이스케이프해 출력한다
- 기각된 실험도 병합한다. EXP 문서, config, 코드가 함께 남아야 재현할 수 있다. 실험 코드는 config로 켜는 형태로 만들어 기준 설정의 동작을 바꾸지 않는다

## 커밋

- 형식: `<타입>: <요약>`. 타입은 `feat`, `fix`, `exp`, `docs`, `test`, `refactor`, `chore`. 다른 타입(`perf` 등)이면 `commit_type_guard` 훅이 커밋을 막는다(ADR-0055). 타입 목록을 바꾸면 훅의 `TYPES`도 같이 바꾼다
- 요약은 한국어 한 줄로 무엇을 바꿨는지, 본문에는 왜 바꿨는지 쓴다
- 커밋 하나에 논리적 변경 하나. 코드와 그 테스트는 같은 커밋에 둔다
- 커밋 전에 `data/`와 `.env`가 스테이징되지 않았는지 확인한다. 저장소는 공개되고, AI Hub 데이터는 재배포가 제한된다

## PR

Claude가 브랜치를 원격에 올리고 `gh pr create`로 PR을 만든다. diff 확인과 병합은 사용자가 한다.

1. `uv run pytest -q`, `uv run ruff check .` 통과를 확인한다. PR 내용이 사용자 결정에 따라 바뀌는 작업이면 결정을 받아 반영한 뒤 올린다(사소한 결정은 PR 코멘트로 받는다). 결정 전에 올리면 PR을 다시 고치게 된다
2. `protocol-auditor`로 브랜치 diff를 평가 프로토콜·금지 조항에 대조하고 위반을 고친다. meet-rag 흐름 밖에서 올리는 PR도 같다(작업 종류는 meet-rag 스킬의 감사 단계를 따른다). 사용자 요청에 따라 self-review를 한다. 작성 맥락과 분리하려고 `/code-review`나 subagent로 실행한다. self-review를 하면 3의 가이드는 그 지적을 반영한 뒤에 부른다(코드 수정이 나오기 쉬워, 먼저 부르면 반영 전 diff를 설명한다). self-review가 없으면 가이드는 검증·감사와 병렬로 부른다(meet-rag 스킬 A4, ADR-0056)
3. `pr-briefer`를 불러 받은 리뷰 가이드(`## 리뷰 가이드`)를 본문 맨 위에 둔다. meet-rag 흐름 밖에서 올리는 PR도 같다. 바뀐 파일이 모두 `docs/` 아래면 부르지 않고, `docs/SPEC.md`·`docs/DECISIONS.md`가 바뀌었거나 test 점수를 기록했을 때만 본문 맨 위에 `위험도: 단방향(…)` 한 줄을 적는다. 괄호에는 걸린 규칙만 적고(SPEC R1, DECISIONS R2, test 점수 R6), 규칙마다 해당 변경을 짧게 붙인다. 예: DECISIONS만 바뀌면 `위험도: 단방향(R2: D-47 추가)`. 걸리지 않은 규칙까지 적으면 사용자가 없는 변경을 찾게 된다(이슈 #142, PR #141이 R2만 걸렸는데 R1·R2·R6을 적음). 이어서 대응 문서(SLICE·EXP), 변경, 검증 결과, self-review 지적과 반영 여부, 범위 밖 항목을 적는다
4. Claude 앱(데스크톱 앱 Code 탭)에서 PR을 만들었으면 `ccd_pr get_status`로 그 PR이 세션에 연결됐는지와 `auto_fix`가 켜졌는지 확인한다. 연결되지 않았으면 `bind_pr`로 연결하고, `auto_fix`가 꺼져 있으면 사용자에게 알린다. 앱의 자동 수정이 세션에 알려 주는 것은 CI 실패와 다른 계정의 코멘트다. PR 작성자와 같은 계정(`buzziru`)의 코멘트는 알려 주지 않는다(데스크톱 앱 문서 "Auto-fix"). Orca 세션에는 이 도구가 없고 PR 연결·CI 알림 기능도 없으므로 이 단계를 하지 않는다. 사용자 리뷰는 아래 5처럼 대화로 받는다(ADR-0064)
5. 사용자는 PR 리뷰를 대화 세션에 남긴다(사용자 결정 2026-10-20). PR 코멘트는 같은 계정이라 세션이 받지 못하고, 코멘트를 달고 따로 알리는 것은 사용자에게 두 번 일이다. 대화로 받은 리뷰를 처리해 커밋하면 push하고 아래를 한다. 사용자는 PR 화면에서 diff를 한 번 읽고 판단하므로, 본문이 반영 전 상태로 남으면 이미 해결된 질문을 다시 보거나 반영으로 새로 생긴 판단 지점을 놓친다
   - PR에 댓글로 처리 기록을 남긴다. 리뷰 항목마다 사용자 리뷰 요지, 처리 내용, 커밋 해시를 적고, 해석해 반영한 것은 입력→동작 사례 하나를 붙인다(meet-rag 스킬 "질문과 해석"). 반영하지 않았거나 미룬 것은 이유와 어디(STATUS, 후속 PR)에 적었는지를 적는다. 리뷰와 처리가 대화에만 있으면 git 기록에 남지 않는다
   - 본문에 "리뷰 반영" 절을 두고 같은 내용을 짧게 적는다(항목, 반영 내용, 커밋 해시)
   - 리뷰 가이드의 "판단할 곳"을 지금 diff에 맞춘다. 번호가 바뀌면 "구조" 그림의 번호(①②)도 맞춘다. 리뷰로 정해진 질문은 지우거나 결정을 적고, 반영하면서 새로 생긴 판단(리뷰를 해석해 정한 부분 등)을 더한다. 위험도와 변경 절도 맞춘다
   - 사용자가 PR에 직접 코멘트를 남긴 경우(병합 직전 코멘트 등, main 맞추기 5)도 같게 처리하고, 댓글 대신 그 코멘트에 답글을 단다

병합은 merge commit으로 한다. squash나 rebase를 쓰면 EXP 문서에 적은 커밋 해시가 `main`에서 사라진다.

## 핸드오프

STATUS는 세션마다 덮어쓰는 스냅샷이고 코드가 아니므로 PR을 거치지 않는다.

- 작업 PR이 병합된 뒤 핸드오프하면 `main`에 직접 커밋한다
  1. 위 "main 맞추기"로 원격과 맞춘다
  2. `docs/STATUS.md`를 덮어쓴다
  3. `git add docs/STATUS.md` 후 `git diff --cached --name-only`가 이 파일 하나뿐인지 확인한다
  4. `docs: STATUS 갱신`으로 커밋하고 원격에 올린다
- 작업 도중 세션이 끝나면 STATUS 커밋을 작업 브랜치에 태운다
- 다른 파일을 고칠 거리가 생기면 이 경로를 쓰지 않고 브랜치를 만든다
