# exp-judgment: 실험 판정 절차

판정 기준은 실행 전에 EXP 문서에 고정되어 있다. 결과를 본 뒤 기준을 해석하면 어떤 결과든 채택할 이유를 찾게 되므로, 이 절차는 기준을 그대로 적용하고 해석은 판정과 분리해 적게 한다.

1\~5절은 검색 EXP(SPEC 판정 절, dev-full Recall@5) 절차다. 생성 EXP(EXP 문서 판정 기준에 SPEC "생성 단계 평가 > 판정"이 적힌 경우)는 6절을 따른다. 3절의 SPEC 우선 원칙과 4절의 해석 분리는 6절에도 적용한다.

## 1. 입력 확인

- EXP 문서의 "기준 실험", "바꾸는 것", "판정 기준", "실행" 절을 읽는다
- 기준 실험과 후보 실험의 순위 파일이 둘 다 dev-full(코퍼스 38,516건, dev 질의 전체)인지 확인한다. 한쪽이라도 dev-small이면 판정하지 않고 보고한다
- 두 파일의 질의 집합(`qid`)이 같은지 확인한다. 다르면 paired 비교가 성립하지 않는다

## 2. 계산

`src/rag/eval/`의 평가 명령으로 계산한다(명령은 `CLAUDE.md` "명령" 절이나 `docs/slices/03-eval.md`에 있다). 필요한 값:

- 두 실험 각각의 Recall@1·5·10, MRR@10 (전체, 회의구분별, `qna_type`별)
- Recall@5 차이의 paired bootstrap: 재표본 단위 회의, 10,000회, seed 20260929. 점 추정과 95% 구간

S9 이후 EXP는 multi-doc 결과도 적는다(PLAN). `src/rag/eval_multi/`의 비교 명령으로 기준·후보 multi-doc 순위 파일의 지표 차이와 95% 구간을 낸다. 판정에는 쓰지 않는다(SPEC "보조 관찰"). 예외는 메타데이터 가설이다(3절).

메타데이터 가설이면 메인이 준 single-doc 비교 결과 JSON(`rag.eval.compare --out`)을 `--single`로 넘겨 판정까지 함수로 낸다(S18, D-43): `uv run python -m rag.eval_multi.compare --base <기준-multidoc.csv> --cand <후보-multidoc.csv> --single <single-doc 결과.json>`. 결과 JSON 끝의 `metadata_verdict`(`verdict`, `stage`, Recall@5·Complete@5 차이와 구간, 읽은 single-doc 결과의 경로·sha256)가 판정이다. 명령이 single-doc 결과의 형식(dev-full 비교인지), 같은 실험의 순위 쌍인지, 지금 `min_gain`으로 다시 판정한 값이 기록과 같은지를 보고 어긋나면 멈춘다. 멈추면 판정하지 않고 그 메시지를 보고한다. 명령 대신 `metadata_result`를 Python에서 직접 부르면 `check_single`을 먼저 불러 같은 확인을 거친다(PR #129, 사용자 결정 2026-10-21). 3절 표를 손으로 적용해 판정을 대신하지 않는다. 손으로 적용하면 형식·짝 확인이 빠진다.

평가 모듈에 필요한 기능이 없으면 직접 구현하지 말고 그 사실을 보고한다.

## 3. 판정

SPEC 판정 절을 적용한다. SPEC이 EXP 문서에 우선한다. EXP 문서 "판정 기준"이 SPEC과 다르면(더 엄격하든 느슨하든) SPEC으로 판정하고, 차이와 EXP 문서에 적힌 이유를 결론 앞에 보고한다. 차이가 사용자 요청이나 판단에서 나온 것이면 메인이 사용자에게 어느 기준을 쓸지 묻는다(PR #48 코멘트). 아래 표는 SPEC의 요약이고, 둘이 다르면 SPEC을 따른다. SPEC이 바뀌어도 이 표가 그대로 남아 옛 규칙으로 판정할 수 있기 때문이다(D-18 개정 때 이 표가 옛 규칙이었다).

single-doc (dev-full Recall@5, 회의 단위 bootstrap):

| 조건 | 판정 |
| --- | --- |
| 95% 구간 하한 > 0 이고 점 추정 차이 ≥ +1.0%p | 채택 |
| 95% 구간 상한 < 0 | 기각 |
| 그 밖 | 보류 |

메타데이터 가설(PLAN에 [메타데이터]로 표시된 가설이고, EXP 문서 판정 기준에도 SPEC "메타데이터 가설의 판정"이 적힌 경우. 둘 중 하나만 맞으면 판정하지 않고 보고한다): single-doc이 채택·기각이면 그대로 쓰고, 보류이면 multi-doc(`pool_id` 단위 bootstrap)으로 정한다.

| multi-doc 조건 | 판정 |
| --- | --- |
| Recall@5 차이 95% 구간 하한 > 0, 점 추정 ≥ +1.0%p, Complete@5 차이 95% 구간 상한 ≥ 0 | 채택 |
| Recall@5 차이 95% 구간 상한 < 0 | 기각 |
| 그 밖 | 보류 |

이 표는 `metadata_verdict`가 하는 판정의 요약이다. 판정 값은 2절 명령의 결과를 쓴다.

+1.0%p는 사람 판단 없이 채택하는 선이다(D-35, 메타데이터 가설의 multi-doc 단계도 같다). multi-doc 단계 보류 중 Recall@5 점 추정이 +1.0%p 미만이고 95% 구간 하한 > 0이면 판정은 보류로 두고 결론에 "예외 검토 대상(D-35)"으로 적는다. 예: multi-doc Recall@5 +0.8%p [+0.2, +1.4], Complete@5 구간 상한 ≥ 0이면 `metadata_verdict`는 보류이고 예외 검토 대상이다. 예외로 올릴지는 사용자가 D-33의 선례로 정하므로 판정·권고로 정하지 않는다.

결론에는 어느 단계(single-doc, multi-doc)에서 판정이 정해졌는지 적는다. multi-doc에서 채택했으면 SPEC 단서(세트가 메타데이터 검색에 유리함, test로 다시 확인할 수 없음)를 함께 적는다.

보류이면 무엇을 더 확인하면 판정할 수 있는지 한 줄 적는다.

## 4. 해석

판정과 분리해 적는다. 판정을 바꾸는 근거로 쓰지 않는다.

- 층별 차이: 회의구분·`qna_type` 중 차이가 전체와 방향이 다르거나 크기가 두드러진 층. 층의 질의 수가 작으면 함께 적는다
- 근거 강도를 구분한다: 계산한 수치, 수치에서 읽은 경향, 원인 추정. 원인 추정은 추정이라고 적는다
- SPEC "평가 결과 해석의 한계"가 이 결과에 특히 걸리는 경우만 적는다. 예: BM25 계열 실험은 질의가 정답 문서를 보고 생성되어 어휘 매칭에 유리할 수 있다

## 5. 기록 형식

EXP 문서 "결과" 절:

```markdown
## 결과
- dev-full Recall@5: 후보 0.xxxx / 기준 0.xxxx / 차이 +x.xx%p (95% CI [a, b], 회의 단위 bootstrap 10,000회)
- Recall@1 / @10 / MRR@10: 후보 … / 기준 …
- 층별: (두드러진 층만)
- multi-doc: Recall@5 / Complete@5 차이와 95% 구간(`pool_id` 단위), 유형별 Recall@5 차이. 메타데이터 가설이면 판정 근거이고, 아니면 관찰이라고 적는다
- 지연·비용: 질의당 검색 지연(인덱스 로딩을 뺀 값을 앞에 둔다. 전체 실행 시간밖에 없으면 로딩 포함이라고 밝힌다), 운영 비용(과금 방식, 월 비용 추정, 추가 인프라, 상주 메모리·디스크). 메인이 준 값이면 그렇다고 적는다. 운영 판단은 질의당 지연으로 하므로 전체 실행 시간의 배수를 결론에 앞세우지 않는다. 인덱스 로딩 등 시작할 때 한 번 드는 시간은 콜드 스타트로 따로 적는다
- 실행: `명령` / 커밋 abc1234 / 소요 시간
```

EXP 문서 "결론" 절: 판정 하나와 이유 한두 줄. 첫 줄은 `- SPEC 판정: 채택|기각|보류`로 쓴다(EXP-001\~016은 첫 줄 형식이 세 가지로 갈렸다, ADR-0074). SPEC 판정의 채택은 성능 기준이고 기준 설정 반영(운영 채택)은 사용자가 비용과 함께 정하므로, 결론에서 둘을 섞지 않는다(D-26). EXP 문서에 판정과 별개로 미리 정한 사용자 결정(보류 판정의 예외 채택 등, D-28)이 있으면 판정 항목과 나눠 적는다. 기각 판정을 채택으로 바꾸는 결론은 쓰지 않는다(PR #65 사용자 코멘트)

`docs/EXPERIMENTS.md` 한 줄:

```markdown
| EXP | 기준 | 바꾼 것 | dev-full R@5 | 차이 (95% 구간) | multi-doc R@5 차이 (95% 구간) | multi-doc C@5 차이 (95% 구간) | 판정 (단계) |
```

## 6. 생성 EXP

판정 규칙은 SPEC "생성 단계 평가 > 판정"(D-53), 기준값은 `configs/eval/gen_v1.yaml`(D-55)이다. 판정은 `rag.gen_eval.compare`가 낸다(S27). 이 명령은 입력이 gen-full인지, 같은 judge로 채점했는지를 보고 어긋나면 멈추므로, 표를 손으로 적용하면 그 확인이 빠진다.

### 입력 확인과 계산

- 메인이 주는 것: 기준·후보 judge 결과 파일(`paths.gen_judge`), 메인이 `--out`으로 쓴 비교 결과 JSON, 기준·후보 각각의 `rag.gen_eval.report` 명령(override 포함)
- `uv run python -m rag.gen_eval.compare --base <기준 judge.jsonl> --cand <후보 judge.jsonl>`를 `--out` 없이 직접 돌린다(파일을 쓰지 않는다). 명령이 멈추면(같은 파일, gen-full 330질의가 아님, judge 설정이 다르거나 섞임, S22 이전 형식) 판정하지 않고 그 메시지를 보고한다. gen-small(작동 확인 20질의) 결과는 판정에 쓰지 않는다(SPEC)
- 출력의 `verdict`·`failed`·`metrics`와 `base.run_sha256`·`cand.run_sha256`이 메인이 준 JSON과 같은지 본다. 다르면 판정하지 않고 차이를 보고한다
- 기준·후보 report를 돌려 판정에 쓰지 않는 보고 값(아래)을 읽는다

### 판정

`verdict`를 그대로 판정으로 쓰고 `failed`(걸린 조건)를 함께 적는다. 아래 표는 SPEC의 요약이고, 둘이 다르면 SPEC을 따른다.

| 조건(차이는 후보 − 기준, 회의 단위 paired bootstrap 95% 구간) | 판정 |
| --- | --- |
| 종합 지표 하한 > 0, 점 추정 ≥ δ, 충실성 하한 ≥ 충실성 하락 허용폭(음수), 관련성 하한 ≥ 관련성 하락 허용폭(음수), 과잉 거부율 상한 ≤ δ_r | 채택 |
| 종합 지표 상한 < 0 | 기각 |
| 그 밖 | 보류 |

- 보류: 걸린 조건(종합 지표 구간, 점 추정 < δ, 충실성 하락, 관련성 하락, 과잉 거부 증가)을 결론에 적는다. 예외로 기준에 올릴지는 사용자가 기준별 값을 보고 정한다(D-28·D-33, D-53 결정 6). 메인과 judge는 판정이나 권고로 정하지 않는다
- 기각: 걸린 안전 조건도 함께 적는다(판정은 바꾸지 않는다). 기각은 예외 채택 대상이 아니다(ADR-0037)
- 보류이면 무엇을 더 확인하면 판정할 수 있는지 한 줄 적는다

### 보고할 값

- 기준별 기준·후보 평균, 차이, 95% 구간, 계산한 질의 수: 충실성, 답변 관련성, 종합 지표, 핵심 답변 포함도(보조), 과잉 거부율. 포함도는 판정에 쓰지 않지만 근거를 바꾸는 실험(H10 등)에서는 반드시 보고한다(D-53 결정 1)
- `check_settings_diff`(거부 문구·도입 문구·날짜 정규식의 차이)가 있으면 적는다. 지정 거부 문구를 쓰지 않은 거부는 거부로 세지 않아, 거부 문구가 바뀐 실험은 문구 준수율 차이가 과잉 거부율 차이에 섞인다(D-52 감수하는 것)
- report 출력에서: 참조 사용 불가(핵심 진술이 빈 질의) 수, 거부 교차 집계(근거 상태별 거부), 전체·부분 거부와 지정 문구 없는 거부, 틀린 처리 유형(거부 정확도는 참고값), 인용·메타데이터 오류율, judge 형식 오류 수와 끝나지 않은 응답 수(D-51 결정 4)
- 지연·비용: 질의당 생성 지연(첫 토큰, 전체)과 생성 토큰·비용. judge 비용은 평가 비용이라 운영 비용과 나눠 적는다
- 생성 점수를 해석할 때 같은 330질의의 검색 지표를 함께 적는다(SPEC "문제", D-44). 메인이 준 값을 쓰고, 없으면 확인하지 못한 것으로 적는다
- multi-doc 보조 관찰은 EXP 문서가 정한 경우에만 적고 판정 라벨을 붙이지 않는다(D-53 결정 7)

### 기록 형식

EXP 문서 "결과" 절:

```markdown
## 결과
- gen-full 종합 지표: 후보 0.xxx / 기준 0.xxx / 차이 +0.xxx (95% CI [a, b], 회의 단위 bootstrap 10,000회, n질의)
- 충실성 / 답변 관련성 / 핵심 답변 포함도(보조) / 과잉 거부율: 기준·후보·차이·구간·질의 수
- 판정에 걸린 조건: (`failed`)
- report 관찰: 참조 사용 불가, 거부 교차 집계, 전체·부분 거부, judge 형식 오류·끝나지 않은 응답
- 지연·비용: 질의당 생성 지연, 생성 비용, judge 호출 수·비용(평가 비용)
- 실행: `명령` / 커밋 abc1234 / 비교 결과 JSON 경로 / 소요 시간
```

"결론" 절은 5절과 같다(판정과 운영 채택을 섞지 않는다, D-26).

`docs/EXPERIMENTS.md`의 "생성 단계" 표 한 줄(표가 없으면 첫 생성 EXP 기록에서 아래 머리줄로 만든다). 종합 지표는 계산한 질의 집합이 실행마다 달라, 기준은 단독 report 값(기준 실행에서 계산된 질의)과 짝지은 값(두 실행에서 함께 계산된 질의)을 둘 다 질의 수와 함께 적고 후보는 짝지은 값을 적는다(PR #180 리뷰). 차이는 짝지은 두 값의 차이다:

```markdown
| EXP | 기준 | 바꾼 것 | 기준 종합 지표 (단독 / 짝지은) | 후보 종합 지표 (짝지은) | 차이 (95% 구간) | 충실성 차이 (95% 구간) | 관련성 차이 (95% 구간) | 포함도 차이 (95% 구간, 보조) | 과잉 거부율 차이 (95% 구간) | 판정 (걸린 조건) |
```
