# meet-rag 오케스트레이터

**실행 모드:** 서브에이전트 위임. 구현과 문서 작성은 메인이 직접 하고, 작성 맥락과 떨어진 판단이 필요한 검증·감사·판정만 에이전트에 맡긴다. 각 흐름 사이에 사용자 승인이 필요하고(EXP 판정 기준, Colab·유료 API) 서브에이전트는 사용자에게 물을 수 없으므로, 승인 지점과 Colab VM 조작(E)은 모두 메인이 처리한다.

| 에이전트 | 맡는 일 | 호출 시점 |
| --- | --- | --- |
| `slice-verifier` | SLICE 완료 기준을 명령으로 실행해 판정 | SLICE 구현 후 |
| `protocol-auditor` | diff를 평가 프로토콜·금지 조항에 대조 | 모든 PR 전 |
| `exp-judge` | dev-full 결과를 SPEC 규칙으로 판정하고 기록 초안 작성 | EXP 실행 후 |
| `pr-briefer` | diff로 PR 본문의 리뷰 가이드(위험도, 판단할 곳, 구조) 작성 | `docs/`만 바꾼 PR이 아니면 PR 전 |

**작업자 풀.** 항목 여러 개를 서브에이전트 여러 개에 나눠 맡길 때(G 항목의 일괄 판단 등)는 `references/worker-pool.md`를 읽고 따른다. 동시 수, 범위를 좁히는 프롬프트, 결과 대조, `scripts/worker_queue.py` 큐 기록, 중단 절차가 있다.

**PR 전 감사·가이드** (ADR-0016·0026·0033)

- `protocol-auditor`를 부르는 단계(A4·B5·D2·D5·F6)에서는 `pr-briefer`도 같은 메시지에서 병렬로 부른다. 프롬프트에 auditor와 같은 기준·브랜치·대응 문서·작업 종류와 검증 결과 요약을 넣는다. 바뀐 파일이 모두 `docs/` 아래면 부르지 않는다(`git.md` PR 절 3)
- 지적은 둘로 나눈다. 변경의 원래 목적에 대한 결함(틀린 동작, 문서와 코드 불일치)은 고친다. 새로 생긴 드문 경우에 대비하는 기능은 더하지 않고 PR 본문이나 진행 기록에 관찰로 남기며, 반복되면 그때 만든다. 가이드의 "판단할 곳"은 사용자가 판단할 지점이지 메인의 할 일 목록이 아니다
- 감사·가이드 지적을 반영한 커밋이 있으면 반영을 마친 뒤 최종 diff로 가이드를 직전 가이드와 함께 한 번 더 받아 PR 본문에 넣는다. 본문 가이드가 반영 전 diff를 설명하면 사용자가 diff를 한 번 읽고 판단할 수 없다. 이 마지막 가이드의 지적은 원래 목적의 결함일 때만 고쳐 "self-review 지적과 반영"에 적고, 가이드는 더 부르지 않는다(지적마다 장치를 더하면 끝나지 않는다). 가이드 대응 커밋은 메인이 `protocol-guard` 점검표로 확인하고, 보호 경로나 금지 조항에 걸리는 파일을 바꿨으면 `protocol-auditor`를 다시 부른다
- 단방향 판정은 메인이 걸린 규칙의 `file:line`을 직접 확인한 뒤 본문에 넣는다
- 하네스 보조 스크립트(`scripts/`, `.claude/hooks/`)를 새로 만들거나 고치면 옆에 `test_*.py` 동작 테스트를 같은 커밋에 두고 `uv run pytest -q .claude/skills/meet-rag/scripts .claude/hooks`로 따로 돌린다. 프로젝트 `tests/`에 두면 하네스 때문에 SLICE·EXP PR의 병합 조건이 막힌다

일반 코드 리뷰는 `/code-review`를 쓴다. 에이전트 결과는 반환 메시지로 받는다. 판정에 걸리는 근거(실패 출력, 위반 `file:line`, 판정 수치)는 메인이 직접 한 번 확인한 뒤 반영한다.

## 0. 맥락 확인

새 조각·게이트·실험으로 넘어갈 때마다 이 단계부터 다시 한다. 같은 세션에서 이어지는 작업도 마찬가지다. 직전 작업의 흐름을 기억에 기대어 이어 가면 확인·감사 단계가 빠지기 쉽기 때문이다(S2·G1에서 지시서 확인이 빠진 사례).

1. `git branch --show-current`. `main`이면 작업 종류에 맞는 브랜치를 만든다(`.claude/rules/git.md`)
2. `docs/STATUS.md`의 "다음 행동", "판정 대기", "실행 중 작업"을 읽는다. `_workspace/`에 이 작업의 진행 기록이 있으면 읽고 이어서 한다. 멈춘 작업자 풀 작업이 있으면 `references/worker-pool.md`의 큐 기록으로 이어 간다
3. 요청을 흐름에 대응시킨다
   - 조각 구현, 파이프라인 수정 → A
   - 백로그 가설 시험, 실행 끝난 실험 판정 → B (판정만이면 B4부터)
   - PLAN의 G 항목(사람 검수 게이트), 검수 결과 집계·결정 → D
   - STATUS "다음 행동" 진행 요청 → 항목에 적힌 흐름 표기(`[A]`·`[B]`·`[C]`·`[D]`·`[F]`)를 따른다
   - "검증만 다시", "감사만 다시" → 해당 에이전트만 다시 부른다. 직전 지적 목록을 프롬프트에 넣는다
   - 세션 마무리, 핸드오프 → C
   - 하네스(`.claude/`의 스킬·에이전트·규약·보조 스크립트) 수정, 하네스 피드백 반영 → F
   - 전체 코퍼스 임베딩·인덱스 구축 등 GPU 작업 → 해당 A·B 단계 안에서 E

## 작업 기록 (`_workspace/`)

`_workspace/`는 로컬 전용 작업 디렉터리다(`.gitignore`). 두 가지 용도로 쓴다. 단계가 바뀔 때 앞 단계의 산출물·결정·주의 사항을 다음 단계와 에이전트에게 넘기고, 사용자가 진행 상황을 확인한다. 서브에이전트는 매번 새로 떠서 이전 맥락을 모르고, 메인의 맥락도 세션이 바뀌면 사라지므로 파일로 이어 준다.

- 파일 이름은 `{작업}_{작성자}_{내용}.md`다. 예: `s05_main_progress.md`, `exp002_main_progress.md`
- 진행 기록: 흐름을 시작할 때 만들고, 단계가 끝날 때마다 상태·산출물 경로·커밋·다음 단계가 알아야 할 것을 갱신한다. 에이전트를 부를 때 프롬프트에 이 경로를 넣는다
- `00_main_harness-pending.md`: 작업 중 발견한 하네스 개선 거리를 바로 적어 두는 대기 목록이다. 작업 PR 뒤 `chore/` 브랜치에서 `harness:evolve`로 반영하고 상태를 바꾼다. 반영한 결정은 `docs/harness/adr/`에 ADR로 남긴다(CLAUDE.md 변경 이력 표 대신)
- 최종 결과와 결정은 여기에 두지 않는다. SLICE·EXP 문서, DECISIONS, STATUS가 기록처다

## 결정과 PR의 순서

- **노트북이 결정보다 먼저**: 데이터·점수를 보고 정하는 결정(설정 값, 프로토콜 미결 사항, 검수 규칙, EXP 채택 뒤 방향)은 근거 노트북(`notebooks/`, `.claude/rules/notebook.md`)을 먼저 쓰고 사용자에게 보인 뒤 DECISIONS에 기록한다. 노트북은 결정의 근거 자료다. 결정 뒤에 쓰면 노트북이 결정을 설명하는 자료가 되고, 사용자가 같은 근거를 보고 정했는지 확인할 수 없다(S4는 D-04 결정 뒤에 노트북을 써 PR #15에서 지적받음). 결정이 걸린 조각·실험은 지시서에 노트북과 결정의 순서를 적는다
- **결정을 반영한 뒤 PR**: PR 내용이 사용자 결정에 따라 바뀌는 작업이면, 결정을 받아 반영하고 작업을 마무리한 뒤 PR을 올린다. 결정이 사소하면(표현, 경로 이름 등) PR 코멘트로 받아도 된다. 결정 전에 PR을 올리면 PR을 다시 고치게 되고, 사용자가 diff를 두 번 읽어야 한다(여러 차례 반복됨)
- **리뷰 중에 커지지 않게**: 리뷰 코멘트 중 원래 목적의 결함(판단할 곳의 답, 틀린 동작, 문서·코드 불일치)은 같은 PR에서 고친다. 리뷰 중 새로 생긴 설계·실험 과제는 원래 PR이 그 자체로 맞으면 먼저 병합하고 후속 PR로 나눈다. 나눌지 애매하면 묻는다. Draft PR은 쓰지 않고, 의견이 필요한 지점은 PR 전에 대화로 결정받는다. PR #106은 리뷰 중 judge 실험·검수가 더해져 31커밋·30파일·약 22시간 열렸고 가이드를 여러 번 다시 쓰고 재감사했다(사용자와 토의 2026-10-20)
- **승인 문서는 초안에서 고친다**: 사용자 승인이 필요한 문서(SPEC 평가 프로토콜 등)를 바꾸는 작업은 `docs/drafts/`에 초안을 두고 결정을 모두 받은 뒤 옮긴다. 승인 문서를 직접 고치면 고칠 때마다 승인 때문에 작업이 멈춘다(PR #99 코멘트)

## 질문과 해석

PR 본문의 질문과 STATUS "사용자 확인 필요"는 사용자만 정할 수 있는 것(목표·기준, 비용·위험을 감수할지, 지시의 해석이 갈리는 곳)으로 한정한다. PR #1\~#75에서 답 없이 병합된 질문은 대부분 값·문구 대조와 이미 정한 것의 재확인이었고, 그만큼 사용자가 판단할 질문이 묻혔다(ADR-0041).

- 묻기 전에 DECISIONS, 이 스킬, 이전 PR 코멘트에서 답을 찾는다. 있으면 묻지 않고 근거를 적어 따른다. 명령으로 확인되는 것은 확인한 결과를 적는다
- 사용자 리뷰(대화로 받은 PR 리뷰, PR 코멘트)를 규칙·코드로 옮길 때는 해석을 리뷰가 다루는 경우 하나의 입력→동작 사례로 PR 댓글과 본문 "리뷰 반영"에 적는다(`git.md` PR 절 5). "재시도 3회"를 형식 오류 거부 횟수로 구현했지만 뜻은 중단된 작업의 재시작이었다(PR #37→#38). 사례가 있으면 사용자가 같은 리뷰에서 어긋남을 보고, 후속 PR이 생기지 않는다
- 규칙은 그 규칙이 막으려는 대상까지만 적용한다. 넓게 해석해 금지·예외·단서를 늘리지 않고, 적용 범위가 애매하면 묻는다. CLAUDE.md 금지 절과 평가 프로토콜을 좁히는 해석도 메인이 정하지 않고 묻는다(protocol-guard 기준은 그대로다). 비용·위험은 예상값을 앞에 두고 최대치는 그 조건과 함께 적는다. 재배포 제한(공개 금지)을 외부 처리 금지로 넓혀 일회성 예외(D-25)를 만들었다가 D-31로 고쳤고, 리랭커 비용을 상시 가동 최대치(월 $365)로만 적어 scale-to-zero 예상(월 $1 이하)을 사용자가 보충했다(PR #61)
- 사용자에게 묻는 판단(PR 판단할 곳, STATUS, 질문 상자)에는 선택지마다 무엇이 달라지는지와 입력→동작 사례(또는 수치)를 붙인다. 근거 없이 결정만 물으면 사용자가 되물어야 답할 수 있다(PR #106 코멘트: 경계값 0.5를 근거 없이 묻고 사례를 요청받음)
- 지연·비용·수치에 영향이 있다고 PR에 적을 때는 잰 값을 붙인다. 잴 수 없으면 그 이유와 확인 방법을 적는다. 재지 않은 추정을 근거로 사용자에게 판단을 묻지 않는다(PR #79 코멘트: 추적 데코레이터 지연을 "ms 단위로 예상, 측정 안 함"으로 적고 지연 지표를 계속 써도 되는지 물음)

## 구현 원칙: 기록과 입력이 조용히 바뀌지 않게

A2(구현)와 B3(실험 코드)에 적용한다. 실험 기록은 다시 만드는 비용이 크고, 바뀐 것을 알아채지 못하면 이후 판정이 틀린 기준과 비교된다.

- **과거 코드와 병용하지 않는다**: 과거 실험·노트북은 그 커밋의 코드로 재현한다. 리팩터링으로 함수 위치·이름이 바뀌어도 과거 노트북을 위한 재수출·호환 분기를 두지 않는다(PR #71 코멘트)
- **산출물은 덮어쓰지 않는다**: `data/` 아래 산출물(순위·점수·후보 쌍·인덱스·분할·judge 기록·검수 파일)은 커밋하지 않아 덮어쓰면 되돌릴 사본이 없다. 다시 만들려면 그 커밋의 코드로 재실행해야 하고, GPU 산출물은 Colab 비용이 다시 든다. 운영 보류(D-26)·기각 실험의 기록도 재판단·재현에 쓰므로 보존 대상이다(PR #71 코멘트). `data/`에 쓰는 경로는 새로 만들 때와 기존 쓰기 경로를 고칠 때 모두 둘 중 하나를 거친다(`rag.index`). 같은 모듈이라도 고치지 않는 쓰기 줄은 그 작업에서 바꾸지 않는다(PR 범위 유지). 덮어쓰기는 `search.overwrite=true`로만 한다
  - 같은 입력이면 같은 내용이 나오는 출력(순위, 후보 쌍, 분할): `write_guarded`. 내용이 다르면 멈추고 같으면 그대로 둔다
  - 다시 만들면 값이 달라지는 출력(GPU 채점·지연 측정, judge 기록, 사람이 채우는 검수 파일): 시작할 때 `refuse_existing`. 끝에서 멈추면 채점·측정 시간을 잃는다(PR #122 리뷰)
- **실행 config에 따라 바뀌는 입력을 미리 만든 파일로 읽지 않는다**: 설정·코퍼스가 바뀐 뒤 옛 파일이 오류 없이 쓰인다(S12 이전 조건 파일·값 사전). 실행 시점에 만들거나, 만든 설정을 지문으로 남기고 읽을 때 대조해 다르면 멈춘다(`rag.index.check_basis`. 인덱스 `basis.json`, 재정렬 점수 `.basis.json`, S15). 지문이 없는 기존 산출물은 만든 설정을 EXP 실행 기록과 대조한 뒤 `adopt_basis=true`로만 지문을 쓴다. 대조 없이 쓰면 다른 설정으로 만든 파일에 틀린 지문이 붙는다(S15 결정 사항 1). 경로 규칙도 config 템플릿 한 곳에서만 만든다(`rag.index.index_path`, PR #71 코멘트)
- 위 두 조항은 2026-10-14부터 있었지만 새 쓰기 경로에만 적용되고 확인 단계가 없어, 이전 모듈은 그대로 남고 이후 모듈(`gen_eval/review.py`)도 통과했다(코드 리뷰 2026-10 높음 6건, S15). PR 전에 `protocol-guard` P10으로 확인한다
- **API로 LLM을 부르는 코드는 처음부터 LangSmith로 추적한다**: 생성, 질의 재작성, Jev 판정처럼 요청마다 입력·출력·토큰·지연을 나중에 보고 디버깅할 수 있어야 한다. 방식은 `rag.generate`와 같다(`wrap_openai`, 단계마다 `@traceable`, 메타데이터에 qid·설정, 끝에 `get_cached_client().flush()`). urllib로 직접 부르면 호출 함수를 `traceable`로 감싼다(`rag.rerank`, PR #79). EXP-013 재작성기가 추적 없이 만들어져, Google 경로 지연(평균 46초)이 어느 단계에서 생겼는지 답할 기록이 없었다(사용자 지시 2026-10-15)

## A. SLICE 흐름

1. **지시서**: `docs/slices/NN-이름.md`가 없으면 `docs/PLAN.md` 해당 줄을 바탕으로 쓴다. 완료 기준은 명령과 기대 결과로, 성능 수치는 넣지 않는다. 수정 허용 파일과 범위 밖을 적는다. `docs: SLICE NN 지시서`로 구현과 따로 커밋하고, 사용자에게 보여 확인받는다. 결정이 걸린 조각이면 노트북과 결정의 순서를 적는다("결정과 PR의 순서"). 확인을 받기 전에는 구현을 시작하지 않고 이 지점에서 멈춘다. 지시서가 구현 커밋에 섞이면 확인을 거쳤는지 이력으로 알 수 없다
2. **구현**: 메인이 구현한다("구현 원칙"). 파라미터는 `configs/`에, 코드와 테스트는 같은 커밋에 둔다. dev-small로 먼저 돌려 본다. 전체 규모 임베딩이 필요하면 E를 따른다
3. **검증**: `slice-verifier`를 부른다. 프롬프트에 SLICE 문서 경로, 브랜치, 진행 기록 경로, 허용 실행 범위(기본 dev-small)를 넣는다. 로컬 PC CPU 임베딩이 필요한 기준은 판정에 필요한 최소 규모로 허용한다(예: 재개 확인은 문서 2\~3개와 작은 `index.shard_size`, ADR-0008). 실패하면 고치고 같은 검증을 다시 부른다
4. **감사**: `protocol-auditor`를 부른다. 프롬프트에 기준 `main`, 브랜치, SLICE 문서 경로, 작업 종류 SLICE를 넣는다. 사용자가 요청하면 `/code-review`도 돌린다. 둘은 서로 독립이므로 한 메시지에서 병렬로 부른다
5. **PR**: 지시서의 사용자 결정이 모두 반영됐는지 확인한다("결정과 PR의 순서"). 지적을 반영하거나 반영하지 않는 이유를 정한 뒤 `.claude/rules/git.md` PR 절차를 따른다. PR 본문에 검증 결과와 감사 지적·반영 여부를 적는다

## B. EXP 흐름

1. **초안**: `docs/PLAN.md` 백로그에서 가설을 고르고, `docs/SPEC.md`, `docs/DECISIONS.md`, 기준 실험 문서를 읽은 뒤 `docs/experiments/EXP-NNN.md`와 `configs/exp/expNNN.yaml`을 쓴다. 판정 기준은 SPEC 판정 절을 그대로 옮긴다. SPEC이 EXP 문서에 우선한다. 사용자가 이 EXP에 SPEC과 다른 기준을 요청하면 그 기준과 이유를 EXP 문서에 적고, 판정 때 judge가 차이를 보고하면 어느 기준을 쓸지 사용자에게 묻는다(PR #48 코멘트). PLAN에 [메타데이터]로 표시된 가설이면 SPEC "메타데이터 가설의 판정" 절을 옮긴다. 같은 백로그 항목의 두 번째 이후 EXP이면 몇 번째 변형인지와 앞 변형들의 판정을 적는다(SPEC 가설 단위 중단, 첫 EXP는 세지 않는다). EXP 문서와 config를 먼저 커밋하고 B2 착수 지시를 받은 뒤 구현·dev-small로 넘어간다. 문서가 dev-small 뒤에 오면 가설·판정 기준을 결과를 보고 쓴 것처럼 읽히고 이력으로 반박할 수 없다(EXP-010 사용자 지적, ADR-0037). 같은 세션에서 다음 EXP로 넘어갈 때도 0단계부터 다시 한다
2. **승인 지점**: 가설, 바꾸는 것, 판정 기준을 사용자에게 보이고 승인받는다. 재임베딩이 필요하면(Colab) 예상 시간·크레딧을, 유료 API가 필요하면 예상 비용을 함께 보고한다. 착수 지시(이 EXP를 시작하라는 명시적인 말)를 받기 전에는 구현·dev-small도 하지 않는다. 초안의 결정 사항에 답을 받은 것은 착수 지시가 아니다. 답을 초안에 반영해 다시 보이고 착수 여부를 묻는다. 다른 작업이 끼어들어 흐름이 끊긴 뒤 이어 갈 때도 착수 지시를 받았는지 진행 기록에서 확인하고, 기록이 없으면 다시 묻는다. EXP-012에서 결정 사항(BM25 함께 변경, Colab CLI 업데이트 선행)에 대한 답만 받고 구현과 로컬 확인을 시작했다(사용자 지적 2026-10-14)
3. **실행**: 실험 코드가 새로 필요하면 config로 켜는 형태로 만들고 기준 설정의 동작을 바꾸지 않는다("구현 원칙"). 기존 모듈을 크게 바꿔야 하면 먼저 SLICE(A 흐름)로 분리한다. dev-small로 동작을 확인한 뒤 dev-full을 실행한다. 재임베딩이 필요하면 E를 따른다
4. **판정**: `exp-judge`를 부른다. 프롬프트에 EXP 문서 경로, 기준·후보 순위 파일 경로(single-doc, multi-doc), 실행 명령, 커밋 해시를 넣는다
5. **감사**: `protocol-auditor`를 작업 종류 EXP로 부른다. 4와 서로 독립이므로 병렬로 부른다
6. **기록**: judge 초안의 수치를 직접 확인한 뒤 아래를 하고, EXP 문서 결과·결론, `docs/EXPERIMENTS.md`, 채택이면 `docs/DECISIONS.md`, `docs/PLAN.md` 백로그 상태를 갱신한다. 기각·보류도 병합한다
   - **지연·비용**: 판정 보고에 성능과 함께 지연과 운영 비용(과금 방식, 월 비용 추정, 추가 인프라, 상주 메모리·디스크)을 낸다. 지연은 질의당 시간을 앞에 두고, 로딩을 포함한 dev-full 전체 실행 시간이나 그 배수는 운영 판단 근거로 쓰지 않는다. 인덱스 로딩처럼 시작할 때 한 번 드는 시간은 콜드 스타트로 EXP 문서 결과 절에 따로 적고, 배포 SLICE에서 배포 페이지에 첫 구동 대기 시간으로 안내한다. 나눠 잴 수 없으면 그렇다고 적는다(ADR-0038·0039)
   - **채택의 두 층**: SPEC 판정의 채택은 성능 기준이고, 기준 설정으로 올릴지(운영 채택, DECISIONS)는 사용자가 비용과 함께 정한다(D-26). 최종 판정(메타데이터 가설은 multi-doc 단계까지 간 결과)이 보류인 실험만 사용자가 근거를 들어 예외로 기준에 올릴 수 있고, 그때는 SPEC을 고치지 않고 DECISIONS에 이유·감수하는 점·새 기준 순위 해시를 적는다(D-28·D-33). 예외 채택 여부는 사용자가 정하고, 메인과 judge는 선례와 비슷해 보여도 판정이나 권고로 정하지 않는다. 예외 채택한 EXP의 결론은 SPEC 판정(보류, 기준에 못 미친 수치), 예외 근거, 사용자 채택 결정 순으로 적어 DECISIONS와 맞춘다. 기각 판정의 채택은 금지한다(ADR-0037)
   - **원인 분석 노트북**: 판정과 관계없이 쓰고 사용자에게 보인다. 채택이면 기준 반영 결정 전에("결정과 PR의 순서"), 기각·보류이면 PR에서 결과와 함께 보인다. 기존 요소에 새 요소를 더한 구성(예: 512 청크에 256 청크를 더함)이면 순위가 바뀐 질의마다 어느 요소가 결과를 냈는지 세어 요소별 기여를 보이고 EXP 결과 절에 종합한다(ADR-0038·0039). 지속 커널은 PR을 올리기 전에 `stop`한다(notebook.md §8)
   - **가설 단위 중단**: 같은 백로그 항목에서 첫 EXP 뒤 변형을 바꾼 EXP가 3회 연속 비채택이면 사용자에게 알리고 다음 항목으로 넘어간다. 첫 EXP는 세지 않고, 사이에 다른 항목의 EXP가 있어도 끊지 않으며, 서로 다른 항목의 비채택은 이어서 세지 않는다(D-18)

## D. 사람 검수 게이트 (PLAN의 G 항목)

사람이 데이터를 직접 보고 프로토콜 미결 사항을 정하는 단계다. SLICE 문서를 쓰지 않고 PLAN의 G 항목 줄과 SPEC 미결 절을 대응 문서로 쓴다.

1. **표본 도구**: `chore/gN-이름` 브랜치에서 표본 추출 코드를 쓴다. dev 분할에서만 뽑고, 표본 크기·seed는 `configs/config.yaml`에 둔다(`configs/eval/`은 보호 경로). 검수 칸은 비워 둔다
2. **감사·PR**: `protocol-auditor`를 작업 종류 게이트로 부른 뒤 PR을 올린다. STATUS에 사용자 검수 대기와 표본 파일 경로·해시를 적고 멈춘다
3. **집계**: 사용자가 검수 파일을 주면 판정·유형별 건수와 비율을 낸다. 집계에서 나온 불량을 표본 밖으로 넓혀 다시 판정하게 할 때는, 재판정 파일이 앞에서 나온 불량 유형을 모두 판정할 수 있는 정보를 담게 만든다. 어떤 유형을 그 파일로 판정할 수 없으면 파일을 주기 전에 알리고 방법을 정한다. 판정할 수 없던 유형을 동결 뒤 단서나 PR 질문으로 넘기지 않는다(G3 범위 재판정 파일이 안건만 보여 정답 내용 불일치를 판정할 수 없었던 일, 사용자 지적 2026-10-08, ADR-0025). 검수 기준과 평가 용도(SPEC 평가 질의·정답)가 다르면 그 차이가 지표에 미치는 영향을 구분해 보고한다. 검수 칸이 자유 기술이면 유형을 묶어 제시한다. 사용자 요청으로 Claude가 사용자 기준에 맞춰 검수 칸을 채우면 출처 열(예: `filled_by`)을 두고, 그 행은 사람 판정(judge 보정의 일치율·kappa 등)에 넣지 않는다(S14 검수, 사용자 판정은 20행 중 5행)
4. **결정 지점**: 집계를 노트북으로 쓰고("결정과 PR의 순서"), 규칙(필터 등)을 둘지 사용자에게 노트북과 권고를 함께 보이며 묻는다. 결정은 사용자가 한다. 질의 필터 같은 규칙은 검색 점수를 보기 전에 정한다(SPEC 누수 방지). 점수를 본 뒤 정하면 규칙이 점수에 맞춰질 수 있다
5. **기록**: `docs/` 브랜치에서 `docs/DECISIONS.md`에 집계·결정·이유를, `docs/PLAN.md`에 G 체크를 반영한다. `protocol-auditor`를 작업 종류 문서로 부르고 PR을 올린다. 사용자가 SPEC 미결 사항을 결정했으면 같은 PR에서 SPEC 미결 절에 `(해결, D-NN)`을 표시한다. 그 결정이 해결 표시의 승인이므로 따로 묻지 않는다(미결 1을 PR #8·#18·#21에서 세 번 묻고도 표시가 빠졌다). 결정이 미결 문항의 일부만 정했으면 남은 부분을 PR에서 묻는다. 규칙을 채택했으면 적용은 SLICE(A 흐름)로 분리하고, 보호 경로(CLAUDE.md 금지 절: `src/rag/eval/`, `src/rag/eval_multi/`, `data/splits/` 등)를 건드려야 하면 사용자 승인 후 DECISIONS에 기록한다

## E. GPU 작업 (Colab)

전체 코퍼스 임베딩·인덱스 구축·재임베딩처럼 GPU가 필요한 작업(A2, B3)이나 생성 단계 test 1회의 Colab 처리(업로드 허용 ADR을 다시 둔 뒤, protocol-guard P6)가 필요해지면, 시작 전에 `references/colab.md`와 `colab-operator` 스킬을 Skill 도구로 불러와 E1\~E7을 따른다. 기억으로 대신하지 않는다(S4에서 두 번 모두 불러오지 않고 진행). 승인(GPU 종류, 예상 시간, 요율 환산 compute unit)과 VM 조작은 메인만 한다. 로컬 PC에는 GPU가 없고(SPEC 자원 제약), 생성(OpenRouter, D-37)과 judge(opencode Go, D-38)는 GPU를 쓰지 않는다.

3. **PR 코멘트 수집**: 마지막 하네스 PR 이후 병합된 PR의 사용자 리뷰 코멘트를 읽는다(`gh pr view N --comments`, `gh api repos/{owner}/{repo}/pulls/N/comments`). 같은 유형의 지적이 다시 나오지 않게 고칠 수 있는 것(작업 순서, 빠진 확인, 문서 형식)은 근거 PR 번호와 함께 대기 목록에 더한다. 그 PR 하나의 내용 수정 요청은 더하지 않는다. 사용자 지적이 대기 목록에 들어오는 경로가 메인이 기억해 옮기는 것뿐이면 빠지는 지적이 생긴다(PR #15 노트북 순서 지적은 사람이 옮김)
4. **변경마다 검증**: 변경을 하나씩 적용하고, 그때마다 frontmatter·참조 경로를 확인한다. description을 바꾸면 should-trigger·near-miss 요청 각 3개 이상으로 트리거를 검증한다. 검증은 작성 맥락과 분리하려고 서브에이전트에 맡긴다
5. **기록**: evolve Phase 4의 CLAUDE.md 변경 이력 표 대신 `docs/harness/adr/`에 ADR을 추가하고 목록을 갱신한다(ADR-0014). 앞 ADR을 바꾸면 그 상태를 고친다
6. **감사·PR**: `protocol-auditor`를 작업 종류 하네스로 부르고, 수정안을 사용자에게 보인 뒤 PR을 올린다("결정과 PR의 순서")

## 오류 처리

- 에이전트가 실패하거나 결과가 비어 있으면 한 번 다시 부른다. 또 실패하면 그 검증 없이 멈추고 사용자에게 보고한다. 검증·감사·판정을 메인이 대신 채우지 않는다. 분리된 판단이라는 목적이 사라지기 때문이다
- 사용량 한도, 권한 거부처럼 다시 시도해도 같은 실패는 다시 시도하지 않는다. 한도라면 풀리는 시각을 함께 보고한다
- 외부 API(OpenRouter, opencode Go, Google AI Studio 등)가 5xx를 내면 다시 시도하기 전에 그 제공자의 서버 상태(OpenRouter https://status.openrouter.ai, Google AI Studio https://aistudio.google.com/status 등)를 먼저 확인한다. 장애·성능 저하로 표시되면 멈추고 상태와 함께 보고한다. 정상으로 표시될 때만 한 번 다시 시도하고, 또 실패하면 보고한다. SDK 자동 재시도에 반복 실행을 겹치면 호출만 늘고 원인은 그대로다(S6 노트북을 서버 장애 중 일곱 번 다시 실행한 사례, ADR-0012). 402(결제)·403(인증)은 다시 시도하지 않고 보고한다
- 노트북은 `scripts/nb_kernel.py`(지속 커널)로 실행한다. 셀 하나가 실패하면 처음부터 다시 돌리지 않고 그 셀을 고쳐 이어서 실행한다. 커널 유지와 `stop` 시점은 `.claude/rules/notebook.md` §8을 따른다
- 에이전트 보고가 "사용자 승인 필요"를 포함하면 그 지점에서 멈추고 사용자에게 묻는다
- 이스케이프(`\n`, `\~`)가 든 문자열을 파일에 넣거나 바꿀 때는 Bash heredoc 안의 Python·sed로 하지 않고 Edit 도구로 한다. 함수·테스트를 통째로 덧붙이는 스크립트도 같다. 셸과 Python이 이스케이프를 두 번 해석해 실제 줄바꿈이 들어가거나 `\~`가 어긋나 파일이 깨졌다(S14 2회, 하네스 1회, S17 1회). 스크립트로 파일을 쓸 때는 `open(..., newline="\n")`로 쓴다(`write_text`·`open`은 Windows에서 CRLF로 쓴다, S16). `python`·`sed -i`가 든 Bash 명령 뒤에는 `file_damage_check` 훅이 바뀐 파일의 구문 오류와 CRLF를 알린다(ADR-0055). 알림이 오면 그 자리에서 Edit로 바로잡는다

## 테스트 시나리오

- 정상: SLICE PR 병합 후 같은 세션에서 "다음 조각 진행" → 0단계부터 다시 → A1 지시서를 별도 커밋한 뒤 멈춤 → 사용자 확인 → A2 구현
- 정상: "G5 검수 결과 검토해" → 0에서 D3으로 대응 → 집계와 권고 보고 → D4 사용자 결정 → D5 DECISIONS·PLAN PR
- 정상: dev-full 결과를 보고 설정 값을 정해야 함 → 근거 노트북을 쓰고 사용자에게 보임 → 사용자 결정 → DECISIONS 기록 → 검증·감사 → PR (노트북 전에 결정을 기록하거나, 결정 전에 PR을 올리지 않는다)
- 오류: B4에서 후보 순위 파일이 dev-small로 만들어져 있음 → judge가 판정하지 않고 보고 → 메인이 dev-full 실행 여부를 사용자에게 묻는다
- 오류: A4에서 auditor가 P4(하드코딩 top-k) 위반 보고 → 메인이 `file:line`을 확인하고 config로 옮김 → auditor를 직전 지적 목록과 함께 다시 부른다
