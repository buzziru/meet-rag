# meet-rag 오케스트레이터

**실행 모드:** 서브에이전트 위임. 구현과 문서 작성은 메인이 직접 하고, 작성 맥락과 떨어진 판단이 필요한 검증·감사·판정만 에이전트에 맡긴다. 각 흐름 사이에 사용자 승인이 필요하고(EXP 판정 기준, Colab·유료 API) 서브에이전트는 사용자에게 물을 수 없으므로, 승인 지점과 Colab VM 조작(E)은 모두 메인이 처리한다.

| 에이전트 | 맡는 일 | 호출 시점 |
| --- | --- | --- |
| `slice-verifier` | SLICE 완료 기준을 명령으로 실행해 판정 | SLICE 구현 후 |
| `protocol-auditor` | diff를 평가 프로토콜·금지 조항에 대조 | 모든 PR 전 |
| `exp-judge` | dev-full 결과를 SPEC 규칙으로 판정하고 기록 초안 작성 | EXP 실행 후 |

일반 코드 리뷰는 `/code-review`를 쓴다. 에이전트 결과는 반환 메시지로 받는다. 판정에 걸리는 근거(실패 출력, 위반 `file:line`, 판정 수치)는 메인이 직접 한 번 확인한 뒤 반영한다.

## 0. 맥락 확인

새 조각·게이트·실험으로 넘어갈 때마다 이 단계부터 다시 한다. 같은 세션에서 이어지는 작업도 마찬가지다. 직전 작업의 흐름을 기억에 기대어 이어 가면 확인·감사 단계가 빠지기 쉽기 때문이다(S2·G1에서 지시서 확인이 빠진 사례).

1. `git branch --show-current`. `main`이면 작업 종류에 맞는 브랜치를 만든다(`.claude/rules/git.md`)
2. `docs/STATUS.md`의 "다음 행동", "판정 대기", "실행 중 작업"을 읽는다
3. 요청을 흐름에 대응시킨다
   - 조각 구현, 파이프라인 수정 → A
   - 백로그 가설 시험, 실행 끝난 실험 판정 → B (판정만이면 B4부터)
   - PLAN의 G 항목(사람 검수 게이트), 검수 결과 집계·결정 → D
   - STATUS "다음 행동" 진행 요청 → 항목에 적힌 흐름 표기(`[A]`·`[B]`·`[C]`·`[D]`)를 따른다
   - "검증만 다시", "감사만 다시" → 해당 에이전트만 다시 부른다. 직전 지적 목록을 프롬프트에 넣는다
   - 세션 마무리, 핸드오프 → C
   - 전체 코퍼스 임베딩·인덱스 구축 등 GPU 작업 → 해당 A·B 단계 안에서 E

## A. SLICE 흐름

1. **지시서**: `docs/slices/NN-이름.md`가 없으면 `docs/PLAN.md` 해당 줄을 바탕으로 쓴다. 완료 기준은 명령과 기대 결과로, 성능 수치는 넣지 않는다. 수정 허용 파일과 범위 밖을 적는다. `docs: SLICE NN 지시서`로 구현과 따로 커밋하고, 사용자에게 보여 확인받는다. 확인을 받기 전에는 구현을 시작하지 않고 이 지점에서 멈춘다. 지시서가 구현 커밋에 섞이면 확인을 거쳤는지 이력으로 알 수 없다
2. **구현**: 메인이 구현한다. 파라미터는 `configs/`에, 코드와 테스트는 같은 커밋에 둔다. dev-small로 먼저 돌려 본다. 전체 규모 임베딩이 필요하면 E를 따른다
3. **검증**: `slice-verifier`를 부른다. 프롬프트에 SLICE 문서 경로, 브랜치, 허용 실행 범위(기본 dev-small)를 넣는다. 실패하면 고치고 같은 검증을 다시 부른다
4. **감사**: `protocol-auditor`를 부른다. 프롬프트에 기준 `main`, 브랜치, SLICE 문서 경로, 작업 종류 SLICE를 넣는다. 사용자가 요청하면 `/code-review`도 돌린다. 둘은 서로 독립이므로 한 메시지에서 병렬로 부른다
5. **PR**: 지적을 반영하거나 반영하지 않는 이유를 정한 뒤 `.claude/rules/git.md` PR 절차를 따른다. PR 본문에 검증 결과와 감사 지적·반영 여부를 적는다
6. S3(평가 모듈)이 끝나면 `src/rag/eval/` 명령을 `CLAUDE.md` "명령" 절에 추가한다. `exp-judge`가 이 명령을 쓴다

## B. EXP 흐름

1. **초안**: `docs/PLAN.md` 백로그에서 가설을 고르고, `docs/SPEC.md`, `docs/DECISIONS.md`, 기준 실험 문서를 읽은 뒤 `docs/experiments/EXP-NNN.md`와 `configs/exp/expNNN.yaml`을 쓴다. 판정 기준은 SPEC 판정 절을 그대로 옮기거나 더 엄격하게 쓴다
2. **승인 지점**: 가설, 바꾸는 것, 판정 기준을 사용자에게 보이고 승인받는다. 재임베딩이 필요하면(Colab) 예상 시간·크레딧을, 유료 API가 필요하면 예상 비용을 함께 보고한다. 승인 전에는 dev-small까지만 실행한다
3. **실행**: 실험 코드가 새로 필요하면 config로 켜는 형태로 만들고 기준 설정의 동작을 바꾸지 않는다. 기존 모듈을 크게 바꿔야 하면 먼저 SLICE(A 흐름)로 분리한다. dev-small로 동작을 확인한 뒤 dev-full을 실행한다. 재임베딩이 필요하면 E를 따른다
4. **판정**: `exp-judge`를 부른다. 프롬프트에 EXP 문서 경로, 기준·후보 순위 파일 경로, 실행 명령, 커밋 해시를 넣는다
5. **감사**: `protocol-auditor`를 작업 종류 EXP로 부른다. 4와 서로 독립이므로 병렬로 부른다
6. **기록**: judge 초안의 수치를 직접 확인하고 EXP 문서 결과·결론, `docs/EXPERIMENTS.md`, 채택이면 `docs/DECISIONS.md`, `docs/PLAN.md` 백로그 상태를 갱신한다. 기각·보류도 병합한다. 비채택이 3회 연속이면 SPEC 중단 기준에 걸렸다고 사용자에게 알린다

## C. 세션 마무리

`CLAUDE.md` "세션 마무리" 절 순서를 따른다. STATUS "다음 행동"의 각 항목 앞에 다음 세션이 탈 흐름을 `[A]`·`[B]`·`[C]`·`[D]`로 적는다. 판정이 끝나지 않은 실험이 있으면 B4~B6을 먼저 한다. 핸드오프는 사용자가 요청할 때만 한다.

## D. 사람 검수 게이트 (PLAN의 G 항목)

사람이 데이터를 직접 보고 프로토콜 미결 사항을 정하는 단계다. SLICE 문서를 쓰지 않고 PLAN의 G 항목 줄과 SPEC 미결 절을 대응 문서로 쓴다.

1. **표본 도구**: `chore/gN-이름` 브랜치에서 표본 추출 코드를 쓴다. dev 분할에서만 뽑고, 표본 크기·seed는 `configs/config.yaml`에 둔다(`configs/eval/`은 보호 경로). 검수 칸은 비워 둔다
2. **감사·PR**: `protocol-auditor`를 작업 종류 게이트로 부른 뒤 PR을 올린다. STATUS에 사용자 검수 대기와 표본 파일 경로·해시를 적고 멈춘다
3. **집계**: 사용자가 검수 파일을 주면 판정·유형별 건수와 비율을 낸다. 검수 기준과 평가 용도(SPEC 평가 질의·정답)가 다르면 그 차이가 지표에 미치는 영향을 구분해 보고한다. 검수 칸이 자유 기술이면 유형을 묶어 제시한다
4. **결정 지점**: 규칙(필터 등)을 둘지 사용자에게 권고와 함께 묻는다. 결정은 사용자가 한다. 질의 필터 같은 규칙은 검색 점수를 보기 전에 정한다(SPEC 누수 방지). 점수를 본 뒤 정하면 규칙이 점수에 맞춰질 수 있다
5. **기록**: `docs/` 브랜치에서 `docs/DECISIONS.md`에 집계·결정·이유를, `docs/PLAN.md`에 G 체크를 반영한다. `protocol-auditor`를 작업 종류 문서로 부르고 PR을 올린다. SPEC 미결 절의 해결 표시는 SPEC 수정이므로 사용자 승인 없이 하지 않는다. 규칙을 채택했으면 적용은 SLICE(A 흐름)로 분리하고, 보호 경로(`src/rag/eval/`, `data/splits/`)를 건드려야 하면 사용자 승인 후 DECISIONS에 기록한다

## E. GPU 작업 (Colab)

임베딩은 KURE-v1이고 다른 임베딩 모델로 바꿔도 직접 임베딩하므로, 전체 코퍼스 임베딩·인덱스 구축·재임베딩 실험에는 GPU가 필요하다. 노트북에는 GPU가 없어(SPEC 자원 제약) 이 작업은 Colab VM에서 `colab` CLI로 한다. CLI 사용법은 `colab-operator` 스킬을 읽는다. 이 절은 그 위에 얹는 프로젝트 규칙이다. dev-small은 노트북 CPU에서 하고, 생성(Gemma 4, Google AI Studio)은 GPU를 쓰지 않는다.

A2(S4 등 전체 인덱스)와 B3(재임베딩 실험)에서 dev-full 규모 임베딩이 필요하면 이 절차를 따른다.

1. **사전 확인**: dev-small을 노트북에서 먼저 돌려 코드가 동작하고 중간 산출물에서 재개되는지 확인한다. VM에서 처음 버그를 찾으면 그동안 크레딧이 나간다
2. **승인 지점**: GPU 종류, 예상 시간, 예상 compute unit을 사용자에게 보고하고 승인받는다. 예상 시간은 dev-small 처리량을 전체 문서 수로 늘려 잡는다. GPU는 사용자가 지정한 것을 쓰고, 지정이 없으면 묻는다. 서브에이전트는 VM을 만들지 않는다. 과금이 걸린 결정이라 사용자에게 물을 수 있는 메인만 한다
3. **할당**: `colab new -s meet-rag-<작업> --gpu <GPU>`. 할당이 실패하면(400 등) `colab-operator` 안내대로 `--gpu T4`로 바꿔 다시 할당한다. 이 대체는 다시 승인받지 않지만, 바뀐 GPU와 다시 잡은 예상 시간을 사용자에게 알린다. T4도 실패하면 멈추고 보고한다
4. **실행**: VM에서 공개 저장소를 작업 커밋으로 clone하고, 입력(`data/processed/` 코퍼스)은 업로드한다. 실행 명령은 로컬과 같은 모듈·config를 쓴다. 산출물은 `paths.index_dir`(설정 식별자가 들어간 경로)로 내려받는다. 실행 중에는 `docs/STATUS.md` "실행 중 작업"에 세션 이름, 커밋, 예상 종료 시각을 적는다
5. **기록과 정리**: 실제 소요 시간과 compute unit을 SLICE·EXP 문서에 적는다(SPEC: 첫 실행의 소요 시간과 소모율 기록). 끝나면 `colab stop -s <이름>`을 하고 `colab sessions`로 남은 세션이 없는지 확인한다. 멈추지 않은 VM은 24시간까지 크레딧을 쓴다

산출물 취급:
- 내려받은 인덱스·임베딩은 `data/` 아래에만 둔다. 원문을 담고 있어 AI Hub 재배포 제한을 받는다
- `colab exec -f nb.ipynb`가 만드는 `*_output.ipynb`와 `colab log -o`로 내보낸 기록은 저장소 밖(스크래치 디렉터리)에 둔다. 출력에 `summary_q` 같은 AI Hub 생성물이 남을 수 있다
- `colab auth`, `colab drivemount`는 사람이 터미널에서 해야 하므로 필요하면 사용자에게 요청한다

## 오류 처리

- 에이전트가 실패하거나 결과가 비어 있으면 한 번 다시 부른다. 또 실패하면 그 검증 없이 멈추고 사용자에게 보고한다. 검증·감사·판정을 메인이 대신 채우지 않는다. 분리된 판단이라는 목적이 사라지기 때문이다
- 사용량 한도, 권한 거부처럼 다시 시도해도 같은 실패는 다시 시도하지 않는다. 한도라면 풀리는 시각을 함께 보고한다
- 에이전트 보고가 "사용자 승인 필요"를 포함하면 그 지점에서 멈추고 사용자에게 묻는다
- Colab 세션이 끊기거나 VM이 회수되면(404·401) `colab sessions`로 확인하고, 새 VM에서 중간 산출물부터 재개한다. 재개 명령과 진행 위치를 STATUS에 적는다. 인증 오류(403 등)는 다시 시도하지 않고 사용자에게 보고한다

## 테스트 시나리오

- 정상: "S1 시작해줘" → 0에서 `feat/s01-data` 브랜치 생성 → A1 `docs/slices/01-data.md` 작성·확인 → A2 구현 → A3 verifier가 재생성 건수(코퍼스 38,516, 질의 39,633)와 두 번 실행 일치를 확인 → A4 auditor가 P5(`data/` 스테이징) 등 점검 → A5 PR
- 정상: S1 PR 병합 후 같은 세션에서 "S2 진행" → 0단계부터 다시 → A1 `docs/slices/02-splits.md` 별도 커밋 후 멈춤 → 사용자 확인 → A2 구현
- 정상: "G1 검수 결과 검토해" → 0에서 D3으로 대응 → 집계와 권고 보고 → D4 사용자 결정 → D5 DECISIONS·PLAN PR
- 정상: S4 dev-small 통과 후 "전체 인덱스 Colab에서 만들어" → E1 재개 확인 → E2 A100·예상 시간·compute unit 보고, 승인 → E3 `colab new -s meet-rag-s04 --gpu A100` → E4 clone·업로드·실행·`paths.index_dir`로 다운로드, STATUS 기록 → E5 소요 시간 기록, `colab stop`, `colab sessions` 확인 → A3 verifier가 내려받은 인덱스로 검증
