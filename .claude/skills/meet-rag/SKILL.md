# meet-rag 오케스트레이터

**실행 모드:** 서브에이전트 위임. 구현과 문서 작성은 메인이 직접 하고, 작성 맥락과 떨어진 판단이 필요한 검증·감사·판정만 에이전트에 맡긴다. 예외는 Sonnet 에이전트가 맡는 multi-doc 생성·검사 작업(`multidoc-writer`, `multidoc-checker`)이다. 각 흐름 사이에 사용자 승인이 필요하고(EXP 판정 기준, Colab·유료 API) 서브에이전트는 사용자에게 물을 수 없으므로, 승인 지점과 Colab VM 조작(E)은 모두 메인이 처리한다.

| 에이전트 | 맡는 일 | 호출 시점 |
| --- | --- | --- |
| `slice-verifier` | SLICE 완료 기준을 명령으로 실행해 판정 | SLICE 구현 후 |
| `protocol-auditor` | diff를 평가 프로토콜·금지 조항에 대조 | 모든 PR 전 |
| `exp-judge` | dev-full 결과를 SPEC 규칙으로 판정하고 기록 초안 작성 | EXP 실행 후 |
| `pr-briefer` | diff로 PR 본문의 리뷰 가이드(위험도, 판단할 곳, 구조) 작성 | `docs/`만 바꾼 PR이 아니면 PR 전 |
| `multidoc-writer` | multi-doc 질의 생성(문서 선택, 질의, 기대 답, 근거 인용) | S8 파일럿·G3 본 생성에서 `rag.multidoc.prepare` 뒤, 작업 하나에 후보 집합 10개 |
| `multidoc-checker` | multi-doc 질의 검사(필요한 사실, 사실마다 근거 문서·인용) | 생성 뒤 `rag.multidoc.check --prepare` 다음, 작업 하나에 후보 집합 2개 |

`multidoc-writer`·`multidoc-checker`는 검증 에이전트가 아니라 S8·G3의 작업자다. 메인이 직접 생성·검사하지 않고 Sonnet 에이전트에 맡긴다(D-14, ADR-0020). 프롬프트에 넣는 것은 다음과 같다. 디렉터리를 빼면 에이전트가 경로를 추측해 범위 밖을 읽거나 쓸 수 있다.

- 생성: 생성 지시 파일 경로, `pool_id` 목록, `paths.multidoc_gen_in`·`multidoc_docs`·`multidoc_gen_out`
- 검사: `pool_id` 목록, `paths.multidoc_check_in`·`multidoc_check_out`. 검사 지시는 검사 입력 파일 안에 있다. 생성 출력 경로는 알려 주지 않는다

출력 파일이 이미 있는 후보 집합은 넣지 않는다. 사용자가 지시 변경 뒤 기존 결과를 버리기로 정하면 메인이 해당 출력 파일을 지운 뒤 다시 부른다. 실행 단계(파일럿, 본 생성)마다 부르기 전에 후보 집합 수와 예상 소요 시간을 보고하고 승인받는다(SPEC 자원 제약). API 과금이 없어도 이 승인 대상이다.

**작업자 풀.** 생성·검사는 작업자 풀로 돌린다(ADR-0020).

- 에이전트는 백그라운드로 동시 3개(최대 4개)까지 띄운다. 로컬 자원과 메인의 결과 확인이 병목이라 그 이상은 빨라지지 않는다
- 메인이 남은 작업 큐를 들고, 작업 하나가 끝날 때마다 새 에이전트를 띄워 칸을 채운다. 끝난 에이전트를 다시 쓰지 않는다. 앞 작업의 원문이 맥락에 남아 다른 후보 집합과 섞인다(파일럿에서 6건 묶음 에이전트가 conf-0012를 conf-0017로 오판)
- 판정 기준의 일관성은 고정된 지시 파일과 코드 판정이 맡는다. 에이전트끼리 소통하게(팀) 하지 않는다
- 에이전트가 끝나면 반환 메시지와 출력 파일 존재를 대조한다. 출력이 없는 후보 집합은 큐로 되돌린다

**작업 큐 기록.** 메인은 작업을 띄우고 끝낼 때마다 `_workspace/{작업}_queue.jsonl`(예: `s08_queue.jsonl`)에 한 줄을 더한다: 작업 번호, 단계(`gen`·`check`), `pool_id` 목록, 상태(`running`·`done`·`rejected`·`stopped`), 시각. 사람이 진행을 보고 멈춘 작업을 찾는 기록이다. 남은 작업의 기준은 파일 상태(`rag.multidoc.check --dry-run`의 생성·검사·판정 대기 수)이고, 둘이 다르면 파일 상태를 따른다(사용자 결정 2026-10-07). 큐만 믿으면 출력을 쓴 뒤 큐 갱신 전에 멈춘 작업이 다시 돌거나 빠진다.

**중단과 재개.** 사용자가 중단을 지시하면 새 작업을 띄우지 않고, 실행 중인 에이전트를 `TaskStop`으로 멈추고, 큐에 `stopped`를 적는다. 이어서 진행 기록과 `docs/STATUS.md` "실행 중 작업"에 남은 수(`--dry-run` 출력)와 재개 절차를 적는다. 멈춘 에이전트가 쓰지 못한 후보 집합은 출력 파일이 없어 대기로 남고, 쓰다 만 검사 출력은 판정 단계의 형식 검사에서 `rejected/`로 옮겨져 다시 대기가 된다. 새 세션은 0단계에서 STATUS "실행 중 작업"을 보고 `--dry-run`으로 남은 수를 확인한 뒤, 큐의 `running` 항목을 파일 상태로 정리하고(출력이 있으면 `done`, 없으면 대기) 이어 간다.

`protocol-auditor`를 부르는 단계(A4·B5·D2·D5·F6)에서는 `pr-briefer`도 같은 메시지에서 병렬로 부른다. 바뀐 파일이 모두 `docs/` 아래면(D5 등) 부르지 않고 `git.md` PR 절 3을 따른다. 프롬프트에 auditor와 같은 기준·브랜치·대응 문서·작업 종류와 검증 결과 요약을 넣는다. 감사 지적을 고쳐 커밋했으면 briefer도 직전 가이드와 함께 다시 부른다. 가이드가 수정 전 diff를 설명하면 사용자가 다른 코드를 판단하게 된다. 단방향 판정은 메인이 걸린 규칙의 `file:line`을 직접 확인한 뒤 본문에 넣는다.

일반 코드 리뷰는 `/code-review`를 쓴다. 에이전트 결과는 반환 메시지로 받는다. 판정에 걸리는 근거(실패 출력, 위반 `file:line`, 판정 수치)는 메인이 직접 한 번 확인한 뒤 반영한다.

## 0. 맥락 확인

새 조각·게이트·실험으로 넘어갈 때마다 이 단계부터 다시 한다. 같은 세션에서 이어지는 작업도 마찬가지다. 직전 작업의 흐름을 기억에 기대어 이어 가면 확인·감사 단계가 빠지기 쉽기 때문이다(S2·G1에서 지시서 확인이 빠진 사례).

1. `git branch --show-current`. `main`이면 작업 종류에 맞는 브랜치를 만든다(`.claude/rules/git.md`)
2. `docs/STATUS.md`의 "다음 행동", "판정 대기", "실행 중 작업"을 읽는다. `_workspace/`에 이 작업의 진행 기록이 있으면 읽고 이어서 한다. 멈춘 생성·검사 작업이 있으면 위 "중단과 재개"로 이어 간다
3. 요청을 흐름에 대응시킨다
   - 조각 구현, 파이프라인 수정 → A
   - 백로그 가설 시험, 실행 끝난 실험 판정 → B (판정만이면 B4부터)
   - PLAN의 G 항목(사람 검수 게이트), 검수 결과 집계·결정 → D
   - STATUS "다음 행동" 진행 요청 → 항목에 적힌 흐름 표기(`[A]`·`[B]`·`[C]`·`[D]`·`[F]`)를 따른다
   - "검증만 다시", "감사만 다시" → 해당 에이전트만 다시 부른다. 직전 지적 목록을 프롬프트에 넣는다
   - 세션 마무리, 핸드오프 → C
   - 하네스(`.claude/`의 스킬·에이전트·규약·보조 스크립트) 수정, 하네스 피드백 반영 → F
   - 전체 코퍼스 임베딩·인덱스 구축 등 GPU 작업 → 해당 A·B 단계 안에서 E

## 작업 기록 (`_workspace/`)

`_workspace/`는 로컬 전용 작업 디렉터리다(`.gitignore`). 두 가지 용도로 쓴다. 단계가 바뀔 때 앞 단계의 산출물·결정·주의 사항을 다음 단계와 에이전트에게 넘기고, 사용자가 진행 상황을 확인한다. 서브에이전트는 매번 새로 떠서 이전 맥락을 모르고, 메인의 맥락도 세션이 바뀌면 사라지므로 파일로 이어 준다.

- 파일 이름은 `{작업}_{작성자}_{내용}.md`다. 예: `s05_main_progress.md`, `exp002_main_progress.md`
- 진행 기록: 흐름을 시작할 때 만들고, 단계가 끝날 때마다 상태·산출물 경로·커밋·다음 단계가 알아야 할 것을 갱신한다. 에이전트를 부를 때 프롬프트에 이 경로를 넣는다
- `00_main_harness-pending.md`: 작업 중 발견한 하네스 개선 거리를 바로 적어 두는 대기 목록이다. 작업 PR 뒤 `chore/` 브랜치에서 `harness:evolve`로 반영하고 상태를 바꾼다. 반영한 결정은 `docs/harness/adr/`에 ADR로 남긴다(CLAUDE.md 변경 이력 표 대신)
- 최종 결과와 결정은 여기에 두지 않는다. SLICE·EXP 문서, DECISIONS, STATUS가 기록처다

## 결정과 PR의 순서

- **노트북이 결정보다 먼저**: 데이터·점수를 보고 정하는 결정(설정 값, 프로토콜 미결 사항, 검수 규칙, EXP 채택 뒤 방향)은 근거 노트북(`notebooks/`, `.claude/rules/notebook.md`)을 먼저 쓰고 사용자에게 보인 뒤 DECISIONS에 기록한다. 노트북은 결정의 근거 자료다. 결정 뒤에 쓰면 노트북이 결정을 설명하는 자료가 되고, 사용자가 같은 근거를 보고 정했는지 확인할 수 없다(S4는 D-04 결정 뒤에 노트북을 써 PR #15에서 지적받음). 결정이 걸린 조각·실험은 지시서에 노트북과 결정의 순서를 적는다
- **결정을 반영한 뒤 PR**: PR 내용이 사용자 결정에 따라 바뀌는 작업이면, 결정을 받아 반영하고 작업을 마무리한 뒤 PR을 올린다. 결정이 사소하면(표현, 경로 이름 등) PR 코멘트로 받아도 된다. 결정 전에 PR을 올리면 PR을 다시 고치게 되고, 사용자가 diff를 두 번 읽어야 한다(여러 차례 반복됨)

## A. SLICE 흐름

1. **지시서**: `docs/slices/NN-이름.md`가 없으면 `docs/PLAN.md` 해당 줄을 바탕으로 쓴다. 완료 기준은 명령과 기대 결과로, 성능 수치는 넣지 않는다. 수정 허용 파일과 범위 밖을 적는다. `docs: SLICE NN 지시서`로 구현과 따로 커밋하고, 사용자에게 보여 확인받는다. 결정이 걸린 조각이면 노트북과 결정의 순서를 적는다("결정과 PR의 순서"). 확인을 받기 전에는 구현을 시작하지 않고 이 지점에서 멈춘다. 지시서가 구현 커밋에 섞이면 확인을 거쳤는지 이력으로 알 수 없다
2. **구현**: 메인이 구현한다. 파라미터는 `configs/`에, 코드와 테스트는 같은 커밋에 둔다. dev-small로 먼저 돌려 본다. 전체 규모 임베딩이 필요하면 E를 따른다
3. **검증**: `slice-verifier`를 부른다. 프롬프트에 SLICE 문서 경로, 브랜치, 진행 기록 경로, 허용 실행 범위(기본 dev-small)를 넣는다. 로컬 PC CPU 임베딩이 필요한 기준은 판정에 필요한 최소 규모로 허용한다(예: 재개 확인은 문서 2\~3개와 작은 `index.shard_size`). 검증이 CPU 임베딩에 오래 묶이면 사용자를 기다리게 할 뿐 판정은 더 정확해지지 않는다(S4 검증이 CPU 임베딩 두 번으로 약 20분 걸린 사례). 실패하면 고치고 같은 검증을 다시 부른다
4. **감사**: `protocol-auditor`를 부른다. 프롬프트에 기준 `main`, 브랜치, SLICE 문서 경로, 작업 종류 SLICE를 넣는다. 사용자가 요청하면 `/code-review`도 돌린다. 둘은 서로 독립이므로 한 메시지에서 병렬로 부른다
5. **PR**: 지시서의 사용자 결정이 모두 반영됐는지 확인한다("결정과 PR의 순서"). 지적을 반영하거나 반영하지 않는 이유를 정한 뒤 `.claude/rules/git.md` PR 절차를 따른다. PR 본문에 검증 결과와 감사 지적·반영 여부를 적는다
6. S3(평가 모듈)이 끝나면 `src/rag/eval/` 명령을 `CLAUDE.md` "명령" 절에 추가한다. `exp-judge`가 이 명령을 쓴다

## B. EXP 흐름

1. **초안**: `docs/PLAN.md` 백로그에서 가설을 고르고, `docs/SPEC.md`, `docs/DECISIONS.md`, 기준 실험 문서를 읽은 뒤 `docs/experiments/EXP-NNN.md`와 `configs/exp/expNNN.yaml`을 쓴다. 판정 기준은 SPEC 판정 절을 그대로 옮기거나 더 엄격하게 쓴다
2. **승인 지점**: 가설, 바꾸는 것, 판정 기준을 사용자에게 보이고 승인받는다. 재임베딩이 필요하면(Colab) 예상 시간·크레딧을, 유료 API가 필요하면 예상 비용을 함께 보고한다. 승인 전에는 dev-small까지만 실행한다
3. **실행**: 실험 코드가 새로 필요하면 config로 켜는 형태로 만들고 기준 설정의 동작을 바꾸지 않는다. 기존 모듈을 크게 바꿔야 하면 먼저 SLICE(A 흐름)로 분리한다. dev-small로 동작을 확인한 뒤 dev-full을 실행한다. 재임베딩이 필요하면 E를 따른다
4. **판정**: `exp-judge`를 부른다. 프롬프트에 EXP 문서 경로, 기준·후보 순위 파일 경로, 실행 명령, 커밋 해시를 넣는다
5. **감사**: `protocol-auditor`를 작업 종류 EXP로 부른다. 4와 서로 독립이므로 병렬로 부른다
6. **기록**: judge 초안의 수치를 직접 확인한다. 채택이면 근거 노트북을 먼저 쓰고 사용자에게 보인다("결정과 PR의 순서"). 이어서 EXP 문서 결과·결론, `docs/EXPERIMENTS.md`, 채택이면 `docs/DECISIONS.md`, `docs/PLAN.md` 백로그 상태를 갱신한다. 기각·보류도 병합한다. 비채택이 3회 연속이면 SPEC 중단 기준에 걸렸다고 사용자에게 알린다

## C. 세션 마무리

`CLAUDE.md` "세션 마무리" 절 순서를 따른다. STATUS "다음 행동"의 각 항목 앞에 다음 세션이 탈 흐름을 `[A]`·`[B]`·`[C]`·`[D]`·`[F]`로 적는다. 판정이 끝나지 않은 실험이 있으면 B4\~B6을 먼저 한다. 핸드오프는 사용자가 요청할 때만 한다.

## D. 사람 검수 게이트 (PLAN의 G 항목)

사람이 데이터를 직접 보고 프로토콜 미결 사항을 정하는 단계다. SLICE 문서를 쓰지 않고 PLAN의 G 항목 줄과 SPEC 미결 절을 대응 문서로 쓴다.

1. **표본 도구**: `chore/gN-이름` 브랜치에서 표본 추출 코드를 쓴다. dev 분할에서만 뽑고, 표본 크기·seed는 `configs/config.yaml`에 둔다(`configs/eval/`은 보호 경로). 검수 칸은 비워 둔다
2. **감사·PR**: `protocol-auditor`를 작업 종류 게이트로 부른 뒤 PR을 올린다. STATUS에 사용자 검수 대기와 표본 파일 경로·해시를 적고 멈춘다
3. **집계**: 사용자가 검수 파일을 주면 판정·유형별 건수와 비율을 낸다. 검수 기준과 평가 용도(SPEC 평가 질의·정답)가 다르면 그 차이가 지표에 미치는 영향을 구분해 보고한다. 검수 칸이 자유 기술이면 유형을 묶어 제시한다
4. **결정 지점**: 집계를 노트북으로 쓰고("결정과 PR의 순서"), 규칙(필터 등)을 둘지 사용자에게 노트북과 권고를 함께 보이며 묻는다. 결정은 사용자가 한다. 질의 필터 같은 규칙은 검색 점수를 보기 전에 정한다(SPEC 누수 방지). 점수를 본 뒤 정하면 규칙이 점수에 맞춰질 수 있다
5. **기록**: `docs/` 브랜치에서 `docs/DECISIONS.md`에 집계·결정·이유를, `docs/PLAN.md`에 G 체크를 반영한다. `protocol-auditor`를 작업 종류 문서로 부르고 PR을 올린다. SPEC 미결 절의 해결 표시는 SPEC 수정이므로 사용자 승인 없이 하지 않는다. 규칙을 채택했으면 적용은 SLICE(A 흐름)로 분리하고, 보호 경로(`src/rag/eval/`, `data/splits/`)를 건드려야 하면 사용자 승인 후 DECISIONS에 기록한다

## E. GPU 작업 (Colab)

임베딩은 KURE-v1이고 다른 임베딩 모델로 바꿔도 직접 임베딩하므로, 전체 코퍼스 임베딩·인덱스 구축·재임베딩 실험에는 GPU가 필요하다. 로컬 PC에는 GPU가 없어(SPEC 자원 제약) 이 작업은 Colab VM에서 `colab` CLI로 한다. 생성(Gemma 4, Google AI Studio)은 GPU를 쓰지 않는다.

VM 조작은 `scripts/colab_job.py`로 한다. colab CLI를 손으로 부를 때 반복해 생긴 함정(Git Bash 경로 변환, cp949 출력 오류, 미push 커밋, override 오타, Colab Python 3.13, 20분 전후 연결 끊김, tar의 `C:` 해석)을 스크립트가 막는다. 함정을 기억으로 피하면 다음 세션에서 같은 실수가 난다. 스크립트가 다루지 않는 일(세션 할당, 상태 확인, 복구)만 colab CLI를 직접 쓴다.

A2(S4 등 전체 인덱스)와 B3(재임베딩 실험)에서 GPU 임베딩이 필요하면 이 절차를 따른다.

1. **로컬 확인**: 로컬 PC CPU에서는 코드가 돌고 재개되는지만 본다. 문서 수십 개 이하, 후보 하나로 충분하다. 로컬 CPU는 문서 20개·256 토큰에 약 6분 걸려, 그 이상은 시간만 쓴다. dev-small이라도 임베딩은 GPU에서 하고, GPU 실행은 E3 승인 대상이다. dev-small 작업 과정과 결과는 Jupyter 노트북(`notebooks/`)에 남긴다. 노트북은 Colab 산출물을 불러와 확인하는 자리이고, 노트북에서 무거운 임베딩을 돌리지 않는다
2. **colab-operator 불러오기**: VM을 할당하기 전에 `colab-operator` 스킬을 Skill 도구로 불러온다. 설치 때 읽은 기억으로 대신하지 않는다(S4에서 두 번 모두 불러오지 않고 진행한 사례)
3. **승인 지점**: GPU 종류, 예상 시간, 예상 compute unit을 사용자에게 보고하고 승인받는다. GPU는 사용자가 지정한 것을 쓰고, 지정이 없으면 묻는다. 서브에이전트는 VM을 만들지 않는다. 과금이 걸린 결정이라 사용자에게 물을 수 있는 메인만 한다
   - 예상 시간: 같은 GPU의 직전 실측 처리량(SLICE·EXP "실행 기록")을 문서 수 비율로 늘리고, 준비(환경 설치·모델 다운로드)와 결과 다운로드 시간을 더한다
   - 예상 compute unit: 요율 × 예상 세션 시간. 요율은 사용자가 Colab 웹 화면에서 확인한 값을 쓴다(2026-10-01 L4 1.54 CU/시간. S4 전체 인덱스 32분 세션의 실측은 0.73 CU로 환산치 0.83보다 낮았다). 처리량에서 요율을 거꾸로 추정하지 않는다. S4 1차에서 그렇게 해 예상치를 낮게 냈다
4. **사전 점검**: `colab_job.py preflight <override...>`. 커밋되지 않은 변경, 원격에 없는 HEAD, 틀린 override를 VM 할당 전에 막는다
5. **할당과 환경**: `colab new -s meet-rag-<작업> --gpu <GPU>` 뒤 `colab_job.py setup -s <세션> --commit <HEAD>`. VM에 uv를 깔고 `uv sync --extra cu126`으로 Python 3.12와 `uv.lock` 버전을 그대로 맞춘다. 로컬과 같은 버전이어야 결과를 재현할 수 있다. 출력된 Python·torch·transformers·sentence-transformers 버전을 실행 기록에 남긴다
   - 할당이 실패하면(400 등) `--gpu T4`로 바꿔 다시 할당한다. 이 대체는 승인 범위 안이라 다시 승인받지 않고 바뀐 GPU와 다시 잡은 예상 시간만 알린다. T4도 실패하면 멈추고 보고한다. 비용이 예상과 달라졌다는 이유만으로 작업을 멈추지는 않는다
6. **입력과 실행**: `colab_job.py upload`로 입력(`data/processed/` 코퍼스, 필요하면 범위에 맞게 거른 파일)을 올리고, `colab_job.py launch -s <세션> -- python -m <모듈> <override...>`로 VM 안 nohup 실행을 띄운 뒤 `colab_job.py poll`로 로그를 본다. 질의는 dev 질의만 거른 파일을 올린다(`upload`가 dev가 아닌 qid가 있으면 막는다). `test` 질의와 분할 파일(`queries.csv`)은 올리지 않는다(SPEC 자원 제약, DECISIONS D-07). 질의를 담은 데이터는 jsonl로 쓰고 질의 ID 키는 `qid`로 한다. 업로드 검사가 이 형식에만 기대기 때문이다. 노트북에는 질의 원문을 대량 출력하지 않는다. `docs/STATUS.md` "실행 중 작업"과 `_workspace/` 진행 기록에 세션 이름, 커밋, 예상 종료 시각을 적는다
7. **회수와 정리**: `colab_job.py fetch -s <세션> <저장소 기준 산출물 경로>`로 내려받아 로컬 같은 경로에 푼다. 이어서 `colab_job.py finish -s <세션>`으로 세션 기록을 `outputs/notebooks/`에 남기고 VM을 멈춘 뒤 남은 세션이 없는지 확인한다. 멈추지 않은 VM은 24시간까지 크레딧을 쓴다. 실제 세션 시간과 compute unit(사용자 확인값)을 SLICE·EXP 문서 "실행 기록"에 적는다

산출물 취급:
- 내려받은 인덱스·임베딩은 `data/` 아래에만 둔다. 원문을 담고 있어 AI Hub 재배포 제한을 받는다
- `colab exec -f nb.ipynb`가 만드는 `*_output.ipynb`와 `colab log -o`로 내보낸 기록은 `outputs/notebooks/`에 둔다. `outputs/`는 프로젝트 진행 중 커밋하지 않고(`.gitignore`) 완료 후 결과 공개 때 공개한다. 출력에 질의가 조금 들어가는 것은 괜찮다. 회의록 발언 원문은 AI Hub 생성물이 아니지만, 질의응답쌍과 그 분할은 AI Hub 고유 자료일 수 있어 대량으로 남기지 않는다
- `colab auth`, `colab drivemount`는 사람이 터미널에서 해야 하므로 필요하면 사용자에게 요청한다

## F. 하네스 수정

1. **evolve 불러오기**: `harness:evolve`를 Skill 도구로 불러온 뒤 시작한다. 절차를 기억으로 대신하지 않는다. 기억으로 진행하면 단계별 검증과 트리거 검증이 빠진다(S4의 `colab-operator`, PR #19·이번 하네스 브랜치의 `harness:evolve` 미호출, ADR-0015)
2. **브랜치**: 작업 PR과 섞지 않고 `chore/` 브랜치에서 한다. `_workspace/00_main_harness-pending.md`의 대기 항목을 근거로 쓴다
3. **PR 코멘트 수집**: 마지막 하네스 PR 이후 병합된 PR의 사용자 리뷰 코멘트를 읽는다(`gh pr view N --comments`, `gh api repos/{owner}/{repo}/pulls/N/comments`). 같은 유형의 지적이 다시 나오지 않게 고칠 수 있는 것(작업 순서, 빠진 확인, 문서 형식)은 근거 PR 번호와 함께 대기 목록에 더한다. 그 PR 하나의 내용 수정 요청은 더하지 않는다. 사용자 지적이 대기 목록에 들어오는 경로가 메인이 기억해 옮기는 것뿐이면 빠지는 지적이 생긴다(PR #15 노트북 순서 지적은 사람이 옮김)
4. **변경마다 검증**: 변경을 하나씩 적용하고, 그때마다 frontmatter·참조 경로를 확인한다. description을 바꾸면 should-trigger·near-miss 요청 각 3개 이상으로 트리거를 검증한다. 검증은 작성 맥락과 분리하려고 서브에이전트에 맡긴다
5. **기록**: evolve Phase 4의 CLAUDE.md 변경 이력 표 대신 `docs/harness/adr/`에 ADR을 추가하고 목록을 갱신한다(ADR-0014). 앞 ADR을 바꾸면 그 상태를 고친다
6. **감사·PR**: `protocol-auditor`를 작업 종류 하네스로 부르고, 수정안을 사용자에게 보인 뒤 PR을 올린다("결정과 PR의 순서")

## 오류 처리

- 에이전트가 실패하거나 결과가 비어 있으면 한 번 다시 부른다. 또 실패하면 그 검증 없이 멈추고 사용자에게 보고한다. 검증·감사·판정을 메인이 대신 채우지 않는다. 분리된 판단이라는 목적이 사라지기 때문이다
- 사용량 한도, 권한 거부처럼 다시 시도해도 같은 실패는 다시 시도하지 않는다. 한도라면 풀리는 시각을 함께 보고한다
- 외부 API(Google AI Studio·Gemini API 등)가 5xx를 내면 다시 시도하기 전에 서버 상태(https://aistudio.google.com/status)를 먼저 확인한다. 장애·성능 저하로 표시되면 멈추고 상태와 함께 보고한다. 정상으로 표시될 때만 한 번 다시 시도하고, 또 실패하면 보고한다. SDK 자동 재시도에 반복 실행을 겹치면 호출만 늘고 원인은 그대로다(S6 노트북을 서버 장애 중 일곱 번 다시 실행한 사례, ADR-0012). 402(결제)·403(인증)은 다시 시도하지 않고 보고한다
- 노트북 실행이 셀 하나에서 실패하면 처음부터 다시 돌리지 않는다. `scripts/nb_kernel.py`(지속 커널)로 실행하고, 실패한 셀을 고쳐 그 셀부터 이어서 실행한다(`.claude/rules/notebook.md` §8, ADR-0013)
- 에이전트 보고가 "사용자 승인 필요"를 포함하면 그 지점에서 멈추고 사용자에게 묻는다
- 진행 중이던 VM이 오류로 회수되는 등(404·401) 승인 때 예상하지 않은 GPU 사용이 생기면, 새 VM을 만들기 전에 `colab sessions`로 상태를 확인하고 사용자에게 보고한다. 재할당은 사용자가 정한 뒤 중간 산출물부터 재개하고, 재개 명령과 진행 위치를 STATUS에 적는다. 조용히 반복 재시도해 비용을 쓰지 않는다. 인증 오류(403 등)도 다시 시도하지 않고 보고한다
