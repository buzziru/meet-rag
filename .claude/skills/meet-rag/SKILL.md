# meet-rag 오케스트레이터

**실행 모드:** 서브에이전트 위임. 구현과 문서 작성은 메인이 직접 하고, 작성 맥락과 떨어진 판단이 필요한 검증·감사·판정만 에이전트에 맡긴다. 각 흐름 사이에 사용자 승인이 필요하고(EXP 판정 기준, Colab·유료 API) 서브에이전트는 사용자에게 물을 수 없으므로, 승인 지점은 모두 메인이 처리한다.

| 에이전트 | 맡는 일 | 호출 시점 |
| --- | --- | --- |
| `slice-verifier` | SLICE 완료 기준을 명령으로 실행해 판정 | SLICE 구현 후 |
| `protocol-auditor` | diff를 평가 프로토콜·금지 조항에 대조 | 모든 PR 전 |
| `exp-judge` | dev-full 결과를 SPEC 규칙으로 판정하고 기록 초안 작성 | EXP 실행 후 |

일반 코드 리뷰는 `/code-review`를 쓴다. 에이전트 결과는 반환 메시지로 받는다. 판정에 걸리는 근거(실패 출력, 위반 `file:line`, 판정 수치)는 메인이 직접 한 번 확인한 뒤 반영한다.

## 0. 맥락 확인

1. `git branch --show-current`. `main`이면 작업 종류에 맞는 브랜치를 만든다(`.claude/rules/git.md`)
2. `docs/STATUS.md`의 "다음 행동", "판정 대기", "실행 중 작업"을 읽는다
3. 요청을 흐름에 대응시킨다
   - 조각 구현, 파이프라인 수정 → A
   - 백로그 가설 시험, 실행 끝난 실험 판정 → B (판정만이면 B4부터)
   - "검증만 다시", "감사만 다시" → 해당 에이전트만 다시 부른다. 직전 지적 목록을 프롬프트에 넣는다
   - 세션 마무리, 핸드오프 → C

## A. SLICE 흐름

1. **지시서**: `docs/slices/NN-이름.md`가 없으면 `docs/PLAN.md` 해당 줄을 바탕으로 쓴다. 완료 기준은 명령과 기대 결과로, 성능 수치는 넣지 않는다. 수정 허용 파일과 범위 밖을 적는다. 사용자에게 보여 확인받는다
2. **구현**: 메인이 구현한다. 파라미터는 `configs/`에, 코드와 테스트는 같은 커밋에 둔다. dev-small로 먼저 돌려 본다
3. **검증**: `slice-verifier`를 부른다. 프롬프트에 SLICE 문서 경로, 브랜치, 허용 실행 범위(기본 dev-small)를 넣는다. 실패하면 고치고 같은 검증을 다시 부른다
4. **감사**: `protocol-auditor`를 부른다. 프롬프트에 기준 `main`, 브랜치, SLICE 문서 경로, 작업 종류 SLICE를 넣는다. 사용자가 요청하면 `/code-review`도 돌린다. 둘은 서로 독립이므로 한 메시지에서 병렬로 부른다
5. **PR**: 지적을 반영하거나 반영하지 않는 이유를 정한 뒤 `.claude/rules/git.md` PR 절차를 따른다. PR 본문에 검증 결과와 감사 지적·반영 여부를 적는다
6. S3(평가 모듈)이 끝나면 `src/rag/eval/` 명령을 `CLAUDE.md` "명령" 절에 추가한다. `exp-judge`가 이 명령을 쓴다

## B. EXP 흐름

1. **초안**: `docs/PLAN.md` 백로그에서 가설을 고르고, `docs/SPEC.md`, `docs/DECISIONS.md`, 기준 실험 문서를 읽은 뒤 `docs/experiments/EXP-NNN.md`와 `configs/exp/expNNN.yaml`을 쓴다. 판정 기준은 SPEC 판정 절을 그대로 옮기거나 더 엄격하게 쓴다
2. **승인 지점**: 가설, 바꾸는 것, 판정 기준을 사용자에게 보이고 승인받는다. 재임베딩이 필요하면(Colab) 예상 시간·크레딧을, 유료 API가 필요하면 예상 비용을 함께 보고한다. 승인 전에는 dev-small까지만 실행한다
3. **실행**: 실험 코드가 새로 필요하면 config로 켜는 형태로 만들고 기준 설정의 동작을 바꾸지 않는다. 기존 모듈을 크게 바꿔야 하면 먼저 SLICE(A 흐름)로 분리한다. dev-small로 동작을 확인한 뒤 dev-full을 실행한다. Colab 실행이면 `docs/STATUS.md` "실행 중 작업"에 위치와 예상 종료 시각을 적는다
4. **판정**: `exp-judge`를 부른다. 프롬프트에 EXP 문서 경로, 기준·후보 순위 파일 경로, 실행 명령, 커밋 해시를 넣는다
5. **감사**: `protocol-auditor`를 작업 종류 EXP로 부른다. 4와 서로 독립이므로 병렬로 부른다
6. **기록**: judge 초안의 수치를 직접 확인하고 EXP 문서 결과·결론, `docs/EXPERIMENTS.md`, 채택이면 `docs/DECISIONS.md`, `docs/PLAN.md` 백로그 상태를 갱신한다. 기각·보류도 병합한다. 비채택이 3회 연속이면 SPEC 중단 기준에 걸렸다고 사용자에게 알린다

## C. 세션 마무리

`CLAUDE.md` "세션 마무리" 절 순서를 따른다. 판정이 끝나지 않은 실험이 있으면 B4~B6을 먼저 한다. 핸드오프는 사용자가 요청할 때만 한다.

## 오류 처리

- 에이전트가 실패하거나 결과가 비어 있으면 한 번 다시 부른다. 또 실패하면 그 검증 없이 멈추고 사용자에게 보고한다. 검증·감사·판정을 메인이 대신 채우지 않는다. 분리된 판단이라는 목적이 사라지기 때문이다
- 사용량 한도, 권한 거부처럼 다시 시도해도 같은 실패는 다시 시도하지 않는다. 한도라면 풀리는 시각을 함께 보고한다
- 에이전트 보고가 "사용자 승인 필요"를 포함하면 그 지점에서 멈추고 사용자에게 묻는다
- Colab 세션이 끊기면 중간 산출물에서 재개한다. 재개 명령과 진행 위치를 STATUS에 적는다

## 테스트 시나리오

- 정상: "S1 시작해줘" → 0에서 `feat/s01-data` 브랜치 생성 → A1 `docs/slices/01-data.md` 작성·확인 → A2 구현 → A3 verifier가 재생성 건수(코퍼스 38,516, 질의 39,633)와 두 번 실행 일치를 확인 → A4 auditor가 P5(`data/` 스테이징) 등 점검 → A5 PR
- 오류: B4에서 후보 순위 파일이 dev-small로 만들어져 있음 → judge가 판정하지 않고 보고 → 메인이 dev-full 실행 여부를 사용자에게 묻는다
- 오류: A4에서 auditor가 P4(하드코딩 top-k) 위반 보고 → 메인이 `file:line`을 확인하고 config로 옮김 → auditor를 직전 지적 목록과 함께 다시 부른다
