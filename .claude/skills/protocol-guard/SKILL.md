# protocol-guard: 평가 프로토콜 점검표

검색 실험의 수치는 평가가 고정되어 있을 때만 서로 비교할 수 있다. 점수를 올리라는 목표를 받은 에이전트는 평가 쪽을 바꾸거나 test 정보를 쓰는 방식으로도 목표를 달성할 수 있다. 이 점검표는 그런 경로를 diff 단위로 막는다. 근거 문서는 `CLAUDE.md` "금지" 절과 `docs/SPEC.md` "누수 방지"·"자원 제약" 절이다. 두 문서와 이 표가 어긋나면 두 문서를 따르고 어긋남을 보고한다.

## 준비

```bash
git diff --name-status main...HEAD
git diff main...HEAD
git status --short
```

대응 SLICE·EXP 문서의 "수정 허용 파일", "바꾸는 것", "범위 밖"을 읽어 둔다.

## 점검 항목

### P1. test 분할 접근

test 질의를 읽거나 test 점수를 계산하는 실행·코드 경로가 아래 예외 밖에서 생기면 위반이다.

예외는 단계(검색, 생성)를 마칠 때 사용자 지시로 단계마다 1회 하는 종료 측정이다. 목적은 test 점수나 질의로 설정·결정을 조정하지 않는 것이고(P2), 그래서 이 1회 밖의 읽기·채점은 결정 조정 여부와 관계없이 위반이다(사용자 의도 2026-10-20).

- 검색 단계 1회는 S13에서 마쳤다(D-39)
- 생성 단계 1회는 생성 단계를 마칠 때 사용자 지시로 한다(SPEC 개정 D-53). 생성 단계를 마치는 때는 사용자가 정한다. 백로그의 생성 실험을 우선순위대로 진행하고, 남은 실험의 예상 개선 폭이 작으면 실행하지 않고 닫은 뒤 마친다(검색 단계 S13과 같음, 사용자 설명 2026-10-27). 생성 입력을 만들려고 test 질의로 검색을 다시 돌리는 것을 포함하고, 생성 단계 중 검색 설정을 dev로 다시 정했으면 그 1회에서 바뀐 검색의 test 점수도 기록한다(S13과 별도). 검색과 생성은 서로 영향을 주므로 생성을 위한 검색 수정을 막지 않는다. test 제한의 목적은 test 데이터에 대한 긍정 편향을 막는 것이다(PR #116 코멘트)
- 검색 단계에서 쓴 test 경로(`search.allow_test`, `rag.eval.score --allow-test`)는 생성 단계 1회에 다시 쓰려고 남긴 것이라 그대로 있는 것은 위반이 아니다. test를 실행하지 않는 코드·설정 준비도 위반이 아니다
- 지시를 받은 1회 안에서 본 실행 전에 실행이 되는지 확인하는 것(소수 질의 드라이런 등)은 같은 1회로 본다. 1회 제한이 막는 것은 test 결과를 보고 점수를 올리려 바꾸는 것이고, 실행 여부 확인은 막지 않는다(사용자 결정 2026-10-27, PR #166). 드라이런 결과로 설정·코드를 바꾸면 결과에 맞춘 변경이므로 두 번째 실행으로 본다. 실행 오류를 고치는 것은 해당하지 않는다
- 위반: 사용자 지시 기록 없는 실행(드라이런 포함), 같은 단계의 두 번째 실행

diff에서 찾을 코드 경로:

- `split == "test"`, `"test"` 문자열로 분할을 고르는 코드
- `data/splits/queries.csv`를 읽고 split으로 거르지 않은 채 질의 전체를 쓰는 코드. 필터가 없으면 test가 섞인다
- config에서 평가 분할을 바꿀 수 있게 하면서 기본값이나 호출부가 test인 경우
- 질의를 담은 데이터 파일을 jsonl이 아닌 형식으로 쓰거나, 질의 ID를 `qid`가 아닌 키로 쓰는 코드. `colab_job.py upload`의 dev 확인은 `.jsonl`의 `qid` 키로만 판정하므로, 다른 형식이면 test 질의가 검사 없이 VM으로 나갈 수 있다(평가 프로토콜, D-31)

`tests/` 디렉터리(pytest)는 분할과 무관하다. 이름만 보고 판정하지 않는다.

### P2. 설정 선택에 test·dev-small 사용

필터 규칙, 프롬프트, 하이퍼파라미터 선택에 test 질의를 쓰면 위반이다. dev-small 점수로 채택을 판정하면 위반이다(SPEC: dev-small은 방향 확인용).

### P3. 보호 경로 수정

- 항상 보호된다: `configs/eval/`, `src/rag/eval/`, `src/rag/eval_multi/`와 `configs/config.yaml`의 `multidoc.eval` 키, `data/splits/`, G3 동결 세트를 정하는 `configs/multidoc/g3_exclude.yaml`과 `paths.multidoc_frozen` 키. CLAUDE.md 금지 절과 같은 목록이다. multi-doc 채점이나 세트가 바뀌면 EXP마다 보고하는 multi-doc 관찰을 기준선(D-16)과 비교할 수 없다. 처음에는 S2·S3·S9 완료와 G3 동결(D-15) 뒤부터 보호했으나 모두 끝나 조건을 지웠다(ADR-0057)
- 앞으로 어떤 작업이 끝난 뒤부터 보호되는 경로가 생기면, 완료 여부는 그 항목이 `docs/PLAN-done.md`에 있는지로 판단한다. 끝난 항목은 완료를 처리하는 커밋에서 PLAN-done으로 옮기므로 PLAN-done이 완료의 유일한 근거다(ADR-0057)
- `docs/SPEC.md`의 평가 프로토콜 절 수정

보호 경로를 바꿨으면, 사용자 승인 기록과 `docs/DECISIONS.md` 항목이 같은 diff에 있는지 확인한다. 둘 다 있으면 통과이고 기록만 남긴다.

### P4. 파라미터 하드코딩

청크 길이, top-k, 모델명, 배치 크기, seed, 경로, `base_url` 같은 값이 `src/rag/`에 리터럴로 들어가면 위반이다. 값은 `configs/`에서 받아야 한다. 알고리즘의 정의상 고정된 상수(예: RRF의 순위 역수 형태)는 해당하지 않지만, RRF의 `k`처럼 바꿀 수 있는 값은 해당한다. 판단이 어려우면 "불확실"로 둔다.

### P5. 커밋 금지 파일

`data/` 아래 파일, `.env`가 스테이징·커밋되면 위반이다. 노트북 출력에 들어간 회의록 발언 원문은 공개 자료라 허용되지만, `summary_q`·`summary_a`·`context_learn`(AI Hub 생성물)이 출력에 대량으로 남았으면 보고한다. Colab 실행 기록(`colab exec -f`가 만든 `*_output.ipynb`, `colab log -o`로 내보낸 기록)은 `outputs/notebooks/`에 둔다. `outputs/`는 프로젝트 진행 중 커밋하지 않으므로(완료 후 공개) 스테이징됐으면 위반이다. 공개 시점의 내용 점검은 위 기준을 따르고, 질의가 조금 들어간 것은 보고하지 않는다.

### P6. 평가 질의의 외부 전송

`summary_q`(질의 파일의 `query`)와 multi-doc 질의를 외부 API(Google AI Studio, OpenRouter, 생성 평가 judge용 opencode Go(D-38))나 Colab에 보내는 것은 처리 목적이면 허용된다(D-31). 이 항목이 막는 것은 `test` 질의의 전송이다. 평가 프로토콜(누수 방지) 때문이고 데이터 공개와는 별개다. split으로 거르지 않은 질의 파일이나 `test` 질의가 외부 호출·업로드 경로에 들어갈 수 있으면 위반이다. 예외는 P1의 단계별 종료 측정 1회다. 검색 단계 1회(S13)는 2026-10-19에 끝났다(D-39). 생성 단계 1회의 외부 전송(OpenRouter 생성, opencode Go judge)은 허용된다(SPEC 개정 D-53, CLAUDE.md 금지 절 외부 전송 줄). Colab으로 보내려면 업로드 허용을 새 ADR로 다시 둔 뒤에 한다(ADR-0045, PLAN 생성 단계 평가 항목). 질의 전체처럼 많이 보내는 실행이 SLICE·EXP 문서에 호출 수·소요 시간·비용과 사용자 승인 기록 없이 들어 있으면 보고한다. `context`만 보내는 생성 경로는 해당하지 않는다.

### P7. EXP 범위 밖 변경 (EXP 작업일 때)

diff를 EXP 문서의 "바꾸는 것"과 대조한다. 목록에 없는 설정·코드 변경이 있으면 위반이다. 실험 코드는 config로 켜는 형태여야 하고, 기준 설정(`configs/config.yaml`과 기본 그룹)의 동작을 바꾸면 위반이다.

### P8. SLICE 범위 밖 변경 (SLICE 작업일 때)

SLICE 문서의 "수정 허용 파일" 밖의 파일이 바뀌었으면 보고한다. 문서 갱신(`docs/`)은 세션 마무리 절차에 속하므로 해당하지 않는다.

### P9. 질의 쪽 라벨을 검색 입력으로 사용

질의의 정답이나 정답 문서에서 온 값이 검색(색인·질의 처리·순위 결정)의 입력에 들어가면 위반이다. 판단 기준은 그 값을 어느 파일·모듈이 읽느냐가 아니라 검색·순위 결정에 들어가느냐다. 문서 쪽 메타데이터를 쓰는 것은 정상이다(D-18·D-19).

- 정답 쪽 값: 질의 파일의 `query` 밖 필드(`doc_id`·`answer`·`qna_type`·`question_comment`·`answer_comment`), `load_gold`가 돌려주는 열 중 index(`qid`) 밖의 열(정답 `doc_id`, `conference_number`, 정답 문서의 `meeting_name` 등), `data/splits/queries.csv`의 `conference_number`, multi-doc 동결 세트의 `gold_doc_ids`·`pool_doc_ids`·`answer`·`elements`·`type`·`pool_id`
- `qid` 문자열 파싱: `qid`는 `{conference_number}-{question_number}`라 정답 회의 번호를 담는다. `qid`를 질의 식별·순서·분할 선택에 쓰는 것은 정상이다(`rag.search`가 `load_gold(...).index`로 질의 목록만 얻는 것 등). `qid`를 나눠 회의 조건으로 쓰면 위반이다
- 원천 라벨 결합: QA 단위 필드(`questioner_name`·`answerer_name`·`law` 등)를 `qid`로 질의에 붙여 필터·가점 조건으로 쓰는 경우. 질의 조건(H14)은 질의 텍스트에서 뽑은 값만 쓴다(PLAN H12·H14)
- 조건 사전의 출처: 질의 조건 추출에 쓰는 사전(위원회·이름 등)은 코퍼스 전체 문서의 필드에서 만든다. 평가 질의 레코드에서 값을 모으거나, 정답 문서 목록으로 문서를 골라 값을 모으면 위반이다. 같은 필드 이름(`meeting_name` 등)이라도 출처가 코퍼스 전체인지 정답 문서인지로 가른다
- 평가 층 범위는 해당하지 않는다: SPEC이 정한 분할과 평가 층(`data/splits/`, `dev_small_docs`로 색인 문서를 거르는 것, 분할에 따라 질의 집합을 고르는 것)은 정답 쪽 값을 쓰지만 검색이 풀 문제의 범위를 정하는 것이라 위반이 아니다
- 위치로 면제하지 않는다: 채점 코드(`src/rag/eval*`)와 분석 노트북이 정답 쪽 값을 읽는 것은 해당하지 않지만, 노트북 안에서도 그 값이 검색 호출이나 순위 계산에 들어가면 위반이다
- 문서에 붙인 화자 필드(S10)는 QA 라벨에서 모으지만 그 문서 발언자의 속성이라 위반이 아니다(D-19). 위의 원천 라벨 결합(QA 필드를 `qid`로 질의에 붙이는 것)과 구분한다

### P10. 산출물 보존 (코드 diff일 때)

근거는 `meet-rag` 스킬 "구현 원칙"이다. `data/`는 커밋하지 않아, 덮어쓴 산출물이나 다른 설정으로 만든 입력이 조용히 쓰이면 되돌리거나 알아챌 기록이 없다. 원칙이 있었는데도 확인 단계가 없어 위반 모듈이 PR을 통과했다(코드 리뷰 2026-10, S15).

- diff에서 `data/` 아래에 쓰는 코드(`open(..., "w")`, `write_text`, `to_csv`, `np.save`, `json.dump` 등)가 `rag.index.write_guarded`(같은 입력이면 같은 내용)나 시작 때 `rag.index.refuse_existing`(다시 만들면 값이 달라지는 채점·측정·judge 기록·검수 파일)을 거치지 않으면 보고한다. 덮어쓰기는 `search.overwrite=true`로만 열려야 하고, 보호 경로(`data/splits/`)처럼 덮어쓰기를 아예 열지 않는 경로는 해당하지 않는다. 임시 파일을 쓴 뒤 바꿔 넣는 조각 쓰기(인덱스 임베딩 조각처럼 있는 조각을 건너뛰는 재개)는 해당하지 않는다
- diff가 실행 config에 따라 달라지는 `data/` 산출물(인덱스, 재정렬 점수, 조건·값 사전, 질의 임베딩 등)을 읽는 새 경로를 만들 때, 실행 시점에 만들거나 `rag.index.check_basis` 같은 지문 대조를 거치지 않으면 보고한다
- 지문이 없는 기존 산출물에 `adopt_basis=true`를 쓴 실행이 있으면, SLICE·EXP 문서나 진행 기록에 만든 설정을 실행 기록과 대조한 내용이 있는지 본다

이 항목은 평가 오염이 아니라 기록 보존을 본다. 위반이 아닌 "보고"로 두고, 메인이 원래 목적의 결함인지 정한다.

## 판정

- 위반: 코드 경로를 따라가 확인한 것
- 보고: P10(산출물 보존)에 걸리는 것. 위반과 따로 적는다
- 불확실: 경로 끝까지 확인하지 못한 것. 무엇을 보면 확정되는지 적는다
- 해당 없음: 이 diff와 무관한 항목
