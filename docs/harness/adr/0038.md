# ADR-0038 CU는 요율 환산으로 기록하고, 커널은 PR 전에 멈추며, 운영 지연은 질의당 시간으로 본다

- 상태: 채택
- 날짜: 2026-10-14

## 맥락

- EXP-006·009의 compute unit이 "사용자 확인값 대기"로 남아 STATUS와 PR에 확인 요청이 쌓였다. 사용자는 실제 값을 확인해 주지 않고 요율 × 세션 시간 환산값을 쓰라고 지시했다(2026-10-14)
- EXP-011에서 사용자가 채택을 결정한 뒤에도 근거 노트북의 지속 커널을 "질문이 더 있을 수 있다"는 이유로 PR 뒤까지 켜 두었다(사용자 지적 2026-10-14). 같은 세션에서 이전 세션의 커널 기록 때문에 `nb_kernel.py run`이 실패하기도 했다. notebook.md §8의 "판단이 확정된 뒤"가 언제인지 문구에 없었다
- EXP-011 보고와 리뷰 가이드가 로딩을 포함한 dev-full 전체 실행 시간의 배수("검색 시간 2.1배")를 앞세웠다. PR #68 코멘트: 운영에서 볼 것은 질의당 지연이고, 사용자는 질의당 20\~40ms가 3초 안이라 문제가 아니라고 판단했다. 이 3초는 사용자 판단이고 SPEC 미결 3의 상한으로 정한 값이 아니다
- PR #68 코멘트: EXP-011은 256과 512 중 하나를 고른 것이 아니라 둘을 함께 쓰는 선택이라, 요소별 기여를 노트북으로 분석해 문서로 종합한다

## 결정

- meet-rag E3·E7: 예상과 사후 기록 모두 요율 × 세션 시간 환산값을 쓰고 "요율 환산"으로 표시한다. 사용자에게 실제 값을 묻지 않는다
- notebook.md §8, meet-rag B6·오류 처리: 판단이 확정된 때는 사용자가 그 노트북을 근거로 결정을 내린 때다. 그 결정에 따른 실행을 마친 뒤, 노트북을 담은 PR을 올리기 전에 `stop`한다
- meet-rag B6, exp-judgment: 지연은 인덱스 로딩을 뺀 질의당 시간을 앞에 두고, 운영 비용에 상주 메모리·디스크를 넣는다. 전체 실행 시간의 배수를 결론에 앞세우지 않는다
- meet-rag B6: 기존 요소에 새 요소를 더해 함께 쓰는 후보는 근거 노트북에서 순위가 바뀐 질의마다 어느 요소가 결과를 냈는지 세어 EXP 결과 절에 종합한다
