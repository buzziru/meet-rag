# ADR-0056 사람이 넣는 입력은 읽을 때 전제를 확인하고, SLICE 검증과 감사·가이드를 병렬로 부름

- 상태: 채택
- 날짜: 2026-10-21

## 맥락

- 입력 확인: S18(PR #129)과 S19(PR #130)에서 예외 처리가 모자란 결함이 감사·리뷰에서 뒤늦게 잡혔다(사용자 지적 2026-10-21).
  - S19(리뷰 B-8): `conditions.fuse: false`(EXP-016)가 점수 결합 목록을 전제하는데 확인하지 않아, RRF 결합과 함께 쓰면 첫 질의에서 `KeyError`가 났다
  - S18: `--single`로 받은 결과 파일의 종류·출처·짝을 확인하지 않아, 다른 실험의 결과여도 판정이 나오거나 원인과 다른 오류가 났다
  - 예외 처리를 다루는 규칙은 전역 `rules/code.md`의 "일어날 수 없는 상황에 대한 오류 처리를 넣지 않는다"뿐이었다. 스킬 구현 원칙은 `data/` 산출물(지문, 덮어쓰기)만 다뤘다. 그래서 일어날 수 있는 사람 입력을 쓸 때 확인할지 따질 기준이 없었다
- 병렬 호출: 스킬 A 흐름은 검증(A3) 뒤 감사(A4)를 순서대로 불렀다. S17에서 검증 지연을 줄인 뒤, S18·S19에서는 셋(slice-verifier, protocol-auditor, pr-briefer)을 한 메시지에서 병렬로 불렀다. 셋 다 diff와 저장소를 읽기만 하는 독립 작업이고 결과에 문제가 없었다

## 결정

- 스킬 "구현 원칙"에 "사람이 넣는 입력은 읽을 때 전제를 확인한다"를 더한다. 사람이 넣는 설정 값·옵션 조합과 명령 인자(값·파일)의 전제를 읽는 시점에 확인하고, 어긋나면 원인을 적고 멈춘다. 처음에는 대상을 조합과 인자 파일 두 종류로 적었으나, 값 하나가 잘못된 경우가 빠져 원칙으로 넓히고 대상을 "어긋났을 때 원인을 알 수 없는 오류나 조용히 틀린 결과가 나오는 입력"으로 한정했다(가이드 판단할 곳, 사용자 결정 2026-10-21). 예: `gen_eval.n=0`은 대상, 라이브러리가 원인이 분명한 오류를 내는 범위 밖 정수는 대상 아님. 내부 값처럼 일어날 수 없는 경우에는 넣지 않으며, 이것이 전역 규칙과의 경계다
- 확인 단계(점검표·감사 항목)는 더하지 않는다. 확인 단계가 늘면 검증 부담이 늘어나므로 규칙만 두고 관찰한다. 같은 유형이 감사·리뷰에서 다시 잡히면 그때 pr-briefer나 protocol-guard에 항목을 둔다(ADR-0054는 원칙만 있고 확인 단계가 없어 위반이 통과한 사례다)
- A 흐름 4단계: 구현과 결과 기록을 커밋한 뒤 검증·감사·가이드를 한 메시지에서 병렬로 부른다. 가이드 프롬프트의 검증 결과 요약은 메인이 직접 돌린 확인 결과로 채우고 verifier 결과는 PR 본문에 적는다. 검증이 실패해 파일(코드·설정·테스트·문서)을 고치면 감사는 그 반영 커밋으로, 가이드는 반영 뒤 최종 diff로 다시 받는다(실패할 때만 비용이 든다). 감사의 지적으로 이 세 곳(가이드 입력, "코드" 범위, 다시 받는 범위)을 PR 전에 맞췄다
- 관찰로만 둔 것(각 1회, 대기 목록): 에이전트가 도는 동안 메인이 검증 대상 파일을 고쳐 어느 코드로 검증했는지 확정하지 못함(S18), 병합된 PR 브랜치에 push해 원격 브랜치를 다시 만듦(이슈 #120 세션), 보호 경로 재수정 때 반영 커밋만 재감사(S18)

## 결과

`.claude/skills/meet-rag/SKILL.md`(구현 원칙, A 흐름 4단계). description은 바꾸지 않아 트리거 검증은 하지 않았다.

## 삭제 조건

- 입력 확인 항목: 설정을 스키마(예: pydantic·structured config)로 검증하게 되어 조합 확인이 코드 구조로 보장되면 지운다
- 병렬 호출: 검증이 자주 실패해 감사·가이드를 다시 받는 일이 잦아지면 순서 호출로 되돌린다
