# ADR-0060 nb_kernel 실행 보조와 하네스 점검(2026-10-26) 결과 반영

- 상태: 일부 대체(→ 0061, wrap_up 보고 훅 대기 방식)
- 날짜: 2026-10-26

## 맥락

S24 작업 중 nb_kernel에서 세 가지가 반복됐다. 노트북 셀의 ruff 오류를 PR 전에 따로 고쳤고(PR #96 예외 기록과 같은 종류), 34_01 셀 6의 pandas 오류처럼 traceback이 수십 줄 출력됐고, `run`이 노트북을 CRLF로 다시 써 34_01·35_01에서 `file_damage_check`가 실행마다 알렸다. 사용자는 jupyter-mcp-server 대신 nb_kernel을 고치기로 했다(사용자 결정 2026-10-26. 린트를 하지 않고 셀마다 주변 셀과 출력을 돌려줘 토큰이 줄지 않으며, 노트북 규약 §8과 충돌한다).

같은 날 하네스 점검에서 규칙과 장치가 어긋난 곳이 나왔고, 사용자는 nb_kernel 개선과 같은 PR로 묶기로 했다.

- `data_delete_guard`가 `git -C <경로> worktree remove`와 `(Get-Item x).Delete($true)`(재귀 삭제)를 삭제 명령으로 보지 않았다. ADR-0058 사고의 명령 형태다
- `commit_type_guard`·`file_damage_check`는 Bash에만 걸려 PowerShell로 커밋·스크립트 실행을 하면 보지 않았다. PowerShell 커밋 메시지는 here-string(`-m @'…'@`)이라 그대로 PowerShell에 걸면 모든 커밋을 `@'` 타입으로 막는다
- `protocol-auditor` 작업 종류에 하네스가 없어 F6이 부르는 종류와 맞지 않았고, meet-rag description에 하네스 수정 요청 표현이 없었다
- D-49는 judge 지시 j_v8과 판정표를 보호 경로가 아니라 테스트(`tests/test_gen_eval_freeze.py`)로 동결했다. 테스트와 대상을 함께 바꾸면 테스트가 통과해 pr-briefer의 위험도 규칙(R3)에도 걸리지 않는다
- `wrap_up_report_guard`가 wrap_up과 같은 메시지의 본문을 세지 못했다. 같은 날 앞 세션에서 막힌 12건은 모두 "훅이 본 글자 수 = 최종 기록 − 같은 메시지 본문"이었고, 최근 세 세션 기록에서 같은 메시지의 본문 행은 언제나 tool_use 행보다 앞에 기록됐다(뒤에 기록된 경우 0건). 이 ADR을 만든 세션에서는 같은 메시지의 본문이 끝까지 기록되지 않은 경우도 한 번 있었다
- 그 밖: 끝난 G5를 쓴 테스트 시나리오, 쓰지 않는 Jev를 든 LangSmith 예시, protocol-guard description에 빠진 G3 동결 세트 설정(ADR-0028), git.md PR 절차에 없는 감사 단계, slice-verifier의 `/usr/bin/time`·`bc`·대기 루프(S20 관찰 2회), 테스트가 없던 `wrap_up_reminder`, 오류 출력 없이 오류 응답이 오면 `StopIteration`이 나는 nb_kernel

## 결정

- nb_kernel `run`: 실행 전 `ruff check --fix`·`ruff format`을 노트북에 적용하고 남은 지적을 출력한다. 실패한 셀은 ANSI를 지운 traceback 끝 15줄만 출력한다(전체는 노트북 출력에 남는다). 노트북은 LF로 쓴다. 오류 출력이 없으면 그렇다고 적는다. 노트북 E501 완화는 이 ADR에서 정하지 않는다
- `data_delete_guard`: `git -C <경로> worktree remove`를 삭제·재귀 동사로 보고 상대 경로를 `<경로>` 기준으로 푼다. `.Delete(`는 인자와 관계없이 삭제 동사로 보고, `.Delete($true)`는 재귀로 본다. `(Get-Item <대상>)`에서 대상을 뽑는다. settings.json `if`도 `*Delete(*`로 넓힌다. 인자 없는 `.Delete()`로 링크만 지우는 것은 그대로 둔다
- `wrap_up_report_guard`는 훅 입력의 `tool_use_id` 행이 transcript에 보일 때까지 최대 10초 동안 다시 읽은 뒤 글자 수를 센다(사용자 결정 2026-10-26, 앞 세션 점검의 제안). 임시 탐침 훅으로 확인한 결과(2026-10-26), 훅 입력에 `tool_use_id`가 오고, 훅이 뜰 때 그 행은 아직 없다가 2.5초 뒤 훅이 도는 동안 기록됐으며, 같은 메시지의 본문 행이 그보다 먼저 기록됐다. 상한은 이 값에 여유를 두어 정했다. `tool_use_id`가 없거나 시간이 지나면 그때까지 읽은 행으로 센다. 본문이 끝까지 기록되지 않는 경우는 이 방식으로 잡히지 않아 관찰로 둔다
- PowerShell matcher에 `commit_type_guard`(`git commit *`)와 `file_damage_check`(`*python*`)를 더하고, 커밋 훅은 here-string 메시지를 읽는다
- `protocol-auditor` 작업 종류에 하네스를 더한다(대응 문서 대신 ADR, 감사 규칙이 좁아지는지와 스크립트·훅의 test·data 접근을 본다). meet-rag description에 하네스 수정 흐름과 요청 표현을 더한다
- pr-briefer 위험도 규칙에 R7(D-49 동결 대상 변경, 걸리면 단방향)을 더한다. 처음에는 briefer가 판단해 올리는 경우에 넣었으나, 그러면 단방향 표시가 briefer가 놓치지 않는지에 달려 R7로 옮겼다(사용자 결정 2026-10-26, PR #150 리뷰). D-49가 정한 동결 방식은 고치지 않고 새 버전 파일을 만드는 것이라 정상 작업이 R7에 걸리는 일은 드물다. R7은 PR 표시이고 수정을 막지 않으므로 "CLAUDE.md 보호 경로에 넣지 않는다"(D-49)와 어긋나지 않는다
- nb_kernel 자동 수정은 노트북 파일 전체에 적용한다. `--from N`으로 이어서 실행할 때 이미 실행한 셀의 원본이 정리돼 출력과 글자 단위로 어긋날 수 있으나, 정리 내용이 동작과 무관해 그대로 둔다(사용자 결정 2026-10-26, PR #150 리뷰)
- 그 밖 위 항목을 각 파일에서 맞춘다. 이유는 모두 같다: 규칙이 가리키는 대상이 없어졌거나(G5, Jev) 장치가 규칙보다 좁아(설명·절차·도구) 규칙만 읽고 따르면 틀린다

## 삭제 조건

nb_kernel 대신 다른 노트북 실행 도구를 쓰면 그 부분을 지운다. 훅 항목은 ADR-0055·0058의 삭제 조건을 따른다.
