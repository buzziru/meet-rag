# ADR-0032 질의 쪽 라벨을 검색 입력으로 쓰는지 감사(protocol-guard P9)

- 상태: 채택
- 날짜: 2026-10-08

## 맥락

D-19로 메타데이터를 질의 조건 방식(H14)으로 쓰기로 했고, S10은 문서에 화자 필드를 더한다. 평가 질의 레코드에는 정답 문서에서 온 필드(`doc_id`, 정답 문서의 화자 등)가 함께 있다. 질의 조건 코드가 질의 텍스트 대신 이 필드를 `qid`로 이어 쓰면 정답이 검색에 샌다. PLAN H12에 "질의 행의 라벨을 그대로 쓰면 정답이 샌다"는 문장이 있지만 감사 점검표(protocol-guard)에는 없어, `protocol-auditor`가 이 경로를 보지 않았다. 사용자가 H14·S10 전에 하네스를 먼저 고치라고 지시했다(2026-10-08).

## 결정

protocol-guard에 P9를 더했다. 판단 기준은 정답이나 정답 문서에서 온 값이 검색·순위 결정에 들어가느냐이고, 어느 파일이 읽느냐가 아니다. 정답 쪽 값(질의 파일의 `query` 밖 필드, `load_gold` 반환 열 중 `qid` 밖, 분할 파일의 `conference_number`, 동결 세트의 정답 필드), `qid` 문자열 파싱으로 얻는 회의 번호, `qid`로 이은 원천 QA 라벨, 평가 질의 쪽에서 모은 조건 사전을 위반으로 본다. `qid`를 식별·순서·분할 선택에 쓰는 것은 정상이다. 채점과 분석 노트북이 읽는 것은 해당하지 않지만 노트북 안에서도 검색 입력에 들어가면 위반이다(위치로 면제하지 않는다). 문서에 붙인 QA 라벨 유래 필드(S10의 화자)는 쓸 수 있으나 single-doc 해석의 단서가 EXP 문서에 없으면 보고한다. description은 바꾸지 않았다(감사자는 점검표 본문을 읽는다). SPEC 평가 층 범위(분할, `dev_small_docs`)를 정하는 것은 정답 쪽 값을 쓰지만 위반이 아니다. 첫 안은 "`query` 밖 필드를 읽으면 위반"이라 기존 검색 코드의 `qid`·`load_gold` 사용까지 오탐하고, `qid` 파싱과 노트북 경로를 놓쳐 감사·리뷰 가이드 지적으로 고쳤다.

## 결과

`.claude/skills/protocol-guard/SKILL.md` P9.

## 삭제 조건

평가 질의 레코드에서 정답 관련 필드를 분리해 검색 코드가 읽을 수 없게 만들 때.
