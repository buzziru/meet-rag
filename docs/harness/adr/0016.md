# ADR-0016 PR 리뷰 가이드 에이전트 pr-briefer, F 흐름에 PR 코멘트 수집

- 상태: 채택
- 날짜: 2026-10-05
- 커밋: (PR 병합 후 기록)

## 맥락

사용자는 PR 화면에서 diff를 한 번 읽고 병합을 정한다. 최근 PR은 #20 1,631줄, #23 745줄, #21 25파일이었고, PR 본문은 검증·감사 통과를 보고할 뿐 어디를 판단해야 하는지는 알려 주지 않았다. 사용자는 위험도 판별, 다이어그램·의사 코드, 회고로 리뷰 부담을 줄이자고 요청했다(2026-10-05). 회고는 대기 목록과 F 흐름으로 이미 있지만, PR 리뷰 코멘트는 메인이 기억해 옮길 때만 대기 목록에 들어왔다(PR #15).

## 결정

- 읽기 전용 에이전트 `pr-briefer`를 둔다. `protocol-auditor`를 부르는 단계(A4·B5·D2·D5·F6)에서 병렬로 부르고, 결과는 PR 본문 맨 위 "리뷰 가이드"가 된다(`git.md` PR 절 3). 작성 맥락과 분리해, 다이어그램이 작성 의도가 아니라 diff의 실제 동작을 옮기게 한다
- 위험도는 단방향·양방향 두 단계다(사용자 결정). 경로 규칙 R1\~R6(SPEC, DECISIONS, 보호 경로, `config.yaml` 기존 값, 감사 규약, test 분할)이 최저선이고 에이전트 판단은 위험도를 올릴 때만 쓴다. 저위험 판정을 믿고 읽지 않은 PR에서 잘못된 결정이 병합되는 것을 막기 위해서다
- 다이어그램·의사 코드는 새 흐름이 생긴 SLICE·EXP PR에만 둔다. 문서·하네스 PR에서는 본문만 길어진다
- 규칙은 별도 스킬로 두지 않고 에이전트 파일에 둔다. 쓰는 곳이 이 에이전트 하나다
- F 흐름 3단계에 병합 PR의 사용자 리뷰 코멘트 수집을 넣는다. 저장소 밖(GitHub Actions)에 리뷰 에이전트를 두지 않았다. 모든 PR이 하네스에서 만들어지고, Actions에서는 `data/`와 검증 결과를 볼 수 없다

## 결과

`.claude/agents/pr-briefer.md`(신규), `.claude/skills/meet-rag/SKILL.md` 에이전트 표·F절, `.claude/rules/git.md` PR 절. 에이전트 신설은 `harness:harness`의 범위지만, 구성 확장이 작아 CLAUDE.md 규약대로 F 흐름(`harness:evolve`)으로 했다.

## 삭제 조건

PR 리뷰 가이드를 사용자가 읽지 않거나 판단에 쓰지 않는다고 확인될 때, 또는 PR이 하네스 밖에서 만들어지기 시작해 저장소 쪽(GitHub Actions) 리뷰로 옮길 때.
