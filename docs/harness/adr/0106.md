# ADR-0106 화면을 만들거나 바꾸는 SLICE에 전역 디자인 스킬을 쓴다

- 상태: 채택
- 날짜: 2026-11-06

## 맥락

- 배포 세션이 화면을 기능 위주로 구현했다(사용자 2026-11-06). SLICE 흐름과 "화면 검증" 절에는 디자인 방향을 정하거나 리뷰하는 단계가 없고, Aside는 모양과 클릭 흐름만 본다
- 사용자는 두 가지가 필요하다고 봤다: 프로젝트·앱 성격에 맞는 초기 디자인 설계와, 기능 추가 뒤 리뷰를 통한 수정. 페이지는 프로젝트 데모와 개인 포트폴리오다
- GitHub trending 조사(opencode worker, ADR-0105) 뒤 전역 `~/.claude/skills`에 설치했다: 초기 설계 `frontend-design`(anthropics/skills), 리뷰 `better-interface`와 그것이 부르는 `better-*` 6개, 변경 리뷰 `interface-review`(jakubkrehel/skills, MIT). 다른 프로젝트에도 쓰려고 저장소에 두지 않았다(사용자 결정 2026-11-06)
- 전역 스킬은 요청이 스킬 설명과 맞으면 불리지만, "S41 진행"처럼 기능을 말하는 요청에서는 불리지 않을 수 있다. `interface-review`는 모델이 부를 수 없다

## 결정

1. 화면 요소를 새로 만들거나 모양을 바꾸는 SLICE는 A1 지시서에 `frontend-design`으로 정한 "디자인 방향"(대상, 독자, 화면의 주된 역할, 지금 토큰 유지 여부)을 적는다
2. A4 PR 전에 `better-interface`로 바뀐 화면을 리뷰하고 `HIGH`는 고친다. 사용자가 정했거나 결정을 기다리는 화면 동작을 바꿔야 하는 지적은 고치지 않고 PR 본문 "판단할 곳"에 올린다(결정 3과 부딪치지 않게). `MEDIUM`·`LOW`는 고칠지 정해 PR 본문에 적는다. 변경분만 보는 `interface-review`는 메인이 요청하지 않고 사용자가 원하면 부른다(ADR-0101, 수작업 반복). 리뷰 중 렌더링 확인은 "화면 검증" 절의 대상 주소·데이터 항목을 따른다
3. 디자인 결정은 사용자가 한다. 스킬 결과는 판단 근거다
4. 0단계 대응에 "앱 화면을 만들거나 모양을 바꾸는 작업"을 더해 SLICE가 "화면 검증" 절을 읽게 한다

입력→동작: S41 추천 질의 칸은 지시서에 방향을 적고 PR 전에 `better-interface`로 본다. 연결 코드나 API만 바꾼 PR은 쓰지 않는다.

감수하는 것: 화면 SLICE마다 리뷰 한 번만큼 시간과 토큰이 더 든다. 스킬은 저장소 밖이라 다른 PC나 클라우드 세션에는 없다. 없으면 이 단계를 건너뛰었다고 PR 본문에 적는다. `better-writing`은 영어 문구 기준이라 한국어 화면 문구에는 일부만 맞는다.

## 결과

`.claude/skills/meet-rag/SKILL.md` 0단계 대응 줄, "화면 검증" 절의 "디자인 스킬" 항목.

## 삭제 조건

전역 디자인 스킬을 지우거나 다른 스킬로 바꾸면 이 결정을 고친다.
