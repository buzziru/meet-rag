# ADR-0104 배포 코드는 PR 전 리뷰에 넣지 않고 일일 코드 리뷰가 본다

- 상태: 채택
- 날짜: 2026-11-06

## 맥락

- PR 전 코드 리뷰 범위(ADR-0080 결정 6)는 배포 작업 전인 2026-11-03에 판정 코드로 정했다. 배포 코드는 다음 날(S35, `src/rag/app.py`)부터 생겼다
- 일일 코드 리뷰(ADR-0081)는 `src/`, `tests/`의 `.py`만 입력으로 받아 `deploy/space/`, `deploy/web/`은 어느 리뷰도 보지 않았다. 이슈 #239의 `deploy/web/app.js` 변경은 코드 리뷰가 아니라 종합이 "본문에 설명이 없다"로만 짚었다
- `src/rag/embed_worker.py`의 동시 처리 위험(#221)은 `src/` 아래라 일일 리뷰가 잡았고 PR #240에서 고쳤다
- 2026-11-04 뒤 병합된 코드 PR 15개 중 배포 코드(`deploy/`의 `.py`·`.js`·`.html`, `src/rag/app.py`·`docs.py`·`display.py`·`embed_worker.py`)를 바꾼 것이 9개다. 지금 PR 전 범위만으로 86개 중 19개(22%)다. 사용자는 PR 전 리뷰가 전체의 20% 수준을 넘지 않게 하고 일일 리뷰와 역할을 나누려 한다(사용자 2026-11-06)

## 결정

1. PR 전 리뷰 범위는 그대로 둔다. 배포 코드는 일일 리뷰가 맡는다(`git.md` PR 절 2). 판정 코드는 병합되면 실험 기록과 판정에 남아 되돌리기 어렵고, 배포 코드는 다음 날 지적을 받아 다시 올리면 바로잡힌다
2. 일일 리뷰 입력에 `deploy/`를 더하고, diff와 파일 전체를 `.py`, `.js`, `.html`로 거른다(`CODE_DIRS`, `CODE_EXTS`). `.css`, `vercel.json`, `requirements.txt`, `README.md`는 넣지 않는다. 지금 `deploy/` 코드 파일은 합쳐 약 1.8만 자로 상한 30만 자에 견줘 작다
3. 일일 리뷰 지시의 "볼 것"에 5번을 더한다: 배포 앱에서 방문자 입력이나 응답 글이 이스케이프 없이 화면 HTML에 들어가거나, 비밀 값(토큰, API 키)이 페이지·응답·로그로 나가는가. 기존 네 기준은 평가 코드용이라 화면 코드에 볼 기준이 없었고, 공개(S41) 뒤에 가장 비싼 오류가 이 둘이다

입력→동작: `deploy/web/app.js`만 바꾼 PR은 PR 전 `/code-review`를 돌리지 않고, 병합된 날의 일일 리뷰에 diff와 파일 전체가 들어간다. `deploy/web/style.css`만 바꾼 PR은 일일 리뷰도 부르지 않는다.

감수하는 것: 배포 코드의 결함은 병합 다음 날에야 지적되고, 그사이 Space에 올라갈 수 있다. 지금은 비공개 Space라 방문자 피해가 없다. 일일 리뷰는 지적을 많아야 5개 내므로, 배포 지적이 판정 코드 지적을 밀어낼 수 있다.

## 결과

`.github/scripts/daily_pr_digest.py`와 테스트, `.github/prompts/daily-code-review.md`, `.claude/rules/git.md` PR 절 2. ADR-0081의 입력 범위는 이 결정으로 일부 대체된다. 바뀐 입력은 병합 뒤 첫 일일 실행에서 처음 돈다(ADR-0081 결과 절의 federation 제약).

## 삭제 조건

S41 공개 뒤 배포 코드의 결함이 방문자에게 닿아 하루 지연을 감수할 수 없게 되면 PR 전 범위를 다시 정한다.
