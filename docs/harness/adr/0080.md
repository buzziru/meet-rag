# ADR-0080 폴더 규약 src·tests, 입력 전제 감사, E225, worktree는 하위 세션으로, 병합 전 코드 리뷰 범위

- 상태: 채택
- 날짜: 2026-11-03

## 맥락

- 세 코드 리뷰(`docs/reviews/2026-10-*.md`) 지적 102건을 묶어 재발을 조사했다. 재발해 병합된 것은 근거를 댈 수 있는 것만 12건이다(테스트 진입점·단언 미검증 6, 덮어쓰기 2, 규칙 중복 2, 입력 전제 1, 동시 실행 1). 문장만 있던 입력 전제 규칙은 S27에서 G2-1로 어겨졌고, 막은 것은 감사와 변형 확인이었다. 그래서 규약을 짧게 두고, 재발 근거가 없는 유형의 규칙은 더하지 않는다(사용자 동의 2026-11-03)
- 구현 원칙이 `meet-rag` 스킬에만 있어 스킬을 부르지 않은 코드 수정에는 보이지 않았다
- 편집에서 생긴 `=` 공백 오류(2ce6267, cd6dac4, b4ff216)를 `E225`가 잡지만 preview 규칙이라 켜져 있지 않았다
- PR #193은 메인이 worktree만 나눠 진행해 사용자가 진행 상황을 따로 물어야 했다
- 위험도(단방향)로 코드 리뷰 대상을 정하면 DECISIONS를 함께 고친 PR이 모두 걸려 대상이 너무 넓어진다

## 결정

1. `tests/CLAUDE.md` 신설: 판정·동결·산출물 보호 코드의 테스트는 진입점을 지나 결과 값을 단언하고, 망가뜨린 사본에서 실패하는지 한 번 확인한다. S30에서 쓴 방식을 옮겼다
2. `src/CLAUDE.md` 신설: `meet-rag` "구현 원칙" 본문을 옮기고 스킬에서는 지웠다. 적용 범위는 A2·B3에서 `src/`를 고치는 작업으로 넓혔다. 새 문장은 "이미 있는 지표·검사의 정의를 다시 계산하지 않는다" 한 줄이다. A2·B3, protocol-guard P10의 참조를 경로로 바꿨다
3. protocol-guard P13(사람이 넣는 입력의 전제): 전제를 읽는 시점에 멈추는지, 짝지은 값이 0개이거나 NaN일 때 통과하지 않는지 본다. P10처럼 "보고"로 두되, 판정·집계 코드에서 0개·NaN이 통과로 이어지면 원래 목적의 결함이므로 고친다(사용자 결정 2026-11-03). `protocol-auditor` 출력의 보고 항목에 더했다
4. ruff: `lint.preview = true`, `lint.explicit-preview-rules = true`, `lint.extend-select = ["E225"]`로 preview 규칙 중 이 하나만 켠다. 켠 뒤 저장소 전체에서 새로 잡힌 것은 `tests/test_multidoc_check.py:196` 1건이고 고쳤다. `lint.preview`는 린트에만 적용되어 `ruff format`에는 영향이 없다. 안정 규칙의 preview 동작도 함께 켜지지만, 지금 코드에서는 켠 쪽과 끈 쪽 모두 `ruff check --diff` 결과가 없다. 대안인 별도 명령 대신 이 방식을 쓴다(사용자 결정 2026-11-03). 노트북(`*.ipynb`)은 뺀다. `nb_kernel`이 실행 전에 `ruff check --fix`를 적용하므로 E225를 켜면 `x=[1,2]`가 고쳐져 노트북을 포맷하지 않는 규약(ADR-0063)과 어긋난다(`test_nb_kernel.py`가 잡았다)
5. `meet-rag` "공유 `data/`와 위임": 메인 작업과 다른 브랜치라 worktree가 필요한 작업은 하위 세션으로 한다. 지금 브랜치에서 할 수 있는 짧은 수정과 검증·감사 서브에이전트는 해당하지 않는다. `src/`·`tests/`를 고치는 일을 넘길 때는 지시에 규약 경로를 넣는다
6. `git.md` PR 절 2와 스킬 A4: `src/rag/eval/`, `src/rag/eval_multi/` 아래 파일이나 `src/rag/gen_eval/`의 `compare.py`·`report.py`·`checks.py`를 바꾸는 PR은 병합 전에 `/code-review`를 돌린다(`judge.py` 제외, 병합 코드 PR 71개 중 15개, 사용자 결정 2026-11-03). 범위 문장은 이 15개가 되는 쪽으로 읽었다. 세 파일 이름을 세 폴더 모두에 걸면 14개이고, 차이는 `eval/metrics.py`를 바꾼 PR #166이다

## 결과

- 폴더 규약은 Read·Write·Edit로 그 폴더 파일을 다룰 때만 불러와진다. 셸로 고칠 때와 사용자 정의 서브에이전트에서 적용되는지는 실측이 없다. 그래서 A2·B3, 위임 프롬프트, 루트 `CLAUDE.md`가 경로를 직접 가리킨다(루트 줄은 사용자 결정 2026-11-03)
- 사례 확인: `eval.compare.main`의 diff를 `base - cand`로 뒤집은 사본에서 `tests/test_eval.py` 2 failed, 원본 24 passed
- 판정 코드 PR에는 `/code-review` 시간과 토큰이 더 든다

## 삭제 조건

다음 코드 리뷰에서 진입점 미검증이 다시 나오면 문장이 효과가 없다는 뜻이니 자동 검사로 바꾼다. 프로젝트가 오래 이어지지 않으므로 장기 측정 장치를 만들지 않는다.
