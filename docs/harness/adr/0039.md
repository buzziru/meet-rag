- PR #69 코멘트 3: 채택과 기각 모두 원인 분석 노트북이 필요하다. B6은 "채택이면 근거 노트북"이었다
- PR #71 코멘트 1-3: 과거 실험은 그 커밋의 코드로 재현하고 과거 코드와 현재 코드를 병용하지 않는다. S12 첫 구현은 이전 노트북을 위한 재수출을 두었다

- PR #71 코멘트 2-2: 평가가 미리 만든 조건 파일·값 사전을 읽어, 설정·코퍼스가 바뀐 뒤 옛 파일이 오류 없이 쓰일 수 있었다

## 결정

- notebook.md §7.1: `main`에 들어간 노트북은 고치거나 지금 코드로 다시 실행하지 않는다. 개정본과 PR 코멘트로 생긴 분석은 새 노트북으로 쓴다. 수십 분 이상 걸리는 계산은 시작 전에 사용자 확인을 받는다
- meet-rag B6·exp-judgment: 콜드 스타트(인덱스 로딩 등 시작할 때 한 번 드는 시간)를 질의당 지연과 따로 적는다. 콜드 스타트는 사용자가 인지해야 하는 문제라, 배포 SLICE에서 배포 페이지(사용자 화면)에 첫 구동 때 기다려야 하는 시간으로 안내한다(사용자 설명 2026-10-14). 그 전까지는 EXP 문서 결과 절에 값을 적는다. 원인 분석 노트북은 판정과 관계없이 쓰고, 요소별 기여 분석도 채택에 한정하지 않는다
- meet-rag "구현 원칙"(A2·B3): 과거 코드와 병용하지 않는다, 실험 산출물은 덮어쓰지 않는 것을 기본으로 둔다, 실행 config에 따라 바뀌는 입력은 미리 만든 파일로 읽지 않고 실행 시점에 만들거나 만든 기준을 대조한다
