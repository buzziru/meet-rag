# 데이터

AI Hub 「생성형AI 국회 회의록 기반 지식 검색 데이터」의 배포 형태와 필드 정의.

근거는 벤더 데이터설명서(`data/데이터설명서.hwp`)와 배포 파일을 직접 잰 실측이다.
**설명서와 실측이 어긋나는 곳에서는 실측을 따르고, 차이를 그 자리에 적었다.**

수치 옆의 표기

- **[설명서]** — 벤더 문서에 적힌 값. 검증하지 않았다
- **[실측]** — 배포 파일에서 직접 잰 값
- **[표본]** — 실측이되 전수가 아닌 표본값. 표본 크기를 함께 적었다
- **[전수]** — 배포분 39,633건 전체를 훑은 값

근거 링크가 필요하면 레코드의 `original` 필드(회의록시스템 URL)를 쓴다.

## 4. 파일 단위와 대응

**파일 하나 = 질의응답 한 쌍이다.** 회의 하나가 아니다. **[실측]**

```text
원천   /SRC_15대_제180회_제10차_본회의_국회본회의_0001(020475).xlsx
라벨   /LAB_15대_제180회_제10차_본회의_국회본회의_0001(020475).json
메타   /SLAB_15대_제180회_제10차_본회의_국회본회의_0000(020475).json
```

`{대수}_{회수}_{차수}_{회의구분}_{위원회}_{질의응답번호}({회의번호})` 구조다.
접두사와 확장자만 다르고 나머지는 같다. 파일명 끝의 괄호 안이 회의번호이므로
**파일을 열지 않고도 회의번호를 셀 수 있다.**

TS_본회의 ↔ TL_본회의 대응은 1:1이다(공통 1,118, 한쪽에만 있는 것 0). **[실측]**
`SbL`의 질의응답번호 자리는 항상 `0000`이다 — 회의 단위 레코드이기 때문이다.

## 5. 원천데이터 — TS/VS (xlsx)

### 회의록 전문이 아니다

표본 204개 파일 전부가 **정확히 2행**이고, 컬럼 구성도 1종이다. **[표본 n=204]**
1행이 질문(Q), 2행이 답변(A)이다. 회의 메타데이터는 행마다 반복된다.

### 파싱 주의

- `안건\t발언자` — 컬럼명 안에 탭 문자가 들어 있다. 벤더 산출물 그대로다

- openpyxl이 파일마다 `Workbook contains no default style` 경고를 낸다. 파싱에는 영향이 없다

## 7. 텍스트 필드의 성격

### 어떻게 만들어졌나

국회 회의록의 발언을 질문과 답변으로 분리한 뒤, **LLaMA 7B 기반 KoAlpaca를 회의록으로
self-instruct 학습시켜 `context_learn` · `summary_q` · `summary_a`를 생성했다.**
`question.comment` · `answer.comment`만 회의록 원문이고 나머지 텍스트는 모델 출력이다.

> 출처는 AI Hub 데이터 소개 페이지다. 벤더 데이터설명서(`data/데이터설명서.hwp`)에는
> 생성 모델도 기법도 기재되어 있지 않다. 모델·기법 자체를 이 저장소에서 재현·검증하지는 않았다.

이 사실이 두 가지를 설명한다.

- **하나의 `context`에서 질문이 여러 개 나오는 것은 정상이다.** 한 회의록 구간이 여러 층위의 정보를 담고 있으면 self-instruct는 층위마다 질문을 만든다. 설계된 동작이지 중복이나 오류가 아니다
- 생성물이므로 원문에 없는 표현이 들어간다. 검색 대상으로 쓸 때 원문과 같은 것으로 다루면 안 된다

### 네 종류

네 종류의 텍스트가 있고, **성격이 서로 다르다.** 같은 것으로 취급하면 안 된다.

| 필드 | 성격 | 근거 |
| --- | --- | --- |
| `question.comment` / `answer.comment` | 발언 원문 | 원천 xlsx와 문자열 동일 |
| `context` | 발언 원문을 포함하는 **더 넓은 회의록 구간** | q·a 두 발언이 `context`에 부분문자열로 존재. 다만 전건은 아니다 — 아래 |
| `context_learn` | **`context` 구간의 재작성 요약.** 원문 발췌가 아니고, 질의응답쌍 단위도 아니다 | 공백 제거 후에도 `context`의 부분문자열인 경우 0 / 2,649 |
| `summary_q` / `summary_a` | 질의응답쌍 단위의 생성 문장 | 원문에 없는 문장 형태(`~인가요?`) |

### 발언이 자기 `context` 안에 없는 레코드가 169건 있다 **[전수]**

표본 38건에서는 `question.comment` · `answer.comment`가 모두 `context`의 부분문자열이었다.
전수는 다르다.

| | 전수 39,633 | 표본 n=38 |
| --- | ---: | ---: |
| `question.comment` ⊂ `context` | 39,623 | 38 |
| `answer.comment` ⊂ `context` | 39,467 | 38 |
| 둘 중 하나라도 어긋남 | **169 (0.43%)** | 0 |

**공백 문제가 아니다.** 어긋난 176개 (레코드, 역할) 조합 전부가 공백을 지우고 비교해도
들어맞지 않는다. 갈라지는 지점을 보면 앞 두세 글자가 우연히 겹칠 뿐 발언 전체가 그
`context`에 없다. 정규화로 살릴 수 있는 종류가 아니다.

- `answer` 쪽이 166건으로 대부분이다. `question`은 10건뿐이다
- 회의구분은 소위원회 110 / 국정감사 38 / 특별위원회 16 / 예결위 3 / 본회의 2다.
  소위원회는 `context` 중앙값이 1,142자로 가장 짧다(§8)

**원인은 규명하지 않았다.** 라벨링 단계에서 발언이 다른 구간에 붙은 것인지, `context`를
잘라낼 때 답변이 밖으로 밀려난 것인지 구분하려면 같은 회의의 다른 `context`까지 대조해야 한다.

영향은 코퍼스가 아니라 평가 쪽이다. 청킹 후 정답 청크를 문자 offset으로 특정하는 방법이
이 169건에서는 성립하지 않는다.

### 생성 단위가 다르다 **[전수]**

`summary_q` · `summary_a` · `keyword`는 **질의응답쌍 단위**로 생성됐다.
반면 `context_learn`은 **`context` 단위**다 — 고유 `context` 38,516개, 고유 `context_learn`
38,516개로 수가 정확히 같고, 같은 `context`인데 `context_learn`이 갈리는 경우는 4건뿐이다.

**한 `context`에서 질의응답쌍을 여러 개 뽑으면 그 쌍들이 `context_learn` 하나를 공유한다.**
그 하나는 그룹 전체를 아우르는 요약이 아니라 **특정 한 쌍**을 따라간다. 문자 3-gram Jaccard로
재보면 최고 매칭 멤버는 기준선 수준(중앙값 0.098 vs 0.087)인데 나머지 멤버는 0.029로
기준선의 1/3이다. 그 한 쌍은 86%가 발언순번상 **마지막** 쌍이다.

따라서 **자기 질의응답쌍과 맞지 않는 `context_learn`을 가진 레코드가 1,117건(2.82%)** 있다.
`summary_q` · `summary_a`에는 이 문제가 없다.

**`context_learn`을 "이 질의응답의 요약"으로 취급하면 안 된다.**

`context_learn`이 `context`보다 **긴** 경우가 10.6%(281/2,649) 있다. `context`가 아주 짧은
레코드에서 요약이 오히려 길어진 것으로, "요약이 원문을 압축한다"는 가정이 전건에 성립하지 않는다.

`summary_q`는 완결된 의문문 형태다. 대화 맥락에 묶인 발화가 아니라 검색 질의로 쓸 만한 모양이지만,
**표본을 정성 검수하지는 않았다.** 형태만 보고 판단했다.

결측은 키를 빼는 방식이 아니라 **빈 문자열**로 들어 있다. 표본에서 필드 구성은 1종으로 일정했다.

주의할 점 둘.

- **공백 한 칸(`' '`)이 들어간 필드가 있다**(`answerer_ID` 등). `if not value` 로는 결측으로 안 잡힌다. `strip()`이 필요하다
- 질문자 소속, 응답자 의원 ID·ISNI는 사실상 전부 비어 있다. 응답자가 대개 의원이 아니라 정부측이어서다. **이 필드들을 메타데이터 필터의 근거로 쓸 수 없다**

전수는 확인하지 않았다. 표본 밖에서 키가 통째로 빠지는 레코드가 없다고 단정하지 않는다.
파싱 코드는 `.get()`으로 읽는 편이 안전하다.

## 10. 식별자

`id`는 레코드 ID가 아니라 **회의번호**다. `conference_number`와 값이 같고(표본 전건 일치),
한 회의에서 질의응답쌍이 여러 건 나오므로 중복된다.

**레코드를 유일하게 지목하려면 `(conference_number, question_number)`를 쓴다.**
표본 2,649건에서 고유 `id`는 2,300개, 고유 `(conference_number, question_number)`는 2,649개다.

`filename`도 유일하지만 문자열이 길고 회의구분·위원회명이 섞여 있어 키로 쓰기에는 무겁다.

## 11. context 중복 **[전수 39,633건]**

표본값(2,649건 중 2건, 0.08%)은 1/15 간격 표본이라 같은 회의에서 나온 쌍이 함께
뽑히지 않아 크게 과소평가한 값이다. 전수로 다시 쟀다.

| 항목 | 값 |
| --- | ---: |
| 고유 `context` | 38,516 / 39,633 |
| 중복 그룹 | 729 |
| 중복 그룹에 속한 레코드 | 1,846 (4.66%) |
| 중복 제거 시 사라지는 레코드 | 1,117 (2.82%) |

**세 가지가 확인됐다.**

1. **표기 흔들림에 의한 중복은 없다.** 공백을 정규화해도 고유 수가 같다. 중복은 문자열 완전 동일뿐이다
2. **중복은 전부 같은 회의 안에서 생긴다.** 회의를 넘는 중복 그룹이 **0개**다. 회의번호로 그룹을 지으면 중복을 전부 잡는다
3. **근접 중복은 별도 위험이 아니다.** 같은 회의 안 236,397쌍을 30자 shingle containment로 비교했을 때 임계를 0.1에서 0.95로 올려도 쌍 수가 13개밖에 줄지 않는다. 부분적으로 겹치는 중간 지대가 사실상 없다 — 거의 같거나 거의 안 겹친다. **완전 일치만 처리하면 되고, 근접 중복 제거기를 도입할 근거가 없다**

### 중복은 같은 구간에서 뽑은 다른 질의응답쌍이다

중복 그룹 안에서 모든 필드가 동일한 그룹은 **0개**다. 레코드가 통째로 복제된 것이 아니라,
같은 `context` 구간의 서로 다른 위치에서 질의응답쌍을 여러 개 뽑은 것이다
(`question.tag` 상이 711/729 그룹, 발언순번 폭 중앙값 12).

**이것 자체는 정상이다.** self-instruct가 한 구간에서 층위가 다른 질문을 여러 개 만든 결과다(§7).
검색 관점에서 문제가 되는 것은 문서가 겹친다는 사실이지 질문이 여러 개라는 사실이 아니다.

다만 `context_learn`은 이 단위를 따르지 않아 1,117건에서 어긋난다 — §7 참조.

### 평가 누수

Validation 4,400건 중 **189건(4.30%)** 은 `context`가 Training에도 존재한다(고유 171개).
Validation을 평가 세트로, Training을 코퍼스로 쓰면 그만큼 검색 성능이 낙관적으로 잡힌다.
평가는 AI Hub 구분을 쓰지 않고 회의 단위로 분할한다(`docs/SPEC.md`).

### 회의당 레코드 수 (전수)

고유 회의 9,662개, 평균 4.10건. 다만 분포가 한쪽으로 몰려 있다.
**회의의 75.4%(7,286개)는 질의응답쌍을 하나만 내놓고**, 나머지 24.6%가 전체 레코드의 82%를 차지한다.
최대는 한 회의에서 60건이다. 회의 단위로 분할하거나 표본을 뽑을 때 건수 균형이 맞지 않는다.

## 12. Sublabel — SbL.zip

AI Hub 문서에도 데이터설명서에도 설명이 없다. 열어보니 **회의록 단위 메타데이터**였다. **[실측]**

파일 11,827개 = 설명서의 원문 규모(회의록 건수)와 정확히 같다. 라벨링데이터의 회의번호는
전부 SbL에 포함된다.

```json
{"id": "020475", "date": "1996년7월20일(토)", "meeting_name": "본회의",
 "conference_number": "020475", "generation_number": "15",
 "committee_name": "국회본회의", "meeting_number": "제180회", "session_number": "제10차",
 "agenda": "개의 | o 국무위원 인사 | 1. 사회․문화에 관한 질문 | ...",
 "speaking_count": 75, "token_count": 35168}
```

**발언 텍스트는 없다.** 회의 식별 정보와 두 개의 수치뿐이다. **[표본 n=1,183]**

| | speaking_count | token_count |
| --- | ---: | ---: |
| 평균 | 749 | 20,119 |
| 중앙값 | 579 | 16,609 |
| 90% | 1,642 | 41,143 |
| 최대 | 4,024 | 69,856 |

`agenda`는 라벨링데이터 쪽과 형식이 다르다. SbL은 항목을 `|` 로 잇고 개의·인사 같은 진행 항목까지
담는다. 라벨 쪽은 구분자 없이 이어붙는다(§6).

`token_count`는 **어떤 토크나이저 기준인지 명시되어 있지 않다.** 임베딩 모델의 토큰 수로 그대로 쓸 수 없다.

용도는 회의 규모 파악과 회의 단위 메타데이터 조인이다. 코퍼스 텍스트로는 쓸 수 없다.

## 14. 이 문서가 바꾸는 전제

"원문 회의록을 파싱해 코퍼스로 쓴다"는 선택지는 배포 데이터만으로
성립하지 않는다. 원천데이터(TS/VS)가 회의록 전문이 아니라 질의응답 발췌이기 때문이다.
회의록 전문이 필요하면 `original` URL에서 별도 수집하는 단계가 앞에 붙는다.

## 15. 코퍼스로 쓸 때의 한계

코퍼스는 `context`를 그대로 쓴다(`docs/SPEC.md`). 다음 한계를 안고 간다. **성능 수치를 쓸 때 함께 적는다.**

| 한계 | 근거 |
| --- | --- |
| `context`는 회의록 원본이 아니라 질의응답이 만들어진 구간의 발췌다 | §3, §5 |
| 회의 커버리지 81.7% (9,662 / 11,827) | §3 |
| 회의 안에서도 일부만 덮는다. 질의응답에 쓰인 발언은 전체 발언의 중앙값 0.5%(하한) | §3 |
| 코퍼스의 구멍은 무작위가 아니라 "질문이 만들어진 구간만 남은" 편향된 구멍이다 | 위 두 항의 결과 |
| 20·21대가 83%를 차지한다 | §3 |
| 평가 질의(`summary_q`)가 정답 문서를 보고 생성됐다. 검색이 실제보다 쉽다 | §7 |
| 정답이 언제나 단일 문서에 완결되어 있다 | §4 |
| 청킹 후 정답 청크를 문자 offset으로 특정할 수 없는 레코드가 169건(0.43%) 있다 | §7 |

앞의 다섯은 코퍼스의 성질이고 뒤의 셋은 평가의 성질이다. 169건은 문서 단위 평가에서는
정답이 성립하므로 평가에 포함한다(`docs/SPEC.md`).

| `data/processed/corpus_context.jsonl` | 고유 `context` = 검색 문서 | 38,516 | 281.6 MB |

`doc_id`는 `{회의번호}-{context SHA-1 앞 10자리}`다. 내용에서 유도되므로 파일 순서나 실행
시점에 좌우되지 않고, 같은 `context`는 자동으로 같은 ID를 받는다. 절단 충돌은 0이다.

```json
// corpus_context.jsonl
{"doc_id": "046770-7a2d49803f", "context": "...",
 "conference_number": "046770", "date": "...", "meeting_name": "국정감사",
 "generation_number": "20", "committee_name": "...", "meeting_number": "...",
 "session_number": "...", "agenda": "...", "original": "http://likms...",
 "splits": ["Training", "Validation"], "n_qa": 3}

// queries_summary_q.jsonl
{"qid": "046770-0001", "doc_id": "046770-7a2d49803f", "split": "Validation",
 "qna_type": "추출형", "query": "...", "answer": "...",
 "question_comment": "...", "answer_comment": "..."}
```

**Training–Validation 교차 171개는 지우지 않았다.** 문서마다 `splits`에 AI Hub 분할 출처를 남겼다. 평가는 이 구분 대신 회의 단위 분할을 쓴다(`docs/SPEC.md`).

| `splits` | 문서 수 |
| --- | ---: |
| `["Training"]` | 34,139 |
| `["Validation"]` | 4,206 |
| `["Training", "Validation"]` | 171 |

짧은 문서(최소 16자)도 자르지 않았다. 몇 자 미만이 쓸모없는지 측정된 바가 없고, 잘라내면
그 레코드의 `summary_q`가 정답 문서를 잃어 평가 세트에 구멍이 생긴다.
