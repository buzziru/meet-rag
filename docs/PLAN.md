# PLAN: 국회 회의록 RAG (SPEC.md 기준)

naive RAG(고정 길이 청킹 → KURE-v1 dense 검색 → 생성)로 베이스라인을 세우고, advanced RAG 기법을 한 부분씩 더해 검색 성능을 높인다. 검색 단계 판정은 SPEC의 dev-full Recall@5로 한다.

완료된 조각·게이트, 끝난 가설, 지난 "다음 순서" 기록은 [`docs/PLAN-done.md`](PLAN-done.md)에 옮겼다. 옮긴 문장은 고치지 않았다.

## 생성 평가

생성 단계 평가 프로토콜은 SPEC "생성 단계 평가"(D-53)다. 기준(충실성, 답변 관련성, 종합 지표, 보조 지표 핵심 답변 포함도, 과잉 거부 안전 조건), judge, 판정 규칙이 있고, 생성 EXP 실행 절차는 `.claude/skills/meet-rag/references/gen-exp.md`, 생성 실험 순서는 D-56이다(H11 생성 경로는 D-37). 초안(`docs/drafts/spec-generation-eval.md`)의 출발점은 사용자 요청(2026-10-14, PR 히스토리 분석과 Lauren Tan 발표 정리 대화)과 사용자 결정(2026-10-19, PR #99 코멘트)이다.

- 코드로 판정할 항목(인용 번호 유효성, 거부 문구, 발언자·회의 일자의 메타데이터 일치)은 LLM 없이 처리하고, judge에는 남는 기준만 맡긴다
- judge는 사람 채점으로 보정한 뒤 쓴다. 이후 주기적으로 소량을 다시 사람이 확인한다. 블라인드 확인을 S25에서 1질의 검수 뒤 중단해(D-51) 지금 judge는 사람과 독립 대조 없이 쓴다
- multi-doc 질의(G3 동결 세트)는 생성에서 판정에 쓰지 않고, 여러 문서를 합쳐 답하는 것을 겨냥한 실험에서만 일부로 본다(D-38, D-53 결정 7)
- 진행 순서(제안. 번호는 착수 때 확정)
  - [ ] H20 발언자 표시(SLICE): 근거 청크에 문서의 질의자·답변자 이름·직위와 질의·답변 발언(라벨 `question.comment`·`answer.comment`)과 겹치는 부분의 표지를 더하는 기능을 config로 켜게 만든다(기본 동작은 그대로). 원천 데이터는 회의록 전문이 아니라 질의·답변 2행이라(`docs/data.md` §5) 본문 전체의 발언별 발언자는 없다. 범위(사용자 결정 2026-10-27, PR #170 대화): 생성과 judge가 같은 `speakers` 필드를 보고(생성 기록의 근거 `text`는 원문 그대로, 발언자 정보는 별도 필드), 필드가 없는 기록의 judge 렌더링은 지금과 같게 한다. 충실성은 생성 모델이 받은 근거로 재므로 judge도 같은 정보를 봐야 하고, 기준(S25) 생성은 발언자 정보를 받지 않았으므로 기준 재채점은 없다. 필드가 없는 기록의 judge 요청 본문 sha가 지금과 같음을 테스트로 고정하고(리뷰 G1-3과 같은 장치), judge 입력 코드(`format_contexts`)를 바꾸는 이유를 DECISIONS에 남긴다. 머리에 질의자·답변자를 붙이는 단계와 청크 안 겹침 표지 단계를 나눌지, corpus의 `questioners`·`answerers` 채움 비율은 지시서에서 정하고 센다. 채택은 H20 EXP 판정으로 정하고, EXP의 위치는 H22 결과를 보고 정한다. API 비용이 없어 리뷰 수정 SLICE·H24·H22와 병렬로 할 수 있다(사용자 결정 2026-10-27, D-56)
  - [ ] DECISIONS 정합 점검(생성 단계 test 1회 전): `docs/CLAUDE.md` "정합 점검" 절차로 DECISIONS 전체를 검토한다(사용자 결정 2026-10-28, ADR-0071)
  - [ ] DECISIONS 정합 점검(프로젝트 마무리 전): 위와 같은 절차를 한 번 더 한다(사용자 결정 2026-10-28)

## 실험 백로그

예상 효과는 사전 추정이다. 재임베딩이 필요한 실험은 Colab 크레딧을 쓰므로 비용 칸에 표시했다.

- [대기] H10 생성 컨텍스트 구성: 단위(청크 / 앞뒤 청크 확장 / 문서 전체, DECISIONS D-05), 문서 수, 청크 선택 규칙을 함께 정한다. 판정은 SPEC "생성 단계 평가 > 판정"(D-53)의 종합 지표로 하고, 실행 절차는 `.claude/skills/meet-rag/references/gen-exp.md`다. 순서는 D-56 (효과 미상 / 재임베딩 없음)
  - 문서 수: `generator.context_docs` 5는 주지표 Recall@5에 맞춘 값이고 시험하지 않았다(D-11). 프롬프트 길이는 문서 수 × 단위 크기라 단위와 함께 정한다
  - 청크 선택: 지금은 문서마다 dense 점수가 가장 높은 청크 하나다(`rag.retrieve`의 `best_chunks`, S6 naive 설정. 재정렬 후보 쌍도 같은 함수를 쓴다, S16). 검색 단계 종료 뒤 문서 순위를 정한 검색 점수로 고르도록 바꾼다(사용자 방향 2026-10-19). RRF는 문서 순위끼리 합친 점수라 청크 단위 hybrid 점수를 새로 정의해야 한다(예: 문서 안 청크의 dense·BM25 순위 RRF). BM25는 512 청크만 색인해 256 청크(EXP-011)에는 BM25 점수가 없다. 리랭커가 운영에 들어가면(EXP-017) 리랭커 입력 청크도 같은 규칙으로 맞춘다. 문서 순위 방식(H7)이 바뀌면 함께 바뀐다. 단위가 문서 전체로 정해지면 필요 없다
  - 문서 단위 중복 제거의 의도(사용자, 2026-10-19): 질의마다 정답 문서가 하나인 데이터에서 한 문서의 청크가 상위 5개를 대부분 차지하지 않게 하려 했다. 관련도와 함께 이미 고른 결과와의 유사도를 빼 다양성을 얻는 MMR(Carbonell & Goldstein, "The Use of MMR, Diversity-Based Reranking for Reordering Documents and Producing Summaries", SIGIR 1998)에서 착안했다. 같은 문서 청크끼리 유사도 1, 다른 문서 0으로 두고 벌점을 충분히 크게 둔 MMR과 같은 결과다(추론). 대신 정답 문서의 두 번째 근거 청크는 생성에 들어가지 않는다. 앞뒤 확장·문서 전체 후보가 이 손실을 다룬다
  - 문서 전체 후보는 무료 쿼터(TPM 16K)로 긴 문서(최대 약 4.2만 토큰)를 한 호출에 보낼 수 없어 H11의 유료 경로가 먼저다
  - 단위의 참고 자료(S14 결과 절): 정답 문서의 근거 청크가 `answer.comment`를 담은 비율(문자열 겹침 0.5 이상, dev-small 1,039질의)은 근거 청크가 256이면 67.5%, 512이면 83.9%였고, 정답 문서의 청크 수(256·512 합)가 2\~3이면 93.4%, 4\~7이면 77.0%, 8 이상이면 60.3%였다. 짧은 청크와 긴 문서에서 근거 청크 하나에 답이 덜 들어간다
- [아이디어] H17 검색기별 상위 슬롯 보장: 최종 상위 5개 중 일부를 dense 상위 1\~2개, BM25 상위 1\~2개에 먼저 주고 나머지를 RRF 순서로 채운다. 한 목록의 상위 문서가 결합에서 밀리는 경우를 구조적으로 막는다(사용자 구상 2026-10-19) (효과: 상한 +0.40%p 미만 / 비용 없음, 재임베딩 없음). 진행하지 않는다(사용자 결정 2026-10-19). 검토: D-34의 결합 손실 12개를 모두 살려도 +0.40%p이고, 이 안이 살리는 것은 그중 정답이 한 목록 1\~2위였던 질의뿐이다. RRF k 20에서 한 목록 1위(1/21)는 두 목록 모두 약 22위 안인 문서 5개 이상에만 밀려, 실제로 바뀌는 것은 주로 2위다(추론). 예약한 슬롯만큼 RRF 4\~5위의 합의 정답을 잃고(EXP-014 5개, EXP-015 10개 선례), 최다 일치 필터(EXP-004)가 올린 조건 일치 문서를 밀어내 multi-doc이 떨어질 수 있다(추론, BM25는 multi-doc에서 약함, D-17). 근거인 결합 손실을 판정과 같은 dev-full에서 얻었다. 리랭커(EXP-017)가 운영에 들어가지 못하면 비용 없는 대안으로 다시 본다
- [아이디어] H18 생성 프롬프트에서 모호함·회피를 전하기: 근거가 "예정", "검토 중", "정해지지 않음"으로만 말하거나 답변자가 답을 피한 내용을 거부 문구 대신 그 상황("아직 정해지지 않았다[n]", "답변자가 답하지 않았다[n]")으로 답하게 지시한다. 지금 프롬프트(v1·v2)는 "답할 수 없으면 거부"만 지시해 이런 내용도 거부로 낸다. S14c의 항목 단위 상황 미전달 수로 효과를 본다(S14b의 거부 이유 분류는 PR #118 리뷰로 뺐다. 사용자 결정 2026-10-20, D-41) (효과 미상 / 재임베딩 없음)
  - 바람직한 처리는 "상황을 밝히고 답함"이고, "일부만 있다"는 안내만 한 답변은 상황 미전달이다(D-47 결정 1). 확답이 없는 내용은 원문 표현대로 전한다(사용자 S14c c11·c13, `docs/gen-eval-criteria.md` "지금 평가하지 않는 것")
  - 순서: H23 뒤(D-56). 베이스라인 상황 미전달은 28항목(27질의)이고 종합 지표 상한 +0.010이라 단독 실험 뒤 보류면 상황 미전달 수와 두 안전 조건으로 예외 채택을 정한다
  - 지금 수준: S14 표본 20질의를 v2로 생성해 j_v7로 본 동작 확인에서 모호·회피 항목 5개 중 상황 전달은 0개였다(판정에 쓰지 않는 값, `docs/slices/14c-item-refusal.md` 결과 절)
  - 참조 발언이 회피·부동의일 때의 모범 답안은 "어느 위원이 무엇을 제안·질의했고 답변자는 어떤 입장이었다"를 종합한 답변이다(사용자 결정 2026-10-20, `docs/slices/14-gen-eval.md` 사고 과정 켬·끔 검수). 누가 한 말인지 밝히려면 H20이 필요하다
- [아이디어] H19 거부를 별도 문장으로 쓰기: 한 문장에 내용과 거부 문구를 함께 쓰면("A 위원은 B를 제안했으나 C의 시행 시기는 제공된 회의록에서 답을 찾지 못했습니다[1].") 평가가 문장 전체를 거부로 보아 내용이 채점되지 않는다(S14b `refusal_split`). 평가를 문장 안까지 나누지 않고, 생성 프롬프트에서 거부는 답하지 못한 내용만 담은 별도 문장으로 쓰게 지시한다(사용자 결정 2026-10-20, PR #118) (효과: 채점 손실 방지 / 재임베딩 없음)
  - H24와 한 실험으로 본다(D-56). 베이스라인에서 내용과 거부 문구가 한 문장에 든 거부는 1문장이라 종합 지표 상한은 0이다. 무엇을 못 찾았는지 밝히는 지시는 지정 문구 문장을 그대로 두고 대상을 따로 쓰게 해 H24와 맞춘다(예시안, 실험 지시서에서 정한다)
  - 거부 문장에 어느 항목을 찾지 못했는지 밝히게 하는 지시를 함께 시험한다. 평가는 항목마다 판정하므로 이미 잡히지만, 전체 거부에서 사용자가 무엇을 못 찾았는지 알 수 없다(사용자 S14c c14, `docs/gen-eval-criteria.md` "지금 평가하지 않는 것")
- [아이디어] H21 대화로 질의를 구체화하거나 추가 정보 확인하기: 근거가 잘렸거나(예: 이어지는 청크에 답변자 의견이 있을 수 있음) 질의가 여러 사건에 걸리면(예: 연도를 특정하지 않아 2019년·2021년 다른 사건의 답변이 섞임) 에이전트가 사용자에게 후속 청크를 확인할지, 어느 사건인지 묻는다. 지금 평가는 질의 하나에 답변 하나라 이 동작을 잴 수 없어 다중 턴 평가를 따로 설계해야 한다. 고정된 앞뒤 청크 확장은 H10에서 다룬다(사용자 결정 2026-10-22, S14c 검수)
- [아이디어] H20 청크에 발언자 붙이기(데이터 처리): 청크 본문에는 발언자 표기가 없어 잘린 조각만으로는 질의자·답변자를 가리기 어렵다. 원천 회의록은 발언마다 발언자·발언순번·발언내용이 있으므로(`docs/data.md` 원천 데이터 형식) `context`를 원천 회의록과 맞춰 발언자를 표시하면 생성 모델과 judge가 누가 한 말인지 알 수 있다. 원천 회의록 보유 여부와 대조 비용·정확도는 확인하지 않았다. 생성 입력·평가 모두에 영향이 있어 착수 전에 범위를 정한다(사용자 지시 2026-10-20, D-41 결정 4) (효과 미상 / 재임베딩 여부 미정)
  - 범위(사용자 결정 2026-10-27, D-56): SLICE(PLAN "생성 평가"의 H20 발언자 표시)와 EXP로 나눈다. 검색 텍스트(임베딩)는 바꾸지 않는다. 원천 데이터에는 본문 전체의 발언별 발언자가 없다(`docs/data.md` §5). 베이스라인 발언자 구분 불가 표시는 진술 25개(14질의)·항목 110개(82질의)이고 종합 지표 상한 +0.042다
  - 근거에 발언자 정보가 없어 judge의 정보 상태 판정이 흔들린다(S25 블라인드 확인 검수 의견, 사용자 2026-10-26)
  - H18의 모범 답안("어느 위원은 \~, 답변자는 \~")과 H22(질의자 주장 구분)는 발언자 표기를 전제한다. 기준 문서도 이 답변을 모범으로 보되 지금 청크로는 생성 모델이 할 수 없다고 적었다(사용자 S14 3, S14c c12, `docs/gen-eval-criteria.md` "지금 평가하지 않는 것")
- [아이디어] H22 생성 프롬프트에서 질의자 주장을 사실처럼 쓰지 않게 하기: 답변자가 확인하지 않은 질의자(위원) 주장·수치를 사실처럼 쓴 진술은 충실성 0이다(`verdicts` 규칙 5, G2·F5·F6). S22에서 j_v8로 다시 채점하자 S14 표본 20질의 중 4질의에서 진술 7개가 이 이유로 1에서 0으로 바뀌었고(`docs/slices/22-gen-eval-criteria.md` 결과 절), 사용자는 이 엄격함을 유지하기로 했다(PR #145 리뷰, "RAG에서 근거를 넘어선 추측은 근본적으로 피해야"). 생성 프롬프트에서 질의자 주장은 "○○ 위원은 \~라고 물었다"처럼 주장으로 전하게 지시한다. 청크에 발언자 표기가 없어 모델이 주장과 확인을 가리기 어려운 경우가 남으므로 H20과 함께 본다. 평가 판정에서 메인이 이끈 생성 쪽 대응이다(사용자 확인 2026-10-26) (효과 미상 / 재임베딩 없음)
- [아이디어] H23 회의·연도가 다른 근거를 나눠 답하기: 생성 모델이 근거 5개를 하나의 정보로 묶어 답해, 근거가 서로 다른 회의·연도에서 나오면(예: 종자 수출과 벼 수출을 다룬 다른 해의 회의) 다른 맥락의 질문과 답이 섞인 답변이 생성되고 그대로 평가될 수 있다. 생성 프롬프트(`configs/prompt/v2.yaml`의 `context`)와 judge(`rag.gen_eval.judge.format_contexts`)는 근거마다 날짜·위원회·회의 차수를 이미 받으므로, 빠진 것은 정보가 아니라 "회의·연도가 다른 근거는 나눠 다루라"는 지시다. 생성 쪽은 실험으로 시험하고, 평가 쪽 반영은 judge 지시 동결(D-49) 때문에 지금 하지 않는다. 사용자에게 어느 사건인지 묻는 다중 턴 동작(H21)과 달리 단일 턴 생성 지시다(S25 블라인드 확인 검수 의견, 사용자 결정 2026-10-26) (효과 미상 / 재임베딩 없음)
- [아이디어] H24 지정 거부 문구를 그대로 쓰게 하기: 생성 모델이 거부 문구 사이에 대상을 넣어("제공된 회의록에서 청장의 대응 계획에 대한 답을 찾지 못했습니다.") 코드가 거부로 판별하지 못한다. S25 베이스라인 330질의 중 23개였고, 그중 4개는 충실성 진술 없음으로 빠지고 19개는 일반 답변으로 채점됐다(PR #158 report 표). 지정 방식대로 답하지 않은 것이라 감점은 그대로 두고(사용자 결정 2026-10-27, 이슈 #156) 생성 프롬프트(`configs/prompt/v2.yaml`의 "근거로 답할 수 없으면 …라고 답하세요")에서 문구를 바꾸지 말고 그대로 쓰게 지시한다. 거부 수를 판정에 쓰면(D-52) 두 설정의 문구 준수율 차이가 거부 수 차이가 되므로 거부를 바꾸는 생성 실험보다 먼저 하거나 함께 본다. 무엇을 찾지 못했는지 밝히게 하는 H19의 지시와 충돌하지 않게 함께 정한다 (효과: 거부 판별 누락 23개 / 재임베딩 없음)
  - 생성 실험의 첫 번째로 H19와 함께, 다른 가설과 묶지 않고 실험한다. H22 지시가 질의자 주장만 있는 항목을 거부로 돌릴 수 있어 거부 판별을 먼저 맞춘다. 종합 지표 상한 +0.001이라 보류면 지정 문구 없는 거부 수와 두 안전 조건으로 예외 채택을 정한다(사용자 결정 2026-10-27, D-56)
- [아이디어] H25 modular RAG 확장(질의 분해, 검증 루프, 라우팅): 생성 평가 모듈을 만들며 나온 아이디어 범주다(PLAN "생성 실험 순서"). 우선순위가 높은 생성 실험(H10 등) 뒤에 한다. 그 전에 진행하는 생성 실험이 이 범주와 겹치면(예: 다중 턴 확인 H21, 회의별로 나눠 답하기 H23) 그때 함께 논의한다(사용자 결정 2026-10-27, 이슈 #156) (효과 미상 / 재임베딩 없음)

평가(judge) 쪽 아이디어. 생성 실험이 아니라 블라인드 확인·평가 모듈에서 다룬다.

- [아이디어] 핵심 답 유무 경계 0.5(기준 문서 C1, D-40 결정 4)를 사람 판정과 대조하기: 사용자가 판단 근거가 부족하다고 지적해(PR #106 코멘트 3) 잠정값으로 두고 질의별 비율 분포를 보고하기로 했다(2026-10-20, fe9d355). 그때 G5 보정에서 사람 판정("청크에 답이 있는가")과 대조해 정하자고 제안했지만 승인 기록은 없고, G5를 블라인드 확인으로 바꾸며(2026-10-22) 이 대조를 맡은 단계가 없다. 블라인드 확인 표본에 넣을지 그 지시서에서 정한다
- [아이디어] 발언자 구분 불가 표시의 빈도 차이 확인: 같은 S14 표본에서 `verdicts`는 진술 1개, `items`는 항목 6개에 표시했다. 두 단계가 같은 규칙(G2)인데 빈도가 달라 블라인드 확인에서 함께 본다(`docs/slices/22-gen-eval-criteria.md` 결과 절 관찰)

순서는 예상 효과 대비 비용 순이다. 실험 결과가 나올 때마다 다시 정렬한다. 결과 수치는 EXPERIMENTS.md에 둔다.

생성 실험 순서(사용자 결정 2026-10-27, D-56, 근거 `notebooks/38_01_생성실험순서.ipynb`): H24+H19 거부 형식 → H22 → H10 → H23 → H18, H25는 H10 뒤. H20은 SLICE(발언자 표시 기능)를 먼저 하고 EXP 위치는 H22 결과를 보고 정한다. 베이스라인 종합 지표 0.843(314질의)에서 겨냥 질의가 모두 고쳐질 때의 상한은 H22 +0.086(충실성 0 진술 193개 중 질의자 주장 167개), H10 +0.103(넓은 합집합 163질의), H20 +0.042, H23 +0.027, H18 +0.010, H24 +0.001, H19 0이다. H18·H19·H24는 상한이 δ 0.02 미만이라 다른 가설과 묶지 않고 실험하고(H24·H19는 거부 형식 한 실험) 보류면 겨냥 지표와 두 안전 조건을 보고 사용자가 예외 채택을 정한다(D-56)

다음 순서(2026-10-27, 생성 실험 순서 정리 뒤 갱신): 생성 평가 모듈 리뷰 수정(SLICE)·H20 발언자 표시(SLICE) → H24+H19 → H22 → (H20 EXP 위치 결정) → H10 → H23 → H18

## 보조 관찰: multi-doc 질의

SPEC "보조 관찰: multi-doc 질의" 절을 따른다. 정답 문서가 여러 개인 dev 질의 세트를 만들어, 채택 판정(single-doc)과 별도로 각 EXP가 multi-doc 질의에서 어떻게 평가되는지 함께 보고한다. 실험 백로그와 병렬로 진행할 수 있다. 다만 G3에서 세트를 동결하기 전에는 어떤 EXP의 multi-doc 점수도 보지 않는다.

S9 이후의 EXP는 EXP 문서 결과 절에 single-doc 판정과 multi-doc 관찰을 함께 적는다. S9 전에 끝난 EXP는 config로 다시 실행해 multi-doc 점수를 채운다.

## 이후 단계

- 생성 단계 평가: 평가 프로토콜은 SPEC "생성 단계 평가"(D-53)이고, 생성 실험 백로그는 위 "실험 백로그" 절, 순서는 D-56이다
  - 생성 단계 test 1회는 검색 단계와 같이 사용자 지시로 쓸 수 있다(D-38, PR #102 코멘트). 그때 리랭커 채점 등으로 test 질의를 Colab에서 처리해야 하면, 지운 업로드 허용(ADR-0045)을 새 ADR로 다시 둔다
- 배포(HF Spaces): 생성 단계 이후 조각으로 추가한다. 할 일(사용자, 2026-10-15): 리랭커를 채택하면 추론 서버의 네트워크 왕복과 기동 지연(scale-to-zero)을 잰다. 배포에 문제가 생기면 config에서 리랭커만 뺀 구성(EXP-014 설정)으로 배포한다. 생성이 반복 실패하면 유료 API로 생성하는 분기를 둔다(D-30 정정. 기본 경로가 유료가 되어 필요 없어짐, D-37). 답변은 스트리밍으로 출력하고, 질의당 시간은 질의 입력부터 답변 출력 시작(첫 토큰)까지로 3초와 비교한다(D-30). 배포 페이지에 사용자가 고를 수 있는 시험용 질문 샘플을 둔다. 실사용 형태(multi-doc에 가까운) 질의가 되도록 고르고, 실사용 질의 성능은 따로 생성한 질의로 재지 않는다(사용자, PR #101 코멘트. test로 확인하지 못하는 한계(D-39)에 대한 처리)
- 벡터스토어 선정: 배포 조각에서 정한다. 지금은 청크 임베딩 행렬(118,039 × 1024, 404MB)을 메모리에 올려 전수 내적으로 검색하고 BM25는 bm25s 파일, 조건 목록은 파이썬 역색인이다. 먼저 전수 검색으로 충분한지(질의당 지연, 메모리)를 보고, 필요하면 저장 용량, 메타데이터 필터 지원, 문서 추가 비용, SPEC 자원 제약(상시 지출 0, HF Spaces 무료 CPU)으로 후보를 비교한다. late-interaction(KURE-v2)처럼 다중 벡터를 쓰면 MaxSim 지원 여부가 조건이 된다(`docs/research/embedding-candidates.md`)

## 아이디어 (채택하지 않음, 보고 때 개선·발전 방향으로 쓴다)

- 멀티턴 대화 메모리: 후속 질의를 대화 이력으로 재작성(H8과 같은 부품)하고, 앞 턴의 조건(위원회·날짜·이름·법률명)을 이어받아 지금 검색기로 검색한 뒤 이력과 함께 생성한다. 구현은 검색 파이프라인을 거의 바꾸지 않는다. 채택하지 않는 이유(사용자 결정 2026-10-13): 프로젝트 전반을 싱글턴·single-doc으로 진행했고 multi-doc 세트(600건)도 전체에 비해 작다. 대화 단위 평가 세트를 새로 만드는 부담이 커서, 적합한 멀티턴 데이터셋을 구했을 때 시도한다
- 법령 조회 도구(MCP): 법제처 Open API 기반 MCP(예: korean-law-mcp, 현행 법령·판례 조회)를 생성 단계 도구로 붙이는 안을 검토했다. 채택하지 않는 이유(사용자 결정 2026-10-13): 회의록은 당시 심사 대상 법률안을 다루므로 현행 법령 조문은 생성 품질에 도움이 된다고 볼 수 없다. 필요한 것은 심사 중인 법률안을 조회하고 발의에서 심사까지 법안이 어떻게 바뀌었는지 추적해 보여 주는 기능이고, 이는 의안 정보(국회 의안정보시스템 등)를 다루는 도구가 맞다. EXP-008의 법률명 사전을 그 도구의 호출 조건(법률명이 잡힌 질의)으로 쓸 수 있다
- late-interaction 임베딩(KURE-v2): 공개 벤치마크에서 KURE-v1보다 크게 앞섰지만(평균 nDCG@10 +5.4%p) 토큰마다 벡터를 저장해 용량이 dense의 약 5\~33배라 벡터스토어·운영 제약이 생기고, 리랭커로는 cross-encoder(EXP-006)보다 기대치가 낮아 채택하지 않았다(사용자 결정 2026-10-13, `docs/research/embedding-candidates.md`)
