# PLAN: 국회 회의록 RAG (SPEC.md 기준)

naive RAG(고정 길이 청킹 → KURE-v1 dense 검색 → 생성)로 베이스라인을 세우고, advanced RAG 기법을 한 부분씩 더해 검색 성능을 높인다. 검색 단계 판정은 SPEC의 dev-full Recall@5로 한다.

완료된 조각·게이트, 끝난 가설, 지난 "다음 순서" 기록은 [`docs/PLAN-done.md`](PLAN-done.md)에 옮겼다. 옮긴 문장은 고치지 않았다.

## 생성 평가

SPEC 개정 초안 `docs/drafts/spec-generation-eval.md`에 기준(충실성, 답변 관련성, 핵심 답변 포함도, 거부 정확도), 코드 판정 항목, judge, 오라클 진단, 남은 결정 사항이 있다(D-38). 초안이 SPEC에 옮겨지기 전에는 생성 EXP를 판정하지 않으므로 H10은 그때까지 기다린다(H11 생성 경로는 D-37로 정했다). 초안의 출발점은 사용자 요청(2026-10-14, PR 히스토리 분석과 Lauren Tan 발표 정리 대화)과 사용자 결정(2026-10-19, PR #99 코멘트)이다.

- 코드로 판정할 항목(인용 번호 유효성, 거부 문구, 발언자·회의 일자의 메타데이터 일치)은 LLM 없이 처리하고, judge에는 남는 기준만 맡긴다
- judge는 사람 채점으로 보정한 뒤 쓴다. 이후 주기적으로 소량을 다시 사람이 확인한다
- multi-doc 질의(G3 동결 세트)는 검색 단계와 같이 생성에서도 보조 관찰로 함께 보고하고 판정에 쓰지 않는다(D-38)
- 진행 순서(제안. 번호는 착수 때 확정)
  - [ ] 기준 문서와 모듈 점검(문서 PR): 사람 검수에서 정리한 사용자 판단(D-40·D-41, S14·S14b·S14c 결정 사항)과 judge 근거 문헌 조사(`docs/research/llm-judge-evidence.md`)를 근거로, 모듈 점검에 바로 적용할 수 있는 기준 문서를 쓴다. 그 기준으로 기존 DECISIONS와 평가 모듈(`src/rag/gen_eval/`, judge 지시)을 대조해 수정 사항 목록을 만든다. "생성 평가 모듈을 만들며 검토한 사안 정리"(사용자 지시)를 여기에 합친다. 모호·회피에 "부분임을 밝히고 답함"이 나온 경우(S14c는 상황 미전달)를 여기서 다시 정한다(PR #137 판단할 곳 1). 사용자 결정이 필요한 곳은 이 PR에서 받는다(사용자 결정 2026-10-22)
  - [ ] 수정 사항 반영(SLICE, j_v8): 위 목록을 한 번에 반영한다. 충실성 판정(`verdicts` 규칙 5)의 발언자 규칙을 D-41 결정 4의 세 갈래로 고치고, 구분할 수 없는 경우를 코드로 따로 센다. S14 표본을 다시 채점해 동작을 확인한다(재채점 허용, 사용자 결정 2026-10-22). 지시 변경은 이것을 마지막으로 한다
  - [ ] 평가 모듈 동결(근거 문서의 2단계): judge 모델·경로, 지시 전문과 해시, 사고 과정 설정·temperature, 집계 코드(report), 캐시 키 규칙을 기록하고 고정한다. 동결 뒤에는 정답과 비교하며 지시를 고치지 않는다
  - [ ] 변동 폭 측정과 질의 규모 결정(D-44, 근거 문서의 2단계 일관성 측정을 함께 한다): judge 캐시 키에 반복 번호를 넣어 저장한 응답을 같은 지시로 다시 채점할 수 있게 하고, 생성 잡음과 judge 잡음을 나눠 잰다. 사고 과정 설정·다수결 같은 실행 설정은 이 일관성 수치로만 골라 동결한다(사람 라벨 쓰지 않음). 생성 평가 세트는 dev-full에서 seed 순서의 앞 n개로 고정하고, multi-doc 동결 세트에서도 일부를 뽑아 보조 관찰로 쓴다. 기준 설정을 반복 실행해 생성 API 비결정성과 judge 잡음의 변동 폭을 재고 n을 정한다. 생성 실험 1회가 dev-small 전체 기준 비피크 약 $4.1·피크 약 $8.0이라 베이스라인 앞으로 당겼다(사용자 결정 2026-10-21). 측정 실행은 호출 수·비용을 보고하고 승인 후에 한다
  - [ ] 블라인드 확인 1회(근거 문서의 3단계, 기존 G5를 대신함): 동결한 judge로 채점한 dev-full 답변 중 처음 보는 것에서 실패가 예상되는 항목을 층화해 30\~40개 판정을 사용자가 judge 결과를 보지 않고 매기고, 기준별 κ와 실패 클래스 TPR을 낸다. 일치 기준값에 못 미친 기준은 보조 지표로 내리고 지시는 고치지 않는다. 이 표본은 판정용 세트에서 뺀다(D-44). 그 전까지 항목 평가의 거부 정확도는 참고값으로만 쓴다(PR #137 판단할 곳 3, 사용자 결정 2026-10-22)
  - [ ] 생성 베이스라인과 핵심 답변 포함도 관찰: 기준 설정(EXP-017 검색, 생성 프롬프트 v2, 동결한 judge)으로 D-44 세트(위에서 정한 n)에서 생성 평가 베이스라인을 잡는다. 실행 전 호출 수·비용·opencode Go 사용 한도를 보고하고 승인받는다(추정: 생성 약 $0.26, judge 약 5,500회). G5에서 judge 지시가 바뀌면 생성 기록은 그대로 두고 judge만 다시 채점한다. 같은 실행에서 dev-small에서 `answer.comment`를 참조 답변으로 핵심 답변 포함도를 재 보고(참조 사용 불가 비율, 사람 판단과의 일치), 종합 지표에 넣을지 보조 지표로 관찰할지 정한다(초안 결정 사항 1·2). 기준 설정 출력만 보고, 후보 설정끼리 비교한 결과로 정하지 않는다. judge 형식 오류(응답이 JSON이 아님) 수를 함께 보고, 나오면 구조화된 응답(API JSON 형식 지정, 실패 시 다시 묻는 parser)으로 바꿀지 다시 논의한다. 바꾸면 요청 본문이 달라져 기존 judge 캐시를 쓰지 못한다(사용자 결정 2026-10-21, PR #128. 지금까지 저장 응답 660개 중 0건)
  - [ ] 오라클 진단과 최소 개선 폭: 정답 문서를 넣은 오라클 조건과 정답 문서를 뺀 거부 세트를 한 번 만든다. 최소 개선 폭은 위에서 잰 변동 폭으로 추가 논의한다(초안 결정 사항 3). 실행은 호출 수·비용을 보고하고 승인 후에 한다
  - [ ] SPEC 개정: 남은 결정 사항이 정해지면 초안을 SPEC에 옮기고 사용자 승인을 받는다
  - [ ] 하네스 반영(F 흐름, SPEC 개정 뒤 생성 실험 H10 착수 전에 반드시 한다): exp-judgment 스킬·exp-judge의 메타데이터 판정을 S18 함수(`rag.eval_multi.compare --single`)로 바꾸고 D-35 확장(multi-doc 단계 +1.0%p 미만이고 하한 > 0인 보류는 예외 검토 대상으로 보고)을 반영한다. 함수를 직접 부르면 `check_single`을 먼저 부른다(PR #129, 사용자 결정 2026-10-21). 생성 EXP 판정 스킬(종합 지표, judge 점수 paired bootstrap, 변동 폭 대비 판정, 참조 사용 불가·거부 교차 집계 보고), meet-rag B 흐름의 생성 EXP 갈래, 생성·judge 실행 절차(비용 승인, judge 레시피·저장 응답, 지시 버전 변경 시 재채점, 형식 오류율 확인), protocol-guard 생성 단계 항목. 지금 만들지 않는 것은 judge 설정·지시·판정 규칙이 미정이기 때문이다(사용자 결정 2026-10-19). 원재료는 slices/14-gen-eval.md, D-38·D-40, SPEC 개정본
  - [ ] 생성 실험 순서: H10·H18·H19·H20의 순서는 SPEC 개정과 하네스 반영 뒤, 생성 베이스라인의 거부·상황 미전달 수를 보고 정한다. H20은 착수 전에 범위를 정한다(사용자 결정 2026-10-21, 이슈 #120)

## 실험 백로그

예상 효과는 사전 추정이다. 재임베딩이 필요한 실험은 Colab 크레딧을 쓰므로 비용 칸에 표시했다.

- [대기] H10 생성 컨텍스트 구성: 단위(청크 / 앞뒤 청크 확장 / 문서 전체, DECISIONS D-05), 문서 수, 청크 선택 규칙을 함께 정한다. 생성 평가 초안(D-38)이 SPEC에 옮겨진 뒤 시험한다. 판정은 RAGAS 지표를 고친 LLM judge 주지표로 한다(D-38) (효과 미상 / 재임베딩 없음)
  - 문서 수: `generator.context_docs` 5는 주지표 Recall@5에 맞춘 값이고 시험하지 않았다(D-11). 프롬프트 길이는 문서 수 × 단위 크기라 단위와 함께 정한다
  - 청크 선택: 지금은 문서마다 dense 점수가 가장 높은 청크 하나다(`rag.retrieve`의 `best_chunks`, S6 naive 설정. 재정렬 후보 쌍도 같은 함수를 쓴다, S16). 검색 단계 종료 뒤 문서 순위를 정한 검색 점수로 고르도록 바꾼다(사용자 방향 2026-10-19). RRF는 문서 순위끼리 합친 점수라 청크 단위 hybrid 점수를 새로 정의해야 한다(예: 문서 안 청크의 dense·BM25 순위 RRF). BM25는 512 청크만 색인해 256 청크(EXP-011)에는 BM25 점수가 없다. 리랭커가 운영에 들어가면(EXP-017) 리랭커 입력 청크도 같은 규칙으로 맞춘다. 문서 순위 방식(H7)이 바뀌면 함께 바뀐다. 단위가 문서 전체로 정해지면 필요 없다
  - 문서 단위 중복 제거의 의도(사용자, 2026-10-19): 질의마다 정답 문서가 하나인 데이터에서 한 문서의 청크가 상위 5개를 대부분 차지하지 않게 하려 했다. 관련도와 함께 이미 고른 결과와의 유사도를 빼 다양성을 얻는 MMR(Carbonell & Goldstein, "The Use of MMR, Diversity-Based Reranking for Reordering Documents and Producing Summaries", SIGIR 1998)에서 착안했다. 같은 문서 청크끼리 유사도 1, 다른 문서 0으로 두고 벌점을 충분히 크게 둔 MMR과 같은 결과다(추론). 대신 정답 문서의 두 번째 근거 청크는 생성에 들어가지 않는다. 앞뒤 확장·문서 전체 후보가 이 손실을 다룬다
  - 문서 전체 후보는 무료 쿼터(TPM 16K)로 긴 문서(최대 약 4.2만 토큰)를 한 호출에 보낼 수 없어 H11의 유료 경로가 먼저다
- [아이디어] H17 검색기별 상위 슬롯 보장: 최종 상위 5개 중 일부를 dense 상위 1\~2개, BM25 상위 1\~2개에 먼저 주고 나머지를 RRF 순서로 채운다. 한 목록의 상위 문서가 결합에서 밀리는 경우를 구조적으로 막는다(사용자 구상 2026-10-19) (효과: 상한 +0.40%p 미만 / 비용 없음, 재임베딩 없음). 진행하지 않는다(사용자 결정 2026-10-19). 검토: D-34의 결합 손실 12개를 모두 살려도 +0.40%p이고, 이 안이 살리는 것은 그중 정답이 한 목록 1\~2위였던 질의뿐이다. RRF k 20에서 한 목록 1위(1/21)는 두 목록 모두 약 22위 안인 문서 5개 이상에만 밀려, 실제로 바뀌는 것은 주로 2위다(추론). 예약한 슬롯만큼 RRF 4\~5위의 합의 정답을 잃고(EXP-014 5개, EXP-015 10개 선례), 최다 일치 필터(EXP-004)가 올린 조건 일치 문서를 밀어내 multi-doc이 떨어질 수 있다(추론, BM25는 multi-doc에서 약함, D-17). 근거인 결합 손실을 판정과 같은 dev-full에서 얻었다. 리랭커(EXP-017)가 운영에 들어가지 못하면 비용 없는 대안으로 다시 본다
- [아이디어] H18 생성 프롬프트에서 모호함·회피를 전하기: 근거가 "예정", "검토 중", "정해지지 않음"으로만 말하거나 답변자가 답을 피한 내용을 거부 문구 대신 그 상황("아직 정해지지 않았다[n]", "답변자가 답하지 않았다[n]")으로 답하게 지시한다. 지금 프롬프트(v1·v2)는 "답할 수 없으면 거부"만 지시해 이런 내용도 거부로 낸다. S14c의 항목 단위 상황 미전달 수로 효과를 본다(S14b의 거부 이유 분류는 PR #118 리뷰로 뺐다. 사용자 결정 2026-10-20, D-41) (효과 미상 / 재임베딩 없음)
- [아이디어] H19 거부를 별도 문장으로 쓰기: 한 문장에 내용과 거부 문구를 함께 쓰면("A 위원은 B를 제안했으나 C의 시행 시기는 제공된 회의록에서 답을 찾지 못했습니다[1].") 평가가 문장 전체를 거부로 보아 내용이 채점되지 않는다(S14b `refusal_split`). 평가를 문장 안까지 나누지 않고, 생성 프롬프트에서 거부는 답하지 못한 내용만 담은 별도 문장으로 쓰게 지시한다(사용자 결정 2026-10-20, PR #118) (효과: 채점 손실 방지 / 재임베딩 없음)
- [아이디어] H21 대화로 질의를 구체화하거나 추가 정보 확인하기: 근거가 잘렸거나(예: 이어지는 청크에 답변자 의견이 있을 수 있음) 질의가 여러 사건에 걸리면(예: 연도를 특정하지 않아 2019년·2021년 다른 사건의 답변이 섞임) 에이전트가 사용자에게 후속 청크를 확인할지, 어느 사건인지 묻는다. 지금 평가는 질의 하나에 답변 하나라 이 동작을 잴 수 없어 다중 턴 평가를 따로 설계해야 한다. 고정된 앞뒤 청크 확장은 H10에서 다룬다(사용자 결정 2026-10-22, S14c 검수)
- [아이디어] H20 청크에 발언자 붙이기(데이터 처리): 청크 본문에는 발언자 표기가 없어 잘린 조각만으로는 질의자·답변자를 가리기 어렵다. 원천 회의록은 발언마다 발언자·발언순번·발언내용이 있으므로(`docs/data.md` 원천 데이터 형식) `context`를 원천 회의록과 맞춰 발언자를 표시하면 생성 모델과 judge가 누가 한 말인지 알 수 있다. 원천 회의록 보유 여부와 대조 비용·정확도는 확인하지 않았다. 생성 입력·평가 모두에 영향이 있어 착수 전에 범위를 정한다(사용자 지시 2026-10-20, D-41 결정 4) (효과 미상 / 재임베딩 여부 미정)

순서는 예상 효과 대비 비용 순이다. 실험 결과가 나올 때마다 다시 정렬한다. 결과 수치는 EXPERIMENTS.md에 둔다.

다음 순서(2026-10-22, 하네스 PR #140 뒤 갱신, 사용자 결정): 기준 문서와 모듈 점검(문서 PR) → 수정 사항 반영(SLICE, j_v8 포함) → 평가 모듈 동결 → 반복 재채점 코드와 변동 폭 측정·질의 규모 결정(일관성으로 실행 설정 동결) → 블라인드 확인 1회 → 생성 베이스라인(비용 승인) → 오라클 진단·최소 개선 폭 → SPEC 생성 평가 개정 → 하네스 생성 평가 반영 → H10. j_v8을 기준 문서 앞에 두면 기준 문서 단계(모호·회피 재결정, 모듈 점검)에서 지시를 다시 바꾸게 되어, 지시 변경을 기준 문서 뒤 한 번으로 모았다

## 보조 관찰: multi-doc 질의

SPEC "보조 관찰: multi-doc 질의" 절을 따른다. 정답 문서가 여러 개인 dev 질의 세트를 만들어, 채택 판정(single-doc)과 별도로 각 EXP가 multi-doc 질의에서 어떻게 평가되는지 함께 보고한다. 실험 백로그와 병렬로 진행할 수 있다. 다만 G3에서 세트를 동결하기 전에는 어떤 EXP의 multi-doc 점수도 보지 않는다.

S9 이후의 EXP는 EXP 문서 결과 절에 single-doc 판정과 multi-doc 관찰을 함께 적는다. S9 전에 끝난 EXP는 config로 다시 실행해 multi-doc 점수를 채운다.

## 이후 단계

- 생성 단계 평가: 검색 단계 종료(test 1회 보고) 후 SPEC 개정 초안(D-38)의 남은 결정 사항을 정해 SPEC에 옮긴 뒤 백로그를 만든다. 진행 순서는 위 "생성 평가" 절
  - 생성 단계 test 1회는 검색 단계와 같이 사용자 지시로 쓸 수 있다(D-38, PR #102 코멘트). 그때 리랭커 채점 등으로 test 질의를 Colab에서 처리해야 하면, 지운 업로드 허용(ADR-0045)을 새 ADR로 다시 둔다
- 배포(HF Spaces): 생성 단계 이후 조각으로 추가한다. 할 일(사용자, 2026-10-15): 리랭커를 채택하면 추론 서버의 네트워크 왕복과 기동 지연(scale-to-zero)을 잰다. 배포에 문제가 생기면 config에서 리랭커만 뺀 구성(EXP-014 설정)으로 배포한다. 생성이 반복 실패하면 유료 API로 생성하는 분기를 둔다(D-30 정정. 기본 경로가 유료가 되어 필요 없어짐, D-37). 답변은 스트리밍으로 출력하고, 질의당 시간은 질의 입력부터 답변 출력 시작(첫 토큰)까지로 3초와 비교한다(D-30). 배포 페이지에 사용자가 고를 수 있는 시험용 질문 샘플을 둔다. 실사용 형태(multi-doc에 가까운) 질의가 되도록 고르고, 실사용 질의 성능은 따로 생성한 질의로 재지 않는다(사용자, PR #101 코멘트. test로 확인하지 못하는 한계(D-39)에 대한 처리)
- 벡터스토어 선정: 배포 조각에서 정한다. 지금은 청크 임베딩 행렬(118,039 × 1024, 404MB)을 메모리에 올려 전수 내적으로 검색하고 BM25는 bm25s 파일, 조건 목록은 파이썬 역색인이다. 먼저 전수 검색으로 충분한지(질의당 지연, 메모리)를 보고, 필요하면 저장 용량, 메타데이터 필터 지원, 문서 추가 비용, SPEC 자원 제약(상시 지출 0, HF Spaces 무료 CPU)으로 후보를 비교한다. late-interaction(KURE-v2)처럼 다중 벡터를 쓰면 MaxSim 지원 여부가 조건이 된다(`docs/research/embedding-candidates.md`)

## 아이디어 (채택하지 않음, 보고 때 개선·발전 방향으로 쓴다)

- 멀티턴 대화 메모리: 후속 질의를 대화 이력으로 재작성(H8과 같은 부품)하고, 앞 턴의 조건(위원회·날짜·이름·법률명)을 이어받아 지금 검색기로 검색한 뒤 이력과 함께 생성한다. 구현은 검색 파이프라인을 거의 바꾸지 않는다. 채택하지 않는 이유(사용자 결정 2026-10-13): 프로젝트 전반을 싱글턴·single-doc으로 진행했고 multi-doc 세트(600건)도 전체에 비해 작다. 대화 단위 평가 세트를 새로 만드는 부담이 커서, 적합한 멀티턴 데이터셋을 구했을 때 시도한다
- 법령 조회 도구(MCP): 법제처 Open API 기반 MCP(예: korean-law-mcp, 현행 법령·판례 조회)를 생성 단계 도구로 붙이는 안을 검토했다. 채택하지 않는 이유(사용자 결정 2026-10-13): 회의록은 당시 심사 대상 법률안을 다루므로 현행 법령 조문은 생성 품질에 도움이 된다고 볼 수 없다. 필요한 것은 심사 중인 법률안을 조회하고 발의에서 심사까지 법안이 어떻게 바뀌었는지 추적해 보여 주는 기능이고, 이는 의안 정보(국회 의안정보시스템 등)를 다루는 도구가 맞다. EXP-008의 법률명 사전을 그 도구의 호출 조건(법률명이 잡힌 질의)으로 쓸 수 있다
- late-interaction 임베딩(KURE-v2): 공개 벤치마크에서 KURE-v1보다 크게 앞섰지만(평균 nDCG@10 +5.4%p) 토큰마다 벡터를 저장해 용량이 dense의 약 5\~33배라 벡터스토어·운영 제약이 생기고, 리랭커로는 cross-encoder(EXP-006)보다 기대치가 낮아 채택하지 않았다(사용자 결정 2026-10-13, `docs/research/embedding-candidates.md`)
