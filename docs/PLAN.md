예상 효과는 사전 추정이다. 재임베딩이 필요한 실험은 Colab 크레딧을 쓰므로 비용 칸에 표시했다.

- [채택] H1 hybrid: dense + BM25(Kiwi 형태소), RRF 결합 (효과 큼 / 인덱스 재사용, BM25 인덱스 CPU 구축) → EXP-001
- [채택] H2 reranker: 상위 후보를 cross-encoder로 재정렬 (효과 큼 / 재임베딩 없음, CPU 지연 증가. SPEC 미결 3과 연결). 배포 지연 상한(SPEC 미결 3)은 H2 채택 여부를 판단한 뒤 지연 시간과 성능 변동을 함께 보고 정한다(사용자 결정 2026-10-12) → EXP-005 기각, H2를 멈춘다(사용자 결정 2026-10-12). cross-encoder(KURE-Reranker-nano)는 무료 CPU 2스레드에서 질의당 37초라 배포할 수 없어 실행하지 않았고, 판단 모델 Jev(OpenRouter)는 지연 p95 0.83초였지만 dev-full Recall@5 −3.08%p [−4.16, −2.04]로 떨어졌다. 리랭커를 쓰지 않으므로 SPEC 미결 3은 이 항목에서 정하지 않는다 → EXP-006 채택·운영 보류(사용자 지시로 재개 2026-10-13, 첫 변형). BM25 문서에만 더하는 변형은 재임베딩이 없고 dense 접두는 재임베딩이 필요하다. multi-doc 질의는 회의를 날짜·위원회·이름으로 지목하는데 그 표현이 정답 본문에는 드물다(D-18, `notebooks/10_03_EXP001_multidoc진단.ipynb`). 판정은 SPEC "메타데이터 가설의 판정" (효과: multi-doc 큼, single-doc 작음 / BM25 변형은 로컬 약 10분, dense 접두는 재임베딩) → EXP-002 기각(BM25 접두, 첫 EXP. BM25 접두의 다음 변형은 하지 않고 H14로 이어 간다(D-19). dense 접두만 대기. single-doc −2.62%p, multi-doc R@5 +15.32%p, 하락은 긴 안건 접두의 길이 정규화) → dense 접두 상한 분석(재임베딩 없음, `notebooks/29_01_H5_접두효과상한.ipynb`): EXP-014가 놓친 정답 중 메타데이터로 가를 수 있는 것이 거의 없다. single-doc 실패 177개 중 166개는 질의에서 조건이 뽑히지 않는다. multi-doc 상위 5개 밖 정답 84개는 최다 일치 동률(5개 초과) 52개, 정답보다 더 많이 맞은 문서가 있는 32개다. 동률 문서는 같은 메타데이터를 받아 접두로 갈리지 않는다(추론). EXP-002의 multi-doc 이득은 조건 목록(EXP-003)과 최다 일치 필터(EXP-004)에 이미 흡수됐다. dense 접두는 진행하지 않는다(사용자 결정 2026-10-15). 메타데이터 일치가 아닌 경로(본문 표현 변화)의 효과는 이 분석으로 보지 않았다
- [예외 채택] H6 임베딩 모델 교체: 후보는 `dragonkue/snowflake-arctic-embed-l-v2.0-ko`(EXP-009). 기존 후보 `BAAI/bge-m3`, `dragonkue/BGE-m3-ko`는 공개 벤치마크에서 모두 KURE-v1보다 낮아 뺐다. Qwen3 계열 다음 변형은 지금 계획하지 않는다
- [기각] H7 청크 점수의 문서 집계 방식: 최고점 대신 상위 n개 합 등 (효과 소 / 비용 없음) → EXP-007 기각(첫 EXP. 상위 2개 합은 dev-small에서 청크 1개 정답 문서를 밀어내 dev-full 전에 max + 0.1·2위로 바꿈. dev-full Recall@5 −2.35%p [−3.01, −1.75], 손실의 90%가 청크 1개 정답). H7을 닫는다(사용자 결정 2026-10-13)
  - 문헌: 문서 점수를 청크 점수 최댓값으로 두는 방식(MaxP)은 Dai & Callan, "Deeper Text Understanding for IR with Contextual Neural Language Modeling"(SIGIR 2019)에서 첫 조각 점수(FirstP)·조각 점수 합(SumP)과 비교해 대체로 가장 좋았고, 긴 문서 검색의 기준선으로 쓰인다. 조각 표현을 학습으로 합치는 방식은 근거가 문서 여러 곳에 흩어진 경우 MaxP보다 낫다고 보고됐지만 학습이 필요하다(Li et al., "PARADE: Passage Representation Aggregation for Document Reranking", 2020). 이 저장소에서는 문서 전체를 한 벡터로 임베딩한 경우(8192 청크, 문서당 1.00개, D-04)와 합 계열(EXP-007)이 MaxP보다 낮았다. 평가 질의는 정답 문서를 보고 만들어 한 청크와 겹치기 쉬워 MaxP가 실사용보다 유리하게 나왔을 수 있다(EXP-007 단서, 추정)

## 아이디어 (채택하지 않음, 보고 때 개선·발전 방향으로 쓴다)

- 멀티턴 대화 메모리: 후속 질의를 대화 이력으로 재작성(H8과 같은 부품)하고, 앞 턴의 조건(위원회·날짜·이름·법률명)을 이어받아 지금 검색기로 검색한 뒤 이력과 함께 생성한다. 구현은 검색 파이프라인을 거의 바꾸지 않는다. 채택하지 않는 이유(사용자 결정 2026-10-13): 프로젝트 전반을 싱글턴·single-doc으로 진행했고 multi-doc 세트(600건)도 전체에 비해 작다. 대화 단위 평가 세트를 새로 만드는 부담이 커서, 적합한 멀티턴 데이터셋을 구했을 때 시도한다
- 법령 조회 도구(MCP): 법제처 Open API 기반 MCP(예: korean-law-mcp, 현행 법령·판례 조회)를 생성 단계 도구로 붙이는 안을 검토했다. 채택하지 않는 이유(사용자 결정 2026-10-13): 회의록은 당시 심사 대상 법률안을 다루므로 현행 법령 조문은 생성 품질에 도움이 된다고 볼 수 없다. 필요한 것은 심사 중인 법률안을 조회하고 발의에서 심사까지 법안이 어떻게 바뀌었는지 추적해 보여 주는 기능이고, 이는 의안 정보(국회 의안정보시스템 등)를 다루는 도구가 맞다. EXP-008의 법률명 사전을 그 도구의 호출 조건(법률명이 잡힌 질의)으로 쓸 수 있다
- late-interaction 임베딩(KURE-v2): 공개 벤치마크에서 KURE-v1보다 크게 앞섰지만(평균 nDCG@10 +5.4%p) 토큰마다 벡터를 저장해 용량이 dense의 약 5\~33배라 벡터스토어·운영 제약이 생기고, 리랭커로는 cross-encoder(EXP-006)보다 기대치가 낮아 채택하지 않았다(사용자 결정 2026-10-13, `docs/research/embedding-candidates.md`)
