# PLAN: 국회 회의록 RAG (SPEC.md 기준)

naive RAG(고정 길이 청킹 → KURE-v1 dense 검색 → 생성)로 베이스라인을 세우고, advanced RAG 기법을 한 부분씩 더해 검색 성능을 높인다. 검색 단계 판정은 SPEC의 dev-full Recall@5로 한다.

완료된 조각·게이트, 끝난 가설, 지난 "다음 순서" 기록은 [`docs/PLAN-done.md`](PLAN-done.md)에 옮겼다. 옮긴 문장은 고치지 않았다.

## 생성 평가

생성 단계 평가 프로토콜은 SPEC "생성 단계 평가"(D-53)다. 기준(충실성, 답변 관련성, 종합 지표, 보조 지표 핵심 답변 포함도, 과잉 거부·잘못 귀속 안전 조건), judge, 판정 규칙이 있고, 생성 EXP 실행 절차는 `.claude/skills/meet-rag/references/gen-exp.md`, 생성 실험 순서는 D-56이다(H11 생성 경로는 D-37). 초안(`docs/drafts/spec-generation-eval.md`)의 출발점은 사용자 요청(2026-10-14, PR 히스토리 분석과 Lauren Tan 발표 정리 대화)과 사용자 결정(2026-10-19, PR #99 코멘트)이다.

- 코드로 판정할 항목(인용 번호 유효성, 거부 문구, 회의 일자·위원회의 메타데이터 일치)은 LLM 없이 처리하고, judge에는 남는 기준만 맡긴다
- 주기적인 사람 재확인은 하지 않는다. 블라인드 확인을 S25에서 1질의 검수 뒤 중단해(D-51) 지금 judge는 사람과 독립 대조 없이 쓴다
- multi-doc 질의(G3 동결 세트)는 생성에서 판정에 쓰지 않고, 여러 문서를 합쳐 답하는 것을 겨냥한 실험에서만 일부로 본다(D-38, D-53 결정 7)
- 진행 순서: 남은 항목 없음(마무리 정합 점검과 회고 보강을 마쳤다, D-93)

## 실험 백로그

예상 효과는 사전 추정이다. 재임베딩이 필요한 실험은 Colab 크레딧을 쓰므로 비용 칸에 표시했다.

- [아이디어] H17 검색기별 상위 슬롯 보장: 최종 상위 5개 중 일부를 dense 상위 1\~2개, BM25 상위 1\~2개에 먼저 주고 나머지를 RRF 순서로 채운다. 한 목록의 상위 문서가 결합에서 밀리는 경우를 구조적으로 막는다(사용자 구상 2026-10-19) (효과: 상한 +0.40%p 미만 / 비용 없음, 재임베딩 없음). 진행하지 않는다(사용자 결정 2026-10-19). 검토: D-34의 결합 손실 12개를 모두 살려도 +0.40%p이고, 이 안이 살리는 것은 그중 정답이 한 목록 1\~2위였던 질의뿐이다. RRF k 20에서 한 목록 1위(1/21)는 두 목록 모두 약 22위 안인 문서 5개 이상에만 밀려, 실제로 바뀌는 것은 주로 2위다(추론). 예약한 슬롯만큼 RRF 4\~5위의 합의 정답을 잃고(EXP-014 5개, EXP-015 10개 선례), 최다 일치 필터(EXP-004)가 올린 조건 일치 문서를 밀어내 multi-doc이 떨어질 수 있다(추론, BM25는 multi-doc에서 약함, D-17). 근거인 결합 손실을 판정과 같은 dev-full에서 얻었다. 리랭커(EXP-017)가 운영에 들어가지 못하면 비용 없는 대안으로 다시 본다

## 보조 관찰: multi-doc 질의

SPEC "보조 관찰: multi-doc 질의 (검색 단계)" 절을 따른다. 정답 문서가 여러 개인 dev 질의 세트를 만들어, 채택 판정(single-doc)과 별도로 각 검색 EXP가 multi-doc 질의에서 어떻게 평가되는지 함께 보고한다. 실험 백로그와 병렬로 진행할 수 있다. 다만 G3에서 세트를 동결하기 전에는 어떤 EXP의 multi-doc 점수도 보지 않는다.

S9 이후의 검색 EXP는 EXP 문서 결과 절에 single-doc 판정과 multi-doc 관찰을 함께 적는다. S9 전에 끝난 EXP는 config로 다시 실행해 multi-doc 점수를 채운다.

- 지연 관찰: EXP-021에서 첫 토큰 시간이 늘었다(EXP-021 결과 절). 다음 실행에서 반복되는지 보고 해결 필요성을 정한다(사용자 지시 2026-11-03, D-70) EXP-022·023에서도 첫 토큰 시간이 실행마다 달랐다(각 EXP 결과 절). 기준 프롬프트가 바뀌어도 배포 측정에서 함께 본다
- 배포(HF Spaces): 배포·운영 작업은 생성 실험과 별도로 병행한다. 배포 환경에서 LangSmith 추적을 켰고(D-71), 공개 Space는 끈다(D-92). 다음 세션부터 이렇게 진행한다(사용자 결정 2026-11-03). 남은 조각은 아래 순서로 한다(사용자 결정 2026-11-04). 할 일(사용자, 2026-10-15): 배포에 문제가 생기면 config에서 리랭커만 뺀 구성으로 배포한다(`deploy.rerank.enabled=false`). 생성이 반복 실패하면 유료 API로 생성하는 분기를 둔다(D-30 정정. 기본 경로가 유료가 되어 필요 없어짐, D-37). 답변은 스트리밍으로 출력하고, 질의당 시간은 질의 입력부터 답변 출력 시작(첫 토큰)까지로 3초와 비교한다(D-30). 배포 페이지에 사용자가 고를 수 있는 시험용 질문 샘플을 둔다. 실사용 형태(multi-doc에 가까운) 질의가 되도록 고르고, 실사용 질의 성능은 따로 생성한 질의로 재지 않는다(사용자, PR #101 코멘트. test로 확인하지 못하는 한계(D-39)에 대한 처리) 대화 이어 가기(H21, 사용자 결정 2026-11-04, D-76): 지금 앱은 질의 한 번으로 끝난다. 메모리를 더해 대화를 이어 가게 한다. 근거가 잘렸을 때 후속 청크를 확인하거나 여러 사건에 걸린 질의에서 어느 사건인지 묻는 동작이 여기 든다. 평가는 질의 하나에 답변 하나라 판정 지표로 재지 않는다. 앞 대화를 검색과 생성에 넣는 방법은 착수 때 정하고, 후속 질문을 독립 질의로 바꾸는 단계가 필요하면 H25의 방법론으로 쓴다

## 아이디어 (채택하지 않음, 보고 때 개선·발전 방향으로 쓴다)

- 상대 시점 표현 풀기: 답변이 회의록의 "작년 12월"처럼 회의 날짜 기준 표현을 그대로 옮겨 지금 읽으면 다른 해로 읽힌다(사용자 대화 2026-11-06, S51 범위 밖). 첫 질문에도 생기는 일이라 생성 지시를 바꿔야 하고 생성 기준이 바뀐다
- 멀티턴 대화 메모리: 후속 질의를 대화 이력으로 재작성(H8과 같은 부품)하고, 앞 턴의 조건(위원회·날짜·이름·법률명)을 이어받아 지금 검색기로 검색한 뒤 이력과 함께 생성한다. 구현은 검색 파이프라인을 거의 바꾸지 않는다. 채택하지 않는 이유(사용자 결정 2026-10-13): 프로젝트 전반을 싱글턴·single-doc으로 진행했고 multi-doc 세트(600건)도 전체에 비해 작다. 대화 단위 평가 세트를 새로 만드는 부담이 커서, 적합한 멀티턴 데이터셋을 구했을 때 시도한다
- 법령 조회 도구(MCP): 법제처 Open API 기반 MCP(예: korean-law-mcp, 현행 법령·판례 조회)를 생성 단계 도구로 붙이는 안을 검토했다. 채택하지 않는 이유(사용자 결정 2026-10-13): 회의록은 당시 심사 대상 법률안을 다루므로 현행 법령 조문은 생성 품질에 도움이 된다고 볼 수 없다. 필요한 것은 심사 중인 법률안을 조회하고 발의에서 심사까지 법안이 어떻게 바뀌었는지 추적해 보여 주는 기능이고, 이는 의안 정보(국회 의안정보시스템 등)를 다루는 도구가 맞다. EXP-008의 법률명 사전을 그 도구의 호출 조건(법률명이 잡힌 질의)으로 쓸 수 있다
- late-interaction 임베딩(KURE-v2): 공개 벤치마크에서 KURE-v1보다 크게 앞섰지만(평균 nDCG@10 +5.4%p) 토큰마다 벡터를 저장해 용량이 dense의 약 5\~33배라 벡터스토어·운영 제약이 생기고, 리랭커로는 cross-encoder(EXP-006)보다 기대치가 낮아 채택하지 않았다(사용자 결정 2026-10-13, `docs/research/embedding-candidates.md`)
