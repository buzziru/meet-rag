# EXP-017: 지금 기준(EXP-014) 위에서 KURE-Reranker-nano로 상위 후보 재정렬 (H2, 운영 재판단)

## 가설
- EXP-006은 EXP-004 기준 위에서 RRF 상위 20개를 KURE-Reranker-nano로 다시 줄 세워 dev-full Recall@5 +3.08%p [+2.29, +3.86]를 냈지만, 운영 비용 때문에 기준으로 올리지 않았다(D-26). 그 뒤 기준은 snowflake-ko 임베딩, 256 청크 추가, 법률명 조건, RRF k 20(EXP-014, D-32)으로 바뀌었다. 같은 리랭커를 지금 기준의 상위 20개에 적용해도 Recall@5가 오른다
- G2(D-34)에서 기준 실패 177개 중 검색기로 좁힐 수 있는 오답은 17개(결합 손실 12, 근접 4)였다. 리랭커는 상위 20개 안의 순서를 바꾸므로 결합 손실·근접 오답을 겨냥한다. 상승 폭이 EXP-006보다 작을 수 있다. EXP-006 당시 기준 Recall@5는 0.9164였고 지금은 0.9413이다(추정, 실행 전)
- 이 EXP의 결과(성능, 질의당 시간, 운영 비용)로 리랭커 운영 채택을 정하고, 그 뒤 test 1회 실행으로 검색 단계를 마친다(D-34, 사용자 결정 2026-10-15)

## 기준 실험
- EXP-014 설정(D-32). 기준 순위: single-doc `data/runs/snowflake-ko-fixed-512-64-hybrid-cond-filter-law-ms256-k20-dev-full.csv`(SHA-256 `084bc83e39a59ddc70b8cc1303c3d64b8169269ccaef0484976741fa123edc30`), multi-doc `…-ms256-k20-multidoc.csv`(SHA-256 `951e68bf810e1dfbc8ffd487b35abc4f91c694cefe16369f787c02ea784d03d6`)
- 백로그 H2의 세 번째 EXP이고 두 번째 변형이다(첫 EXP EXP-005 기각, 첫 변형 EXP-006 채택·운영 보류). 바꾸는 것은 기준 설정뿐이고 리랭커와 파라미터는 EXP-006과 같다
- D-26은 "운영 채택 때 그 사이 채택한 EXP를 리랭커 위에서 다시 판정한다"고 적었다. 이번에는 지금 기준 전체에 리랭커를 더한 구성 하나만 판정한다(사용자 지시 2026-10-15). EXP-008·009·011·014를 하나씩 리랭커 위에서 다시 판정하지 않는다

## 바꾸는 것
- 기준 EXP-014 설정 위에 EXP-006의 재정렬을 더한다: RRF 후보(필터 전) 상위 20개를 KURE-Reranker-nano(revision `f3b3eff`, `max_length` 1024)로 다시 줄 세운 뒤 최다 일치 필터를 적용하고 상위 10개를 낸다
- 문서 입력: 문서마다 질의와 dense 점수가 가장 높은 청크 하나. 지금 기준은 512 청크와 256 청크를 함께 쓰므로(`retriever.extra_chunks`), 두 인덱스의 청크 중 최고점 청크를 쓴다. dense 문서 점수(청크 최댓값)를 고르는 방식과 같다
- 코드: 후보 쌍 내보내기(`rag.search search.mode=rerank-pairs`)는 지금 `extra_chunks`와 함께 쓰면 멈춘다. 청크 본문을 인덱스들을 이어 붙인 순서로 읽도록 고쳐 이 제한을 푼다. `extra_chunks`가 없으면 지금과 같은 쌍을 쓴다(EXP-006 dev-small 후보 쌍을 다시 만들어 그대로인지 확인)
- 실행 장치: Colab GPU, float16
- 경로: 후보 쌍·점수·지연 파일 이름에 기준 설정을 넣어 EXP-005·006 파일을 덮어쓰지 않는다. 순위 파일 `snowflake-ko-fixed-512-64-hybrid-cond-filter-law-ms256-k20-ce-{층}.csv`
- 파라미터(모델, 깊이 20, 청크 입력, `max_length`)는 EXP-006 값으로 고정하고 dev-full 결과를 보고 조정하지 않는다

## 판정 기준 (실행 전 확정)
H2는 [메타데이터] 가설이 아니므로 SPEC 판정 절을 그대로 옮긴다. 비교 기준은 EXP-014다.

- dev-full Recall@5 차이를 회의 단위 paired bootstrap(10,000회, seed 20260929)으로 계산한다
- 채택: 95% 구간 하한 > 0 이고 점 추정 ≥ +1.0%p
- 기각: 95% 구간 상한 < 0
- 보류: 그 밖
- multi-doc은 관찰로 보고 판정에 쓰지 않는다(SPEC 보조 관찰)
- 운영 채택(기준 설정으로 올릴지)은 SPEC 판정과 별개로 사용자가 성능, 질의당 시간(D-30 상한 3초), 운영 비용(D-26)을 함께 보고 정한다

## 질의당 시간 측정
- 운영 구성은 질의 임베딩과 1차 검색을 CPU(배포처 HF Spaces)에서, 재정렬을 GPU 추론 서버에서 하는 것을 가정한다(D-30 범위: 질의 임베딩부터 문서 순위까지, 인덱스 로딩 제외)
- GPU 재정렬: EXP-006과 같은 방식으로 질의 100개를 하나씩 재정렬해 질의당 계산 시간을 잰다(`rag.rerank mode=latency`)
- CPU 단계: 로컬 PC에서 같은 질의 100개를 하나씩 질의 임베딩(캐시 없이), 1차 검색, 후보 20개 청크 본문 준비까지 잰다
- 두 값을 질의마다 더해 질의당 시간으로 보고한다. 추론 서버의 네트워크 왕복과 scale-to-zero 기동 지연은 이 측정에 들어 있지 않다(결정 사항 2)
- D-30 상한(3초)은 질의 입력부터 답변 출력 시작(스트리밍 첫 토큰)까지다(D-30 정정, PR #90). 이 EXP는 검색 부분(임베딩·1차 검색·재정렬)만 재고, 생성 첫 토큰 지연은 배포 SLICE에서 잰다. 운영 채택 판단에는 검색 부분이 3초 중 얼마를 쓰는지로 보고한다
- 운영 채택 보고에 단서를 함께 적는다: 생성 첫 토큰 지연은 재지 않았다. 개발 중 무료 쿼터 호출에서 네트워크 지연이 자주 생겼고(사용자 관찰 2026-10-19), 생성 경로(PLAN H11)에 따라 검색이 쓸 수 있는 남은 시간이 달라진다

## 결론에 함께 적을 것
- 생성 근거 청크와의 관계(PLAN H10): 운영 채택이면 상위 문서의 순위를 정하는 점수가 리랭커 입력 청크(문서마다 dense 최고점 청크)에서 나온다. 생성 근거 청크(`rag.generate`의 `best_chunks`)도 같은 청크라, 생성은 검색 점수가 가리키는 청크를 받는다. 기각이나 운영 보류면 기준(EXP-014)에는 청크 단위 검색 점수가 없어(RRF는 문서 순위끼리 합친다) H10에서 새로 정의한다

## 범위 밖
- 리랭커 입력 규칙(문서마다 dense 최고점 청크 하나)은 이 EXP 뒤 test 1회 실행으로 검색 단계를 마치면 바꾸지 않는다. 문서마다 청크 여러 개를 재정렬해 최댓값을 쓰는 변형은 test로 다시 확인할 수 없는 검색 변경이 되고, 쌍 수가 문서당 청크 수만큼 늘어 GPU 시간·운영 비용과 D-30 예산 부담이 커진다. 시험하지 않는다(2026-10-19)

4. 로컬: 순위·판정, multi-doc 관찰, CPU 단계 지연 측정
5. 원인 분석 노트북(판정과 관계없이): EXP-014 대비 순위가 바뀐 질의, G2 개선 가능 17개와 좁힐 수 없음 160개에서 각각 몇 개가 상위 5개에 들어오고 나갔는지

## 예상 비용·시간

- Colab에는 dev 질의만 담긴 후보 쌍 파일을 올린다(D-31). test 질의는 보내지 않는다
