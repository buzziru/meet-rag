# EXP-007: dense 문서 점수에 두 번째 청크 가점 (H7)

## 가설
- 지금은 dense와 BM25 모두 문서 점수가 그 문서의 최고점 청크 점수다(청크 순서에서 문서가 처음 나온 순서, `src/rag/search.py:25-55`). 이 방식은 청크 하나만 강하게 맞은 문서와 여러 청크가 맞은 문서를 구분하지 못한다. dense 문서 점수에 두 번째로 높은 청크 점수를 작게 더하면(max + 0.1·2위), 질의 내용이 두 청크 이상에 걸친 정답 문서가 dense 목록에서 올라가 RRF 결과의 Recall@5가 오른다
- 반대 방향의 위험: 청크가 하나뿐인 문서(코퍼스의 28%)는 가점을 받지 못해, 점수 차가 가점보다 작으면 청크가 여러 개인 문서 뒤로 밀린다
- 정답이 RRF 6\~20위인 질의는 약 150개(5.0%)다. +1.0%p는 순증 30개 질의 이상이 5위 안으로 들어와야 하는 크기라, 예상 효과는 작다(PLAN 사전 추정 "소")

## 기준 실험
- EXP-004 (hybrid + 조건 목록 + 최다 일치 필터). D-24, D-26(리랭커 운영 보류로 기준 유지)
- 기준 순위: single-doc `data/runs/kure-v1-fixed-512-64-hybrid-cond-filter-dev-full.csv`(SHA-256 `0a64961758eed7a78162e989c5f44d64d3a69453a5f9fd4f9ccf024908e375d2`), multi-doc `…-hybrid-cond-filter-multidoc.csv`(SHA-256 `bf4b8968ee63b859524138aa7c6040a7cfcc66251785f2f8155d1a42a662e5f4`)
- 백로그 H7의 첫 EXP다(SPEC 가설 단위 중단의 셈에 넣지 않는다)

## 바꾸는 것
- dense 문서 점수: 최고점 청크 점수 → 최고점 + 0.1 × 두 번째 청크 점수(`retriever.doc_agg.weights: [1.0, 0.1]`). 청크가 하나뿐인 문서는 최고점만 쓴다
- dense 목록은 이 문서 점수 내림차순 상위 100개(`fusion.depth`)다. 조건 목록이 dense 문서 점수로 동점을 가르는 부분(`condition_docs`)도 같은 문서 점수를 쓴다
- BM25 목록, RRF(k 60), 조건 목록 규칙, 최다 일치 필터는 EXP-004와 같다. BM25는 점수 척도가 달라 이번에는 바꾸지 않는다(변수를 dense 하나로 둔다)
- 순위 파일 이름 `…-hybrid-cond-filter-agg2-{층}.csv`(`retriever.run_name`)
- 파라미터(가중치 [1.0, 0.1], dense만)는 위 값으로 고정하고 dev-full 결과를 보고 조정하지 않는다

### 설계를 정한 경위
- 처음 승인한 설계(2026-10-13)는 상위 2개 청크 점수의 합(`weights: [1.0, 1.0]`)이었다. dev-small에서 Recall@5가 0.9808 → 0.6978로 떨어졌고, 5위 밖으로 밀린 297개 질의 중 97.6%가 정답 문서의 청크가 1개였다(청크 1개 정답 304개 중 299개 손실). dense 점수(코사인 유사도)가 대체로 양수라 청크 두 개의 합이 청크 하나의 높은 점수를 거의 항상 이긴다. 기준 동작은 같다(exp004 dev-small 순위 파일 해시 동일)
- 사용자 결정(2026-10-13)으로 dev-full을 보기 전에 max + α·2위로 바꿨다. α 0.1은 청크 1개 문서가 손해를 덜 보는 작은 가점으로, 선택지를 제시할 때(α 0.1의 dev-small 결과를 보기 전) 정했다. dev-small(α 0.1) Recall@5 0.9769, Recall@1 0.8845(기준 0.9808, 0.9105)로 약간 떨어졌다(5위 진입 1, 이탈 5, 이탈 5개 모두 청크 1개 정답). dev-small은 판정 근거가 아니고 α는 바꾸지 않는다(`notebooks/17_01_EXP007_devsmall확인.ipynb`)

## 고정 조건
- SPEC 평가 프로토콜 v1 / 인덱스·질의 임베딩 캐시·BM25 인덱스·조건 파일 재사용(재임베딩 없음) / config: `configs/exp/exp007.yaml`(EXP-004 설정을 불러와 위 항목만 더한다)

- 운영 비용: 추가 서버 비용은 없다. 검색 시간 변화(dev-full 전체 실행 시간, 질의당 평균)를 기준과 같은 PC에서 재서 함께 보고한다(D-26, 운영 채택은 비용과 함께 판단)

## 판정 기준 (실행 전 확정)
H7은 [메타데이터] 가설이 아니므로 SPEC 판정 절을 그대로 옮긴다. 비교 기준은 EXP-004다.

- dev-full Recall@5 차이를 회의 단위 paired bootstrap(10,000회, seed 20260929)으로 계산한다
- 채택: 95% 구간 하한 > 0 이고 점 추정 ≥ +1.0%p
- 기각: 95% 구간 상한 < 0
- 보류: 그 밖
- multi-doc은 관찰로 보고 판정에 쓰지 않는다(SPEC 보조 관찰)
- 단서(SPEC): 질의가 정답 문서를 보고 생성돼 어휘가 겹친다. 청크가 여러 개인 정답 문서는 질의와 겹치는 청크가 하나일 가능성이 높아, 합 집계의 이득이 실사용보다 작게 나올 수 있다(추정)

## 실행
- dev-small 확인: `uv run python -m rag.search +exp=exp007 index.scope=dev-small` → `uv run python -m rag.eval.score --run data/runs/kure-v1-fixed-512-64-hybrid-cond-filter-agg2-dev-small.csv --layer dev-small`
- dev-full·판정: `uv run python -m rag.search +exp=exp007 index.scope=full` → `uv run python -m rag.eval.compare --base data/runs/kure-v1-fixed-512-64-hybrid-cond-filter-dev-full.csv --cand data/runs/kure-v1-fixed-512-64-hybrid-cond-filter-agg2-dev-full.csv`
- multi-doc: `uv run python -m rag.search +exp=exp007 index.scope=full search.queries=multidoc` → `uv run python -m rag.eval_multi.compare --base data/runs/kure-v1-fixed-512-64-hybrid-cond-filter-multidoc.csv --cand data/runs/kure-v1-fixed-512-64-hybrid-cond-filter-agg2-multidoc.csv`

## 결과
- dev-full Recall@5: 후보 0.8929 / 기준(EXP-004) 0.9164 / 차이 −2.35%p (95% 구간 [−3.01, −1.75]%p, 회의 단위 paired bootstrap 10,000회, seed 20260929)
- Recall@1 / @10 / MRR@10: 후보 0.7497 / 0.9317 / 0.8122, 기준 0.7954 / 0.9450 / 0.8488 (차이 −4.58 / −1.33 / −3.65%p)
- 층별 Recall@5 차이: 모든 층에서 떨어졌다. 본회의 −6.25%p(112개), 소위원회 −3.63%p(1,214개), 특별위원회 −3.26%p(307개), 예산결산특별위원회 −3.16%p(158개), 국정감사 −0.41%p(1,225개), 단답형 −2.42%p(289개), 추출형 −2.35%p(2,727개)
- 정답 문서의 청크 수별 Recall@5(코퍼스의 청크 1개 문서 27.96%): 1개 0.9085 → 0.8294(−7.91%p, 885개), 2개 −0.30%p(660개), 3\~4개 −0.10%p(999개), 5개 이상 +0.42%p(472개). 5위 이탈 78개 중 70개(89.7%)가 청크 1개 정답이고, 5위 진입 7개는 모두 청크 2개 이상이다. 청크 2개 이상 정답만 보면 이탈 8, 진입 7로 가설이 기대한 이득은 나타나지 않았다
- multi-doc(관찰, 판정에 쓰지 않음): Recall@5 0.9361 → 0.9277, −0.84%p [−1.45, −0.26], Complete@5 −1.33%p [−2.67, 0.00]. 유형별 Recall@5 conf −0.69%p, law −2.48%p, questioner +0.16%p
- 지연·비용: 추가 서버 비용 없음(로컬 CPU). dev-full 검색 프로세스 전체 시간(같은 PC, 모델·인덱스 로드 포함) 기준 36초, 후보 128초. 문서마다 청크를 정렬하는 계산이 더해졌다. 로드 시간이 섞여 질의당 순수 검색 시간 차이는 재지 않았다

- 실행: 위 "실행" 절 명령 / 커밋 c67e9ad

## 결론
- 기각. dev-full Recall@5 차이의 95% 구간 상한 −1.75%p < 0(SPEC 판정 절)
- 손실의 90%가 정답 문서의 청크가 1개인 질의에서 났고, 청크가 여러 개인 정답에서는 순변화가 거의 없었다. 이 코퍼스는 문서가 질의응답 구간 단위라 짧고 질의도 구간 하나를 보고 만들어져, 여러 청크에 걸친 근거라는 신호가 약한 것으로 본다(추정). 가점 0.1도 청크 1개 문서를 밀어낼 만큼 컸다(dense 점수 분포는 보지 않은 추정)
- H7의 첫 EXP라 가설 단위 중단 셈에 넣지 않는다. 두 설계(합, 작은 가점)가 같은 원인으로 떨어져 H7의 다음 변형은 권하지 않는다(사용자 결정 대기)
