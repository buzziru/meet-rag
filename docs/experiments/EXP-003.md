# EXP-003: 질의 조건 목록을 RRF에 더함 (H14 첫 EXP)

## 가설
- multi-doc 질의는 회의를 날짜·위원회·회의 종류·회차·사람 이름으로 지목하는데, 그 표현은 정답 본문에 드물고 메타데이터에만 있다(D-18). 질의에서 뽑은 조건(S11·S11b)에 맞는 문서 목록을 hybrid에 세 번째 RRF 목록으로 더하면, 본문 점수로는 순위에 들지 못하던 정답 문서가 올라와 multi-doc Recall@5가 오른다
- 메타데이터를 본문 BM25 점수에 섞지 않으므로 EXP-002의 single-doc 하락 원인(긴 안건 접두의 길이 정규화)이 생기지 않는다. 조건 필드가 2개 이상 뽑히지 않은 질의는 EXP-001과 순위가 같다. dev 질의 3,016건 중 그런 질의는 7건이라 single-doc 변화는 거의 없을 것으로 예상한다(보류 예상, multi-doc으로 판정)

## 기준 실험
- EXP-001 (hybrid: dense + BM25 Kiwi, RRF k 60, 깊이 100). D-17
- 기준 순위: single-doc `data/runs/kure-v1-fixed-512-64-hybrid-dev-full.csv`(SHA-256 `0260382f1e6afe6233528fc3b653167a9fe6c4bd255ec923fb60a34998cb3678`), multi-doc `data/runs/kure-v1-fixed-512-64-hybrid-multidoc.csv`(SHA-256 `28918a409dbc9765561e6706f443e565906596068f2ee663590f223a3a0f89ce`)
- multi-doc 회복 여부 참고(D-17): dense `data/runs/kure-v1-fixed-512-64-multidoc.csv`
- 백로그 H14 [메타데이터]의 첫 EXP다(SPEC 가설 단위 중단의 셈에 넣지 않는다)

## 바꾸는 것
- 조건 목록: 질의마다 조건 파일(`data/conditions/{summary_q|multidoc}.jsonl`, `rag.conditions` 출력)의 조건을 문서 값(`rag.conditions.doc_values`)과 대조해 문서 순위 목록 하나를 만든다
  - 필드: 추출기가 내는 8개 전부(`date`, `year_ref`, `generation_number`, `meeting_number`, `session_number`, `committee_name`, `meeting_name`, `names`)
  - 필드 일치: 질의 값 중 하나라도 문서 값에 있으면 그 필드가 맞는다. 여러 값을 내는 약칭(`외통위` 등, D-22)과 질의에 이름이 둘 이상인 경우도 같다
  - `year_ref`: 문서 회의 연도가 Y-1, Y, Y+1 중 하나면 맞는다. 회계연도 Y의 예산안은 Y-1년, 집행 점검(국정감사)은 Y년, 결산은 Y+1년에 다루는 국회 일정에서 정했다. G3 분포(-1이 70%, D-22)에 맞추지 않는다
  - 순위: 맞은 필드 수 내림차순, 같으면 dense 문서 점수(문서 청크와 질의 임베딩 내적의 최댓값) 내림차순. 필드가 2개 이상 맞은 문서만 넣고(`min_fields: 2`) 상위 100개(결합 깊이와 같다)를 쓴다
  - `min_fields: 2`는 dev-small 확인 뒤 바꾼 설계다(사용자 결정 2026-10-12, dev-full·multi-doc은 보기 전). 처음 설계(필드 1개 이상)는 dev-small Recall@5를 0.9808 → 0.9750으로 낮췄다. 조건이 뽑힌 58건 중 6건에서 정답이 5위 밖으로 밀렸고, 6건 모두 조건 필드가 하나였으며 정답 문서는 그 조건에 맞지 않았다. 필드 하나(`국정감사`, `제1차` 등)는 맞는 문서가 수천 개라 조건 목록이 그 조건에 맞는 문서만 남긴 dense 순위가 되고, dense 점수를 한 번 더 더하는 것으로 본다(`notebooks/14_01_EXP003_조건목록확인.ipynb`). 조건이 뽑힌 질의 중 필드가 2개 이상인 질의는 dev 176건 중 7건, multi-doc 600건 중 600건이다
- 결합: RRF에 dense, BM25, 조건 목록 세 개를 같은 가중치(k 60)로 넣는다. 조건이 없는 질의는 조건 목록이 비어 EXP-001과 같은 순위가 된다. 동점은 dense 목록에 먼저 나온 문서가 앞선다(EXP-001과 같다)
  - 가점 방식을 쓰지 않는 이유: 가점은 dense·BM25 후보 안에서만 순서를 바꿔, 후보에 없는 정답 문서를 올리지 못한다. EXP-001 multi-doc Recall@5가 0.4336이라 후보 밖 정답이 많다. 가점 크기라는 새 파라미터도 생긴다
- 안건 항목 색인은 이번에 넣지 않는다. 질의에서 안건을 뽑는 추출기가 없어 새 구현이 필요하고, 조건 목록의 효과를 먼저 따로 본다. 다음 변형 후보로 둔다
- 후속 변형(사용자 지시 2026-10-12): 이 EXP 결과를 보고 가중 결합(조건 목록의 가중치를 dense·BM25보다 낮게), 필터링 순으로 검토한다. 메타데이터만으로 찾는 검색은 정확도가 낮고 EXP-002에서 single-doc을 떨어뜨렸으므로 가중치는 낮게 두고, 필터링은 single-doc에 해가 될 위험이 커 마지막에 본다. dense + BM25 + 조건 목록 뒤 리랭킹은 H2(reranker)와 이어지므로 앞 변형들 뒤에 따로 논의한다. 이 EXP 뒤 변형부터 SPEC 가설 단위 중단의 셈에 들어간다
- 순위 파일 이름 `…-hybrid-cond-{층}.csv`(`retriever.run_name`). EXP-001 순위 파일을 덮어쓰지 않는다
- 파라미터는 위 값으로 고정하고 dev-full·multi-doc 결과를 보고 조정하지 않는다

## 고정 조건
- SPEC 평가 프로토콜 v1 / 임베딩·청킹·dense 인덱스·BM25 인덱스(`kiwi-v1`)·질의 임베딩 캐시 재사용(재임베딩 없음) / config: `configs/exp/exp003.yaml`(EXP-001 설정을 불러와 위 항목만 더한다)
- 조건은 질의 텍스트와 값 사전만으로 뽑은 것이다(D-19, protocol-guard P9). 질의 행의 라벨은 쓰지 않는다
- 로컬 CPU에서 실행한다. Colab·유료 API를 쓰지 않는다

## 판정 기준 (실행 전 확정)
SPEC "메타데이터 가설의 판정"(D-18)을 그대로 옮긴다.

1. single-doc: dev-full Recall@5 차이를 회의 단위 paired bootstrap(10,000회, seed 20260929)으로 계산한다. 95% 구간 하한 > 0 이고 점 추정 ≥ +1.0%p이면 채택, 95% 구간 상한 < 0이면 기각한다
2. 1이 보류이면 multi-doc 동결 세트(600건)로 정한다. 재표본 단위 `pool_id`, 반복 10,000회, seed 20260929
   - 채택: Recall@5 차이의 95% 구간 하한 > 0, 점 추정 ≥ +1.0%p, Complete@5 차이의 95% 구간 상한 ≥ 0
   - 기각: Recall@5 차이의 95% 구간 상한 < 0
   - 보류: 그 밖
- 단서(SPEC): multi-doc 세트는 메타데이터로 묶음을 만들고 질의도 메타데이터로 회의를 지목해 이 가설에 유리하다. multi-doc 세트에는 test가 없어 multi-doc 단계 채택은 검색 단계 종료 시 test로 다시 확인할 수 없다
- 단서(D-21): 조건 추출 규칙은 G3 오류를 본 뒤 결함 A·C·D를 고쳤다. 이름 정밀도가 `conf` 0.48 → 0.85, `questioner` 0.52 → 0.99로 오른 만큼 multi-doc 점수에 낙관 편향이 있을 수 있다
- 단서(D-22): 약칭 표의 `국회 본회의` 항목은 G3 관찰에서 처음 확인한 표기이고 G3 위원회 적중 증가 16개가 모두 이 항목에서 나왔다. 사용자는 빠뜨린 규칙으로 보고 낙관 편향으로 보지 않는다

## 실행
- dev-small 확인(노트북): `uv run python -m rag.conditions` → `uv run python -m rag.search +exp=exp003`
- single-doc: `uv run python -m rag.search +exp=exp003 index.scope=full` → `uv run python -m rag.eval.compare --base data/runs/kure-v1-fixed-512-64-hybrid-dev-full.csv --cand data/runs/kure-v1-fixed-512-64-hybrid-cond-dev-full.csv`
- multi-doc: `uv run python -m rag.conditions search.queries=multidoc` → `uv run python -m rag.search +exp=exp003 index.scope=full search.queries=multidoc` → `uv run python -m rag.eval_multi.compare --base data/runs/kure-v1-fixed-512-64-hybrid-multidoc.csv --cand data/runs/kure-v1-fixed-512-64-hybrid-cond-multidoc.csv`
- 예상 시간: BM25 인덱스를 다시 쓰므로 EXP-001 실측(인덱스 생성 포함 9분 42초)보다 짧다. 두 세트 합쳐 10분 안팎
