# EXP-012: 문장 경계 청킹 (H4)

## 가설
- 지금 고정 토큰 청크는 경계가 거의 다 문장 중간에 걸린다. dev-small에서 문서 끝이 아닌 청크 경계 중 문장 끝과 맞지 않는 비율이 512 청크 96.2%(1,989개 중 1,913개), 256 청크 96.4%(4,584개 중 4,420개)다(Kiwi 문장 분리 기준, 2026-10-14 측정)
- 답이 걸친 문장이 두 청크로 잘리면 어느 청크도 질의와 맞는 내용을 온전히 담지 못해 dense 점수와 BM25 점수가 낮아진다. 문장을 자르지 않고 토큰 상한까지 묶으면 정답 문서의 청크 점수가 오르고, hybrid Recall@5가 오른다
- 문장 길이는 표본(dev-small 문서 200개, 문장 9,229개)에서 중앙값 20토큰, p95 66토큰, 최대 180토큰이다. 256보다 긴 문장이 없어 상한 안에 문장을 묶는 데 무리가 없다
- 예상: EXP-011에서 청크 구성 변화가 dense 순위를 크게 움직였다(dense 단독 Recall@5 +2.82%p). 경계 이동은 크기 추가보다 변화가 작을 수 있어 효과 크기는 모른다

## 기준 실험
- EXP-011 설정(snowflake-ko, hybrid + 조건 목록 + 최다 일치 필터 + 법률명 조건, dense 512+256). D-29
- 기준 순위: single-doc `data/runs/snowflake-ko-fixed-512-64-hybrid-cond-filter-law-ms256-dev-full.csv`(SHA-256 `855e9fbac75221da6963b9ad4d3b34508c6df42c33eb50847fd6b4cd3ed5c21a`), multi-doc `…-ms256-multidoc.csv`(SHA-256 `c51dc1658d2252d0873474fe0a3290984e11fb119ee23e97306822dd1b51b9b2`)
- 백로그 H4의 첫 EXP다(SPEC 가설 단위 중단의 셈에 넣지 않는다)

## 바꾸는 것
- 청킹 방식: 512/64와 256/32 두 인덱스를 고정 토큰(`fixed`)에서 문장 경계(`sentence`)로 바꾼다(`configs/chunking/sentence.yaml`, `configs/exp/exp012.yaml`). 크기·overlap 토큰 수와 두 크기를 함께 쓰는 방식(EXP-011)은 그대로다
- 문장 경계 청킹 규칙
  - 문장 분리: Kiwi `split_into_sents`. 토큰 수는 임베딩 모델 토크나이저로 센다(고정 청킹과 같음)
  - 묶기: 문서 앞에서부터 문장을 더하다가 다음 문장을 넣으면 `chunk_tokens`를 넘을 때 청크를 끝낸다
  - overlap: 다음 청크는 앞 청크 끝의 문장들 중 합이 `overlap_tokens` 이하인 만큼을 다시 넣고 시작한다. 최소 한 문장은 앞으로 나아간다
  - 상한보다 긴 문장: 그 문장만 고정 토큰 규칙으로 자른다(표본에서는 없었다)
  - 청크 텍스트는 원문의 문자 범위로 자른다(고정 청킹과 같음)
- BM25: 기본 청크(512)에 붙어 있어 함께 문장 경계 512 청크로 바뀐다(결정 1)
- 그대로 두는 것: 임베딩 모델과 질의 임베딩(재사용), 조건 목록, 최다 일치 필터, RRF k 60·깊이 100·가중치 [1, 1, 1], 문서 점수(청크 최댓값)
- 순위 파일 `snowflake-ko-sentence-512-64-hybrid-cond-filter-law-ms256-{층}.csv`
- 파라미터는 실행 전에 고정하고 dev-full 결과를 보고 조정하지 않는다

## 판정 기준 (실행 전 확정)
H4는 [메타데이터] 가설이 아니므로 SPEC 판정 절을 그대로 옮긴다. 비교 기준은 EXP-011이다.

- dev-full Recall@5 차이를 회의 단위 paired bootstrap(10,000회, seed 20260929)으로 계산한다
- 채택: 95% 구간 하한 > 0 이고 점 추정 ≥ +1.0%p
- 기각: 95% 구간 상한 < 0
- 보류: 그 밖. 보류일 때 예외 채택은 D-28의 범위(합당한 근거, 사용자 결정)를 따른다
- multi-doc은 관찰로 보고 판정에 쓰지 않는다(SPEC 보조 관찰)

## 분석 (판정과 관계없이)
- 원인 분석 노트북: 순위가 바뀐 질의마다 dense·BM25·조건 목록 순위가 어떻게 움직였는지(`Retriever.explain`의 단계별 순위), 512·256 중 어느 청크가 정답 문서 점수를 냈는지, 정답 청크가 문장 경계로 바뀌며 길이가 어떻게 달라졌는지
- 운영: 청크 수와 인덱스 용량, 질의당 검색 시간(로딩 제외), 콜드 스타트(인덱스 로딩), 구축 시간·compute unit(요율 환산)

## 결정 사항
1. BM25도 문장 경계 512 청크로 바꾼다(사용자 결정 2026-10-14). BM25 문서 순위도 청크 최댓값이라 경계 문제를 똑같이 겪고, 기본 청크를 바꾸는 것이 가설("청킹 방식")에 맞다. dense와 BM25의 몫은 단계별 순위로 나눠 본다
2. colab CLI를 0.7.4로 올리고, 이 실험의 Colab 실행 전에 작동을 확인한다(사용자 지시 2026-10-14). 확인 대상은 ADR-0036과 EXP-011에서 지적된 연결 문제(exec 멈춤, 업로드 멈춤, 압축 뒤 fetch 멈춤)다

## 고정 조건
- SPEC 평가 프로토콜 v1 / config: `configs/exp/exp012.yaml`(EXP-011 위에 청킹 방식만 바꾼다)
- 기준 설정의 동작은 바뀌지 않는다. 문장 경계 청킹은 `chunking.name=sentence`일 때만 쓴다

## 실행
- 인덱스(Colab L4, 승인 대상): `rag.index +exp=exp012 index.scope=dev-small|full embedding.device=cuda embedding.dtype=float16`, 256은 `chunking.chunk_tokens=256 chunking.overlap_tokens=32`를 더한다 → `data/index/snowflake-ko-sentence-{512-64,256-32}/{dev-small,full}/`. 질의 임베딩은 EXP-009 것을 쓴다
- 예상: 두 인덱스 임베딩이 EXP-009·011 실측(L4, 512 1,098.7초, 256 1,259.4초)과 비슷한 약 40분이다. 환경 준비·업로드·회수를 더해 세션 약 60분, L4 1.54 CU/시간 요율 환산 약 1.5 CU. 문장 단위로 묶으면 청크 끝에 빈 토큰이 생겨 청크 수가 조금 늘 수 있다
- BM25 인덱스는 로컬에서 처음 검색할 때 만든다
- dev-small 확인: `uv run python -m rag.search +exp=exp012 index.scope=dev-small` (노트북 21_01)
- dev-full·판정: `uv run python -m rag.search +exp=exp012 index.scope=full` → `uv run python -m rag.eval.compare --base data/runs/snowflake-ko-fixed-512-64-hybrid-cond-filter-law-ms256-dev-full.csv --cand data/runs/snowflake-ko-sentence-512-64-hybrid-cond-filter-law-ms256-dev-full.csv`
- multi-doc: `… search.queries=multidoc` → `rag.eval_multi.compare`(기준 EXP-011 multi-doc)
