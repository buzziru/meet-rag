# EXP-011: 다중 크기 청킹, 512에 256 청크를 더함 (H9)

## 가설
- 512 청크만으로 dense 검색하면 짧은 사실을 묻는 질의에서 정답 구간이 긴 청크 안에 묻혀 점수가 낮아진다. 같은 문서를 256 청크로도 나눠 dense 목록에 함께 넣으면 정답 문서가 더 위로 오고, hybrid Recall@5가 오른다
- 근거: S4 dev-small(KURE-v1 dense 단독, D-04)에서 256은 512보다 Recall@1 +1.06%p, Recall@5 +0.48%p였다(둘 다 구간이 0을 포함). 질의마다 더 나은 크기를 고르는 오라클 상한은 512 단독 대비 Recall@5 +0.96%p(0.9673 → 0.9769), Recall@1 +3.85%p(0.8739 → 0.9124)다. 512가 놓치고 256이 상위 5위에 넣은 질의는 1,039개 중 10개, 반대는 5개였다(`data/runs/chunk_sweep.json`)
- 예상: Recall@5 상한이 SPEC 채택 기준(+1.0%p) 근처이고, EXP-009에서 dense 단독 개선의 대부분을 BM25·조건 목록이 이미 맞히고 있었다(늘어난 정답의 79%). 그래서 Recall@5는 보류로 끝날 가능성이 높다고 본다. 여지는 Recall@1·MRR 쪽이 더 크다

## 기준 실험
- EXP-009 설정(snowflake-ko, hybrid + 조건 목록 + 최다 일치 필터 + 법률명 조건, RRF 가중치 [1, 1, 1]). D-28
- 기준 순위: single-doc `data/runs/snowflake-ko-fixed-512-64-hybrid-cond-filter-law-dev-full.csv`(SHA-256 `ab695a02b19068dc56b1c31313ed13cd023db36f510ba0da28a414d5d5b4e56e`), multi-doc `…-law-multidoc.csv`(SHA-256 `977fb5432640a82408e888cc47cdf18e76ea499c6ad62a8a23eea12e2faa4e25`)
- 백로그 H9의 첫 EXP다(SPEC 가설 단위 중단의 셈에 넣지 않는다)

## 바꾸는 것
- dense 목록의 청크: 512/64 청크(118,039개)에 같은 문서의 256/32 청크를 더한다(`retriever.extra_chunks: [[256, 32]]`). 두 인덱스의 청크를 하나로 모아 질의와 내적하고, 문서 점수는 그 문서 청크 점수의 최댓값이다. 지금 dense 목록의 문서 순위 방식(청크 점수 순에서 문서가 처음 나온 순서)과 같다
- 크기마다 RRF 목록을 따로 두지 않는다. 그러면 dense 표가 두 개가 되어 EXP-010(dense 가중치 2, 보류)과 효과가 섞인다
- 그대로 두는 것: 임베딩 모델(snowflake-ko, 질의 접두 `query: `), 질의 임베딩(청킹과 무관해 재사용), BM25(512 청크), 조건 목록, 최다 일치 필터, RRF k 60·깊이 100·가중치 [1, 1, 1]
- 256/32는 S4 비교 후보의 값이다(overlap은 크기의 1/8). dev-full 결과를 보고 조정하지 않는다
- 순위 파일 `snowflake-ko-fixed-512-64-hybrid-cond-filter-law-ms256-{층}.csv`

## 판정 기준 (실행 전 확정)
H9는 [메타데이터] 가설이 아니므로 SPEC 판정 절을 그대로 옮긴다. 비교 기준은 EXP-009 설정이다.

- dev-full Recall@5 차이를 회의 단위 paired bootstrap(10,000회, seed 20260929)으로 계산한다
- 채택: 95% 구간 하한 > 0 이고 점 추정 ≥ +1.0%p
- 기각: 95% 구간 상한 < 0
- 보류: 그 밖
- multi-doc은 관찰로 보고 판정에 쓰지 않는다(SPEC 보조 관찰)

### 보류일 때 예외 채택의 조건 (사용자 결정 2026-10-14, 실행 전)
D-28 예외 범위(보류 판정에 한하고 합당한 근거가 필요, 기각은 채택하지 않는다)에 따라, 판정이 보류이면 아래를 함께 보고 사용자가 예외 채택 여부를 정한다. 판정 라벨은 보류 그대로 둔다.

- 순위 상단 개선이 확실한가: dev-full Recall@1과 MRR@10 차이의 95% 구간(위와 같은 회의 단위 paired bootstrap, 10,000회, seed 20260929) 하한이 둘 다 0보다 크다. 하나라도 0을 포함하면 확실하다고 보지 않는다
- 운영 부담: 추가 벡터로 늘어나는 인덱스 용량(임베딩·청크 텍스트, 디스크와 검색 시 메모리), 검색 지연, 인덱스 구축 시간과 비용. 아래 "운영 측정"의 값으로 보고한다
- Recall@1·MRR@10 구간은 SPEC 판정 지표가 아니라 이 예외 판단에만 쓴다. `rag.eval.compare`는 Recall@5만 구간을 내므로, 같은 `paired_bootstrap`(`src/rag/eval/bootstrap.py`)을 판정 근거 노트북에서 불러 계산한다. 평가 모듈은 고치지 않는다

## 실행
- 256 인덱스(Colab L4, 사용자 승인 2026-10-14): `rag.index +exp=exp009 chunking.chunk_tokens=256 chunking.overlap_tokens=32 index.scope=dev-small|full embedding.device=cuda embedding.dtype=float16` → `data/index/snowflake-ko-fixed-256-32/{dev-small,full}/`. 질의 임베딩은 EXP-009 것을 쓴다
- 예상: 256 청크 약 22만 개(dev-small 비율 1.87배). overlap 비율이 같아 총 토큰 수가 512와 비슷하므로 임베딩은 EXP-009 실측(118,039청크 1,098.7초)과 비슷한 약 18분으로 본다. 환경 준비·업로드·회수를 더해 세션 약 50분, L4 1.54 CU/시간 환산 약 1.3 CU

- dev-full·판정: `uv run python -m rag.search +exp=exp011 index.scope=full` → `uv run python -m rag.eval.compare --base data/runs/snowflake-ko-fixed-512-64-hybrid-cond-filter-law-dev-full.csv --cand data/runs/snowflake-ko-fixed-512-64-hybrid-cond-filter-law-ms256-dev-full.csv`
- multi-doc: `… search.queries=multidoc` → `rag.eval_multi.compare`(기준 EXP-009 multi-doc)
- dense 단독 참고(노트북 20_01·20_02): `rag.search +exp=exp011 index.scope=dev-small|full retriever.type=dense retriever.run_name=dense-ms256`. 기준은 `rag.search +exp=exp009 retriever.type=dense retriever.run_name=null`(파일 `snowflake-ko-fixed-512-64-{층}.csv`)

## 결과
- dev-full Recall@5: 후보 0.9337 / 기준 0.9214 / 차이 +1.23%p (95% 구간 [+0.74, +1.73]%p, 회의 단위 paired bootstrap 10,000회, seed 20260929)
- Recall@1 / @10 / MRR@10: 후보 0.8369 / 0.9572 / 0.8815, 기준 0.8103 / 0.9483 / 0.8602
- Recall@1·MRR@10 구간(같은 bootstrap, 노트북 20_02): Recall@1 +2.65%p [+1.78, +3.56], MRR@10 +2.12%p [+1.56, +2.73], Recall@10 +0.90%p [+0.53, +1.29]
- 층별 Recall@5 차이: 본회의(112개) +3.57%p, 국정감사(1,225개) +1.80%p, 특별위원회(307개) +0.98%p, 소위원회(1,214개) +0.66%p, 예산결산특별위원회(158개) 0.00%p. 추출형(2,727개) +1.28%p, 단답형(289개) +0.69%p. Recall@1은 모든 층에서 올랐다
- 순위 이동: 5위 안 진입 51건(기준 6\~10위 29건, 10위 밖 22건), 이탈 14건. 1위 진입 125건(기준 2\~5위 101건, 6\~10위 12건, 10위 밖 12건), 이탈 45건. dev-small에서는 1위 진입 26건이 모두 기준 2\~5위였고 5위 진입은 2건뿐이었는데(20_01), dev-full에서는 5위 밖에서 들어온 정답도 많았다

## 결론
- 채택(single-doc). dev-full Recall@5 +1.23%p, 95% 구간 [+0.74, +1.73]으로 하한 > 0이고 점 추정 ≥ +1.0%p다(SPEC 판정 절). 실행 전 예상(보류)과 달리 Recall@5도 채택 기준을 넘었다. dev-small 오라클 상한(+0.96%p)은 방해 문서가 약 1,000개인 층에서 낸 값이라, 방해 문서가 38배 많은 dev-full의 여지를 작게 잡았다(내 해석)
- 보류일 때의 예외 조건은 쓰지 않는다. 참고로 Recall@1·MRR@10 구간 하한도 0보다 크다
- 가설의 근거(짧은 사실을 묻는 질의)와는 어긋난다. 단답형 이득(+0.69%p)이 추출형(+1.28%p)보다 작아, 단답형에 이득이 몰린다는 기대는 확인되지 않았다
- 기준 설정 반영(운영 채택)은 판정과 별개로 지연·용량과 함께 사용자가 정한다(D-26)
