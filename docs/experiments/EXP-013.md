# EXP-013: 검색 신뢰도가 낮은 질의만 LLM으로 재작성 (H8)

## 가설
- 1차 검색의 신뢰도가 낮은 질의는 질의 표현과 회의록 본문 표현이 달라 정답 문서를 상위 5위 밖으로 놓친다. 이런 질의만 LLM(Gemma 4 31B)으로 회의록 검색에 맞게 다시 쓰고(정식 명칭, 같은 뜻의 핵심어 보강), 재작성 질의의 검색 목록을 원 질의 목록에 더하면 정답 문서가 올라와 hybrid Recall@5가 오른다
- 모든 질의를 재작성하지 않는 이유: 잘 맞히던 질의(Recall@5 93%)를 흔들 위험과 운영 지연(D-30)을 줄인다. 재작성 여부는 추가 호출 없이 1차 검색 결과로 정한다(사용자 결정 2026-10-14). 질의 문장만으로 필요 여부를 판단하는 방식(Jev 판단)은 검색 결과를 보지 못해 뒤로 미뤘다
- 예상: 재작성 대상은 dev-full의 약 12%(라벨 미사용 분포, `notebooks/22_01_H8_재작성신호분포.ipynb`). 신호가 놓친 질의를 얼마나 잡는지는 모른다

## 기준 실험
- EXP-011 설정(D-29). 기준 순위: single-doc `data/runs/snowflake-ko-fixed-512-64-hybrid-cond-filter-law-ms256-dev-full.csv`(SHA-256 `855e9fbac75221da6963b9ad4d3b34508c6df42c33eb50847fd6b4cd3ed5c21a`), multi-doc `…-ms256-multidoc.csv`(SHA-256 `c51dc1658d2252d0873474fe0a3290984e11fb119ee23e97306822dd1b51b9b2`)
- EXP-012(문장 경계 청킹)가 채택돼 기준이 바뀌면, 구현 전에 기준을 그 설정으로 바꾸고 이 절과 판정 신호 임계값(아래 B′)을 다시 계산해 적는다. 임계값은 라벨 없이 계산하므로 다시 정해도 판정이 기울지 않는다
- 백로그 H8의 첫 EXP다(SPEC 가설 단위 중단의 셈에 넣지 않는다)

## 바꾸는 것
### 재작성 판단 (규칙 ③, 사용자 결정 2026-10-14)
1차 검색(EXP-011 설정)의 결과로 두 신호를 계산하고, 하나라도 "낮음"이면 재작성한다. 정답 라벨은 쓰지 않는다.

| 신호 | 정의 | 재작성 조건 |
| --- | --- | --- |
| A′ 상위 5개 합의 | dense 상위 5개 문서와 BM25 상위 5개 문서의 교집합 크기 | 0 (`gate.max_overlap`) |
| B′ dense 점수 폭 | dense 문서 점수(청크 최댓값)의 1위와 10위 차 | 0.0588 이하 (`gate.max_spread`) |

- 1위 문서 기준 신호는 쓰지 않는다. 판정 지표가 Recall@5라 1위 확신과 상위 5개 성공이 다르고, multi-doc은 정답이 여러 개라서다
- B′ 임계값 0.0588은 dev-full summary_q 질의의 B′ 분포 하위 10%다. 정답 여부는 보지 않았다. 운영에서도 이 값을 고정해 쓴다. multi-doc에도 같은 값을 쓴다(multi-doc은 점수가 더 평평해 걸리는 비율이 높다)
- 신호 C(조건이 문서를 좁히지 못함)는 dev-small 작동 확인에서 비율을 보고 넣을지 사용자가 정한다

### 재작성과 결합
- 재작성기: Gemma 4 31B. 실험은 OpenRouter(`configs/rewriter/gemma_openrouter.yaml`), 배포는 Google AI Studio 무료 쿼터(`gemma_google.yaml`). 코드는 OpenAI 호환 클라이언트 하나로 `rewriter` config만 읽고, 경로는 `rewriter=…`로 고른다
- 지시: `configs/rewriter/prompt/rw_v1.yaml`. 질의만 받고 검색 결과·정답 문서는 보지 않는다. 뜻과 대상을 바꾸지 않고, 없는 사실을 지어내지 않으며, 정식 명칭·핵심어를 보강한 한 줄을 쓴다
- 재작성 개수: 질의당 1개, 호출 1번(사용자 결정 2026-10-14). 재작성마다 목록이 2개씩 늘어 원 질의 비중이 줄고, 첫 EXP는 재작성 자체의 효과만 보기 위해서다. 여러 개(한 번 호출로 3개를 만들고 재작성 목록끼리 먼저 합침)는 사후 분석을 보고 다음 변형으로 정한다
- 결합: 원 질의의 세 목록(dense, BM25, 조건 목록)은 그대로 두고, 재작성 질의로 만든 dense·BM25 목록 두 개를 RRF에 더한다(가중치 1). 조건과 최다 일치 필터는 원 질의 기준이다. 재작성하지 않은 질의는 EXP-011과 같은 순위다
- 출력 형식 처리: 사고 과정 태그를 떼고, 한 줄만 쓴다. 비거나 `max_chars`(300)를 넘으면 재작성 없이 원 질의만 쓴다
- 재작성 결과는 파일로 남겨 다시 쓰되, 파일에 만든 기준(모델, 경로, 사고 과정 설정, 지시 버전·SHA-256, 판단 규칙 값)을 함께 적고 읽을 때 지금 config와 대조해 다르면 멈춘다(meet-rag "구현 원칙")
- 재작성 질의 임베딩: 로컬 CPU(snowflake-ko, 질의 접두 `query: `)
- 순위 파일 `snowflake-ko-fixed-512-64-hybrid-cond-filter-law-ms256-rw-{층}.csv`

## 판정 기준 (실행 전 확정)
H8은 [메타데이터] 가설이 아니므로 SPEC 판정 절을 그대로 옮긴다. 비교 기준은 EXP-011이다(위 "기준 실험"의 변경 조건을 따른다).

- dev-full Recall@5 차이를 회의 단위 paired bootstrap(10,000회, seed 20260929)으로 계산한다
- 채택: 95% 구간 하한 > 0 이고 점 추정 ≥ +1.0%p
- 기각: 95% 구간 상한 < 0
- 보류: 그 밖. 보류일 때 예외 채택은 D-28의 범위를 따른다
- multi-doc은 관찰로 보고 판정에 쓰지 않는다(SPEC 보조 관찰)

## 단계
1. dev-small 작동 확인(dev 질의 1,039개): 재작성 대상 비율, 재작성 출력 형식(빈 응답, 태그, 길이, 다른 언어, 뜻 바뀜), 결합 뒤 순위 동작. Google 경로로도 10개를 호출해 지연·출력 형식을 비교한다
2. 구멍 막기: 1에서 나온 출력 형식 문제만 형식 처리 규칙으로 막고, 바꾼 내용과 이유를 이 문서에 적는다. 판단 신호·임계값·지시의 뜻은 dev-small 점수를 보고 바꾸지 않는다
3. dev-full 판정: dev-full 3,016개와 multi-doc 600개. 실행 전에 호출 수·비용·시간을 보고하고 승인받는다

## 분석 (판정과 관계없이)
- 사후 실패 분석(규칙 고정 뒤): 기준이 놓친 질의 중 판단 규칙이 재작성 대상으로 잡은 비율, 재작성으로 살아난 질의와 오히려 밀린 질의, 단계별 순위(`Retriever.explain`)로 본 실패 유형. 이 분석은 이번 규칙의 근거가 아니라 다음 변형의 근거로 쓴다
- 요소별 기여: 순위가 바뀐 질의마다 원 질의 목록과 재작성 목록 중 어느 쪽이 정답 문서를 올렸는지
- 운영: 질의당 지연(재작성 대상만 재작성 호출 지연이 붙음, Google 경로 실측), 콜드 스타트 변화, 무료 쿼터 RPD(14.4K) 대비 하루 처리 가능 질의 수. D-30(질의당 3초)과 비교한다
