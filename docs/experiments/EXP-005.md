# EXP-005: Jev로 상위 후보 재정렬 (H2)

## 가설
- EXP-004의 dev-full Recall@10(0.9450)이 Recall@5(0.9164)보다 2.9%p 높아, 상위 후보 안에 정답이 있지만 5위 밖에 있는 질의가 있다. 질의와 후보를 함께 읽는 판단 모델이 RRF 순서보다 정답을 위로 올려 single-doc Recall@5가 오른다
- 시험 호출(dev-small 50개)에서는 Jev 순서가 RRF보다 1위 정답이 적었다(hit@1 0.94 → 0.88). dev-small은 RRF가 거의 맞히는 층이고 50개라 판정 근거가 아니며, 방향은 모른다

## 기준 실험
- EXP-004 (hybrid + 조건 목록 + 최다 일치 필터). D-24
- 기준 순위: single-doc `data/runs/kure-v1-fixed-512-64-hybrid-cond-filter-dev-full.csv`(SHA-256 `0a64961758eed7a78162e989c5f44d64d3a69453a5f9fd4f9ccf024908e375d2`), multi-doc `…-hybrid-cond-filter-multidoc.csv`(SHA-256 `bf4b8968ee63b859524138aa7c6040a7cfcc66251785f2f8155d1a42a662e5f4`)
- 백로그 H2의 첫 EXP다(SPEC 가설 단위 중단의 셈에 넣지 않는다)

## 바꾸는 것
- 재정렬 모델: Jev(`typesafe/jev-1.13`, OpenRouter Decisions API). `jev-latest` 별칭은 쓰지 않는다
- 재정렬 대상: EXP-004의 RRF 순서(필터 적용 전) 상위 20개 문서. 21위 아래는 RRF 순서를 유지한다
- 문서 입력: 문서마다 질의와 dense 점수가 가장 높은 청크 하나(KURE-v1 토큰 512개, 인덱스의 `chunks.jsonl`)
- 요청: 질의 하나에 후보 20개를 묶어 한 요청을 보낸다. `state`에 질의와 후보(번호 0\~19)를 두고, 후보마다 `score` 질문 하나를 붙인다. 질문은 "후보 i: 이 후보 문서는 질의에 얼마나 답하는가?", 등급은 한국어 5단계(`configs/exp/exp005.yaml`)다. 응답의 `score`(등급별 확률로 가중한 위치, 0\~4)를 점수로 쓴다
- 순서: 상위 20개를 Jev 점수 내림차순으로 바꾸고(같으면 RRF 순서) EXP-004 필터(최다 일치 문서를 앞으로)를 적용한 뒤 상위 10개를 쓴다
- 응답은 요청 본문 해시로 저장해, 다시 실행할 때 같은 점수를 쓴다. 같은 요청을 다시 보내면 점수가 평균 0.04, 최대 0.66 달라졌다(시험 호출 10개 질의)
- 순위 파일 이름 `…-hybrid-cond-filter-rerank-{층}.csv`(`retriever.run_name`)
- 파라미터(모델, 깊이 20, 청크 입력, 등급 문구)는 위 값으로 고정하고 dev-full 결과를 보고 조정하지 않는다

### 설계를 정한 경위
- 처음 초안은 `nlpai-lab/KURE-Reranker-nano`(149M, cross-encoder)를 Colab L4로 채점하는 안이었다. 로컬 CPU를 HF Spaces 무료 CPU와 같은 2스레드로 묶어 dev-small 질의 20개(질의당 20쌍, 쌍 중앙값 566토큰)를 재정렬하니 질의당 평균 37.1초, p95 41.2초였다. 사용자가 배포에서 받아들일 수 없는 지연으로 보고 실행하지 않았다(`rag.rerank +exp=exp005 retriever.rerank.backend=cross-encoder retriever.rerank.mode=latency retriever.rerank.threads=2 retriever.rerank.latency.n_queries=20`)
- Jev 리랭커는 사용자가 LambdaDB의 Jev 재정렬 사례(https://lambdadb.ai/blog/native-reranking-with-jev)를 참조해 제안했다. dev 질의를 OpenRouter로 보내는 것은 사용자 승인(2026-10-12)이다
- 시험 호출(`notebooks/15_01_EXP005_Jev시험.ipynb`, dev-small 질의 50개, 비용 합 약 $0.12)에서 요청 단위를 정했다. 질의당 한 요청에 묶으면 공유 `state`가 한 번만 과금돼 질의당 약 1만 6천 토큰, $0.00067, 지연 p50 0.51초, p95 0.74초였다. 쌍마다 요청하면 토큰이 약 1.4배, 지연 p95 2.29초였고 후보 안 정답 순위도 낮았다(hit@1 0.72). 지시문과 등급만 영어로 바꾼 조건은 한국어와 차이가 없었다
- 번역: Jev가 한국어에 약하다는 평이 있어 영어 번역을 검토했다. 질의 시점에 후보를 번역하면 Jev의 지연 이점이 사라지고, 코퍼스를 미리 번역하는 것은 비용과 관리 부담이 커 하지 않는다(사용자 결정 2026-10-12)

## 판정 기준 (실행 전 확정)
H2는 [메타데이터] 가설이 아니므로 SPEC 판정 절을 그대로 옮긴다. 비교 기준은 EXP-004다.

- dev-full Recall@5 차이를 회의 단위 paired bootstrap(10,000회, seed 20260929)으로 계산한다
- 채택: 95% 구간 하한 > 0 이고 점 추정 ≥ +1.0%p
- 기각: 95% 구간 상한 < 0
- 보류: 그 밖
- multi-doc은 관찰로 보고 판정에 쓰지 않는다(SPEC 보조 관찰). 기각이면 multi-doc은 실행하지 않는다(사용자 결정 2026-10-12)
- 단서(SPEC): 질의가 정답 문서를 보고 생성돼 어휘가 겹친다. 판단 모델도 어휘 겹침의 이득을 볼 수 있다

## 실행
- 후보 쌍: `uv run python -m rag.search +exp=exp005 index.scope=full search.mode=rerank-pairs`
- 채점: `uv run python -m rag.rerank +exp=exp005 index.scope=full` (지연·비용 `data/rerank/latency-summary_q-full-jev.json`)
- 순위·판정: `uv run python -m rag.search +exp=exp005 index.scope=full` → `uv run python -m rag.eval.compare --base data/runs/kure-v1-fixed-512-64-hybrid-cond-filter-dev-full.csv --cand data/runs/kure-v1-fixed-512-64-hybrid-cond-filter-rerank-dev-full.csv`
