# ML 프로젝트 문서 작성 원칙

Sep 29, 2026 · @ingyoung

## 문서 체계

ML·DL 모델 개발 프로젝트에서 코딩 에이전트에게 일을 맡길 때 쓰는 문서의 작성 원칙이다.&#32;

### 작업을 두 종류로 나눈다

| 구분 | 예 | 완료의 의미 | 쓰는 문서 |
| --- | --- | --- | --- |
| 파이프라인 작업 | 데이터 로더, 학습 루프, 평가 코드, 추론·제출 | 명세대로 동작한다 (결정적) | SLICE |
| 실험 작업 | 모델 구조, 증강, 손실 함수, 하이퍼파라미터 | 가설을 판정했다 (채택·기각·보류) | EXP |

파이프라인 작업은 일반 소프트웨어와 같아서 SLICE를 그대로 쓴다. 실험 작업은 결과를 미리 알 수 없고, 목표치에 못 미쳐도 가설에 대한 답을 얻으면 끝난 것이다. 이 차이 때문에 실험에는 별도의 EXP 문서를 쓴다.

### 문서별 역할

| 문서 | 답하는 질문 | 작성 시점 | 갱신 방식 |
| --- | --- | --- | --- |
| CLAUDE.md | 이 저장소에서 무엇을 건드리면 안 되고 어떻게 실행하는가 | 프로젝트 시작 | 규칙이 생길 때 추가 |
| SPEC.md | 무엇으로 성공을 판정하는가 | 실험 시작 전 1회 | 평가 프로토콜은 원칙적으로 고정 |
| PLAN.md | 베이스라인을 어떻게 세우고, 다음에 무엇을 시험하는가 | SPEC 승인 후 | 실험 결과마다 백로그 조정 |
| slices/NN.md | 이번 파이프라인 조각을 무엇으로 완료라 하는가 | 조각 착수 직전 | 진행 기록 갱신 |
| experiments/EXP-NNN.md | 이번 실험은 무엇을 바꾸고 무엇으로 판정하는가 | 실험 실행 직전 | 결과·결론 기록 후 고정 |
| EXPERIMENTS.md | 지금까지 실험 결과는 어땠나 | 실험 판정 때마다 | 한 줄씩 누적 |
| STATUS.md | 지금 무엇이 돌고 있고 다음에 무엇을 하는가 | 매 세션 종료 | 덮어씀 |
| DECISIONS.md | 무엇을 채택했고 근거 실험은 무엇인가 | 채택 결정 때 | 누적 |

- CLAUDE.md에 관련 문서의 위치를 적어 라우팅한다.
- 실험 문서 번호와 config 파일 이름을 맞춘다. 문서와 실행 설정이 일대일로 대응해야 결과를 재현할 수 있다.

### 공통 원칙

- 한 정보는 한 곳에만 둔다. 실험 결과 수치는 EXP 문서와 EXPERIMENTS.md(또는 추적 도구)에만 둔다.
- 평가 기준은 실험 전에 고정한다. 결과를 본 뒤 기준을 바꾸면 실험끼리 비교할 수 없다.
- 수치는 실행한 명령·config와 함께 적는다. 근거 없는 수치는 다음 세션이 검증할 수 없다.

## CLAUDE.md

Claude Code가 매 세션 자동으로 읽는 지침 파일이다. 일반 원칙(짧게, 모든 작업에 해당하는 것만, 다른 문서는 위치만)은 같고, ML 프로젝트에서는 평가와 데이터를 보호하는 규칙이 가장 중요한 항목이다.

### 원칙

- 평가 코드, 검증 분할, 테스트 데이터를 수정·접근 금지 대상으로 명시한다. 에이전트는 점수를 올리라는 지시를 받으면 평가 쪽을 바꾸는 것으로 목표를 달성할 수 있다. 이 규칙이 없으면 실험 결과를 믿을 수 없다.
- 문장 규칙만으로 불안한 경로는 훅으로 수정 자체를 차단한다. CLAUDE.md 규칙은 모델이 따르는 권고이고, 훅은 실행 단계에서 강제된다.
- 실험 조건은 config로만 바꾸게 한다. 코드에 하이퍼파라미터를 직접 쓰면 EXP 문서와 실행 조건이 어긋난다.
- 학습·평가·빠른 확인(작은 데이터로 한 epoch) 명령을 넣는다. 빠른 확인 명령이 있어야 에이전트가 긴 학습 전에 코드 오류를 잡는다.
- 긴 학습 작업을 에이전트가 직접 실행해도 되는지 적는다. 연산 비용이 걸린 결정이므로 기본값을 정해둔다.

### 템플릿

```markdown
# 프로젝트명

## 명령
- 빠른 확인: `uv run python train.py +exp=exp001 debug=true` (데이터 1%, 1 epoch)
- 학습: `uv run python train.py +exp=expNNN`
- 평가: `uv run python evaluate.py run_dir=outputs/expNNN`
- 테스트: `uv run pytest -q`

## 금지
- `src/eval/`, `data/splits/` 수정 금지
- `data/test/` 읽기 금지
- 하이퍼파라미터를 코드에 직접 쓰지 않는다. `configs/exp/`로만 바꾼다
- 전체 학습 실행은 사용자 승인 후에만 한다. 빠른 확인은 자유롭게 실행한다

## 문서
- 성공 기준·평가 프로토콜: docs/SPEC.md
- 베이스라인 조각·실험 백로그: docs/PLAN.md
- 실험 지시서: docs/experiments/EXP-NNN.md (config는 configs/exp/expNNN.yaml)
- 실험 결과 요약: docs/EXPERIMENTS.md
- 세션 종료 전 docs/STATUS.md를 덮어써서 갱신한다 (한 화면 이내)
```

## SPEC.md

풀 문제, 성공을 판정하는 방법, 실험에 쓸 수 있는 자원을 적은 문서다. 일반 SPEC이 "무엇을 만드는가"를 고정한다면, ML SPEC은 "무엇으로 성공을 판정하는가"를 고정한다.

### 작성 방법: 인터뷰

1. 과제를 몇 줄로 설명하고 데이터 위치를 알려준다.
2. 에이전트에게 질문하게 한다. 평가 방식, 데이터 누수 가능성, 연산 예산처럼 나중에 바꾸기 어려운 것을 우선 묻게 한다.
3. 인터뷰가 끝나면 SPEC.md를 쓰게 하고, 사람이 승인한다.

### 원칙

- 평가 프로토콜을 가장 먼저, 가장 구체적으로 쓴다. 검증 분할 방식, fold 수, seed, 지표 계산 방법이 해당한다. 일반 소프트웨어의 테스트에 해당하는 항목이며, 이게 흔들리면 모든 실험 결과를 서로 비교할 수 없다.
- 평가 프로토콜은 실험 시작 후 원칙적으로 바꾸지 않는다. 바꿔야 한다면(누수 발견 등) DECISIONS.md에 기록하고, 이전 실험 결과는 비교 대상에서 뺀다.
- 누수 방지 규칙을 명시한다. 같은 대상(환자, 사용자, 문서)이 학습·검증에 나뉘어 들어가지 않게 하는 group 기준, 시간 순서가 있는 데이터의 분할 방향 같은 것이다.
- 목표치와 함께 중단 기준을 쓴다. 목표치만 있으면 실험이 끝나지 않는다. 연산 예산이나 "개선 없음이 N회 연속" 같은 기준을 둔다.
- 모르는 것은 미결 사항에 적는다. 특히 평가 프로토콜 관련 미결 사항이 남아 있으면 실험을 시작하지 않는다.

### 템플릿

```markdown
# SPEC: 잎 병해 분류

## 문제
- 입력: 잎 이미지 / 출력: 4개 클래스 확률 (multi-label 아님)

## 평가 프로토콜 (실험 중 고정)
- 지표: 클래스별 ROC-AUC 평균
- 분할: StratifiedGroupKFold 5 fold, seed 42, 분할 파일 data/splits/folds.csv
- 보고 값: 5 fold OOF 점수와 fold별 점수

## 누수 방지
- 같은 식물 개체의 이미지는 같은 fold에 둔다 (group: plant_id)

## 자원 제약
- GPU: 단일 24GB / 실험 1회당 학습 3시간 이하
- 외부 데이터: 사용하지 않는다

## 성공·중단 기준
- 목표: OOF AUC 0.97 이상
- 중단: 백로그 소진 또는 개선 폭 0.001 미만이 3회 연속

## 범위 밖
- 앙상블은 단일 모델이 0.96을 넘은 뒤 검토

## 미결 사항
- 중복 이미지 처리 방식
```

## PLAN.md

베이스라인을 세우는 조각 목록과, 그 뒤에 시험할 가설 목록(실험 백로그)을 관리하는 문서다. 앞부분은 순서가 정해진 계획이고, 뒷부분은 결과에 따라 계속 바뀌는 우선순위 목록이다.

### 베이스라인 부분

가장 단순한 모델로 데이터 → 학습 → 평가 → 추론(제출)을 한 번 관통시키는 것이 첫 목표다. vertical slice를 ML에 적용한 형태다. 파이프라인 끝까지 연결되어야 이후 실험 결과를 같은 평가로 비교할 수 있고, 평가 코드의 오류도 이 단계에서 드러난다.

- 조각마다 목표와 의존 관계를 한두 줄로 쓰고, 상세는 slices/ 파일로 넘긴다 (일반 PLAN과 같다).
- 베이스라인 점수가 나오기 전에는 실험 백로그를 실행하지 않는다.
- 베이스라인은 성능보다 재현성을 우선한다. 같은 명령을 두 번 돌려 같은 점수(또는 seed 범위 안의 차이)가 나오는지 확인하는 것을 완료 기준에 넣는다.

### 실험 백로그 부분

- 가설마다 한 줄로 쓴다: 무엇을 바꾸나, 예상 효과, 비용(학습 시간), 상태.
- 상태는 대기 / 진행 / 채택 / 기각 / 보류 중 하나이고, 진행 이후에는 EXP 번호를 붙인다.
- 순서는 예상 효과 대비 비용이 큰 것부터 둔다. 실험 결과가 나올 때마다 다시 정렬한다. 앞 실험 결과가 뒤 가설의 가치를 바꾸는 것이 정상이다.
- 결과 수치는 여기 적지 않는다. EXPERIMENTS.md를 참조한다.

### 템플릿

```markdown
# PLAN: 잎 병해 분류 (SPEC.md 기준)

## 베이스라인
- [x] S1 데이터 로더 + fold 분할 파일 생성 → slices/01-data.md
- [x] S2 학습 루프 + OOF 평가 (resnet18, 224px) → slices/02-train-eval.md
- [ ] S3 추론·제출 파일 생성 (S2 필요) → slices/03-inference.md

## 실험 백로그
- [채택] H1 백본 resnet18 → efficientnet_b3 (효과 큼 / 학습 2배) → EXP-001
- [진행] H2 해상도 224 → 384 (효과 중 / 학습 2.5배) → EXP-002
- [대기] H3 label smoothing 0.1 (효과 소 / 비용 없음)
- [보류] H4 pseudo label (단일 모델 0.96 이후)
```

## SLICE 문서 (slices/NN-이름.md)

파이프라인 조각 하나를 에이전트가 그 문서만 받아 구현하고 검증할 수 있게 구체화한 지시서다. 일반 소프트웨어의 SLICE와 같고, ML 파이프라인에 필요한 완료 기준만 보강한다.

### 원칙

- 해당 조각 착수 직전에 쓰고, 조각마다 파일을 하나 둔다.
- 완료 기준은 명령과 기대 결과로 쓴다. ML 파이프라인에서는 다음을 기준에 자주 넣는다.
  - 빠른 확인 모드(작은 데이터, 1 epoch)로 끝까지 실행된다
  - 출력 shape, 값 범위(확률이면 0\~1, 합이 1)가 맞다
  - 같은 seed로 두 번 실행한 결과가 같다
  - 작은 배치 하나를 과적합시킬 수 있다 (학습 루프가 실제로 학습하는지 확인)
- 성능 수치를 완료 기준으로 쓰지 않는다. 파이프라인 조각의 목적은 동작이고, 성능은 EXP가 다룬다.
- 수정 허용 파일과 범위 밖 항목을 명시한다. 특히 평가 코드 조각을 만든 뒤에는 다른 조각의 범위 밖에 평가 코드를 넣는다.

### 템플릿

```markdown
# SLICE 02: 학습 루프 + OOF 평가

## 대응 PLAN
- 베이스라인 S2

## 완료 기준
- `uv run python train.py +exp=baseline debug=true`가 5 fold 모두 끝까지 실행된다
- outputs/baseline/oof.csv의 확률 값이 0~1이고 행 합이 1이다
- 배치 하나(16장)를 200 step 학습하면 loss가 0.05 미만으로 내려간다
- 같은 명령을 두 번 실행한 OOF 점수가 소수점 넷째 자리까지 같다

## 수정 허용 파일
- src/train.py, src/models/, configs/exp/baseline.yaml, tests/test_train.py

## 범위 밖
- 추론·제출 (S3), 백본 교체 (EXP)

## 진행 기록
- 5 fold 루프 완료. 재현성 확인 중 (dataloader worker seed 미설정 의심)
```

## EXP 문서 (experiments/EXP-NNN.md)

실험 하나의 가설, 기준 실험과의 차이, 판정 기준, 결과를 적은 지시서이자 기록이다. SLICE의 완료 기준이 "동작한다"라면, EXP의 완료 기준은 "실행했고, 기록했고, 판정했다"이다. 목표 지표에 못 미쳐도 가설이 기각되었다는 답을 얻으면 완료다.

### 작성 방법

1. PLAN 백로그에서 다음 가설을 고른다.
2. 에이전트에게 SPEC.md, 기준 실험 문서, DECISIONS.md를 읽히고 EXP 초안과 config를 만들게 한다.
3. 사람이 가설, 바꾸는 것, 판정 기준을 확인하고 승인한다. 판정 기준은 실행 전에 확정한다.
4. 실행 후 결과와 결론을 채우고, 이후에는 문서를 고치지 않는다.

### 원칙

- 판정 기준을 실행 전에 쓴다. 결과를 본 뒤 기준을 정하면 어떤 결과든 채택할 이유를 찾게 된다.
- 판정 기준에는 seed 변동을 고려한 최소 개선 폭을 넣는다. 같은 설정도 seed에 따라 점수가 흔들리므로, 그보다 작은 차이는 개선으로 보지 않는다. 변동 폭을 모르면 베이스라인을 seed만 바꿔 몇 번 돌려 확인한다.
- 기준 실험을 하나 명시하고, 그 실험과의 차이를 "바꾸는 것"에 모두 적는다. 변수 하나일 필요는 없다. 시간 제약으로 여러 변경을 묶어 돌리는 것도 정당한 선택이며, 그 경우 묶은 목록을 적는다. 목적은 결과를 해석할 수 있게 하는 것이다.
- 실행 조건은 config 파일로 고정하고 경로를 적는다. 문서와 config 번호를 맞춘다.
- 에이전트에게 "바꾸는 것" 외의 변경을 금지한다. 점수가 기대보다 낮을 때 에이전트가 다른 설정을 함께 조정하는 것을 막는다. 추가로 시험할 것이 떠오르면 백로그에 새 가설로 올린다.
- 결과에는 fold별 점수, 평균, 학습 시간, 실행 명령, 코드 커밋을 적는다.
- 결론은 채택 / 기각 / 보류 중 하나와 이유 한두 줄로 쓴다. 보류는 결과가 판정 기준 근처라 판단할 수 없을 때 쓰고, 필요한 추가 확인을 적는다.

### 템플릿

```markdown
# EXP-003: label smoothing

## 가설
- label smoothing 0.1이 과신을 줄여 OOF AUC를 높인다

## 기준 실험
- EXP-002 (efficientnet_b3, 384px)

## 바꾸는 것
- loss.smoothing: 0 → 0.1

## 고정 조건
- SPEC 평가 프로토콜 / seed 42 / config: configs/exp/exp003.yaml

## 판정 기준 (실행 전 확정)
- OOF AUC가 EXP-002 대비 +0.002 이상이면 채택 (seed 변동 폭 ±0.001 기준)
- -0.002 이하면 기각, 그 사이면 보류

## 실행
- `uv run python train.py +exp=exp003`

## 결과
- fold: 0.9612 / 0.9588 / 0.9631 / 0.9597 / 0.9605
- OOF: 0.9606 (EXP-002: 0.9579, +0.0027) / 학습 2시간 40분 / 커밋 a1b2c3d

## 결론
- 채택. 개선 폭 +0.0027이 판정 기준 +0.002를 넘는다
```

## EXPERIMENTS.md

모든 실험의 결과를 한 줄씩 모은 요약표다. 실험 이력은 계속 쌓이는 정보라 STATUS.md에 두지 않고 여기에 둔다. 에이전트가 다음 가설을 제안하거나 기준 실험을 고를 때 전체 흐름을 한눈에 보게 하는 용도다.

### 원칙

- 한 실험에 한 줄: 실험 번호, 기준 실험, 바꾼 것, 주 지표, 기준 대비 차이, 판정.
- 상세(fold별 점수, 실행 명령)는 EXP 문서에만 두고 여기서는 반복하지 않는다.
- 최신 실험을 위에 둔다.
- 평가 프로토콜이 바뀌면 표를 나누고 경계에 그 사실을 적는다. 프로토콜이 다른 점수는 한 표에서 비교하지 않는다.
- W&B, MLflow 같은 추적 도구를 쓰면 수치는 도구가 원본이다. 이 파일에는 판정과 도구 링크(run ID)만 남긴다.

### 템플릿

```markdown
# EXPERIMENTS (평가 프로토콜 v1: SPEC 기준)

| EXP | 기준 | 바꾼 것 | OOF AUC | 차이 | 판정 |
| --- | --- | --- | --- | --- | --- |
| 003 | 002 | label smoothing 0.1 | 0.9606 | +0.0027 | 채택 |
| 002 | 001 | 해상도 224 → 384 | 0.9579 | +0.0061 | 채택 |
| 001 | base | resnet18 → efficientnet_b3 | 0.9518 | +0.0142 | 채택 |
| base | - | 베이스라인 (resnet18, 224px) | 0.9376 | - | - |
```

## STATUS.md

새 세션이 이 파일과 저장소만 읽고 작업을 이어가게 하는 스냅샷이다. 일반 원칙(덮어쓰기, 이력은 다른 곳에, 코드와 git에 남지 않는 것을 적는다)은 같다. ML 프로젝트에서는 저장소 밖에서 진행 중인 상태가 많아 그 항목을 추가한다.

### 원칙

- 세션마다 덮어쓴다. "지금까지 한 실험" 절을 두지 않는다. 그 정보는 EXPERIMENTS.md에 있다.
- 실행 중인 학습 작업을 적는다: 실험 번호, 실행 위치(서버, tmux 세션, 작업 ID), 시작 시각과 예상 종료, 로그 경로. 코드와 git 어디에도 남지 않는 정보라 적지 않으면 다음 세션이 알 수 없다.
- 체크포인트와 출력 경로를 적는다. 중단된 학습이 있으면 재개 명령을 적는다.
- 판정 대기 중인 실험을 적는다. 학습은 끝났지만 EXP 문서에 결과·결론을 아직 쓰지 않은 실험이 해당한다.
- 시도했다 버린 것은 코드 수준의 시도만 적는다(예: 특정 라이브러리 버전 충돌). 가설 수준의 기각은 EXP 문서와 EXPERIMENTS.md가 기록한다.
- 다음 행동은 바로 착수할 수 있는 첫 단계로 쓴다.

### 템플릿

```markdown
# STATUS (세션 종료 시 덮어씀)

## 현재 위치
- EXP-004 (mixup) 학습 중 / 다음 백로그: H5

## 다음 행동
```

## DECISIONS.md

채택한 설정과 프로젝트 방향 결정을 근거와 함께 쌓아두는 문서다. ML 프로젝트에서는 이 문서가 "현재 기준 설정"을 정의한다. 다음 실험의 기준 실험을 고를 때 여기를 본다.

### 원칙

- 두 종류를 적는다. 실험으로 채택된 설정(근거 EXP 번호 필수)과, 실험 없이 정한 방향 결정(평가 프로토콜 변경, 외부 데이터 허용 여부 등)이다.
- 실험 채택 결정에는 근거 EXP 번호만 적고 수치는 반복하지 않는다.
- 평가 프로토콜을 바꾼 결정은 반드시 여기에 적고, 이전 실험과 비교할 수 없게 되었다는 점을 함께 적는다.
- 누적하되 기존 항목을 고쳐 쓰지 않는다. 결정이 바뀌면 새 항목을 추가하고 이전 항목에 대체 표시만 한다.
- 맨 위에 현재 기준 설정 한 줄을 둔다. 새 실험은 이 설정을 기준으로 한다.

### 템플릿

```markdown
# DECISIONS

현재 기준 설정: configs/exp/exp003.yaml (D-01, D-02, D-03 반영)

## D-03 label smoothing 0.1 채택
- 근거: EXP-003

## D-02 백본 efficientnet_b3, 입력 해상도 384 채택
- 근거: EXP-001, EXP-002 / 학습 시간 증가를 감수

## D-01 평가 분할에 plant_id group 적용
- 이유: 같은 개체가 학습·검증에 섞이는 누수 발견
- 영향: 이전 분할로 낸 점수는 비교 대상에서 제외
- 날짜: 2026-09-20
```

## 작업 사이클

SPEC과 베이스라인은 한 번 세우고, 그 뒤로는 가설마다 EXP 작성, 실행, 판정, 기록을 반복한다. 중단 기준은 SPEC에서 정한 것을 쓴다.

실험 중 파이프라인을 고쳐야 하면(새 증강 모듈 추가 등) 그 작업은 SLICE로 따로 만들고, 완료된 뒤 EXP에서 그 모듈을 켜는 실험을 돌린다. 코드 작업과 가설 판정을 한 문서에 섞지 않기 위해서다.

### 세션 마무리 절차

CLAUDE.md에 적어두고 세션을 끝내기 전에 에이전트가 수행하게 한다.

1. 끝난 학습이 있으면 평가하고 EXP 문서의 결과·결론을 채운다.
2. 판정한 실험을 EXPERIMENTS.md에 한 줄 추가하고, 채택이면 DECISIONS.md를 갱신한다.
3. PLAN.md 백로그의 상태를 갱신하고 우선순위를 다시 정한다.
4. 커밋할 수 있는 상태면 커밋한다.
5. STATUS.md를 덮어쓴다. 실행 중 작업이 있으면 위치와 예상 종료 시각을 반드시 적는다.
