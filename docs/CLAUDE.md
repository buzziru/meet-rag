# docs 기록 규약

`docs/`는 프로젝트의 결정·실험·조각 기록이다. 이후 세션은 이 기록을 현재 규칙과 근거로 읽으므로, 뒤 결정이나 PR이 앞 기록을 바꿨는데 앞 기록에 표시가 없으면 바뀐 규칙을 놓친다(ADR-0071). 감사는 protocol-guard P12가 한다.

이 저장소의 문서 규약은 이 파일이 정한다. `docs/ML 프로젝트 문서 작성 원칙.md`는 일반 원칙이고, 이 파일과 다르면 이 파일을 따른다(사용자 결정 2026-10-28, ADR-0074).

## 문서 종류와 고치는 방식

| 방식 | 문서 | 고치는 법 |
| --- | --- | --- |
| 진행 문서 | `STATUS.md`, `PLAN.md` | 지금 상태로 고친다. 지난 내용은 지우거나(STATUS) `PLAN-done.md`로 옮긴다(PLAN). `이후 변경` 표시는 쓰지 않는다 |
| 현재 규칙 문서 | `SPEC.md`, `data.md`, `gen-eval-criteria.md`, `harness/adr/README.md`의 머리 문단 | 그 자리에서 고치고, 고친 곳에 근거(결정 번호, 실측, ADR)를 괄호로 단다 |
| 누적 기록 | `DECISIONS.md`, `EXPERIMENTS.md`, `PLAN-done.md`, `harness/adr/NNNN.md`와 README 목록 표 | 덧붙이기만 한다. 앞 줄에는 아래 표시만 붙인다. 예외는 DECISIONS 머리 줄 "현재 기준 설정"과 ADR 상태(파일의 상태 줄, 목록 표의 상태 칸)로, 지금에 맞게 고친다 |
| 조각·실험 문서 | `slices/`, `experiments/` | 조각·실험을 끝낸 PR(SLICE는 구현, EXP는 결과·결론)이 병합되기 전에는 고친다. 병합 뒤에는 당시 기록이다 |
| 스냅샷 | `reviews/`, `research/`, `search-stage-summary.md`, 옮긴 뒤의 `drafts/` | 쓴 PR이 병합된 뒤에는 당시 기록이다 |

ADR README를 머리 문단(현재 규칙)과 목록 표(누적 기록)로 나눈 것은 사용자 결정이다(2026-10-29, 이슈 #182).

## 당시 기록

끝낸 PR이 병합된 조각·실험 문서(지시서 본문 포함. 결과 절이 없는 S1\~S12도 같다), 결정의 근거, 누적 기록, 병합된 스냅샷은 그때의 실행과 판단을 적은 기록이라 문장을 고치지 않는다. 고치면 원래 지시·판단이 git 이력으로만 남아, 문서를 읽는 세션은 무엇이 언제 바뀌었는지 모른다. 지금 동작과 달라졌으면 줄 끝에 `이후 변경: 무엇을, 어디서(PR·결정 번호), 지금은 어떤지`를 한 문장 붙인다. 바꾼 쪽 PR이 붙인다. 사실이 틀렸던 것(조사 오류 등)은 `정정: 무엇을, 근거`를 붙인다.

- 예: S25 문서의 "report는 같은 칸에 센다" 끝에 "이후 변경: PR #158(81789e1)부터 report는 진술 없음을 형식 오류와 따로 센다"
- 예: 뒤 조각이 S6 지시서의 규칙을 바꾸면 S6 해당 줄은 그대로 두고 끝에 `이후 변경: S12(PR #NN)부터 …`를 붙인다. S6은 문장을 직접 고쳐(7471ff3) 원래 지시가 git으로만 보인다

## DECISIONS.md

- 새 결정에는 결정(누가 언제 정했는지), 이유, 바뀌는 것, 감수하는 것, 날짜를 적는다. 바뀌는 것에는 앞 결정 번호와 그 안의 결정 번호를 적고, 없으면 "없음"이라고 적는다
- 바뀌는 앞 결정은 같은 커밋에서 해당 줄 끝에 표시를 붙인다. 원문은 고치지 않는다
  - 값·규칙이 바뀜: `이후 변경: 무엇이 어떻게(D-새번호)`
  - 기준 설정이 다음 결정으로 넘어감: `대체: D-새번호`
  - 남은 일이 끝남: `→ D-새번호`
  - 규칙이 더해짐(값은 그대로): `보강: D-새번호`
  - 아직 구현 전이면 시점을 붙인다: `이후 변경(D-58, 리뷰 수정 SLICE 구현 뒤): …`
- 예전 결정에 새 줄로 단 `변경(D-NN, 날짜): …`(D-01 등)도 표시로 본다
- 기준 설정(검색·생성)을 바꾸는 결정은 머리 줄 "현재 기준 설정"과 별칭 `configs/exp/current.yaml`의 상속 한 줄도 같은 PR에서 고친다. 지금 기준은 이 두 곳에만 둔다(ADR-0076)
- 결정 없이 결정 대상이 바뀌는 경우: config 값, 코드 동작, 명령, 경로가 앞 결정에 적힌 내용을 바꾸면 그 PR에서 새 결정을 쓰거나 앞 결정에 `이후 변경`을 붙인다. 다음 PR로 넘기지 않는다(감사 P12 위반). PR #160이 judge 대기·재시도를 바꿨는데 D-51 "동시 8 근거"는 재시도 2회 전제로 남아 있었다(D-57로 기록)

## PLAN.md, PLAN-done.md

- PLAN에는 진행 중·대기 항목과 지금 "다음 순서"만 둔다. 표시는 조각·게이트 `[ ]`, 가설 `[대기]`, 아이디어 절 `[아이디어]`다
- 항목이 끝나면(완료·채택·예외 채택·기각·닫음·대체) 완료를 처리하는 커밋에서 표시를 `[x]`나 판정(`[채택]` 등)으로 바꾸고, 끝에 `→ slices/NN-이름.md`, `→ EXP-NNN 판정`, `→ D-NN` 중 맞는 것을 붙여 문장 그대로 PLAN-done의 같은 절로 옮긴다. protocol-guard는 PLAN-done만 완료 근거로 읽는다. 세션 마무리 때 옮기면 그 사이 감사가 완료를 보지 못하고, 근거가 PLAN과 PLAN-done 두 곳으로 갈린다(PR #139 리뷰, ADR-0057)
- "다음 순서"를 바꾸면 이전 줄은 문장을 고치지 않고 PLAN-done "지난 다음 순서 기록" 맨 위로 옮긴다
- PLAN 문장이 지난 상태로 남았으면(이미 끝난 선행 조건 등) 지금에 맞게 고친다. 진행 문서라 `이후 변경`을 붙이지 않는다
- 결과 수치는 적지 않고 EXPERIMENTS·EXP 문서를 가리킨다

## STATUS.md

핸드오프 때 덮어쓰는 스냅샷이다(한 화면 이내). 커밋 절차는 `.claude/rules/git.md` 핸드오프 절이다.

- 절: 현재 위치, 실행 중 작업, 판정 대기, 리뷰 대기 PR, 다음 행동, 사용자 확인 필요. 해당 없으면 "없음"
- 실행 중 작업: Colab 작업은 위치와 예상 종료 시각, 작업자 풀은 남은 수와 재개 절차(`.claude/skills/meet-rag/references/worker-pool.md`)
- 다음 행동: 항목 앞에 `meet-rag` 흐름을 `[A]`·`[B]`·`[C]`·`[D]`·`[F]`로 적고, 바로 착수할 첫 단계로 쓴다
- 사용자 확인 필요: 사용자만 정할 수 있는 것만 둔다(`meet-rag` "질문과 해석")
- 이번 세션 결정을 적으려면 결정·ADR 번호와 한 줄만 둔다. 내용은 DECISIONS·ADR이 원본이다

## SLICE 문서 (slices/NN-이름.md)

작성·확인 절차는 `meet-rag` A1이다.

- 지시서 단계 필수 절: 만드는 것, 완료 기준(명령과 기대 결과. 성능 수치는 넣지 않는다), 수정 허용 파일, 범위 밖. 사용자 결정이 걸리면 "결정 사항", 데이터·점수를 보고 정하는 결정이면 "노트북과 결정의 순서"
- 결과 단계: `## 결과 (YYYY-MM-DD)` 첫 줄에 `커밋: 구현 abc1234`, 이어서 검증 결과. 지시서와 다르게 한 것과 리뷰 반영은 그 아래 하위 절로 둔다
- 사용자가 지시서를 확인한 뒤 결정 사항을 바꾸면 그 줄에 처음 지시와 바꾼 이유를 한 문장 남긴다(예: `slices/14b-partial-refusal.md:5`)
- 완료 표시는 문서에 두지 않는다. PLAN-done이 완료 근거다

## EXP 문서 (experiments/EXP-NNN.md), EXPERIMENTS.md

작성·승인·판정 절차는 `meet-rag` B1\~B6이다.

- 필수 절: 가설, 기준 실험, 바꾸는 것, 고정 조건(`config: configs/exp/expNNN.yaml`. 기준 EXP의 config를 직접 상속하고 별칭 `current`는 상속하지 않는다. 별칭을 상속하면 기준이 바뀔 때 이 EXP 설정도 바뀌어 재현되지 않는다), 판정 기준 (실행 전 확정), 실행, 결과, 결론. 사용자 결정이 걸리면 "결정 사항". 같은 백로그 항목의 두 번째 이후 EXP이면 몇 번째 변형인지와 앞 변형들의 판정(SPEC 가설 단위 중단, 첫 EXP는 세지 않는다)
- 판정 기준은 실행 뒤 고치지 않는다. SPEC에서 옮기는 규칙은 `meet-rag` B1이다
- 결과·결론 절과 EXPERIMENTS 한 줄의 형식은 `exp-judgment` 스킬 5절(검색)·6절(생성)이다
- EXPERIMENTS는 한 실험에 한 줄이고, 판정 칸에 결정 번호를 적는다. 평가 프로토콜이 다르면 표를 나눈다(검색 단계, 생성 단계). 새 줄은 표 맨 위(머리줄 바로 아래)에 넣는다

## SPEC.md, drafts/

- SPEC 평가 프로토콜은 사용자 승인 없이 바꾸지 않는다(루트 `CLAUDE.md` 금지 절). 바꿀 때는 `drafts/`에 초안을 두고 결정을 모두 받은 뒤 옮긴다(`meet-rag` "결정과 PR의 순서")
- 고친 곳에 `(D-NN)`을 달고, 개정 사실은 DECISIONS에 결정으로 적는다
- 미결 사항이 정해지면 같은 PR에서 항목 앞에 `(해결, D-NN)`을 붙인다. 일부만 정해졌으면 `(일부 해결, D-NN: 정한 부분)`을 붙인다
- 초안을 옮기면 초안 머리에 `이 초안은 SPEC으로 옮겼다(D-NN, 날짜)`를 한 줄 두고, 이후 당시 기록으로 둔다. 초안을 가리키던 다른 문서의 참조는 옮긴 PR에서 SPEC으로 바꾼다

## data.md, gen-eval-criteria.md

현재 규칙 문서다. 수치·규칙에 출처 표지(data.md `[설명서]`·`[실측]`, criteria `[D-NN]`·`[사용자 S14 n]`)를 붙인다. 설명서와 실측이 어긋나면 실측을 따르고 그 자리에 차이를 적는다. 문서 끝의 점검 결과처럼 날짜가 붙은 절은 당시 기록이다.

## reviews/, research/, search-stage-summary.md

- reviews: 목적, 범위, 기준, 지적 표(심각도), 사용자가 고른 고칠 항목. 지적 ID는 결정 번호(`D-숫자`)와 겹치지 않게 리뷰마다 접두를 둔다(예: `G1-3`). 고치는 진행은 PLAN·PLAN-done에 적고 지적 표에 쓰지 않는다
- research: 머리 문단에 조사일·지시·대조 범위, 근거 표지 `[출처]`·`[해석]`·`[추론]`, "확인하지 못한 것" 절
- search-stage-summary 같은 단계 정리: 만든 날짜와 입력(EXPERIMENTS, 재채점 명령)을 머리에 적는다

## harness/adr/

형식과 상태 표시는 `harness/adr/README.md`다.

## 정합 점검

단계를 마칠 때(생성 단계 test 1회 전, 프로젝트 마무리 전) `DECISIONS.md` 전체를 검토한다. 결정마다 붙이는 표시와 P12 감사는 grep과 작성자의 기억에 기대므로 표현이 다른 충돌을 놓친다. 이 점검이 그것을 거른다.

1. 결정을 번호 범위로 반씩 나눠 읽기 전용 에이전트 둘에 맡긴다. 각자 맡은 결정을 뒤 결정, `configs/`, `src/rag/`, `docs/SPEC.md`, `CLAUDE.md`와 대조한다. test 분할 파일과 `data/`는 열지 않는다
   - 찾을 것: (a) 뒤 결정이 앞 결정의 값·규칙·대상을 바꿨는데 앞 결정에 표시가 없음 (b) 결정의 값·경로·명령·모델 이름이 지금 config·코드와 다름 (c) 같은 대상에 두 결정이 다른 규칙을 말하고 어느 쪽이 현재인지 알 수 없음
   - 찾지 않을 것: 이미 표시가 있는 것, 당시 실행 수치, 문체·오탈자
   - 반환: 줄 번호, 지금 내용, 바뀐 것과 근거(결정 번호·PR·`file:line`), 잘못 읽히는 방식, 붙일 문장 초안, 심각도(높음: 다음 작업이 틀린 규칙을 따를 수 있음, 낮음: 기록 이해에만 영향)
2. 메인이 높음 항목의 근거를 직접 확인하고 사용자에게 보인다. 고칠 범위와 방식은 사용자가 정한다
3. 위 표시 방식으로 붙이고, protocol-auditor로 붙인 문장의 사실(결정 번호, PR, 파일 참조, 붙인 줄의 주제)을 대조한다

2026-10-28 점검은 에이전트 둘에 각 약 4분이 걸렸다.
