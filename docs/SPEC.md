# SPEC: 국회 회의록 RAG

이 SPEC은 검색 단계와 생성 단계의 평가 프로토콜을 고정한다. 생성 단계 평가는 검색 단계 종료 뒤 D-53으로 더했다("생성 단계 평가" 절). 개정은 DECISIONS.md에 기록한다.

## 문제

- 입력: 한국어 자연어 질의 1건
- 출력: 코퍼스 문서 순위 목록 (서로 다른 문서 10개 이상)
- 코퍼스: `data/processed/corpus_context.jsonl`의 고유 `context` 38,516건. 문서 ID는 `doc_id`
- 평가 질의: `data/processed/queries_summary_q.jsonl`의 `query`(= `summary_q`). 질의 ID는 `qid`, 정답은 그 레코드의 `doc_id` 하나

데이터의 성질과 한계는 `docs/data.md`에 있다.

## 평가 프로토콜 (실험 중 고정)

### 분할

- 분할 단위는 회의(`conference_number`)다. 한 회의의 질의는 모두 같은 분할에 들어간다.
- AI Hub의 Training/Validation 구분은 쓰지 않는다. 학습 단계가 없으므로 두 구분은 질의 출처 표시로만 남는다.
- seed 20260929로 회의를 섞은 뒤, 회의구분(`meeting_name`) 비율을 유지하면서 회의를 차례로 배정한다. dev 질의가 3,000건 이상이 되면 멈추고, 이어서 test 질의가 3,000건 이상이 되면 멈춘다. 남은 회의의 질의는 쓰지 않는다.
- `qna_type` 비율은 분할 후 전체 분포와 비교해 기록만 한다.
- 분할 결과는 `data/splits/queries.csv`(`qid`, `conference_number`, `split`)에 저장한다. `data/`는 커밋하지 않으므로 같은 seed로 재생성할 수 있어야 한다. 생성 후 파일 SHA-256을 DECISIONS.md에 적는다.

### 평가 층

| 층 | 코퍼스 | 질의 | 용도 |
| --- | --- | --- | --- |
| dev-small | dev 회의 일부의 전체 문서, 약 1,000건 | 그 문서가 정답인 dev 질의 | 방향을 확인한다. 작업 과정과 결과는 Jupyter 노트북(`notebooks/`)에 남긴다. 판정에 쓰지 않는다 |
| dev-full | 전체 38,516건 | dev 질의 전체 | EXP 채택·기각 판정 |
| test | 전체 38,516건 | test 질의 전체 | 단계(검색·생성)마다 종료 시 1회 보고 |

- dev-small 문서는 dev 회의를 seed 20260929로 섞어 문서 수가 1,000건 이상이 될 때까지 회의 단위로 뽑는다. 문서 목록은 `data/splits/dev_small_docs.txt`에 둔다. 같은 회의 문서를 함께 넣어 회의 내부의 비슷한 문서가 방해 문서로 남게 한다.
- dev-small 점수와 dev-full 점수는 방해 문서 수가 달라 서로 비교하지 않는다. 표를 나눠 적는다.

### 지표

- 문서 순위: 검색기가 청크를 반환하면 각 문서가 처음 나온 순위를 문서 순위로 쓴다.
- 주지표: 문서 단위 Recall@5. 질의별로 정답 문서가 상위 5개 안에 있으면 1, 없으면 0이고, 질의 전체의 평균을 낸다.
- 보조 지표: Recall@1, Recall@10, MRR@10(정답 순위가 10 이내면 1/순위, 아니면 0).
- 모든 지표를 전체와 함께 회의구분별, `qna_type`별로 보고한다.
- 발언이 자기 `context` 안에 없는 169건(`docs/data.md` §7)도 포함한다. 문서 단위 정답은 이 레코드에서도 성립한다.

### 판정

- 기준 실험과의 차이를 dev-full에서 paired bootstrap으로 계산한다. 재표본 단위는 회의, 반복 10,000회, seed 20260929이다. 같은 회의의 질의끼리는 서로 독립이 아니므로 회의 단위로 재표본한다.
- 채택: Recall@5 차이의 95% 구간 하한이 0보다 크고, 점 추정 차이가 +1.0%p 이상
- 기각: 95% 구간 상한이 0보다 작음
- 보류: 그 밖의 경우
- +1.0%p는 사람 판단 없이 채택하는 선이다. 점수의 흔들림(평가 질의 표본)은 95% 구간 하한 > 0 조건이 맡는다. 보류를 예외로 기준에 올릴지는 사용자가 정한다(D-28). +1.0%p 미만이고 구간 하한 > 0인 보류는 D-33의 선례(층별과 multi-doc에서 떨어진 지표 없음, 운영 비용 변화 없음 등)를 참고한다(D-35). 같은 dev-full을 반복해 쓴 대가는 검색 단계 종료 시 test 1회가 확인한다

### 메타데이터 가설의 판정 (D-18)

문서 메타데이터(회의명·위원회·안건·날짜·화자 등)를 검색에 쓰는 가설(PLAN에 [메타데이터]로 표시)은 아래 순서로 판정한다. single-doc 평가 질의(`summary_q`)는 회의를 메타데이터로 지목하는 경우가 드물어(연도·날짜·위원회·이름 중 하나라도 언급 10.4%) 이 가설의 효과를 single-doc으로는 판정하기 어렵기 때문이다.

1. single-doc 판정(위 판정 절)이 채택이면 채택, 기각이면 기각한다
2. 보류이면 multi-doc 질의 세트로 정한다. 재표본 단위는 `pool_id`, 반복 횟수와 seed는 위 판정 절과 같다
   - 채택: Recall@5 차이의 95% 구간 하한이 0보다 크고 점 추정 차이가 +1.0%p 이상이며, Complete@5 차이의 95% 구간 상한이 0 이상
   - 기각: Recall@5 차이의 95% 구간 상한이 0보다 작음
   - 보류: 그 밖의 경우
   - +1.0%p의 해석은 위 판정 절과 같다(D-35). +1.0%p 미만이고 Recall@5 구간 하한 > 0인 보류를 예외로 올릴지는 사용자가 정한다
- 단서: multi-doc 세트는 메타데이터로 묶음을 만들고 질의도 메타데이터로 회의를 지목해, 메타데이터를 쓰는 검색기에 유리하다. multi-doc 세트에는 test가 없어 이 규칙으로 채택한 결정은 검색 단계 종료 시 test로 다시 확인할 수 없다

## 보조 관찰: multi-doc 질의

평가 질의는 정답 문서가 하나라 Recall@k가 정답 적중 여부(hit rate)와 같다. 답의 근거가 여러 문서에 나뉜 질의에서 검색기가 어떻게 동작하는지는 이 질의로 볼 수 없다. 이를 가늠하려고 정답 문서가 여러 개인 질의 세트를 따로 만들어 관찰한다.

- 판정에 쓰지 않는다. EXP의 채택·기각·보류는 위 판정 절(single-doc dev-full Recall@5)로만 정하고, multi-doc 결과는 같은 EXP에서 함께 보고해 두 평가가 기법을 어떻게 다르게 평가하는지 비교한다. 예외는 메타데이터 가설의 판정(위 절)이다.
- 질의 세트: dev 전용이다. 정답 문서는 `test` 분할 회의를 뺀 회의의 문서에서만 고른다. 문서 묶음은 메타데이터(같은 회의, 같은 법안, 같은 질의자, 같은 위원회)로 만들고, 검색기 점수(dense·BM25 유사도)로 고르지 않는다. 검색기로 고르면 세트가 그 검색기에 유리해진다.
- 질의마다 답에 필요한 문서 집합(2개 이상)이 정답이다. 묶음 안의 문서는 모두 정답·무관으로 판정해, 묶음 안에서는 정답 누락이 없게 한다.
- 생성 입력은 `context`와 메타데이터만 쓴다. 기존 평가 질의(`summary_q`)는 넣지 않는다.
- 생성 절차와 검수는 PLAN의 S7·S8·G3에서 정한다. 검수를 마친 세트는 어떤 EXP의 multi-doc 점수도 보기 전에 SHA-256을 DECISIONS.md에 적어 동결하고, 이후 고치지 않는다.
- 지표(문서 순위 규칙은 위 지표 절과 같다)
  - Recall@k: 질의별로 정답 문서 중 상위 k에 든 비율의 평균
  - Complete@k: 정답 문서가 모두 상위 k에 든 질의의 비율
  - Hit@k: 정답 문서가 하나 이상 상위 k에 든 질의의 비율
  - k는 5와 10. 전체와 함께 질의 유형별로 보고한다
- 기준 실험과의 차이는 paired bootstrap 95% 구간으로 보고하되 판정 라벨을 붙이지 않는다(메타데이터 가설의 판정은 예외). 재표본 단위는 질의를 만든 묶음(같은 회의·법안·질의자 등)이고, 반복 횟수와 seed는 판정 절과 같다.
- 해석의 한계: 이 질의도 정답 문서를 보고 생성됐다(아래 해석의 한계 1항). 묶음 밖의 관련 문서는 정답으로 세지지 않는다. 질의 수가 dev-full보다 훨씬 적어 구간이 넓으므로 방향과 큰 순위 변화만 읽는다.

## 생성 단계 평가 (실험 중 고정)

생성 단계 평가 프로토콜이다. `docs/drafts/spec-generation-eval.md`를 옮겼다(D-53). 생성 EXP는 이 절의 판정으로 정한다.

### 문제

- 입력: 평가 질의 1건과 검색 기준 설정(D-36)이 고른 근거 문서 5개(D-11 `generator.context_docs`)
- 출력: 근거 번호 `[n]`을 붙인 한국어 답변, 또는 근거에서 답을 찾지 못했다는 거부 답변
- 생성 조건: OpenRouter `google/gemma-4-31b-it`, 제공자 CoreWeave 고정, 사고 과정 끔(D-37). 실험 간 비교는 `temperature` 0과 고정 프롬프트(`configs/prompt/`의 버전)로 한다
- 평가 질의(**gen-full**, 생성 판정 세트): dev-full(`summary_q` dev 분할 전체)에서 seed 순서의 앞 n개를 고정해 쓴다. n은 기준 설정의 변동 폭으로 정한다(D-44). n = 330(D-50: 생성·judge를 모두 다시 돌린 같은 설정 두 실행의 평균 차이 95% 구간 반폭이 충실성 약 0.03). multi-doc 질의는 필요할 때 동결 세트에서 일부를 뽑아 아래 보조 관찰로 따로 본다(D-53). 블라인드 확인 표본과 judge 지시 개발에 쓴 질의(S14 표본 20질의, S14c 확인 사례의 질의)는 판정용 질의에서 뺀다(아래 judge 검증, D-47). 생성 점수를 해석할 때 같은 세트의 검색 지표를 함께 보고한다(D-44)
- 작동 확인(**gen-small**, 생성 개발 세트): S14 표본 20질의(`gen_eval.queries=dev-small gen_eval.n=20`)로 한다. 판정용 세트에서 뺀 judge 지시 개발 질의라 판정과 섞이지 않는다. 블라인드 확인 표본(12질의)은 다시 확인할 때를 위해 남겨 두어 작동 확인에 쓰지 않는다(D-51·D-53). 검색 단계 dev-small과 같이 판정에는 쓰지 않는다
- test: 검색 단계와 같이 생성 단계 마지막에 사용자 지시로 1회만 쓴다(D-38). 그 전에는 test 질의를 읽거나 보내지 않는다. 이 1회는 CLAUDE.md 금지 절의 외부 전송 줄을 생성 단계에 맞게 고친 뒤에 지시한다(D-53 남은 일)

### 기준

지표 정의는 RAGAS(Es et al., EACL 2024 System Demonstrations, arXiv:2309.15217)와 RGB(Chen et al., AAAI 2024, arXiv:2309.01431)를 빌려 고쳐 직접 구현한다. ragas·deepeval 라이브러리는 쓰지 않는다(D-38).

| 기준 | 묻는 것 | 출처 | 판정 방법 | 참조 답변 |
| --- | --- | --- | --- | --- |
| 충실성 | 답변의 진술이 근거에서 나오는가 | RAGAS 논문 faithfulness | judge가 답변을 진술로 나누고 진술마다 근거로 뒷받침되는지 판정, 뒷받침된 진술 수 / 전체 진술 수 | 필요 없음 |
| 답변 관련성 | 답변이 질의에 답하는가 | 자체 정의. RAGAS 논문 answer relevance(역질문 생성과 임베딩 유사도)를 쓰지 않으므로 그 검증 수치로 정당화하지 않는다(`docs/gen-eval-criteria.md` R절) | judge가 답함 1, 일부 0.5, 답하지 않음 0으로 매긴다(D-40 결정 2). 회의에서 확답이 없었다는 상황을 전한 답변은 답함이다(D-47 결정 2) | 필요 없음 |
| 핵심 답변 포함도 | 질의가 묻는 핵심 답이 답변에 들어 있는가 | ragas 라이브러리 answer correctness(RAGAS 논문에는 없음)를 고쳤다. 원래 지표와 고친 이유는 "기준 설명" 절 | judge가 `answer.comment`에서 질의에 답하는 핵심 진술만 뽑고, 진술마다 답변에 그 내용이 있는지 판정한다. 답변에 담긴 핵심 진술 수 / 핵심 진술 수 | `answer.comment`(D-38) |
| 거부 정확도 | 답이 없는 근거에서 거부하고, 답이 있는 근거에서 거부하지 않는가 | RGB negative rejection | judge가 질의를 항목으로 나누고, 항목마다 근거에 정보가 있는지와 답변의 처리(답함, 부분임을 밝히고 답함, 상황을 밝히고 답함, 거부, 다루지 않음)를 판정한다(D-41, 아래 "거부 답변의 처리"). 블라인드 확인 전까지는 참고값이고 판정에 쓰지 않는다(PR #137). 다만 과잉 거부율은 D-52 안전 조건으로 판정에 쓴다. 답이 없는 근거 세트는 오라클 진단에서 정답 문서를 뺀 입력으로 만든다 | 필요 없음 |

RAGAS 논문의 세 번째 기준 context relevance는 쓰지 않는다. 검색 품질은 검색 단계 지표(Recall@k)가 본다.

### 기준 설명

기준을 고른 근거와 각 기준이 무엇을 재는지 적는다. 예는 모두 지어낸 것이다(AI Hub 데이터가 아니다).

#### 세 judge 기준이 맡는 실패

생성 답변의 실패를 셋으로 나누고, judge 기준이 하나씩 맡는다.

| 실패 | 맡는 기준 |
| --- | --- |
| 근거에 없는 내용을 지어냄 | 충실성 |
| 질의와 다른 이야기를 함 | 답변 관련성 |
| 질의에 맞는 이야기를 했지만 핵심 답을 빠뜨림 | 핵심 답변 포함도 |

충실성과 답변 관련성은 중복이 아니다. 충실성은 답변 진술이 근거 안에 있는지를, 답변 관련성은 답변이 질의에 답하는지를 본다. RAGAS 논문도 답변 관련성이 사실 여부를 보지 않는다고 적는다. 한쪽만 실패하는 경우가 둘 다 있다.

| 답변 | 충실성 | 답변 관련성 |
| --- | --- | --- |
| 근거에 있는 문장을 옮겼지만 질의와 다른 쟁점을 말함 | 높음 | 낮음 |
| 질의에 정면으로 답했지만 근거에 없는 수치를 지어냄 | 낮음 | 높음 |

두 점수 사이에 상관이 나올 수는 있다. 이는 두 실패가 함께 나는 경우가 많다는 뜻이지 같은 것을 잰다는 뜻은 아니다(추론).

세 번째 실패는 앞의 두 기준으로 잡히지 않는다. 근거에 있는 말만 했고(충실성 높음) 주제도 맞는데(관련성 높음) 답의 절반을 빠뜨린 답변이 그렇다. 무엇이 핵심 답인지 알려면 기준이 되는 답이 필요하고, 답변 발언 원문 `answer.comment`가 그 역할을 한다.

#### 핵심 답변 포함도

**정의:** 질의가 묻는 핵심 답이 생성 답변에 얼마나 들어 있는지의 비율이다. 핵심 답은 `answer.comment`에서 뽑는다. 점수는 답변에 담긴 핵심 진술 수 / 핵심 진술 수이고 0\~1이다.

**계산 순서.** 질의 "○○ 사업 예산을 줄인 이유는?"에 대한 `answer.comment`(장관 답변 발언)가 (가) 인사와 질의 경위, (나) 집행률이 낮았다, (다) 유사 사업과 통합했다, (라) 다른 위원 질의 언급, (마) 내년 계획을 담고 있다고 하자.

1. 핵심 진술 뽑기: judge가 `answer.comment`에서 이 질의에 답하는 진술만 뽑는다. (나)·(다) 2개다. (가)·(라)·(마)는 같은 발언에 있지만 질의가 묻지 않은 내용이라 뺀다
2. 포함 판정: judge가 핵심 진술마다 생성 답변에 그 내용이 있는지 판정한다. 답변이 "집행률이 낮아 줄였습니다[1]."이면 (나)는 있고 (다)는 없다
3. 점수: 1 / 2 = 0.5

**원래 지표와 고친 이유.** ragas 라이브러리의 answer correctness(RAGAS 논문에는 없음)는 참조 답변 전체와 답변을 진술 단위로 대조한 F1(TP / (TP + 0.5·(FP + FN)))과 의미 유사도를 가중 결합한다(v0.2.15 기본 0.75·0.25). 의미 유사도의 근거 문헌은 SAS(Risch et al., "Semantic Answer Similarity for Evaluating Question Answering Models", MRQA@EMNLP 2021, arXiv:2108.06130)다. 지금 ragas 문서는 이 지표 대신 factual correctness(진술 단위 정밀도·재현율·F1)와 semantic similarity를 따로 둔다. 두 가지를 고쳤다.

- 질의로 거른다: 위 예에 원래 F1을 쓰면 참조 진술 5개, 답변 진술 1개 중 (나)가 맞아 재현율 1/5, 정밀도 1/1, F1 = 2·(0.2·1) / (0.2 + 1) ≈ 0.33이다. 질의가 묻지 않은 (가)·(라)·(마)를 빠뜨린 것까지 감점되어, 질의에 맞게 간결히 답할수록 점수가 낮아진다. `answer.comment`가 질의자 질문 전체에 대한 응답이라 생기는 문제다
- 재현율만 쓴다: `answer.comment`는 거의 모두 정답 문서 `context` 안에 그대로 있다(`docs/data.md` §7, 39,633건 중 39,467건). 그래서 정밀도(답변 진술이 참조에 있는가)는 "답변이 근거에 있는 말만 했는가"와 거의 같아져 충실성과 겹친다(추론). 답변이 지어낸 내용은 충실성이 감점한다. 의미 유사도 항도 쓰지 않는다

**계산에서 빼는 질의.** 아래 경우는 점수 0으로 두지 않고 뺀다. 0으로 두면 생성 답변의 잘못이 아닌 것을 감점하게 된다.

- 참조 사용 불가: 1단계에서 핵심 진술이 하나도 뽑히지 않는 경우다. `answer.comment`가 "검토해 보겠습니다"처럼 답을 피한 발언이거나 질의와 범위가 맞지 않으면 기준이 될 답이 없다. 비율을 따로 보고한다
- 정답 문서가 근거 상위 5개에 없는 경우: 검색이 놓쳐 답변이 핵심 답을 담을 수 없다. 이 실패는 검색 지표가 맡는다
- 전체 거부 답변: 거부 정확도로만 평가한다. 부분 거부 답변은 거부 문장을 뺀 내용을 채점한다(아래 "거부 답변의 처리")

**짝지은 비교.** 빼는 질의가 실행마다 달라, 기준과 후보를 비교할 때는 두 실행 중 하나라도 빼는 조건에 해당한 질의를 양쪽에서 함께 뺀다. 그대로 두면 paired bootstrap의 짝이 맞지 않는다.

**위치.** 보조 지표로 보고하고 종합 지표에 넣지 않는다(D-53). 판정용 330질의 중 258질의에서만 계산되고(참조 사용 불가 51, 정답 문서 없음 11, 전체 거부 9, judge 판단 불가 1), 정답 청크에 답이 없다고 판정된 68질의의 평균이 0.066(답이 있는 190질의 0.672)이라 생성보다 근거 청크 선택을 크게 반영하며, 다른 두 기준과의 상관이 낮다(Spearman 충실성 0.30, 관련성 −0.05, `notebooks/37_01_SPEC개정_판단재료.ipynb`). 사람 판단과의 일치는 재지 않았다(D-51). 근거를 바꾸는 실험(H10 등)에서는 판정과 함께 반드시 보고한다. 이 결정은 기준 설정 출력만 보고 했고, 후보 설정끼리 비교한 결과를 보지 않았다(사용자 결정, PR #100).

#### 거부 답변의 처리

거부 문장은 문장 단위로 가른다(D-41 결정 1). 거부가 맞았는지는 아래처럼 질의 항목 단위로 판정한다. 거부 문구를 담은 문장이 거부 문장이고, 내용 문장이 없으면 전체 거부, 있으면 부분 거부다.

- 전체 거부 답변은 거부 정확도로만 평가하고 충실성·답변 관련성 계산에서도 뺀다. "근거에서 찾지 못했습니다"는 진술이 없어 충실성이 정의되지 않고, 답변 관련성은 거부를 낮게 매겨 거부 정확도와 같은 일을 두 번 세게 된다
- 부분 거부 답변은 거부 문장을 뺀 내용으로 충실성·인용 검사를 하고, 답변 관련성과 핵심 답변 포함도는 답변 전체로 본다. 관련성은 찾지 못했다고 밝힌 부분을 감점하지 않는다. 답하지 못한 부분은 포함도와 거부 평가가 맡는다(PR #106 코멘트, D-47)
- 거부가 맞았는지는 질의가 묻는 항목 단위로 판정한다. 질의가 x와 y를 함께 물으면 항목마다 근거 5개 전체에 정보가 있는지와 답변이 그 항목을 어떻게 처리했는지를 본다. 근거에 있으면 답하고, 일부만 있으면 부분적인 사실이라는 점을 밝히고 답하며, 없으면 거부하는 것이 맞는 처리다. 일부만 있는 항목을 그 안내 없이 답하면 틀린 처리다
- 근거가 "예정", "검토 중", "정해지지 않음"으로만 말하거나 답변자가 답을 피한 항목(모호·회피)은 거부 정확도에 넣지 않는다. 지금 생성 프롬프트는 이런 경우를 전하라고 지시하지 않기 때문이다(생성 실험 아이디어 PLAN H18). 답변이 그 상황을 그대로 전했으면 상황 전달, 단정하거나 거부하거나 다루지 않았으면 상황 미전달로 따로 센다(S14c 결정 사항 4)
- 틀린 처리는 유형을 나눠 센다: 누락, 무언 생략, 과잉 거부, 안내 없이 부분 답함, 근거 없이 답함, 불필요한 부분 안내. 정보 상태는 judge가 답변 없이 근거 5개로 정하고, 처리는 근거 없이 답변으로 정하며, 맞는 처리인지는 코드가 정한다(S14c, `rag.gen_eval.checks.item_outcome`)
- 근거의 내용이 질의자 발언이 분명하면(의문형, 답변자를 부르는 호칭, 답변자가 확인하지 않은 주장) 그 항목의 근거로 보지 않고, 답변자 발언이 분명하거나 구분할 수 없으면 근거로 본다. 구분할 수 없는 경우는 따로 센다. 청크에 발언자 표기가 없어 잘린 조각으로는 발언자를 가리기 어렵기 때문이다(D-41)

어려운 질의에서 거부를 늘리면 세 judge 기준이 함께 오를 수 있다. 기준마다 두 실행 모두 계산한 질의만 쓰면(아래 판정 절) 이 이득은 막히지만, 답할 수 있는 질의를 거부하는 손해는 주지표에서 감점되지 않는다. 그래서 과잉 거부는 주지표에 넣지 않고 안전 조건으로 본다(D-52): 후보의 과잉 거부율 증가폭의 회의 단위 paired bootstrap 95% 구간 상한이 허용폭 δ_r 이하일 때만 채택한다. 분모와 δ_r 값은 아래 판정 절에 있다(D-53).

### 코드로 판정하는 항목

LLM 없이 처리하고 judge에 넘기지 않는다(PLAN "생성 평가" 절).

- 인용 번호 유효성: 답변의 `[n]`이 실제로 넣은 근거 번호(1\~5) 안에 있는가, 인용이 없는 진술 문장이 있는가
- 거부 문구: 프롬프트가 지정한 거부 문구가 답변에 있는가. RGB도 지정 문구 일치(Rej)를 쓰고, 문구를 따르지 않은 거부는 LLM 판정(Rej\*)으로 따로 셌다. 이 검사는 형식 검사이고, 문구를 따르지 않은 거부를 포함해 거부가 맞았는지는 항목 단위 거부 평가가 의미로 판정한다(`docs/gen-eval-criteria.md` X3)
- 메타데이터 일치: 답변에 나온 회의 일자·위원회 이름이 인용한 문서의 `date`·`committee_name`과 맞는가. 발언자 이름은 대조하지 않는다(D-40 결정 3)

### judge

- 모델은 DeepSeek V4.1 Flash, 경로는 opencode Go 구독(`deepseek-v4.1-flash`)이다(D-38). 생성 모델(Gemma 4)과 다른 계열이다. opencode Go는 judge 용도로 D-31 허용 처리처에 들어 있다(D-38)
- 제공자, 모델, 파라미터(`temperature` 0 등), 프롬프트를 `configs/`에서 버전 관리한다. 실행 기록과 LangSmith 메타데이터에 레시피(git 커밋, 생성 레시피, judge 레시피, 프롬프트 SHA-256)를 남긴다
- opencode Go 이용 조건(https://opencode.ai/docs/go/, 2026-10-19 확인): OpenCode와 비슷한 요청을 내는 코딩 에이전트용으로 설계했고 남용을 감시한다. 사용량 한도는 월 금액이고 5시간에 20%, 주에 50%까지 쓸 수 있다. 학습 미사용, 보존 0일(ZDR)이고 ZDR 협약은 매달 갱신하며 지금 협약은 2026-10-31까지다. 배치 판정으로 의심받아 사용이 막히면 그때 경로를 다시 정한다(D-38). 대안은 같은 모델의 OpenRouter 경로(`deepseek/deepseek-v4.1-flash`, 2026-10-19 확인)다
- judge 검증: 지시를 동결한 뒤 저장한 응답을 반복 재채점해 judge 잡음을 재고, 그 뒤 블라인드 확인을 한 번 한다(PLAN 생성 평가, `docs/research/llm-judge-evidence.md`). 블라인드 확인은 동결한 judge로 채점한 dev-full 답변 중 처음 보는 것에서 실패가 예상되는 항목을 층화해 30\~40개 판정을 사용자가 judge 출력을 보기 전에 매긴다. 기준별로 퍼센트 일치와 κ 또는 π, 실패 클래스 TPR을 질의 단위 구간과 함께 내고, 비교할 두 설정의 답변에서 judge 오류율이 같은지 본다. 기준값에 못 미친 기준은 보조 지표로 내리고 지시는 고치지 않는다. 동결 뒤 지시를 고치면 새 버전으로 검증을 다시 한다(`docs/gen-eval-criteria.md` P1·P5). 블라인드 표본은 판정용 질의에서 뺀다. 블라인드 확인은 S25에서 1질의 검수 뒤 중단했다(D-51). judge는 사람과 독립 대조 없이 쓰고, 거부 정확도는 참고값으로 둔다(과잉 거부율은 D-52 안전 조건으로 판정에 쓴다)

### 오라클 진단

정답 문서를 근거에 직접 넣는 조건은 매 실험이 아니라 진단용으로 한 번 한다(D-38).

- 검색 기준 근거와 오라클 근거의 점수 차이로 생성 실패와 검색 실패를 가른다
- 근거에서 정답 문서를 뺀 입력은 거부 정확도 세트로 쓴다. 다만 정답 문서 밖에도 답을 담은 문서가 있을 수 있어(아래 "평가 결과 해석의 한계" 2항, D-34의 "다른 정답" 9개) 이 세트의 "거부해야 함" 라벨에는 잡음이 있다
- S26에서 한 번 했다(2026-10-27, `docs/slices/26-oracle.md`, `notebooks/36_01_오라클진단.ipynb`). 정답 문서를 넣는 자리는 5번째, 거부 세트는 정답 문서를 빼고 6번째 문서로 채웠고, 근거가 같아지는 질의는 다시 생성하지 않았다(사용자 판단, PR #162)

### 판정

- 주지표는 RAGAS 지표를 고쳐 만든 LLM judge 기준을 결합한 종합 지표다(D-38). 종합 지표는 질의마다 충실성과 답변 관련성의 단순 평균이다(D-53). 두 기준 모두 두 실행에서 계산된 질의만 쓴다. 동일 가중은 원래 점수 척도에서 충실성 1%p와 관련성 1%p를 같게 본다는 뜻이다. 관련성은 0/0.5/1의 3단계 값이라 같은 가중이어도 종합 지표의 흔들림을 더 크게 좌우한다. 가중치를 근거 있게 정하려면 사람 판단 데이터가 필요한데 없어서(D-51) 동일 가중을 쓴다(`docs/research/composite-weighting.md`)
- 재표본 단위는 검색 판정과 같은 회의, 반복 10,000회, seed 20260929로 기준과의 차이를 paired bootstrap 95% 구간으로 낸다
- 기준마다 두 실행 중 하나라도 계산에서 빠진 질의(전체 거부, 포함도의 제외 조건)는 양쪽에서 함께 뺀다. 핵심 답변 포함도 절의 "짝지은 비교"와 같은 이유다
- 채택: 종합 지표 차이의 95% 구간 하한이 0보다 크고, 점 추정 차이가 최소 개선 폭 δ = 0.02 이상이며, 기준별 하락 안전 조건과 과잉 거부 안전 조건을 모두 통과함
- 기각: 종합 지표 차이의 95% 구간 상한이 0보다 작음
- 보류: 그 밖의 경우. 보류를 예외로 기준에 올릴지는 검색 단계와 같이 사용자가 정한다(D-28·D-33). 종합 지표는 기준이 고르게 오른 명백한 향상을 채택하려는 것이고, 기준별로 오르내림이 갈려 하락 안전 조건에 걸린 보류는 사용자가 기준별 값을 보고 예외 채택을 판단한다(D-53)
- 기준별 하락 안전 조건: 충실성과 답변 관련성 각각의 차이(후보 − 기준) 95% 구간 하한이 충실성 −0.05, 관련성 −0.035 이상. 단순 평균은 한 기준의 하락을 다른 기준의 상승으로 가리므로 이 조건으로 막는다. 허용폭은 같은 설정을 다시 돌린 두 실행의 차이 반폭(330질의 어림: 충실성 0.031, 관련성 0.021)의 1.65배로, 같은 설정끼리 비교하면 약 90%가 통과한다(D-53)
- 과잉 거부 안전 조건: 과잉 거부율(질의마다 과잉 거부 항목 수 / 판정 대상 항목 수를 낸 값의 평균. 판정 대상 항목이 없는 질의는 두 실행에서 함께 뺀다) 차이(후보 − 기준)의 95% 구간 상한이 δ_r = 0.02 이하(D-52)
- δ = 0.02와 δ_r = 0.02는 같은 설정을 다시 돌린 두 실행의 차이 반폭(330질의 어림: 종합 지표 0.019, 과잉 거부율 0.012)에 맞췄다. 이보다 작게 잡으면 같은 설정을 다시 돌리기만 해도 판정이 바뀔 수 있다(D-53, `notebooks/37_01_SPEC개정_판단재료.ipynb`)
- 기준별 값(충실성, 답변 관련성, 핵심 답변 포함도)과 구간은 판정과 함께 보고한다

### 보조 관찰: multi-doc 질의

multi-doc 질의로도 생성을 평가할 수 있지만 검색 단계와 같이 판정에는 쓰지 않고, 매 EXP가 아니라 아래 "언제 보나"의 경우에만 본다(사용자 결정 PR #99, D-53 결정 7). 근거가 여러 문서에 나뉜 질의에서 답변이 문서들을 합쳐 답하는지를 single-doc 질의로는 볼 수 없기 때문이다.

- 질의 세트: G3 동결 세트 `queries_g3.jsonl` 600건(D-15)에서 그때 정한 일부를 쓴다. 세트는 dev 전용이고 고치지 않는다
- 언제 보나: 매 생성 EXP에서 보지 않고, 여러 문서를 합쳐 답하는 것을 겨냥한 실험(예: H23, H10의 근거 구성)에서만 필요할 때 본다. 600건 전체가 아니라 일부를 쓰고, 몇 건을 쓸지는 그때 정한다(사용자 결정 2026-10-27, D-53). 생성 입력(근거 5개)과 프롬프트가 single-doc과 같아 참조가 필요 없는 두 기준은 질의 분포만 바뀌고, 따로 볼 가치는 문서를 합쳐 답하는지에 있다
- 기준: 위 기준 표와 코드 판정 항목을 그대로 쓴다
- 기준 실험과의 차이는 paired bootstrap 95% 구간으로 보고하고 판정 라벨을 붙이지 않는다. 재표본 단위는 검색 단계 multi-doc 보조 관찰과 같은 `pool_id`, 반복 횟수와 seed는 위 판정 절과 같다
- 핵심 답변 포함도의 참조 답변: 세트의 기대 답(`answer`)은 검수하지 않은 참고 자료이고, 표본 통과 47건 중 16건에 기대 답·요소 문제가 있었다(D-15 단서). 포함도는 보조 지표라(D-53) 이 기대 답을 참조로 쓸지는 multi-doc 생성 보조 관찰을 처음 할 때 정한다
- 해석의 한계: 질의 수가 single-doc보다 적어 구간이 넓으므로 방향과 큰 변화만 읽는다(검색 단계 multi-doc 보조 관찰과 같다)

## 누수 방지

- dev와 test는 회의 단위로 나뉜다. 같은 `context`를 공유하는 질의는 모두 같은 회의에서 나오므로(`docs/data.md` §11) 문서가 두 분할에 걸치지 않는다.
- test 질의와 test 점수는 단계(검색·생성)마다 종료 시 사용자 지시로 1회 실행할 때 외에는 읽거나 계산하지 않는다(D-38). 설정 선택, 필터 규칙, 프롬프트 작성에 test 질의를 쓰지 않는다.
- 질의 필터 규칙은 검색 점수를 보기 전에 정한다(미결 사항 1).
- multi-doc 질의 세트는 `test` 분할 회의의 문서를 쓰지 않고, 생성·검수 중에 검색 결과(순위·점수)를 보지 않는다.

## 평가 결과 해석의 한계

수치를 보고할 때 아래 한계를 함께 적는다.

- 질의가 정답 문서를 보고 생성됐다. 정답 문서와 어휘가 많이 겹쳐 실제 사용자 질의보다 검색이 쉽고, 어휘 매칭(BM25)에 유리할 수 있다.
- 질의마다 정답 문서를 하나로 본다. 다른 문서도 답을 담고 있으면 정답으로 세지지 않는다.
- 코퍼스는 회의록 전체가 아니라 질의응답이 만들어진 구간의 발췌다(`docs/data.md` §15).
- 질의는 RAG 질의응답에 맞게 만들어지지 않았다. 일반론에 가까운 질의가 많아 정답 문서 밖의 청크도 답의 근거가 될 수 있어, 생성 평가에서 정답 문서를 뺀 근거에도 답이 있다고 판정되는 경우가 있다(S26 사용자 판단, D-53).

## 자원 제약

- 상시 지출은 0으로 둔다. 배포는 HF Spaces 무료 CPU를 쓴다. 생성은 호출당 과금인 OpenRouter 유료 API(D-37)라 상시 지출이 아니다. 생성 평가 judge는 opencode Go 월 구독(D-38)을 쓴다.

- 유료 API(OpenRouter)는 첫 평가 전에 예상 비용을 계산해 사용자에게 보고하고, 사용 여부는 사용자가 결정한다.
- AI Hub 데이터는 처리 목적으로 외부 API(Google AI Studio 무료 쿼터, OpenRouter 유료 API, 생성 평가 judge용 opencode Go 구독(D-38))와 Colab에 보낼 수 있다. 재배포 제한이 막는 것은 데이터를 공개하는 일(저장소 커밋, 저장소에 남는 노트북·로그·문서에 질의 원문 대량 기록, 외부에서 내려받을 수 있게 두기)이다(D-31). 질의 전체처럼 많이 보내는 실행은 호출 수·소요 시간·비용을 보고하고 사용자 승인 후에 한다. `test` 질의는 평가 프로토콜에 따라 단계(검색·생성)마다 종료 시 1회 실행 외에는 보내지 않는다. 프로젝트를 공개할 때 데이터는 출처 링크로만 밝힌다. 회의록 발언 원문(`context`)은 공개 자료라 공개 금지 대상이 아니다.

3. (해결, D-30) 배포 제약: 채택할 설정이 HF Spaces 무료 CPU에서 받아들일 만한 질의당 지연 안에 들어야 하는지, 그 상한을 얼마로 둘지. 질의 입력부터 답변 출력 시작(스트리밍 첫 토큰)까지 3초 이내로 정했다(D-30, 2026-10-15 정정). 운영 채택 판단에 쓰고, EXP 판정(Recall@5)에는 쓰지 않는다
4. judge의 사람 대조 기준: 사람 대조(블라인드 확인)에서 기준별 점추정을 아래 구간에 넣어 판정 사용 여부를 정한다(사용자 결정 2026-10-26, 이슈 #142, 근거 `docs/research/llm-judge-evidence.md`). 블라인드 확인을 중단해(D-51) 적용하지 않았고, 사람 대조를 다시 하면 이 구간을 적용한다
   - 대체 가능: κ 또는 π ≥ 0.8, 실패 클래스 TPR·TNR 각각 ≥ 0.86. 절대 비율 보고, Rogan-Gladen 보정, 사람 채점 대신 사용을 허용한다. TPR·TNR은 근거 문서의 0.85에서 바꿨다. 출처로 든 Lee et al. Proposition 6.1의 문턱(1/2 + 1/(2√2) ≈ 0.8536)보다 낮아, 그 값에서는 judge 보정 추정이 같은 사람 라벨만 쓴 추정보다 분산이 작은 경우가 없다
   - 판정 사용: κ 또는 π ≥ 0.6, 실패 클래스 TPR ≥ 0.8, 비교할 두 설정의 답변에서 judge 오류율 차이 없음. 같은 judge로 설정 A·B를 쌍 비교하는 데 쓴다
   - 보조 지표: 0.4 ≤ κ < 0.6. 진단용으로만 보고하고 판정 규칙에서 뺀다
   - 0.4 미만: 지표에서 빼거나 그 기준은 사람이 채점한다
   - 출처 확인: κ 0.8은 Krippendorff α 0.800(신뢰)과 Landis & Koch almost perfect(0.81 이상)를, 0.6은 Landis & Koch substantial(0.61 이상)과 McHugh(0.60 미만 불충분)를, 0.4는 Landis & Koch moderate(0.41 이상)를 따른다. TPR 0.8은 문헌에 직접 출처가 없는 제안값이다
