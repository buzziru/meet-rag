# SPEC: 국회 회의록 RAG 검색

이 SPEC은 검색 단계의 평가 프로토콜을 고정한다. 생성 단계 평가는 검색 베이스라인 이후 이 문서를 개정해 추가하고, 개정 사실을 DECISIONS.md에 기록한다. 개정 초안은 "생성 단계 평가 (개정 초안, 승인 대기)" 절이다(D-38).

## 문제

- 입력: 한국어 자연어 질의 1건
- 출력: 코퍼스 문서 순위 목록 (서로 다른 문서 10개 이상)
- 코퍼스: `data/processed/corpus_context.jsonl`의 고유 `context` 38,516건. 문서 ID는 `doc_id`
- 평가 질의: `data/processed/queries_summary_q.jsonl`의 `query`(= `summary_q`). 질의 ID는 `qid`, 정답은 그 레코드의 `doc_id` 하나

데이터의 성질과 한계는 `docs/data.md`에 있다.

## 평가 프로토콜 (실험 중 고정)

### 분할

- 분할 단위는 회의(`conference_number`)다. 한 회의의 질의는 모두 같은 분할에 들어간다.
- AI Hub의 Training/Validation 구분은 쓰지 않는다. 학습 단계가 없으므로 두 구분은 질의 출처 표시로만 남는다.
- seed 20260929로 회의를 섞은 뒤, 회의구분(`meeting_name`) 비율을 유지하면서 회의를 차례로 배정한다. dev 질의가 3,000건 이상이 되면 멈추고, 이어서 test 질의가 3,000건 이상이 되면 멈춘다. 남은 회의의 질의는 쓰지 않는다.
- `qna_type` 비율은 분할 후 전체 분포와 비교해 기록만 한다.
- 분할 결과는 `data/splits/queries.csv`(`qid`, `conference_number`, `split`)에 저장한다. `data/`는 커밋하지 않으므로 같은 seed로 재생성할 수 있어야 한다. 생성 후 파일 SHA-256을 DECISIONS.md에 적는다.

### 평가 층

| 층 | 코퍼스 | 질의 | 용도 |
| --- | --- | --- | --- |
| dev-small | dev 회의 일부의 전체 문서, 약 1,000건 | 그 문서가 정답인 dev 질의 | 방향을 확인한다. 작업 과정과 결과는 Jupyter 노트북(`notebooks/`)에 남긴다. 판정에 쓰지 않는다 |
| dev-full | 전체 38,516건 | dev 질의 전체 | EXP 채택·기각 판정 |
| test | 전체 38,516건 | test 질의 전체 | 검색 단계 종료 시 1회 보고 |

- dev-small 문서는 dev 회의를 seed 20260929로 섞어 문서 수가 1,000건 이상이 될 때까지 회의 단위로 뽑는다. 문서 목록은 `data/splits/dev_small_docs.txt`에 둔다. 같은 회의 문서를 함께 넣어 회의 내부의 비슷한 문서가 방해 문서로 남게 한다.
- dev-small 점수와 dev-full 점수는 방해 문서 수가 달라 서로 비교하지 않는다. 표를 나눠 적는다.

### 지표

- 문서 순위: 검색기가 청크를 반환하면 각 문서가 처음 나온 순위를 문서 순위로 쓴다.
- 주지표: 문서 단위 Recall@5. 질의별로 정답 문서가 상위 5개 안에 있으면 1, 없으면 0이고, 질의 전체의 평균을 낸다.
- 보조 지표: Recall@1, Recall@10, MRR@10(정답 순위가 10 이내면 1/순위, 아니면 0).
- 모든 지표를 전체와 함께 회의구분별, `qna_type`별로 보고한다.
- 발언이 자기 `context` 안에 없는 169건(`docs/data.md` §7)도 포함한다. 문서 단위 정답은 이 레코드에서도 성립한다.

### 판정

- 기준 실험과의 차이를 dev-full에서 paired bootstrap으로 계산한다. 재표본 단위는 회의, 반복 10,000회, seed 20260929이다. 같은 회의의 질의끼리는 서로 독립이 아니므로 회의 단위로 재표본한다.
- 채택: Recall@5 차이의 95% 구간 하한이 0보다 크고, 점 추정 차이가 +1.0%p 이상
- 기각: 95% 구간 상한이 0보다 작음
- 보류: 그 밖의 경우

### 메타데이터 가설의 판정 (D-18)

문서 메타데이터(회의명·위원회·안건·날짜·화자 등)를 검색에 쓰는 가설(PLAN에 [메타데이터]로 표시)은 아래 순서로 판정한다. single-doc 평가 질의(`summary_q`)는 회의를 메타데이터로 지목하는 경우가 드물어(연도·날짜·위원회·이름 중 하나라도 언급 10.4%) 이 가설의 효과를 single-doc으로는 판정하기 어렵기 때문이다.

1. single-doc 판정(위 판정 절)이 채택이면 채택, 기각이면 기각한다
2. 보류이면 multi-doc 질의 세트로 정한다. 재표본 단위는 `pool_id`, 반복 횟수와 seed는 위 판정 절과 같다
   - 채택: Recall@5 차이의 95% 구간 하한이 0보다 크고 점 추정 차이가 +1.0%p 이상이며, Complete@5 차이의 95% 구간 상한이 0 이상
   - 기각: Recall@5 차이의 95% 구간 상한이 0보다 작음
   - 보류: 그 밖의 경우
- 단서: multi-doc 세트는 메타데이터로 묶음을 만들고 질의도 메타데이터로 회의를 지목해, 메타데이터를 쓰는 검색기에 유리하다. multi-doc 세트에는 test가 없어 이 규칙으로 채택한 결정은 검색 단계 종료 시 test로 다시 확인할 수 없다

## 보조 관찰: multi-doc 질의

평가 질의는 정답 문서가 하나라 Recall@k가 정답 적중 여부(hit rate)와 같다. 답의 근거가 여러 문서에 나뉜 질의에서 검색기가 어떻게 동작하는지는 이 질의로 볼 수 없다. 이를 가늠하려고 정답 문서가 여러 개인 질의 세트를 따로 만들어 관찰한다.

- 판정에 쓰지 않는다. EXP의 채택·기각·보류는 위 판정 절(single-doc dev-full Recall@5)로만 정하고, multi-doc 결과는 같은 EXP에서 함께 보고해 두 평가가 기법을 어떻게 다르게 평가하는지 비교한다. 예외는 메타데이터 가설의 판정(위 절)이다.
- 질의 세트: dev 전용이다. 정답 문서는 `test` 분할 회의를 뺀 회의의 문서에서만 고른다. 문서 묶음은 메타데이터(같은 회의, 같은 법안, 같은 질의자, 같은 위원회)로 만들고, 검색기 점수(dense·BM25 유사도)로 고르지 않는다. 검색기로 고르면 세트가 그 검색기에 유리해진다.
- 질의마다 답에 필요한 문서 집합(2개 이상)이 정답이다. 묶음 안의 문서는 모두 정답·무관으로 판정해, 묶음 안에서는 정답 누락이 없게 한다.
- 생성 입력은 `context`와 메타데이터만 쓴다. 기존 평가 질의(`summary_q`)는 넣지 않는다.
- 생성 절차와 검수는 PLAN의 S7·S8·G3에서 정한다. 검수를 마친 세트는 어떤 EXP의 multi-doc 점수도 보기 전에 SHA-256을 DECISIONS.md에 적어 동결하고, 이후 고치지 않는다.
- 지표(문서 순위 규칙은 위 지표 절과 같다)
  - Recall@k: 질의별로 정답 문서 중 상위 k에 든 비율의 평균
  - Complete@k: 정답 문서가 모두 상위 k에 든 질의의 비율
  - Hit@k: 정답 문서가 하나 이상 상위 k에 든 질의의 비율
  - k는 5와 10. 전체와 함께 질의 유형별로 보고한다
- 기준 실험과의 차이는 paired bootstrap 95% 구간으로 보고하되 판정 라벨을 붙이지 않는다(메타데이터 가설의 판정은 예외). 재표본 단위는 질의를 만든 묶음(같은 회의·법안·질의자 등)이고, 반복 횟수와 seed는 판정 절과 같다.
- 해석의 한계: 이 질의도 정답 문서를 보고 생성됐다(아래 해석의 한계 1항). 묶음 밖의 관련 문서는 정답으로 세지지 않는다. 질의 수가 dev-full보다 훨씬 적어 구간이 넓으므로 방향과 큰 순위 변화만 읽는다.

## 생성 단계 평가 (개정 초안, 승인 대기)

이 절은 사용자 승인 전의 초안이다(D-38). 승인 전에는 생성 EXP 판정에 쓰지 않는다. 아래 미결 사항이 정해지면 각 항목에 `(해결, D-NN)`을 적고 절 제목의 "개정 초안"을 뗀다.

### 문제

- 입력: 평가 질의 1건과 검색 기준 설정(D-36)이 고른 근거 문서 5개(D-11 `generator.context_docs`)
- 출력: 근거 번호 `[n]`을 붙인 한국어 답변, 또는 근거에서 답을 찾지 못했다는 거부 답변
- 생성 조건: OpenRouter `google/gemma-4-31b-it`, 제공자 CoreWeave 고정, 사고 과정 끔(D-37). 실험 간 비교는 `temperature` 0과 고정 프롬프트(`configs/prompt/`의 버전)로 한다
- 평가 질의: dev 분할의 평가 질의(`summary_q`). 보정 표본은 판정용 질의와 겹치지 않게 뗀다(아래 judge 보정)

### 기준

지표 정의는 RAGAS(Es et al., EACL 2024 System Demonstrations, arXiv:2309.15217)와 RGB(Chen et al., AAAI 2024, arXiv:2309.01431)를 빌려 직접 구현한다. ragas·deepeval 라이브러리는 쓰지 않는다(D-38).

| 기준 | 묻는 것 | 출처 | 판정 방법 | 참조 답변 |
| --- | --- | --- | --- | --- |
| 충실성 | 답변의 진술이 근거에서 나오는가 | RAGAS 논문 faithfulness | judge가 답변을 진술로 나누고 진술마다 근거로 뒷받침되는지 판정, 뒷받침된 진술 수 / 전체 진술 수 | 필요 없음 |
| 답변 관련성 | 답변이 질의에 답하는가 | RAGAS 논문 answer relevance | judge 판정. 계산 방식(논문의 역질문 생성과 임베딩 유사도, 또는 judge 직접 채점)은 생성 평가 SLICE에서 정한다 | 필요 없음 |
| 정답성 | 답변이 참조 답변의 사실과 맞는가 | ragas 라이브러리 answer correctness(논문에는 없음) | judge가 진술 단위로 대조해 TP / (TP + 0.5·(FP + FN)) | 필요(미결 1) |
| 거부 정확도 | 답이 없는 근거에서 거부하고, 답이 있는 근거에서 거부하지 않는가 | RGB negative rejection | 거부 문구를 코드로 판정. 답이 없는 근거 세트는 오라클 진단에서 정답 문서를 뺀 입력으로 만든다 | 필요 없음 |

RAGAS 논문의 세 번째 기준 context relevance는 쓰지 않는다. 검색 품질은 검색 단계 지표(Recall@k)가 본다.

### 코드로 판정하는 항목

LLM 없이 처리하고 judge에 넘기지 않는다(PLAN "생성 평가" 절).

- 인용 번호 유효성: 답변의 `[n]`이 실제로 넣은 근거 번호(1\~5) 안에 있는가, 인용이 없는 진술 문장이 있는가
- 거부 문구: 프롬프트가 지정한 거부 문구가 답변에 있는가. RGB도 지정 문구 일치(Rej)를 쓰고, 문구를 따르지 않은 거부는 LLM 판정(Rej\*)으로 따로 셌다. 지정 문구를 따르지 않는 거부의 비율은 보정 표본에서 본다
- 메타데이터 일치: 답변에 나온 발언자·회의 일자가 인용한 문서의 메타데이터와 맞는가(대조 범위는 생성 평가 SLICE에서 정한다)

### judge

- API로 부르고 제공자, 모델, 파라미터(`temperature` 0 등), 프롬프트를 `configs/`에서 버전 관리한다. 실행 기록과 LangSmith 메타데이터에 레시피(git 커밋, 생성 레시피, judge 레시피, 프롬프트 SHA-256)를 남긴다
- judge 모델은 생성 모델(Gemma 4)과 다른 계열로 둔다. 후보는 DeepSeek V4.1 Flash(D-38). 경로는 미결 2
- judge 보정: dev 표본 30\~50건을 사람이 기준별로 채점하고(G 게이트, meet-rag D 흐름), judge가 같은 표본을 채점해 기준별 일치율과 Cohen's kappa를 잰다. 일치가 낮은 기준은 기준 문구나 judge 모델을 바꾸고, 충분해진 뒤에 판정에 쓴다. 보정 표본은 판정용 질의에서 뺀다. 판정에 쓸 일치 수준은 미결 4

### 오라클 진단

정답 문서를 근거에 직접 넣는 조건은 매 실험이 아니라 진단용으로 한 번 한다(D-38).

- 검색 기준 근거와 오라클 근거의 점수 차이로 생성 실패와 검색 실패를 가른다
- 근거에서 정답 문서를 뺀 입력은 거부 정확도 세트로 쓴다. 다만 정답 문서 밖에도 답을 담은 문서가 있을 수 있어(해석의 한계 2항, D-34의 "다른 정답" 9개) 이 세트의 "거부해야 함" 라벨에는 잡음이 있다

### 판정

- 재표본 단위는 검색 판정과 같은 회의, 반복 10,000회, seed 20260929로 기준과의 차이를 paired bootstrap 95% 구간으로 낸다
- 주지표와 채택·기각·보류 규칙은 미결 3이 정해진 뒤 적는다. 생성 결과와 judge 판정이 같은 설정에서도 실행마다 달라질 수 있으므로(D-11 API 비결정성), 최소 개선 폭은 측정한 변동 폭을 근거로 정한다

### 미결 사항

1. 정답성의 참조 답변: 후보는 `summary_a`와 `answer.comment`다. `summary_a`는 LLaMA 7B 기반 KoAlpaca 생성물이라 품질 위험이 있고, `answer.comment`는 발언 원문이지만 완결된 답이 아니라 응답 발언 전체다(`docs/data.md` §7, §13). 둘 다 정성 검수가 없다(§13). 참조 답변을 정하지 못하면 정답성을 보조 관찰로 두거나 빼는 안도 있다
2. judge 경로: opencode Go 구독(`deepseek-v4.1-flash`) 또는 OpenRouter(`deepseek/deepseek-v4.1-flash`)
   - opencode Go: 문서(https://opencode.ai/docs/go/, 2026-10-19 확인)는 Go를 OpenCode와 비슷한 요청을 내는 코딩 에이전트용으로 설계했다고 적고, 다른 사용자 경험을 떨어뜨리는 남용을 감시한다고 적는다. 배치 판정에 쓰면 남용으로 볼 위험이 있다(추론). 학습 미사용, 보존 0일(ZDR)이고 ZDR 협약은 매달 갱신하며 현재 2026-10-31까지 유효하다. D-31의 허용 처리처(Google AI Studio, OpenRouter, Colab)에 없어, 쓰려면 D-31에 처리처를 더하는 결정이 함께 필요하다
   - OpenRouter: 같은 모델이 있고(2026-10-19 엔드포인트 API 확인) 제공자가 여러 곳이다(fp4·fp8 등 양자화가 섞임). D-31 허용 처리처라 처리처 결정이 따로 필요 없다. ## 누수 방지

- dev와 test는 회의 단위로 나뉜다. 같은 `context`를 공유하는 질의는 모두 같은 회의에서 나오므로(`docs/data.md` §11) 문서가 두 분할에 걸치지 않는다.
- test 질의와 test 점수는 검색 단계 종료 전까지 읽거나 계산하지 않는다. 설정 선택, 필터 규칙, 프롬프트 작성에 test 질의를 쓰지 않는다.
- 질의 필터 규칙은 검색 점수를 보기 전에 정한다(미결 사항 1).
- multi-doc 질의 세트는 `test` 분할 회의의 문서를 쓰지 않고, 생성·검수 중에 검색 결과(순위·점수)를 보지 않는다.

## 평가 결과 해석의 한계

수치를 보고할 때 아래 한계를 함께 적는다.

- 질의가 정답 문서를 보고 생성됐다. 정답 문서와 어휘가 많이 겹쳐 실제 사용자 질의보다 검색이 쉽고, 어휘 매칭(BM25)에 유리할 수 있다.
- 질의마다 정답 문서를 하나로 본다. 다른 문서도 답을 담고 있으면 정답으로 세지지 않는다.
- 코퍼스는 회의록 전체가 아니라 질의응답이 만들어진 구간의 발췌다(`docs/data.md` §15).

## 자원 제약

- 상시 지출은 0으로 둔다. 배포는 HF Spaces 무료 CPU, 생성은 무료 쿼터를 쓴다.
- 개발 환경: 로컬 PC RAM 8GB, 상시 GPU 없음. dev-small 작업은 Jupyter 노트북(`notebooks/`)으로 과정과 결과를 기록한다. 코퍼스 임베딩처럼 GPU가 필요한 계산은 dev-small이라도 Colab에서 하고(예상 시간·비용 보고 후 사용자 승인), 노트북은 그 산출물을 불러와 확인한다. 질의 임베딩은 Colab에서 할 수 있다. `test` 질의는 검색 단계 종료 시 1회 실행 외에는 쓰지 않는다(D-07, D-31). 노트북에는 질의 원문을 대량 출력하지 않는다(공개 금지, D-31). 로컬 CPU는 동작 확인 규모로만 쓴다.
- 전체 코퍼스 임베딩은 Colab(보유 크레딧)에서 한다. 처음 실행할 때 소요 시간과 크레딧 소모율을 기록하고, 이후 실행 여부는 사용자가 결정한다.
- 청킹이나 임베딩 모델을 바꾸지 않는 실험(BM25, 결합 방식, top-k, reranker)은 기존 인덱스를 재사용한다.
- 유료 API(OpenRouter)는 첫 평가 전에 예상 비용을 계산해 사용자에게 보고하고, 사용 여부는 사용자가 결정한다.
- AI Hub 데이터는 처리 목적으로 외부 API(Google AI Studio 무료 쿼터, OpenRouter 유료 API)와 Colab에 보낼 수 있다. 재배포 제한이 막는 것은 데이터를 공개하는 일(저장소 커밋, 저장소에 남는 노트북·로그·문서에 질의 원문 대량 기록, 외부에서 내려받을 수 있게 두기)이다(D-31). 질의 전체처럼 많이 보내는 실행은 호출 수·소요 시간·비용을 보고하고 사용자 승인 후에 한다. `test` 질의는 평가 프로토콜에 따라 검색 단계 종료 시 1회 실행 외에는 보내지 않는다. 프로젝트를 공개할 때 데이터는 출처 링크로만 밝힌다. 회의록 발언 원문(`context`)은 공개 자료라 공개 금지 대상이 아니다.
- multi-doc 질의 생성·검증에 쓰는 모델과 경로(무료 쿼터 API, 유료 API, Claude Code 에이전트)는 S8 지시서에서 정한다. 실행 전에 호출 수·비용·소요 시간을 보고하고 사용자 승인 후에 한다. 보내는 것은 `context`와 메타데이터뿐이다.
