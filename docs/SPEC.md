# SPEC: 국회 회의록 RAG 검색

이 SPEC은 검색 단계의 평가 프로토콜을 고정한다. 생성 단계 평가는 검색 베이스라인 이후 이 문서를 개정해 추가하고, 개정 사실을 DECISIONS.md에 기록한다.

## 문제

- 입력: 한국어 자연어 질의 1건
- 출력: 코퍼스 문서 순위 목록 (서로 다른 문서 10개 이상)
- 코퍼스: `data/processed/corpus_context.jsonl`의 고유 `context` 38,516건. 문서 ID는 `doc_id`
- 평가 질의: `data/processed/queries_summary_q.jsonl`의 `query`(= `summary_q`). 질의 ID는 `qid`, 정답은 그 레코드의 `doc_id` 하나

데이터의 성질과 한계는 `docs/data.md`에 있다.

## 평가 프로토콜 (실험 중 고정)

### 분할

- 분할 단위는 회의(`conference_number`)다. 한 회의의 질의는 모두 같은 분할에 들어간다.
- AI Hub의 Training/Validation 구분은 쓰지 않는다. 학습 단계가 없으므로 두 구분은 질의 출처 표시로만 남는다.
- seed 20260929로 회의를 섞은 뒤, 회의구분(`meeting_name`) 비율을 유지하면서 회의를 차례로 배정한다. dev 질의가 3,000건 이상이 되면 멈추고, 이어서 test 질의가 3,000건 이상이 되면 멈춘다. 남은 회의의 질의는 쓰지 않는다.
- `qna_type` 비율은 분할 후 전체 분포와 비교해 기록만 한다.
- 분할 결과는 `data/splits/queries.csv`(`qid`, `conference_number`, `split`)에 저장한다. `data/`는 커밋하지 않으므로 같은 seed로 재생성할 수 있어야 한다. 생성 후 파일 SHA-256을 DECISIONS.md에 적는다.

### 평가 층

| 층 | 코퍼스 | 질의 | 용도 |
| --- | --- | --- | --- |
| dev-small | dev 회의 일부의 전체 문서, 약 1,000건 | 그 문서가 정답인 dev 질의 | 방향을 확인한다. 작업 과정과 결과는 Jupyter 노트북(`notebooks/`)에 남긴다. 판정에 쓰지 않는다 |
| dev-full | 전체 38,516건 | dev 질의 전체 | EXP 채택·기각 판정 |
| test | 전체 38,516건 | test 질의 전체 | 검색 단계 종료 시 1회 보고 |

- dev-small 문서는 dev 회의를 seed 20260929로 섞어 문서 수가 1,000건 이상이 될 때까지 회의 단위로 뽑는다. 문서 목록은 `data/splits/dev_small_docs.txt`에 둔다. 같은 회의 문서를 함께 넣어 회의 내부의 비슷한 문서가 방해 문서로 남게 한다.
- dev-small 점수와 dev-full 점수는 방해 문서 수가 달라 서로 비교하지 않는다. 표를 나눠 적는다.

### 지표

- 문서 순위: 검색기가 청크를 반환하면 각 문서가 처음 나온 순위를 문서 순위로 쓴다.
- 주지표: 문서 단위 Recall@5. 질의별로 정답 문서가 상위 5개 안에 있으면 1, 없으면 0이고, 질의 전체의 평균을 낸다.
- 보조 지표: Recall@1, Recall@10, MRR@10(정답 순위가 10 이내면 1/순위, 아니면 0).
- 모든 지표를 전체와 함께 회의구분별, `qna_type`별로 보고한다.
- 발언이 자기 `context` 안에 없는 169건(`docs/data.md` §7)도 포함한다. 문서 단위 정답은 이 레코드에서도 성립한다.

### 판정

- 기준 실험과의 차이를 dev-full에서 paired bootstrap으로 계산한다. 재표본 단위는 회의, 반복 10,000회, seed 20260929이다. 같은 회의의 질의끼리는 서로 독립이 아니므로 회의 단위로 재표본한다.
- 채택: Recall@5 차이의 95% 구간 하한이 0보다 크고, 점 추정 차이가 +1.0%p 이상
- 기각: 95% 구간 상한이 0보다 작음
- 보류: 그 밖의 경우

## 보조 관찰: multi-doc 질의

평가 질의는 정답 문서가 하나라 Recall@k가 정답 적중 여부(hit rate)와 같다. 답의 근거가 여러 문서에 나뉜 질의에서 검색기가 어떻게 동작하는지는 이 질의로 볼 수 없다. 이를 가늠하려고 정답 문서가 여러 개인 질의 세트를 따로 만들어 관찰한다.

- 판정에 쓰지 않는다. EXP의 채택·기각·보류는 위 판정 절(single-doc dev-full Recall@5)로만 정하고, multi-doc 결과는 같은 EXP에서 함께 보고해 두 평가가 기법을 어떻게 다르게 평가하는지 비교한다.
- 질의 세트: dev 전용이다. 정답 문서는 `test` 분할 회의를 뺀 회의의 문서에서만 고른다. 문서 묶음은 메타데이터(같은 회의, 같은 법안, 같은 질의자, 같은 위원회)로 만들고, 검색기 점수(dense·BM25 유사도)로 고르지 않는다. 검색기로 고르면 세트가 그 검색기에 유리해진다.
- 질의마다 답에 필요한 문서 집합(2개 이상)이 정답이다. 묶음 안의 문서는 모두 정답·무관으로 판정해, 묶음 안에서는 정답 누락이 없게 한다.
- 생성 입력은 `context`와 메타데이터만 쓴다. 기존 평가 질의(`summary_q`)는 넣지 않는다.
- 생성 절차와 검수는 PLAN의 S7·S8·G3에서 정한다. 검수를 마친 세트는 어떤 EXP의 multi-doc 점수도 보기 전에 SHA-256을 DECISIONS.md에 적어 동결하고, 이후 고치지 않는다.
- 지표(문서 순위 규칙은 위 지표 절과 같다)
  - Recall@k: 질의별로 정답 문서 중 상위 k에 든 비율의 평균
  - Complete@k: 정답 문서가 모두 상위 k에 든 질의의 비율
  - Hit@k: 정답 문서가 하나 이상 상위 k에 든 질의의 비율
  - k는 5와 10. 전체와 함께 질의 유형별로 보고한다
- 기준 실험과의 차이는 paired bootstrap 95% 구간으로 보고하되 판정 라벨을 붙이지 않는다. 재표본 단위는 질의를 만든 묶음(같은 회의·법안·질의자 등)이고, 반복 횟수와 seed는 판정 절과 같다.
- 해석의 한계: 이 질의도 정답 문서를 보고 생성됐다(아래 해석의 한계 1항). 묶음 밖의 관련 문서는 정답으로 세지지 않는다. 질의 수가 dev-full보다 훨씬 적어 구간이 넓으므로 방향과 큰 순위 변화만 읽는다.

## 누수 방지

- dev와 test는 회의 단위로 나뉜다. 같은 `context`를 공유하는 질의는 모두 같은 회의에서 나오므로(`docs/data.md` §11) 문서가 두 분할에 걸치지 않는다.
- test 질의와 test 점수는 검색 단계 종료 전까지 읽거나 계산하지 않는다. 설정 선택, 필터 규칙, 프롬프트 작성에 test 질의를 쓰지 않는다.
- 질의 필터 규칙은 검색 점수를 보기 전에 정한다(미결 사항 1).
- multi-doc 질의 세트는 `test` 분할 회의의 문서를 쓰지 않고, 생성·검수 중에 검색 결과(순위·점수)를 보지 않는다.

## 평가 결과 해석의 한계

수치를 보고할 때 아래 한계를 함께 적는다.

- 질의가 정답 문서를 보고 생성됐다. 정답 문서와 어휘가 많이 겹쳐 실제 사용자 질의보다 검색이 쉽고, 어휘 매칭(BM25)에 유리할 수 있다.
- 질의마다 정답 문서를 하나로 본다. 다른 문서도 답을 담고 있으면 정답으로 세지지 않는다.
- 코퍼스는 회의록 전체가 아니라 질의응답이 만들어진 구간의 발췌다(`docs/data.md` §15).

## 자원 제약

- 상시 지출은 0으로 둔다. 배포는 HF Spaces 무료 CPU, 생성은 무료 쿼터를 쓴다.
- 개발 환경: 로컬 PC RAM 8GB, 상시 GPU 없음. dev-small 작업은 Jupyter 노트북(`notebooks/`)으로 과정과 결과를 기록한다. 코퍼스 임베딩처럼 GPU가 필요한 계산은 dev-small이라도 Colab에서 하고(예상 시간·비용 보고 후 사용자 승인), 노트북은 그 산출물을 불러와 확인한다. 질의 임베딩은 dev 질의만 Colab에 올려 할 수 있고, `test` 질의는 올리지 않는다(D-07). 노트북에는 질의 원문을 대량 출력하지 않는다. 로컬 CPU는 동작 확인 규모로만 쓴다.
- 전체 코퍼스 임베딩은 Colab(보유 크레딧)에서 한다. 처음 실행할 때 소요 시간과 크레딧 소모율을 기록하고, 이후 실행 여부는 사용자가 결정한다.
- 청킹이나 임베딩 모델을 바꾸지 않는 실험(BM25, 결합 방식, top-k, reranker)은 기존 인덱스를 재사용한다.
- 유료 API(OpenRouter)는 첫 평가 전에 예상 비용을 계산해 사용자에게 보고하고, 사용 여부는 사용자가 결정한다.
- dev 평가 질의(`summary_q`)는 Google AI Studio 무료 쿼터로 보낼 수 있다(D-10). 무료 쿼터는 약관상 입력을 제품 개선에 쓰고 사람이 읽을 수 있으므로, 질의 전체처럼 많이 보내는 실행은 호출 수와 소요 시간을 보고하고 사용자 승인 후에 한다. `test` 질의는 검색 단계 종료 시 1회 실행 외에는 보내지 않는다. 노트북·로그에 질의 원문을 대량으로 남기지 않는다. 회의록 발언 원문(`context`)은 공개 자료라 이 제한에 해당하지 않는다.
- multi-doc 질의 생성·검증에 쓰는 모델과 경로(무료 쿼터 API, 유료 API, Claude Code 에이전트)는 S8 지시서에서 정한다. 실행 전에 호출 수·비용·소요 시간을 보고하고 사용자 승인 후에 한다. 보내는 것은 `context`와 메타데이터뿐이다.

## 성공·중단 기준

- 목표: 단계별 실험으로 dev-full Recall@5를 베이스라인(0.8584)보다 높여 0.90에 닿는다(DECISIONS D-09).
- 중단: 실험 백로그 소진, 또는 비채택(기각·보류)이 3회 연속 나올 때

## 범위 밖

- 생성 단계 평가. 검색 베이스라인 이후 SPEC 개정으로 다룬다
- 회의록 원문(`original` URL) 수집으로 코퍼스를 넓히는 것
- 임베딩 모델 파인튜닝
- multi-doc 질의의 `test` 세트. 보조 관찰 세트는 판정에 쓰지 않아 dev만 둔다

## 미결 사항

1. `summary_q` 표본 검수: dev에서 100건을 사람이 검수해 불량 유형과 비율을 기록하고, 필터 규칙을 둘지 정한다. 규칙을 정하지 않으면 전체 질의를 쓴다. 이 항목이 끝나기 전에는 실험을 시작하지 않는다.
2. (해결, D-09) 수치 목표: 베이스라인 dev-full 점수가 나온 뒤 정해 DECISIONS.md에 기록한다. dev-full Recall@5 0.90으로 정했다.
3. 배포 제약: 채택할 설정이 HF Spaces 무료 CPU에서 받아들일 만한 질의당 지연 안에 들어야 하는지, 그 상한을 얼마로 둘지
