## D-04 베이스라인 청크 크기 512 토큰, overlap 64 (S4)
- 방법: dev-small(문서 1,007, 질의 1,039)에서 KURE-v1 고정 토큰 청킹 네 후보를 전수 검색으로 비교했다(`docs/slices/04-index.md`). overlap은 크기의 1/8. 결정 규칙은 점수를 보기 전에 정했다: Recall@5 최고 후보를 기준으로, 차이의 95% 구간(회의 단위 bootstrap)이 0을 포함하는 후보 중 청크 수가 가장 적은 것
- 결과(질의 단위 정답 순위는 `data/runs/chunk_sweep.json`)

| 크기 | 청크 수 | 문서당 청크 | R@1 | R@5 | R@10 | MRR@1 | MRR@5 | MRR@10 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 256 | 5,590 | 5.55 | 0.8845 | 0.9721 | 0.9827 | 0.8845 | 0.9209 | 0.9223 |
| 512 | 2,995 | 2.97 | 0.8739 | 0.9673 | 0.9817 | 0.8739 | 0.9134 | 0.9151 |

- 회의구분별: 소위원회는 R@5가 256·512 모두 0.9612로 같고, 본회의·특별위원회에서 8192가 가장 크게 떨어진다(R@1 0.69·0.72). `qna_type`별 차이는 추출형이 주도한다
- 결정: 512/64. 규칙상 256과 512는 구간이 0을 포함하고, 그중 청크가 적은 512를 고른다. 보조 지표도 256이 근소하게 높지만 모두 구간이 0을 포함한다
- 이유: (1) 사용자가 데이터를 본 결과 256 청크에는 답변에 필요한 내용이 충분히 담기지 않는다 (2) 256은 벡터 수가 약 1.9배라 Colab 시간·인덱스 크기가 비례해 는다 (3) dev-full은 방해 문서가 약 38배 많아, 청크가 작고 많을수록 오답 청크가 상위에 올 기회가 는다. dev-small의 작은 차이보다 512의 이득이 크다고 판단했다
- 한계: dev-small은 방해 문서가 약 1,000개라 전체 코퍼스에서 순위가 달라질 수 있다(H3에서 확인). dev-small 질의는 dev-full 질의의 일부다. 작은 청크가 R@1에서 강한 경향은 다중 크기 청킹(H9)의 근거로 남긴다
- 날짜: 2026-10-01

## D-08 naive 검색은 numpy 전수 검색, `chunk_pool` 200 (S5)
- 결정: 질의마다 모든 청크와 내적해 청크 점수 내림차순에서 문서가 처음 나온 순서로 상위 10개 문서를 고른다. 상위 `retriever.chunk_pool`(200)개 청크만 정렬하고, 그 안에 서로 다른 문서가 10개 없으면 그 질의만 전체를 정렬한다. 질의는 `retriever.query_batch`(256)개씩 나눠 내적한다

- ANN·벡터 DB는 배포 단계나 별도 실험에서 정한다
- 날짜: 2026-10-02

## D-09 수치 목표: dev-full Recall@5 0.90 (SPEC 미결 2)
- 베이스라인(KURE-v1, 512/64, 전수 검색): dev-full Recall@1 0.7062, Recall@5 0.8584(회의 단위 bootstrap 95% 구간 [0.8428, 0.8741]), Recall@10 0.8909, MRR@10 0.7707. 순위 파일 SHA-256 `f15688433784bd1682d6063333150d721957a7233758c512c1a98d8da18bbbe2`
- 결정: 단계별 실험으로 dev-full Recall@5 0.90(베이스라인 대비 +4.2%p)에 닿는 것을 목표로 한다. 사용자가 노트북을 보고 정했다
- 이유: 0.90은 현재 Recall@10(0.8909)보다 높아, 지금 상위 10개를 재순위화하는 것만으로는 닿지 않고 1차 후보 재현율도 올려야 한다. 0.88(+2.2%p)은 구간 폭(3.13%p)보다 작아 실험 두세 개로 닿을 수 있고, 0.92 이상은 10위 밖 실패(10.9%)를 절반 넘게 줄여야 해 근거가 약하다
- 한계: 질의 가운데 질의만으로 정답 문서를 특정하기 어려운 것(G1 추정 4\~6%, 하한)과 같은 주제가 여러 회의에 반복되는 일반적인 질의가 있어, 이 질의 집합에서 닿을 수 있는 Recall@5는 1보다 낮다(약 0.94\~0.96으로 추정). 질의는 고치지 않는다(사용자 결정). 점수를 본 뒤 실패 사례를 보고 고치면 점수가 부풀려지고(SPEC 누수 방지), `test` 질의에는 같은 수정을 할 수 없으며, 이런 잡음은 paired 비교에서 기준·후보에 똑같이 들어간다. G1 무작위 표본 100건에서 5위 밖 비율은 판정별로 PASS 12.5%·PARTIAL 18%·FAIL 14%로 질의 품질과 뚜렷하게 연결되지 않았다. 대신 검색 단계 종료 시 보조 분석(PLAN G2)을 한다
- 날짜: 2026-10-02

## D-12 SPEC 개정: multi-doc 질의 보조 관찰 추가
- 결정: 정답 문서가 여러 개인 dev 질의 세트를 만들어 보조 관찰로 둔다(SPEC "보조 관찰: multi-doc 질의" 절, PLAN S7·S8·G3·S9). 채택·기각·보류 판정은 기존 single-doc dev-full Recall@5 규칙만 쓰고, multi-doc 결과는 같은 EXP에서 함께 보고해 비교한다. 지표는 Recall@k·Complete@k·Hit@k(k=5, 10), 기준과의 차이는 묶음 단위 paired bootstrap 구간으로 보고하되 판정 라벨을 붙이지 않는다. 채점 코드는 `src/rag/eval/`을 고치지 않고 `src/rag/eval_multi/`에 둔다
- 이유: 평가 질의는 정답 문서가 하나라 Recall@k가 적중률과 같아, 근거가 여러 문서에 나뉜 질의에서의 동작을 볼 수 없다. 데이터의 이 한계를 전제로, 만든 검색기가 multi-doc 환경에서 어떻게 동작할지 가늠하려는 관찰이다(사용자 결정). 판정에 넣지 않는 것은 지표를 여럿 두고 유리한 쪽을 고르는 것처럼 보이지 않게 하기 위해서다
- 누수 방지: 문서 묶음은 메타데이터로 만들고 검색기 점수로 고르지 않는다. `test` 분할 회의의 문서는 쓰지 않는다. 세트는 어떤 EXP의 multi-doc 점수도 보기 전에 SHA-256을 이 문서에 적어 동결한다. 판정에 쓰지 않으므로 `test` 세트는 두지 않는다
- 날짜: 2026-10-05

## D-14 multi-doc 질의 생성·검사 방식과 판정 규칙 (S8)
- 결정
  - 생성: Claude Code Sonnet 에이전트 `multidoc-writer`(읽기·쓰기 범위 훅, ADR-0017\~0019). 지시는 `configs/multidoc/prompt/gen_vN.yaml`, 유형별 버전 `conf`·`questioner` gen_v4, `law` gen_v3. 정답 문서 2개 이상 `max_gold` 5개 이하, 같은 회의의 같은 쟁점 문서는 모두 정답에 넣는다. 입력에 질의자 이름·직위를 넣고 `questioner`는 인물 중심 질의(회의별 열거형·입장 변화형, 열거형은 한 회의 안)를 쓴다. `conf`는 쟁점형만 쓴다
  - 검사: Claude Code Sonnet 에이전트 `multidoc-checker`(2026-10-07 사용자 결정, ADR-0020, `docs/slices/08c-checker-agent.md`). 검사 지시는 `check_v3`(사실 하나에 한 가지 내용만 쓴다)이다. 그 전 파일럿은 OpenRouter `openai/gpt-6-luna`(`check_v2`)로 검사했다. 검사 입력에는 생성 쪽 시작 묶음·답·근거를 넣지 않고 질의와 후보 집합 전체 원문·질의자만 넣는다. 검사 에이전트는 훅으로 생성 출력을 읽지 못한다
  - 판정(코드): 생성 쪽 인용이 모두 원문에 있음, `answerable`, 정답 문서 2개 이상, 정답 문서마다 그 문서에만 있는 요소(필요성), 정답 집합 = 생성 쪽 시작 묶음. 규칙 5(시작 묶음 일치)는 G3 검수 뒤 다시 정한다
  - 인용 대조(S8b에서 갱신): 인용이 원문에 그대로 있으면 인정한다. 그대로 없으면 문서를 `multidoc.check.quote_semantic.window_sentences`(3)문장씩 묶은 대목 중 rapidfuzz `partial_ratio` 상위 `top_k`(3)개를 골라 Jev(`typesafe/jev-1.13`, `quote_v1`)에 "후보 대목 가운데 인용과 같은 의미가 있는가"를 `noul`로 묻고, 확률이 `min_prob`(0.9) 이상이면 인정한다. 문자 유사도는 후보를 고르는 데만 쓴다. 이 인정 기준은 생성 쪽 인용에도 같다. 확률은 검사 기록(`quote_checks`)에 남겨 재판정 때 다시 묻지 않는다. 인용 대조는 지어낸 근거를 걸러내는 용도이고, 인정한 인용의 문구를 원문에 맞춰 고치지 않는다. 출력(`queries.jsonl`)의 인용은 검사 모델이 쓴 그대로다. RAG 평가에 필요한 것은 같은 의미의 근거가 원문에 있는지이고, 문구를 원문과 같게 고치는 처리는 부차적이라 세세한 기준을 코드로 두지 않는다(사용자, PR #31). 인정하지 못한 검사 쪽 근거는 확인할 수 없는 근거라 바로 탈락시키지 않고, 그 근거를 빼고 판정한 결과와 두고 판정한 결과의 통과 여부가 다를 때만 `quote_dependent`로 불통과한다
  - 본 생성 후보 집합: `conf`·`questioner` 350, `law` 250(D-13 갱신)
- 근거: `notebooks/08_01_파일럿.ipynb`, `notebooks/08_02_인용의미.ipynb`, `notebooks/08_03_검사모델.ipynb`, `docs/slices/08-multidoc-queries.md` 파일럿 절, `docs/slices/08b-quote-semantic.md`, `docs/slices/08c-checker-agent.md`
  - 파일럿 통과율 v1 5/30, v2 8/30, v3·v4 11/40. v3·v4에서 생성 쪽 인용 오류는 0건, `quote_missing` 11건은 모두 검사 쪽 인용 1\~2개 오류라 규칙 1을 바꿨다(새 규칙 15/40). 1차 뒤에는 규칙 1 완화를 채택하지 않았는데, 생성 쪽 오류 0건이라는 근거가 새로 생겼다
  - 규칙 1 변경의 목적(사용자, PR #30): 검사 모델의 실수·성능 한계로 수율이 떨어지는 것을 막는다. 파일럿에 검사가 인용 오류로 지적했지만 문제가 없던 질의가 있었다. 그래서 검사 쪽 인용 오류만이 문제인 경우 다른 규칙(규칙 2\~5)의 위반 여부로 판정한다. 정답 집합 판정(필요성, 시작 묶음 일치)에도 인용 문제가 끼어들 수 있으나, 인용 문제와 상관없이 다른 규칙에 걸리면 생성 질의가 multi-doc 원칙을 따르지 않은 것으로 판정한다
  - 인용 대조 방식(사용자, PR #30 병합 뒤): 표현을 바꿔 옮긴 인용은 인용 오류로 보지 않는다. LLM은 지시가 있어도 표현을 바꾸므로(`check_v2`에 이미 원문 그대로 복사 지시가 있다) 지시 강화보다 유사도 대조를 택했다. 파일럿의 원문과 다른 검사 쪽 인용 14개는 모두 접속어·존칭·낱말을 바꿔 옮긴 것이고(20자 이상, 유사도 0.86\~0.99), 지어낸 인용은 없었다. 원문에 그대로 있는 인용을 같은 후보 집합의 다른 문서에 대조한 4,285쌍에서 0.8 이상은 1건(같은 명단이 다른 문서에도 있는 경우)이고, 0.6 이상 37건 가운데 격식어가 겹친 짧은 인용(8\~9자)이 섞여 있어 15자 미만은 정확 대조만 한다(노트북 9절). 사용자는 국회 격식어 때문에 문자 유사도가 내용과 무관하게 높아질 수 있어 인용 대조를 필터로 쓰는 것 자체가 어렵다고 보고, 필터를 쓰지 않는 방향과 0.6·0.8 두 기준에 중간 지대를 따로 판정하는 방향을 검토했다. 그 결과 확인되지 않은 근거에 판정이 좌우될 때만 불통과시키는 방식을 채택했다. 필터를 아예 쓰지 않으면 검사가 지어낸 근거가 정답 집합에 그대로 들어가고, 중간 지대 규칙은 파일럿에 그 구간의 바꿔 옮긴 인용이 없어 근거 없이 정해야 하기 때문이다. 근거를 빼고만 판정하면 시작 묶음 밖 문서가 실제로 정답이어도 통과하고, 두고만 판정하면 틀린 근거로 문서가 정답에 들어간다. 이 방식은 두 경우를 모두 막는다. 본 생성에서 인정하지 못한 인용 수와 `quote_dependent` 수를 보고한다. 파일럿은 14개가 모두 대조돼 통과 15건 그대로다
  - 의미 판정으로 바꾼 이유(사용자, S8b): 인용 검증의 목적은 근거로 삼은 문장과 같은 의미가 근거 문서에 있는지이고, 문자 유사도는 의미를 판정하지 못한다. 실제 인용의 뜻을 부정·숫자·주체만 바꾼 변형 30개 중 28개가 `partial_ratio` 0.8 이상이었다. 같은 변형에 Jev는 0.9 이상이 4개였고 모두 부정 변형이다(숫자·주체 변형은 0개). 바꿔 옮긴 인용 14개와 원문 그대로 인용 10개는 모두 0.93\~0.98이다. 다른 문서 대조 37쌍 중 0.84 이상 3쌍은 원문을 보니 실제로 같은 의미였고, 이를 빼면 최대 0.66이다. 같은 입력을 다시 보내면 확률 차이는 0.01 이하이고, 157호출에 $0.0045, 지연 중앙값 0.43초다(`notebooks/08_02_인용의미.ipynb`). 기준을 0.95로 올려도 부정 변형은 0.96으로 통과하고 양성 일부만 떨어져 0.9로 둔다. 남는 위험은 부정 변형을 놓치는 것이고, 판정 대상은 원문에 그대로 없는 인용(파일럿 516개 중 14개)뿐이다. LLM으로 의미를 판정하는 방식은 비용과 지연 때문에, 로컬 NLI는 한국어 회의록 성능을 확인하지 못해 택하지 않았다
  - 인용이 요소의 사실을 뒷받침하는지는 판정 규칙에 넣지 않는다(사용자, S8b). 같은 Jev 실험에서 검사 모델이 붙인 근거 30쌍은 중앙값 0.70, 다른 요소와 엇갈린 30쌍은 0.10으로 갈렸지만, 확률이 낮은 근거 6쌍 중 3쌍은 사실이 여러 내용을 합친 문장이라 인용이 일부만 담은 경우였고, G3 검수에서 무관하다고 본 conf-0005 D2 근거는 0.74로 높게 나왔다. 검사 출력이 사실을 합쳐 쓰는 한 규칙에 넣으면 정상 근거가 떨어진다. 검사를 Sonnet 에이전트(`check_v3`)로 바꾼 뒤 같은 질문으로 다시 잰 결과(S8c, 60호출 $0.00116)는 양성 중앙값 0.80, 0.5에서 양성 26/30·음성 1/30으로 조금 나아졌다. 0.5 아래 양성 4쌍은 모두 사실 문장이 인용보다 넓거나 요소의 근거 여러 개 중 하나인 부분 뒷받침이었고, 재검사에서 사람과 어긋난 conf-0005(무관 문서 추가)와 conf-0011(원문에 없는 인과)은 뒷받침 판정으로 잡히지 않는다. 그래서 규칙에 넣지 않는다(사용자, 2026-10-07)
  - 파일럿 재검사(S8c, `check_v3`, 2026-10-07): 후보 집합 40 → 생성 `ok` 31 → 통과 20(`conf` 8, `law` 7, `questioner` 5). luna 통과 15건은 모두 Sonnet도 통과했다. 불통과 사유는 `seed_mismatch` 10(luna 10), `substitutable` 7(luna 12), `unanswerable` 0(luna 1). 검사 인용 205개가 모두 원문에 그대로 있어 Jev 호출은 0건이다(luna는 413개 중 14개). G3 갈린 5건에서 사람과 같은 판정은 Sonnet 3건, luna 2건이다. 후보 집합당 수율(`conf` 0.40, `law` 0.70, `questioner` 0.50)을 준비 수(`conf`·`questioner` 350, `law` 250)에 그대로 곱하면 약 490건이다. 파일럿이 40개라 불확실하고 G3 검수에서 빠질 분량이 있어 준비 수를 그대로 둔다(사용자. 처음 보인 외삽은 `law`도 350으로 계산한 약 560건이었고, 490건으로 정정한 뒤 다시 확인받았다)
  - 같은 31건을 Sonnet 서브에이전트로 검사한 비교에서(진단용) 새 규칙 통과 luna 15, Sonnet 20이고 갈린 5건은 모두 Sonnet만 통과였다. `seed_mismatch`는 두 검사가 함께 내 생성 쪽 누락으로 본다. 검사 모델을 바꾸면(gpt-6-sol 등) 본 생성 검사 비용이 약 $2.5에서 약 $50으로 늘어 luna를 유지하고, 갈린 5건은 G3 파일럿 검수에서 사람이 본다. luna가 충분하지 않다는 지적에 일부 동의하지만 비용 대비 성능으로 luna로 진행한다(사용자, PR #30). 이 결정은 아래 PR #31 코멘트로 바뀌었다
  - 검사 모델을 Sonnet 에이전트로 바꾼 이유(사용자, PR #31 코멘트 2026-10-07): 생성과 검사가 같은 계열일 때의 self-evaluation bias를 피하려고 가격·성능·한국어 실력을 따져 luna를 골랐지만, 파일럿 검사에서 luna와 Sonnet의 차이를 봤고(위 31건 비교) 벤치마크 성능 차이도 크다(artificialanalysis.ai의 claude-sonnet-5-5 대 gpt-6-luna 비교). 가격을 고려하면 bias를 피하면서 Sonnet에 견줄 모델을 찾지 못해, bias보다 성능을 택했다. Claude Code 에이전트로 돌려 API 비용이 없다. 판단 모델 `typesafe/jev-1.13`도 검토했지만 선택형 출력이라 근거 인용을 낼 수 없어 검사에서 뺐다(인용 의미 판정에는 쓴다). 결정 직후 G3 파일럿 검수로 갈린 5건을 사람이 봤다: Sonnet 판정이 맞은 3건(conf-0005, conf-0018, questioner-0005)은 luna가 무관한 문서를 근거로 붙이거나 요소를 잘못 나눠 `substitutable`로 떨어뜨린 경우이고, luna가 맞은 2건(conf-0011 `unanswerable`, conf-0014 `seed_mismatch`)은 Sonnet이 원문에 없는 인과나 문서 누락을 받아들인 경우다. 같은 계열 bias를 줄이는 장치로 검사 입력에서 생성 쪽 정보를 빼고, 훅으로 생성 출력 읽기를 막고, 통과는 코드가 정한다
  - 새 규칙 통과율로 유형별 250개면 약 312건이라 300건에 여유가 없어 `conf`·`questioner`를 늘렸다(기대 약 378건). `law`를 늘리면 S7 난수 소비가 바뀌어 `questioner` 순서와 이미 만든 생성 결과가 어긋나므로 250에 둔다. 이 경우 기대치의 약 40%가 `law`다. 원천 데이터가 법안 심사와 관련 질의를 학습시키려고 정제한 회의록이라 법안 심사 회의 쏠림은 피할 수 없다고 보고 받아들인다(사용자, PR #30)
  - `queries.jsonl`은 검사 기록 전체에서 만든다. `n_per_type`은 새로 호출할 대상만 고른다(PR #30 코멘트 결정 (a)). 실행 명령에 덧붙이는 값에 따라 동결 세트가 달라지지 않게 하기 위해서다
  - 노트북 출력의 원문 발췌와 생성 질의는 공개한다. 원문은 공개된 국회 회의록이고 생성 질의는 타인에게 저작권이 있는 자료가 아니다(사용자, PR #30)
