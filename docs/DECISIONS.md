## D-04 베이스라인 청크 크기 512 토큰, overlap 64 (S4)

- 한계: dev-small은 방해 문서가 약 1,000개라 전체 코퍼스에서 순위가 달라질 수 있다(H3에서 확인). dev-small 질의는 dev-full 질의의 일부다. 작은 청크가 R@1에서 강한 경향은 다중 크기 청킹(H9)의 근거로 남긴다

- ANN·벡터 DB는 배포 단계나 별도 실험에서 정한다

## D-09 수치 목표: dev-full Recall@5 0.90 (SPEC 미결 2)
- 베이스라인(KURE-v1, 512/64, 전수 검색): dev-full Recall@1 0.7062, Recall@5 0.8584(회의 단위 bootstrap 95% 구간 [0.8428, 0.8741]), Recall@10 0.8909, MRR@10 0.7707. 순위 파일 SHA-256 `f15688433784bd1682d6063333150d721957a7233758c512c1a98d8da18bbbe2`

- 이유: 0.90은 현재 Recall@10(0.8909)보다 높아, 지금 상위 10개를 재순위화하는 것만으로는 닿지 않고 1차 후보 재현율도 올려야 한다. 0.88(+2.2%p)은 구간 폭(3.13%p)보다 작아 실험 두세 개로 닿을 수 있고, 0.92 이상은 10위 밖 실패(10.9%)를 절반 넘게 줄여야 해 근거가 약하다
- 한계: 질의 가운데 질의만으로 정답 문서를 특정하기 어려운 것(G1 추정 4\~6%, 하한)과 같은 주제가 여러 회의에 반복되는 일반적인 질의가 있어, 이 질의 집합에서 닿을 수 있는 Recall@5는 1보다 낮다(약 0.94\~0.96으로 추정). 질의는 고치지 않는다(사용자 결정). 점수를 본 뒤 실패 사례를 보고 고치면 점수가 부풀려지고(SPEC 누수 방지), `test` 질의에는 같은 수정을 할 수 없으며, 이런 잡음은 paired 비교에서 기준·후보에 똑같이 들어간다. G1 무작위 표본 100건에서 5위 밖 비율은 판정별로 PASS 12.5%·PARTIAL 18%·FAIL 14%로 질의 품질과 뚜렷하게 연결되지 않았다. 대신 검색 단계 종료 시 보조 분석(PLAN G2)을 한다 이후 변경: G2 범위와 결과는 D-34

## D-12 SPEC 개정: multi-doc 질의 보조 관찰 추가
- 결정: 정답 문서가 여러 개인 dev 질의 세트를 만들어 보조 관찰로 둔다(SPEC "보조 관찰: multi-doc 질의" 절, PLAN S7·S8·G3·S9). 채택·기각·보류 판정은 기존 single-doc dev-full Recall@5 규칙만 쓰고, multi-doc 결과는 같은 EXP에서 함께 보고해 비교한다. 지표는 Recall@k·Complete@k·Hit@k(k=5, 10), 기준과의 차이는 묶음 단위 paired bootstrap 구간으로 보고하되 판정 라벨을 붙이지 않는다. 채점 코드는 `src/rag/eval/`을 고치지 않고 `src/rag/eval_multi/`에 둔다 이후 변경: 메타데이터 가설은 multi-doc으로 판정하고(D-18), `--single`이면 판정 라벨을 낸다(D-43, 이때 `src/rag/eval/bootstrap.py`도 고침)
- 이유: 평가 질의는 정답 문서가 하나라 Recall@k가 적중률과 같아, 근거가 여러 문서에 나뉜 질의에서의 동작을 볼 수 없다. 데이터의 이 한계를 전제로, 만든 검색기가 multi-doc 환경에서 어떻게 동작할지 가늠하려는 관찰이다(사용자 결정). 판정에 넣지 않는 것은 지표를 여럿 두고 유리한 쪽을 고르는 것처럼 보이지 않게 하기 위해서다
- 누수 방지: 문서 묶음은 메타데이터로 만들고 검색기 점수로 고르지 않는다. `test` 분할 회의의 문서는 쓰지 않는다. 세트는 어떤 EXP의 multi-doc 점수도 보기 전에 SHA-256을 이 문서에 적어 동결한다. 판정에 쓰지 않으므로 `test` 세트는 두지 않는다

## D-14 multi-doc 질의 생성·검사 방식과 판정 규칙 (S8)
- 결정
  - 생성: Claude Code Sonnet 에이전트 `multidoc-writer`(읽기·쓰기 범위 훅, ADR-0017\~0019). 지시는 `configs/multidoc/prompt/gen_vN.yaml`, 유형별 버전 `conf`·`questioner` gen_v4, `law` gen_v3. 정답 문서 2개 이상 `max_gold` 5개 이하, 같은 회의의 같은 쟁점 문서는 모두 정답에 넣는다. 입력에 질의자 이름·직위를 넣고 `questioner`는 인물 중심 질의(회의별 열거형·입장 변화형, 열거형은 한 회의 안)를 쓴다. `conf`는 쟁점형만 쓴다
  - 검사: Claude Code Sonnet 에이전트 `multidoc-checker`(2026-10-07 사용자 결정, ADR-0020, `docs/slices/08c-checker-agent.md`). 검사 지시는 `check_v3`(사실 하나에 한 가지 내용만 쓴다)이다. 그 전 파일럿은 OpenRouter `openai/gpt-6-luna`(`check_v2`)로 검사했다. 검사 입력에는 생성 쪽 시작 묶음·답·근거를 넣지 않고 질의와 후보 집합 전체 원문·질의자만 넣는다. 검사 에이전트는 훅으로 생성 출력을 읽지 못한다
  - 판정(코드): 생성 쪽 인용이 모두 원문에 있음, `answerable`, 정답 문서 2개 이상, 정답 문서마다 그 문서에만 있는 요소(필요성), 정답 집합 = 생성 쪽 시작 묶음. 규칙 5(시작 묶음 일치)는 G3 검수 뒤 다시 정한다 → 유지(D-15)
  - 인용 대조(S8b에서 갱신): 인용이 원문에 그대로 있으면 인정한다. 그대로 없으면 문서를 `multidoc.check.quote_semantic.window_sentences`(3)문장씩 묶은 대목 중 rapidfuzz `partial_ratio` 상위 `top_k`(3)개를 골라 Jev(`typesafe/jev-1.13`, `quote_v1`)에 "후보 대목 가운데 인용과 같은 의미가 있는가"를 `noul`로 묻고, 확률이 `min_prob`(0.9) 이상이면 인정한다. 문자 유사도는 후보를 고르는 데만 쓴다. 이 인정 기준은 생성 쪽 인용에도 같다. 확률은 검사 기록(`quote_checks`)에 남겨 재판정 때 다시 묻지 않는다. 인용 대조는 지어낸 근거를 걸러내는 용도이고, 인정한 인용의 문구를 원문에 맞춰 고치지 않는다. 출력(`queries.jsonl`)의 인용은 검사 모델이 쓴 그대로다. RAG 평가에 필요한 것은 같은 의미의 근거가 원문에 있는지이고, 문구를 원문과 같게 고치는 처리는 부차적이라 세세한 기준을 코드로 두지 않는다(사용자, PR #31). 인정하지 못한 검사 쪽 근거는 확인할 수 없는 근거라 바로 탈락시키지 않고, 그 근거를 빼고 판정한 결과와 두고 판정한 결과의 통과 여부가 다를 때만 `quote_dependent`로 불통과한다
  - 본 생성 후보 집합: `conf`·`questioner` 350, `law` 250(D-13 갱신)
  - 운영(사용자, PR #37 코멘트): 본 생성 한 번 동안 생성·검사 지시(`multidoc.gen`·`multidoc.check`의 `prompt_version`)를 바꾸지 않는다. 검사 기록의 지시 버전·SHA는 판정 시점 config 값이라 이 전제가 있어야 실제 지시와 같다. 검사 모델은 Sonnet으로 정했으므로 기록에는 검사 주체(`multidoc-checker`)만 남긴다. 형식이 틀린 검사 출력(세션이 끊겨 쓰다 만 출력도 같은 경로다)은 다시 검사하되, 후보 집합당 거부가 `max_rejects`(3)회에 닿으면(검사는 처음 포함 모두 3회) 자동 재검사를 멈추고 보류로 둔다. 보류는 통과·불통과 어느 쪽에도 넣지 않고 메인이 보고해 처리를 정한다. 검사 모델의 형식 실수로 생성 질의를 불통과시키지 않기 위해서다(사용자, PR #38 코멘트)
- 근거: `notebooks/08_01_파일럿.ipynb`, `notebooks/08_02_인용의미.ipynb`, `notebooks/08_03_검사모델.ipynb`, `docs/slices/08-multidoc-queries.md` 파일럿 절, `docs/slices/08b-quote-semantic.md`, `docs/slices/08c-checker-agent.md`
  - 파일럿 통과율 v1 5/30, v2 8/30, v3·v4 11/40. v3·v4에서 생성 쪽 인용 오류는 0건, `quote_missing` 11건은 모두 검사 쪽 인용 1\~2개 오류라 규칙 1을 바꿨다(새 규칙 15/40). 1차 뒤에는 규칙 1 완화를 채택하지 않았는데, 생성 쪽 오류 0건이라는 근거가 새로 생겼다

  - 인용 대조 방식(사용자, PR #30 병합 뒤): 표현을 바꿔 옮긴 인용은 인용 오류로 보지 않는다. ## D-18 SPEC 개정: 메타데이터 가설의 multi-doc 판정, 가설 단위 중단 기준
- 변경 1: SPEC 판정 절에 "메타데이터 가설의 판정"을 더했다. 문서 메타데이터를 검색에 쓰는 가설(PLAN [메타데이터])은 single-doc 판정이 채택이면 채택, 기각이면 기각하고, 보류이면 multi-doc 세트로 정한다. 채택은 multi-doc Recall@5 차이의 95% 구간 하한 > 0, 점 추정 ≥ +1.0%p, Complete@5 차이의 95% 구간 상한 ≥ 0이다. 기각은 Recall@5 구간 상한 < 0, 그 밖은 보류다. 재표본 단위는 `pool_id`(D-16), 반복 10,000회, seed 20260929. 보조 관찰 절의 "판정에 쓰지 않는다"에 이 예외를 적었다 보강: D-35(+1.0%p 해석), D-43(판정 함수)
- 이유(사용자): single-doc 기준으로 지금 검색기는 일정 수준 이상의 정확도를 보이고(hybrid dev-full Recall@5 0.9168, D-17), 실사용 환경은 날짜·위원회·위원 이름으로 회의를 지목하는 multi-doc 질의에 가깝다. 진단 결과 single-doc 질의는 이런 표현을 거의 쓰지 않아(연도 1.0%, 날짜 0.3%, 위원회 3.0%, 이름 6.9%, 하나라도 10.4%) 메타데이터 효과를 single-doc으로 판정하기 어렵다. 이 경로의 single-doc 이득 상한은 약 +0.76%p(언급 질의 314건 중 hybrid 5위 밖 비율 0.0732를 모두 고친 경우, 314 × 0.0732 / 3,016. 언급하지 않은 질의에는 효과가 없다고 가정)로 채택 기준 +1.0%p에 못 미친다. multi-doc 질의는 거의 모두 이런 표현을 쓰지만 정답 본문에는 드물다(날짜 2%, 연도 16%, 위원회 18%)
- 지표: 정답 문서가 최대 5개라 Recall@5와 함께 Complete@5를 본다(사용자). Complete@5는 떨어지지 않는 것만 요구한다
- 단서(사용자 인지): multi-doc 세트는 메타데이터로 묶음을 만들고 질의도 메타데이터로 회의를 지목해 메타데이터 검색에 유리하다. 문서 메타데이터를 검색에 쓰는 것은 누수가 아니라 일반적인 방법이다. 질의 행의 라벨(정답 문서의 화자 등)을 쓰는 것은 여전히 누수다(PLAN H12). multi-doc 세트에는 test가 없어 이 규칙으로 채택한 결정은 검색 단계 종료 시 다시 확인할 수 없다
- 변경 2: 성공·중단 기준의 "비채택(기각·보류)이 3회 연속 나올 때 중단"을 "한 가설에서 변형을 바꿔 시험한 EXP가 3회 연속 비채택이면 그 가설을 멈추고 다음 항목으로 넘어간다"로 바꿨다. 서로 다른 가설의 비채택은 이어서 세지 않는다. 전체 중단은 백로그 소진이다. 보완(사용자, PR #47·#48 코멘트): 한 가설은 한 백로그 항목 안의 변형(파라미터 변경 등)이고, 첫 EXP는 세지 않고 그 뒤 변형만 센다. 사이에 다른 항목의 EXP가 있어도 셈을 끊지 않는다
- 이유(사용자): 이 기준은 한 가설 안에서 변형을 계속 바꾸며 파고드는 것을 막으려는 것이지 서로 다른 실험의 실패 횟수를 세려는 것이 아니다

## D-35 SPEC 판정의 +1.0%p는 자동 채택선으로 해석한다
- 결정: SPEC 판정 절의 "점 추정 차이 +1.0%p 이상"은 바꾸지 않고, 사람 판단 없이 채택하는 선으로 해석한다. +1.0%p 미만이고 95% 구간 하한 > 0인 보류는 D-33의 선례(층별·multi-doc 하락 없음, 운영 비용 변화 없음 등)로 사용자가 정한다(사용자 결정 2026-10-19)
- 경위: +1.0%p는 첫 커밋(0dcd1e7, 2026-09-29)의 SPEC에 이유 없이 들어갔고, 베이스라인 점수(2026-10-02, D-09)보다 먼저다. 같은 커밋의 문서 작성 원칙("판정 기준에는 seed 변동을 고려한 최소 개선 폭을 넣는다")을 따르면서 변동 폭을 재지 않고 정한 값으로 본다(추론). D-09의 베이스라인 bootstrap 구간 폭(3.13%p)은 수치 목표를 정하는 데만 썼다. 이전 프로젝트 기록에서도 효과 크기 하한은 미확정이었다
- 이유: 검색 파이프라인은 결정적이라 seed 변동이 없다. 점수의 흔들림은 평가 질의 표본에서 오고, 이것은 회의 단위 paired bootstrap 구간 하한 > 0 조건이 맡는다. +1.0%p에 남는 역할은 비용·복잡도를 더할 만큼의 개선인지와, 같은 dev-full을 반복해 써서 생긴 낙관을 흡수하는 여유인데, 두 역할 모두 1.0이라는 값의 근거는 없다. 지금 값을 바꾸면 결과를 본 뒤 기준을 고치는 셈이고 지난 판정도 달라지지 않는다. 남은 검색 실험은 EXP-017뿐이고, G2 기준 리랭커 밖의 변경은 +1.0%p에 닿지 못한다(D-34)
- 실제 운영: EXP-014는 +0.76%p [+0.38, +1.16]로 예외 채택(D-32), EXP-015는 +0.43%p [+0.07, +0.80]이지만 multi-doc 하락으로 채택하지 않았고, EXP-012는 구간이 0을 포함했다. D-28(EXP-009)은 구간이 0을 포함했지만 이후 실험이 올라설 부품의 편향을 바로잡으려고 예외로 올렸다
- 반복 사용의 확인: dev-full을 반복해 쓴 대가는 검색 단계 종료 시 test 1회가 확인한다. test 보고에 dev 누적 이득(0.8584 → 기준)이 test에서 얼마나 유지되는지 함께 적는다
- 생성 평가: SPEC에 생성 평가를 추가할 때는 기준 설정을 반복 실행해 API 비결정성(D-11)과 judge 잡음의 변동 폭을 잰 뒤, 그 근거로 최소 개선 폭이 필요한지와 값을 정한다(`docs/ML 프로젝트 문서 작성 원칙.md` EXP 원칙) → 변동 폭 D-50, 최소 개선 폭 δ 0.02는 D-53
- 문서 반영: SPEC 판정 절에 이 해석을 한 줄로 더했다(사용자 승인, PR #92 코멘트 2026-10-19 "SPEC 문서를 결정에 맞춰 수정하세요", 반영 2026-10-20). +1.0%p 값과 채택·기각·보류 조건은 그대로다
- 메타데이터 가설: SPEC "메타데이터 가설의 판정" 2단계(multi-doc)의 +1.0%p에도 같은 해석을 적용한다(사용자 결정 2026-10-21, 이슈 #120). 예: multi-doc Recall@5 +0.8%p [+0.2, +1.4]이고 Complete@5 구간 상한 ≥ 0이면 보류이고, 예외로 올릴지는 D-33의 선례로 사용자가 정한다. 판정 함수(코드 리뷰 2026-10 D-2)는 채택·기각·보류만 내고, 이 경우는 판정 보고에서 예외 검토 대상으로 적는다. 지난 multi-doc 단계 채택(EXP-003 +14.71%p, EXP-004 +35.54%p, EXP-008 +1.65%p)은 모두 +1.0%p 이상이라 판정이 바뀌지 않는다. SPEC 메타데이터 판정 절에 이 해석을 한 줄로 더했다(같은 결정, 선택지에 SPEC 한 줄 추가를 적어 승인받음)
- 날짜: 2026-10-19 (메타데이터 가설 2026-10-21)

- 근거(`notebooks/32_01_생성경로_지연.ipynb`, 지어낸 질문 10개, 2026-10-19): Google 무료 경로는 사고 과정을 꺼도 답변 첫 토큰 평균 24.8\~32.8초(최대 31.6\~46.5초)였고 설정마다 10번 중 3\~4번이 500이었다. 기본 설정은 사고 과정만 내고 답변 없이 끝난 호출도 2번 있었다. OpenRouter는 답변 첫 토큰 중앙값 1.03\~1.29초, 최대 3.77\~4.78초, 오류 0이었다. 포트폴리오 데모에서 테스트 질의 몇 개에 수십 초 지연이나 500이 나는 것은 받아들일 수 없다(사용자)
- 사고 과정: 두 경로 모두 끌 수 있다. D-11의 "끌 수 없다"는 맞지 않는 파라미터(`reasoning_effort`, `thinking_budget`)로 시험한 결과다. Google은 `thinking_level`/`thinkingLevel` `minimal`(Gemma on Gemini API 문서), OpenRouter는 이 모델의 기본값이 꺼짐(`reasoning.default_enabled: false`)이고 `reasoning.effort: "none"`으로 명시한다
- 비용: 측정 20번에 $0.0015(입력 약 300토큰). 실제 생성 입력(근거 5개, 약 2,500토큰)이면 호출당 약 $0.0004\~0.0006으로 본다(추정, 제공자 가격에 따라 다름)
- 남은 일(생성 단계 구현에서): OpenRouter는 같은 모델을 여러 제공자(양자화 fp4·fp8·bf16)로 보내므로 제공자는 CoreWeave(`coreweave/fp4`)로 고정한다(`provider.order`, `allow_fallbacks: false`, 사용자 결정 2026-10-19, PR #94 코멘트). 이유(사용자): 제공자 목록에서 입력·출력 가격이 가장 낮고 확인 시점 지연도 가장 낮았다. 가격은 OpenRouter 엔드포인트 API(`/api/v1/models/google/gemma-4-31b-it/endpoints`, 2026-10-19 조회)에서 100만 토큰당 입력 $0.10·출력 $0.34다. 처음 코멘트는 DeepInfra였고 측정 20번도 모두 DeepInfra라, 위 근거의 지연은 CoreWeave 값이 아니다. CoreWeave 첫 토큰 지연은 생성 평가를 실행할 때 함께 재서 기록하고, 제공자 변경만을 위한 별도 측정은 하지 않는다(사용자 결정 2026-10-20, PR #95 코멘트). fp4는 제공자 목록에서 가장 강한 양자화라 답변 품질이 떨어질 수 있다(추론). 품질은 사고 과정 끔 비교와 함께 생성 평가에서 본다. D-30의 3초는 답변 첫 토큰 지연의 중앙값으로 판정한다(같은 결정). 실험 간 비교를 위해 T=0과 함께 반복 실행 변동 폭을 잰다(D-35). 공개 데모용 키에는 크레딧 한도를 둔다. 실제 입력 길이에서 첫 토큰 지연을 다시 잰다(D-30 3초 중 검색이 평균 약 0.84초, EXP-017). 사고 과정을 끈 답변의 품질은 비교하지 않았다(측정은 지연·오류·글자 수만 봄). D-11 베이스라인은 사고 과정을 켠 출력이라, 생성 평가 기준을 정한 뒤 두 설정의 답변을 비교한다 이후 변경(2026-10-26, PLAN-done "생성 실험 순서"): 사고 과정 켬·끔과 fp4 양자화 비교는 하지 않기로 했다
- 관계: D-30 정정의 "생성이 반복 실패하면 유료 API로 생성하는 분기"는 기본 경로가 유료가 되어 필요 없어진다

## D-38 생성 단계 평가 방향: RAGAS 지표 정의를 빌린 LLM judge 직접 구현
- 결정(사용자 결정 2026-10-19): 생성 평가는 LLM judge로 하고, 지표 정의는 RAGAS(Es et al., "RAGAs: Automated Evaluation of Retrieval Augmented Generation", EACL 2024 System Demonstrations, pp. 150\~158, arXiv:2309.15217)를 빌려 직접 구현한다. ragas·deepeval 라이브러리는 쓰지 않는다. SPEC 개정 초안은 SPEC 밖의 `docs/drafts/spec-generation-eval.md`에 둔다. 초안을 고칠 때마다 SPEC 승인을 받느라 작업이 멈추지 않게 하려는 것이다(사용자 결정, PR #99 코멘트). 남은 결정 사항이 정해지면 SPEC에 옮기며 사용자 승인을 받고 그 사실을 이 문서에 적는다 이후 변경: 초안은 SPEC으로 옮겼다(D-53)
- 이유(사용자): judge 프롬프트를 `configs/`에서 버전 관리하고, 한국어 회의록에 맞춘 지시를 쓰기 위해서다
- 고려 중인 기준과 출처
  - 충실성(faithfulness), 답변 관련성(answer relevance): RAGAS 논문의 세 기준(faithfulness, answer relevance, context relevance) 중 둘이다. 논문은 참조 답변 없이 계산하는 지표로 정의한다
  - 핵심 답변 포함도: ragas 라이브러리의 answer correctness(RAGAS 논문에는 없음)를 고친 지표다. 원래 지표는 참조 답변 전체와 답변을 진술 단위로 대조한 F1(TP / (TP + 0.5·(FP + FN)))과 의미 유사도를 가중 결합한다(v0.2.15 기본 0.75·0.25). 의미 유사도의 근거 문헌은 SAS(Risch et al., "Semantic Answer Similarity for Evaluating Question Answering Models", MRQA@EMNLP 2021, arXiv:2108.06130)다(ragas 소스 `_answer_similarity.py`). 지금 ragas 문서는 이 지표 대신 factual correctness와 semantic similarity를 따로 둔다
    - 고친 정의(사용자 결정, PR #100): judge가 `answer.comment`에서 질의에 답하는 핵심 진술만 뽑고, 답변에 담긴 핵심 진술 수 / 핵심 진술 수로 잰다. 정밀도와 의미 유사도는 쓰지 않는다
    - 이유: `answer.comment`는 질문 전체에 대한 응답이라, 참조 전체와 대조하면 질의에 맞게 간결히 답한 답변이 감점된다. `answer.comment`는 거의 모두 정답 문서 안에 있어 정밀도는 충실성과 거의 겹친다(추론). 이 지표는 "핵심 답을 빠뜨렸는가"만 맡는다
    - 계산에서 빼는 질의: 핵심 진술이 뽑히지 않는 참조 사용 불가(비율은 따로 보고), 정답 문서가 근거 상위 5개에 없는 질의(검색 지표가 맡음), 거부 답변(거부 정확도가 맡음). 거부 답변은 충실성·답변 관련성 계산에서도 뺀다
    - 이름: 질의에 대한 핵심 답을 답변이 담았는지를 잰다는 점을 드러내려고 "핵심 답변 포함도"로 한다(사용자 결정, PR #100)
  - 거부 정확도: RGB(Chen et al., "Benchmarking Large Language Models in Retrieval-Augmented Generation", AAAI 2024, arXiv:2309.01431)의 negative rejection 계열이다. RGB는 답을 담지 않은 문서만 근거로 줬을 때 답변을 거절하는 비율(rejection rate)로 잰다
  - context relevance는 고려 기준에 넣지 않았다. 검색 품질은 검색 단계 지표(Recall@k)가 본다
- judge: API로 부르고 제공자, 모델, 파라미터, 프롬프트를 버전 관리한다. judge 모델은 생성 모델(Gemma 4)과 다른 계열인 DeepSeek V4.1 Flash로 하고, 경로는 opencode Go 구독으로 한다(사용자 결정, PR #99 코멘트)
  - 이유(사용자): 같은 가격에 더 많은 사용량을 얻을 수 있어, 대량 호출이 필요한 평가에 쓴다
  - 감수하는 것: opencode Go 문서(2026-10-19 확인)는 Go를 코딩 에이전트용으로 설계했고 남용을 감시한다고 적어, 배치 판정으로 의심받아 사용이 막힐 수 있다. 막히면 그 뒤 경로를 다시 논의한다(사용자). 대안은 같은 모델의 OpenRouter 경로(`deepseek/deepseek-v4.1-flash`)다
  - 데이터 처리처: opencode Go는 학습 미사용·보존 0일(ZDR, 협약은 매달 갱신, 지금 협약은 2026-10-31까지)이다. D-31의 허용 처리처 목록(CLAUDE.md 금지 절, SPEC 자원 제약, protocol-guard P6)에 생성 평가 judge용으로 더했다(사용자 지시 2026-10-19, ADR-0044). 용도는 judge 호출로 한정한다. `test` 질의 제한과 대량 전송 전 보고·승인은 다른 처리처와 같다
- 핵심 답변 포함도의 참조 답변: `answer.comment`로 한다. 답변 발언 원문이라 질의의 답 내용을 그대로 담고 있고, `summary_a`는 KoAlpaca(LLaMA 7B)가 그 내용을 요약한 생성물로 생성·judge 모델보다 성능이 낮고 사용자가 직접 본 품질도 낮아 쓰지 않는다. `answer.comment`는 질의자 질문 전체에 대한 응답이라 평가 질의와 범위가 다를 수 있고 정치적 고려로 직접 답을 피하기도 해서, dev-small에서 핵심 답변 포함도를 재 본 뒤 종합 지표에 넣을지 보조 지표로 관찰할지 정한다(사용자 결정, PR #99). 관찰은 기준 설정 출력만으로 하고 후보 설정끼리 비교한 결과를 보고 정하지 않는다(사용자 결정, PR #100) → 포함도는 보조 지표(D-53 결정 1)
- 주지표: RAGAS 지표를 고쳐 만든 LLM judge 기준을 결합한 종합 지표로 한다. 결합 구성과 최소 개선 폭은 추가 논의한다(사용자 결정, PR #99 코멘트) → D-53 결정 2·4
- multi-doc: 검색 단계와 같이 G3 동결 세트(D-15)로 생성도 평가하되 보조 관찰로 두고 판정에 쓰지 않는다(사용자 결정, PR #99) 이후 변경(D-53 결정 7): 매 EXP가 아니라 여러 문서를 합쳐 답하는 것을 겨냥한 실험에서만 본다
- test: 검색 단계와 같이 생성 단계 마지막에 사용자 지시로 1회만 쓴다(사용자 결정, PR #99 코멘트). 지금 SPEC은 test를 검색 단계 종료 1회로만 허용하므로, 이 사용은 초안을 SPEC에 옮긴 뒤에 효력이 있다. CLAUDE.md 금지 절은 이 조건을 붙여 단계마다 1회로 적었고(이슈 #112, 2026-10-20), 외부 전송 줄과 protocol-guard P1·P6, pr-briefer R6은 SPEC 이관 때 함께 고친다 → SPEC에 옮김(D-53), 안내문은 PR #166과 D-54
- 생성 조건: 실험 간 비교는 T=0과 고정 프롬프트로 하고, 제공자는 OpenRouter CoreWeave로 고정한다(D-37)
- 오라클 조건: 정답 문서를 근거에 직접 넣는 조건은 매 실험이 아니라 진단용으로 한 번 한다. 검색 실패와 생성 실패를 가르는 데 쓰고, 근거에서 정답 문서를 뺀 입력은 거부 정확도 세트로도 쓸 수 있다
- 날짜: 2026-10-19

## D-40 생성 평가 모듈 설정 (S14)
- 결정(사용자 결정 2026-10-19, `docs/slices/14-gen-eval.md` 결정 사항)
  1. 생성의 재정렬은 EXP-017이 Colab에서 만든 점수 파일을 읽는다. 점수가 없는 자유 질의는 멈추고, 실시간 재정렬은 배포 SLICE에서 GPU 추론 서버와 함께 만든다
  2. 답변 관련성은 judge가 3단계(답함 1, 일부 0.5, 답하지 않음 0)로 매긴다. RAGAS 논문의 역질문·임베딩 유사도 방식은 연속값이라 G5 보정의 kappa에 맞지 않아 쓰지 않는다
  3. 메타데이터 일치는 회의 일자와 위원회 이름만 대조한다. 화자 필드는 라벨링된 QA의 화자만 담아(D-19 한계) 맞는 이름을 불일치로 셀 수 있다
  4. 거부 교차 집계의 "근거 청크에 답 있음"은 핵심 답변 포함도에서 뽑은 핵심 진술 중 정답 문서의 근거 청크에 든 비율이 0.5 이상인 경우다(judge). `answer.comment` 전문과의 문자열 겹침은 발언의 핵심이 아닌 부분과 발언·청크 길이에 흔들려 쓰지 않는다

## D-41 부분 거부 답변과 질의 항목 단위의 거부 평가 (S14b, S14c)
- 결정(사용자 결정 2026-10-20, PR #106 부분 거부 코멘트, PR #118 리뷰와 대화)
  1. 거부 문구를 담은 문장 밖에 내용 문장이 있으면 부분 거부다. 거부 문장을 뺀 내용으로 충실성·답변 관련성·인용 검사를 하고, 핵심 답변 포함도는 답변 전체로 본다(S14b). 한 문장 안에 내용과 거부 문구가 함께 있으면 문장 전체를 거부로 보고, 이 손실은 생성 프롬프트에서 거부를 별도 문장으로 쓰게 해 해결한다(생성 실험 아이디어 H19). 답변 관련성 부분은 D-47 결정 4로 바뀌었다(답변 전체로 채점)
  2. 거부가 맞았는지는 거부 문장이나 답변이 아니라 질의가 묻는 항목 단위로 판정한다(S14c). 질의가 x와 y를 함께 물으면(예: 어떤 사안의 현재 상태와 계획) 항목마다 근거 5개 전체에 정보가 있는지와 답변이 그 항목을 어떻게 처리했는지를 본다. 근거에 있으면 답하고, 일부만 있으면 부분적인 사실이라는 점을 밝히고 답하며, 없으면 거부하는 것이 맞는 처리다. 일부만 있는 항목을 그 안내 없이 답하면 틀린 처리다. 이로써 모델이 질의의 핵심 항목을 나눠 파악하고 필요한 정보를 모아 답하는지를 본다
  3. 근거가 "예정", "검토 중", "정해지지 않음"으로만 말하거나 답변자가 답을 피한 항목은 상황 미전달로 따로 세고 거부 정확도에 넣지 않는다. 지금 생성 프롬프트(v1·v2)는 "답할 수 없으면 거부"만 지시해 이 거부는 지시를 따른 결과다. 생성 프롬프트에서 모호함·회피를 전하게 하는 것은 생성 실험 아이디어 H18로 둔다
  4. 근거의 내용이 질의자 발언인지 답변자 발언인지는 세 갈래로 본다. 질의자 발언이 분명하면(의문형, 답변자를 부르는 호칭, 답변자가 확인하지 않은 주장) 그 항목의 근거로 보지 않고, 답변자 발언이 분명하면 근거로 보며, 구분할 수 없으면 근거로 보고 따로 센다. 청크에는 발언자 표기가 없고 잘린 조각만으로는 발언자를 가리기 어려워, 애매한 조각을 질의자 발언으로 보면 답변자 발언이 잘린 경우를 "근거 없음"으로 잘못 판정하기 때문이다. 충실성 판정(`verdicts` 규칙 5)도 같은 규칙으로 맞추고(PLAN 생성 평가), 청크에 발언자를 붙이는 데이터 처리는 별도 작업으로 둔다(PLAN H20) → D-60(기능 SLICE. 채택은 H20 EXP)
- 이유: 지금까지는 답변 어딘가에 거부 문구가 있으면 답변 전체를 거부로 보고 채점하지 않아, "A 위원은 B를 제안했습니다[1]. C의 시행 시기는 … 찾지 못했습니다."의 첫 문장이 평가되지 않았다. 거부한 부분도 근거가 부족한 경우, 근거가 모호한 경우, 답변자가 답을 거부한 경우가 서로 다르다(사용자 코멘트). 처음 S14b에서는 거부 문장마다 이유를 나눴으나, 거부가 맞았는지는 질의가 묻는 항목마다 판단해야 한다는 리뷰로 단위를 바꿨다(PR #118)
- 확인: S14 표본 20질의는 거부가 0건이라 S14b 뒤에도 기록한 점수가 그대로다(재채점 API 호출 0회, report가 같음)
- S14c 구현에서 정한 것(사용자 결정 2026-10-21\~22, `docs/slices/14c-item-refusal.md` 결정 사항)
  - 틀린 처리는 유형을 나눠 센다: 누락, 무언 생략, 과잉 거부, 안내 없이 부분 답함, 근거 없이 답함, 불필요한 부분 안내(결정 사항 2·5). 정보 "없음"은 원인으로 나누지 않는다(결정 사항 1)
  - 결정 3의 상황 미전달을 둘로 나눈다. 모호·회피 항목에서 답변이 예정·검토 중·답을 피함을 그대로 전했으면 상황 전달, 단정하거나 거부하거나 다루지 않았으면 상황 미전달이다. 둘 다 거부 정확도에는 넣지 않는다(결정 사항 4). 예(지어낸 문장): 근거가 "○○ 제도 개선 방안을 검토하겠다"뿐인 항목에 "개선 방안을 검토하겠다고 답했습니다"는 상황 전달, 전체 거부는 상황 미전달
  - 확인 사례의 정답은 메인이 정하고 사용자가 검수해 확정한다(결정 사항 3)
- 날짜: 2026-10-20(S14c 구현 결정 2026-10-22)

## D-44 생성 평가 질의 세트는 dev-full에서 고정 표본으로 뽑고, 규모는 변동 폭으로 정한다

  - 최종 확인은 검색 단계처럼 test로 1회 한다(D-38, SPEC 초안)
- 검색 세트와 다르게 두어도 되는 이유
  - 같은 dev 분할 안의 부분집합이다. 분할이 회의 단위라 dev의 일부를 써도 test와 섞이지 않는다
  - 평가 대상이 다르다. 검색 세트(dev-full 3,016질의)는 순위 지표 차이를 가려낼 크기로 정했고, 생성 평가는 질의당 비용이 커서 judge 잡음과 API 비결정성을 잰 변동 폭에 맞춰 따로 정하는 것이 맞다(D-35 생성 평가 항목)
  - multi-doc 생성 평가는 이미 보조 관찰로 나뉘어 있다
- 지켜야 할 것
  1. 세트를 고정한다. 모든 생성 실험이 같은 질의를 같은 순서로 써야 기준·후보를 질의 단위로 짝지어 비교할 수 있다
  2. 질의 수는 변동 폭으로 정하고, 후보 설정끼리의 점수 차이를 보고 정하지 않는다(규칙은 점수 보기 전에, SPEC 누수 방지)
  3. judge 지시 개발에 쓴 질의(D-47 결정 5)와 블라인드 확인 표본은 판정용 세트에서 뗀다(SPEC 초안 평가 질의 줄). 처음에는 "judge 보정(G5)에 쓴 질의"였고, G5를 블라인드 확인으로 바꾼 결정(PLAN 2026-10-22)에 맞춰 고쳤다(이슈 #142, S22). 목록은 `configs/gen_eval/dev_queries.yaml`이다
  4. 생성 점수를 해석할 때 같은 세트의 검색 지표(Recall@5 등)를 함께 보고한다. 거부가 늘면 검색 탓인지 생성 탓인지 가려야 하는데 검색 지표는 dev-full 전체로 냈기 때문이다. 기존 순위 파일로 계산해 비용이 들지 않는다
  5. 작은 세트를 반복해 쓰는 데서 오는 낙관은 감수하고, 생성 단계 마지막 test 1회로 확인한다(D-35 "반복 사용의 확인"과 같은 구조)
- 날짜: 2026-10-21

## D-47 생성 평가 판정 기준 문서와 세 가지 판정 규칙
- 결정: 생성 답변의 판정 규칙을 `docs/gen-eval-criteria.md` 한 곳에 둔다. 사람 검수(S14, S14c)의 사용자 판단, D-38·D-40·D-41, judge 근거 문헌 조사(`docs/research/llm-judge-evidence.md`)를 규칙 번호와 점검할 곳으로 정리했다. 평가 모듈 점검과 지시 동결은 이 문서로 한다. 문서를 쓰며 정한 것(사용자 결정 2026-10-22)
  1. 모호·회피 항목의 바람직한 처리는 "상황을 밝히고 답함"이다. "일부만 있다"는 안내만 한 답변은 상황 미전달로 센다(PR #137 판단할 곳 1). "일부만 있다"와 함께 검토·예정·협의하겠다는 상황을 전했으면 처리는 "상황을 밝히고 답함"이다
  2. 회의에서 확답이 없었다는 상황을 전한 답변은 답변 관련성 답함(1)이다. 예: 근거가 "실효성 있는 방안을 검토하겠습니다"뿐일 때 "실효성 있는 방안을 검토하겠다고 답했습니다[1]."는 1이다. 지금 지시(j_v7 `relevance`)는 이런 답변을 일부(0.5)로 본다
  3. 핵심 진술의 부수 세부만 빠지고 실질이 있어도 `key_checks`는 0으로 둔다(지금 규칙 유지)
  4. 부분 거부 답변의 답변 관련성은 거부 문장을 넣은 답변 전체로 채점하고, 찾지 못했다고 밝힌 부분은 감점하지 않는다. D-41 결정 1(S14b 결정 사항 1) 중 관련성 부분을 바꾼다. 충실성·인용 검사는 그대로 거부 문장을 뺀다. 예: "1단계 공사를 마쳤습니다[1]. 향후 계획은 제공된 회의록에서 답을 찾지 못했습니다."는 답함(1)이다
  5. judge 지시 개발에 쓴 질의(S14 표본 20질의, S14c 확인 사례의 질의)는 판정용 세트에서 뺀다
  6. 설정 비교에서는 기준마다 두 실행 모두 계산한 질의만 쓴다(포함도뿐 아니라 충실성·관련성도). 예: A가 어려운 질의 2개를 답해 충실성 0.5, B가 그 둘을 거부했으면, 각자 계산하면 B가 거부만으로 높게 나오므로 그 둘을 양쪽에서 뺀다. 버리는 질의가 늘어나는 것은 평가 질의 규모(D-44)를 정할 때 고려한다(PR #141 리뷰)
  7. judge 검증(블라인드 확인)은 κ(또는 π)를 재서 기준에 못 미친 지표를 보조 지표로 내리고, 질의 단위 구간과 두 설정 답변 사이의 judge 오류율 차이를 함께 본다(PR #141 리뷰, PLAN 블라인드 확인 항목) 이후 변경(D-51 결정 1): 블라인드 확인을 1질의 뒤 중단해 κ 기준을 적용하지 않았다
- 이유(4·5): 4는 거부 문장을 빼면 맞게 거부한 답변이 일부(0.5)가 되어 항목 평가와 함께 두 번 감점되고, S14b에서 정한 "답하지 못한 부분은 포함도와 거부 평가가 맡는다"는 뜻과 어긋난다(모듈 점검에서 발견). 5는 지시를 맞추는 데 쓴 질의에서 판정하면 judge가 그 질의에 맞춰진 만큼 낙관적으로 치우칠 수 있다(근거 문서 "첫째")
- 이유: 1은 사용자가 S14c c11에서 근거가 없었던 것이 아니라 답변이 분명하지 못했던 상황을 설명해야 한다고 판단한 것과 맞춘다. 2는 관련성을 일부로 두면 상황을 전한 답변이 평균에서 빠지는 전체 거부보다 불리해지고, 그 상황이 사실인지는 충실성과 항목 평가가 본다. 3은 진술의 실질을 판단하는 것이 judge 본래의 일에 가깝지만, 평가 모듈의 일관성이 확립되지 않아 무엇이 부수 세부인지를 judge 판단에 맡기지 않는다(사용자)
- 남은 일: 2·4의 지시 변경, 5의 제외 목록, F7(충실성 판정의 발언자 구분 불가 표시) 등 모듈 점검에서 나온 수정(`docs/gen-eval-criteria.md` "모듈 점검 결과")은 S22 생성 평가 기준 반영(SLICE, judge 지시 j_v8)에서 한다. S22에서 반영했다(`docs/slices/22-gen-eval-criteria.md`, 2026-10-26). 5의 제외는 판정용 층(dev-full)에만 적용하고 dev-small은 개발 층으로 둔다(S22 결정 사항 1)
- 날짜: 2026-10-22

## D-52 생성 설정 비교에서 과잉 거부는 주지표와 따로 안전 조건으로 본다
- 결정(사용자 결정 2026-10-27, 이슈 #156): 주지표(judge 기준)는 지금처럼 짝지은 제외(D-47 결정 6)로 계산하고, 과잉 거부는 주지표에 넣지 않고 안전 조건으로 판정한다. 후보의 과잉 거부율이 기준보다 늘어난 폭(후보 − 기준)의 회의 단위 paired bootstrap 95% 구간 상한이 미리 정한 허용폭 δ_r 이하일 때만 채택한다(D-50의 최소 개선 폭 δ와 다른 값이다). 주지표가 판정 규칙을 통과해도 이 조건을 넘으면 채택하지 않는다
- 이유: 짝지은 제외는 어려운 질의를 거부해 평균을 올리는 이득은 막지만, 답할 수 있는 질의를 거부해도 그 질의가 양쪽에서 빠질 뿐 주지표가 감점되지 않는다. 거부를 주지표에 넣는 방식(포함도에 거부 0점, 조건부·전체 둘 다 통과)은 충실성이 거부에서 정의되지 않고 관련성은 이중 계산을 피하려고 뺀 기준이라, 종합 지표에 넣으려면 가중치나 0점 규칙을 따로 지어내야 한다. 원시 개수로 비교하면("하나라도 늘면 기각") 1\~2개의 생성 잡음에도 기각이 나므로 주지표와 같은 구간으로 본다
- 근거 문헌(`docs/research/refusal-in-comparison.md`)
  - 거부를 품질과 따로 재는 관행: RGB(Chen et al., AAAI 2024)는 답이 없는 질의 세트에서 거부율을, 답이 있는 질의에서 정확도를 따로 보고하고 합친 점수를 두지 않는다. 과잉 거부 벤치마크 XSTest(Röttger et al., NAACL 2024)와 OR-Bench(Cui et al., ICML 2025)도 과잉 거부율을 품질과 합치지 않는다
  - 안전 조건(guardrail): 온라인 통제 실험에서 주지표(OEC)가 좋아져도 유의하게 나빠지면 출시를 막는 지표를 둔다(Kohavi, Tang, Xu 2020, *Trustworthy Online Controlled Experiments* 7·21장. 정의 문구는 2차 자료로 확인)
  - 조건부 지표만 쓰는 위험: 받아들인 표본만으로 계산한 위험은 거부를 무시해 시스템 전체 평가에 맞지 않는다(Traub et al. 2024). Trust-Score(Song et al., ICLR 2025)는 답한 질의로 나눈 정확도(P_AC)와 답이 있는 질의 전체로 나눈 정확도(R_AC)를 함께 쓰고, R_AC는 과하게 답하는 모델에 유리하다고 적었다(원문 대조). 짝지은 제외 주지표는 조건부 지표라 과잉 거부를 따로 막을 장치가 필요하다(추론)
  - 채택하지 않은 방식: CRAG(Yang et al. 2024)는 정답 1·부분 정답 0.5·누락 0·오답 −1의 전체 평균을 쓴다(원문 대조). 이 방식을 따르면 거부를 0점으로 넣어야 하는데 위 이유로 포함도에만 바로 쓸 수 있다
- 감수하는 것: 과잉 거부율은 judge 항목 평가(S14c)로 세며 사람과의 일치를 재지 않았다(D-51). 지금 거부 정확도는 참고값(기준 문서 I11)인데, 이 결정으로 과잉 거부 항목 수는 판정에 쓰인다. 답이 없는 근거에서 더 잘 거부하게 된 개선은 채택 근거가 되지 않는다. 지정 거부 문구를 쓰지 않은 거부는 거부로 세지 않아(PR #158, H24) 두 설정의 문구 준수율 차이가 과잉 거부율 차이에 섞인다
- 남은 일: SPEC 개정 때 기준 문서 I11과 D-51 결정 2의 "거부 정확도는 참고값"에 과잉 거부율 예외를 적는다(초안은 이 결정에서 고쳤다). δ_r와 과잉 거부율의 분모(판정 대상 항목 또는 답이 있는 질의)는 SPEC 개정에서 기준 설정의 변동 폭(D-50 방식)을 보고 정한다. 비교 명령은 생성 설정 비교 SLICE(PLAN)에서 만든다 → δ_r·분모는 D-53 결정 3, 비교 명령은 S27(D-55)
- 날짜: 2026-10-27

## D-53 생성 단계 평가 프로토콜: 종합 지표, 최소 개선 폭, 안전 조건 (SPEC 개정)
- 결정(사용자 결정 2026-10-27)
  1. 핵심 답변 포함도는 보조 지표로 보고하고 종합 지표에 넣지 않는다. 근거를 바꾸는 실험(H10 등)에서는 판정과 함께 반드시 보고한다
  2. 종합 지표는 질의마다 충실성과 답변 관련성의 단순 평균이다. 두 기준 모두 두 실행에서 계산된 질의만 쓴다(짝지은 제외, D-47 결정 6). 기준별 하락 안전 조건을 둔다: 충실성과 관련성 각각의 차이 95% 구간 하한이 충실성 −0.05, 관련성 −0.035 이상
  3. 과잉 거부 안전 조건(D-52)의 분모는 판정 대상 항목(모호·회피 제외)이고, 허용폭 δ_r = 0.02다
  4. 최소 개선 폭 δ = 0.02. 채택은 종합 지표 차이의 95% 구간 하한 > 0, 점 추정 ≥ δ, 두 안전 조건 통과. 기각은 구간 상한 < 0. 그 밖은 보류이고, 보류를 예외로 기준에 올릴지는 검색 단계와 같이 사용자가 정한다(D-28·D-33)

## D-60 근거 발언자 표시 기능과 judge 지시 j_v9 (S29)
- 결정(사용자 결정 2026-10-28, `docs/slices/29-speakers.md` 결정 사항 1\~3)
  1. 근거 청크의 발언자 표시를 `speakers.mode`(`off` 기본, `head`, `marks`)로 켠다. `head`는 문서의 질의자·답변자 머리 줄, `marks`는 머리 줄과 라벨 질의·답변 발언이 청크 안에서 겹친 구간의 표지다. 생성 기록의 근거에 `speakers` 필드를 두고 `text`는 원문 그대로다. 어느 방식을 시험할지와 채택은 H20 EXP에서 정한다
  2. judge 입력 코드 `format_contexts`를 바꿔, judge도 생성 모델과 같은 렌더링(`rag.speakers.render`)으로 근거를 본다. 충실성은 생성 모델이 받은 근거로 재므로 judge가 다른 근거를 보면 판정이 생성 입력과 어긋난다. `speakers`가 없는 기록은 요청 본문이 그대로다(`tests/test_gen_eval_freeze.py`의 S28 고정값 통과). 정답 청크 발췌를 받는 `chunk_checks`는 발언자를 판정하지 않아 원문 그대로 둔다
  3. judge 지시 j_v9(`configs/judge/prompt/j_v9.yaml`)를 만든다. j_v8의 `verdicts` 규칙 5와 `items` 규칙 3의 첫 문장 "근거에는 발언자 표기가 없다."만 바꾸고 나머지는 글자까지 같다. 청크에는 질의자나 답변자 한 사람의 발언만 있을 수 있어, `speakers`를 받아도 judge는 청크 내용으로 누구의 발언인지 판단해야 하기 때문이다(사용자). 기본 judge 설정은 j_v8 그대로이고, H20 EXP에서 `judge/prompt=j_v9`로 고른다. j_v9 해시는 동결 테스트에 넣는다
  4. j_v9 재검증(D-49 변경 절차)은 H20 EXP 직전의 j_v9 재채점이 겸한다. 같은 생성 기록을 j_v8과 j_v9로 채점해 질의마다 비교하고, 차이가 D-50의 judge 변동 폭 안인지 본다. 재채점은 S28 재채점과 묶지 않는다(D-59 결정 5)
  5. 발언 구간은 test 회의 문서까지 원천 라벨 전체로 만든다. 개발에 쓰지 않는 것은 질의 텍스트(`summary_q`)이고, test 회의 문서가 검색에 올라오는 것은 허용한다(사용자). 검색 대상이 코퍼스 전체라 dev 근거에도 test 회의 문서가 올라오고, 빼면 dev와 test의 생성 입력 조건이 달라진다(D-20과 같은 이유)
  6. 발언자 표시가 붙은 생성 기록(레시피 `speakers`)을 `speaker_marks: true`가 없는 지시(j_v8)로 채점하면 judge가 시작할 때 멈춘다. compare는 judge 설정만 대조해, 기준 off·j_v8과 후보 marks·j_v8은 지시와 입력이 어긋난 채로 판정까지 가기 때문이다. 표시 없는 기록을 j_v9로 채점하는 것은 결정 4의 재검증에 쓰여 막지 않는다(사용자 결정 2026-10-28, PR #178 리뷰 1)
  7. `speakers.repeat_min_chars`(21)보다 짧은 발언이 본문에 여러 번 나오면 표지를 두지 않는다. 반복 발언 2,663개 중 20자 이하 809개는 "예."(378개), "예, 그렇습니다."(166개)처럼 다른 사람의 발언에도 나오는 문자열이라, 모든 위치에 붙이면 화자가 잘못 붙은 표지를 j_v9가 그대로 믿는다. 21자 이상 1,854개(길이 중앙값 114자)는 같은 발언이 본문에 겹쳐 실린 것으로 보고 모든 위치에 둔다(추론). 켜면 이 값도 생성 레시피에 남긴다(사용자 결정 2026-10-28, PR #178 리뷰 2)
  8. j_v9의 바꾼 문장 끝을 "…내용으로 보고 아래 세 갈래로 판정한다."에서 "…내용으로 본다."로 줄인다. 원래 다음 문장이 "세 갈래로 본다"를 이어 말해 같은 말이 겹쳤다. j_v9는 아직 어떤 채점에도 쓰지 않아 다시 채점할 기록이 없다(사용자 결정 2026-10-28, PR #178 리뷰 3)
- 근거: 코퍼스 38,516문서 중 질의자·답변자 이름이 있는 문서 각 38,514개, 원천 라벨 QA 39,633개 중 질의 발언 39,623개·답변 발언 39,467개가 본문에 그대로 있다. S25 생성 기록 430질의의 근거 2,150개 중 1,224개(56.9%, 결정 7 적용 뒤. 적용 전 1,228개)에 겹침 표지가 붙고, 표지 문자는 근거 문자의 33.1%다(`uv run python -m rag.speakers`, S29 결과 절)
- 바뀌는 것: D-56 결정 3(SLICE 범위를 구현하고 judge 지시를 j_v9로 나눔), D-49(동결 대상에 j_v9 해시를 더함, 기본 지시 j_v8은 그대로), D-41 결정 4(청크에 발언자를 붙이는 데이터 처리의 기능을 만듦), D-59 결정 5(j_v9를 만들었고 H20 EXP 직전 재채점에 쓴다)
- 감수하는 것: 평가 질의는 그 QA 발언으로 만들어져 정답 문서 청크의 답변 표지가 정답 발언 구간과 거의 같다. 배포 때도 문서마다 라벨이 있어 표지는 같게 붙지만 새 질의는 라벨 QA와 무관하므로, dev에서 재는 개선 폭이 배포 때보다 클 수 있다(추론, 재지 않음).
