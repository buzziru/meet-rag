# S25 생성 베이스라인과 블라인드 확인

기준 설정으로 판정용 330질의의 생성 평가 베이스라인을 잡고(PLAN "생성 베이스라인과 핵심 답변 포함도 관찰"), 같은 실행에서 판정용 세트 밖 질의로 블라인드 확인 표본 풀을 만든다(PLAN "블라인드 확인 1회"). 블라인드 확인은 동결한 judge(j_v8, `deepseek_go_mixed`, D-49·D-50)의 판정을 사용자가 judge 결과를 보지 않고 매겨, 기준별 κ와 실패 클래스 TPR로 judge를 판정에 쓸지 정한다. 통과 기준은 SPEC 초안 결정 사항 4다(κ 또는 π ≥ 0.6과 실패 클래스 TPR ≥ 0.8이면 판정 사용, 0.4 ≤ κ < 0.6이면 보조 지표).

흐름: 실행은 A(이 지시서·구현·검증), 블라인드 확인은 D(표본 도구 → 사용자 검수 → 집계 → 결정 기록)다. 한 실행으로 묶는 이유는 생성·judge 호출을 한 번에 승인받고 같은 시간대의 지연으로 judge 동시 수를 재기 위해서다.

결정 순서: 표본 도구·검수 문서 코드 → 실행(비용 승인) → 블라인드 표본 추출·검수 문서 → 사용자 검수 → 집계 노트북 → 사용자 결정(기준별 판정 사용·보조 지표) → DECISIONS 기록 → PR. 결정이 걸린 조각이라 노트북을 결정 전에 보인다.

## 정한 것 (사용자 결정 2026-10-26)

- 블라인드 표본은 판정용 330 밖에서 뽑는다. 판정용 순서(개발 질의 제외, seed 순서)의 331\~430번째 100질의를 표본 풀로 쓴다. `gen_eval.n=430`으로 한 번 실행하면 앞 330은 베이스라인, 뒤 100은 풀이다(`sample_qids`는 n을 늘려도 앞 표본을 유지한다)
- 검수 작업량은 세 방법으로 줄인다. ① 질의로 묶기(같은 근거를 한 번 읽고 그 질의의 판정을 모두 매김), ② 찾을 곳 표시(코드가 문자열 유사도로 가장 비슷한 근거 문장을 강조, 판정은 알려 주지 않음), ③ 선택지 답 형식(판정마다 선택지만 고름, 필요하면 사용자가 이유를 남김)
- 검수 문서는 `.md` 한 파일이다. S14c와 달리 메인 판단 칸을 넣지 않는다. 메인 판단을 미리 적으면 사용자 판정이 그쪽으로 끌리고, 메인과 judge가 같은 곳에서 같이 틀리면 κ가 높게 나온다
- judge 질의 동시 수는 8로 첫 실행을 한다(동시 API 호출 최대 32, D-50). 지연과 429를 S24 측정(동시 4)과 비교한다

## 만드는 것

### (a) 실행 (비용 승인 후)

- 명령: `rag.gen_eval.generate` → `rag.gen_eval.judge` → `rag.gen_eval.report`, `+exp=exp017 gen_eval.n=430 judge.concurrency=8`, `LANGSMITH_TRACING=false`(D-50)
- 앞 100질의는 S24의 생성 기록(반복 0)과 judge 저장 응답을 이어 쓴다. 새로 부르는 것은 230(베이스라인) + 100(풀) = 330질의다
- 베이스라인 보고는 `gen_eval.n=330`으로 report를 따로 돌린다(앞 330만 집계). 풀 100은 베이스라인 점수에 넣지 않는다
- 같은 실행에서 PLAN이 요구한 관찰을 report 출력에서 읽는다: 참조 사용 불가 비율(핵심 진술이 빈 질의), judge 형식 오류 수, 길이로 잘린 응답 수, judge 지연·429 수(동시 8과 S24 동시 4 비교)

### (b) 블라인드 표본 도구 (`rag.gen_eval.blind`, 새 파일)

- 풀 100질의의 judge 결과에서 질의를 고른다. 판정 단위는 아래 표다. 단위(진술·핵심 진술·항목)는 judge가 만든 것을 그대로 쓰고, 사용자는 판정만 매긴다

| 기준 | 판정 단위 | 사용자가 보는 것 | 선택지 | 실패 클래스 |
| --- | --- | --- | --- | --- |
| 충실성 | 답변 진술 하나(`verdicts`) | 진술, 근거 5개 | 뒷받침 / 아님 | 아님 |
| 답변 관련성 | 답변 하나(`relevance`) | 질문, 답변 | 답함 / 일부 / 답하지 않음 | 일부·답하지 않음 |
| 핵심 답변 포함도 | 핵심 진술 하나(`key_checks`) | 핵심 진술, 답변 | 들어 있음 / 아님 | 아님 |
| 거부 정확도: 정보 상태 | 질의 항목 하나(`items`) | 항목, 근거 5개 | 있음 / 일부 / 없음 / 모호 / 회피 (`checks.py` `STATES`) | 범주형이라 TPR 대신 상태별 일치와 κ |
| 거부 정확도: 처리 | 질의 항목 하나(`item_handling`) | 항목, 답변 | 답함 / 부분임을 밝히고 답함 / 상황을 밝히고 답함 / 거부 / 다루지 않음 (`HANDLINGS`) | 사용자의 정보 상태·처리로 판정표(`OUTCOMES`)를 거친 결과가 "맞음"이 아닌 것 |

- 질의 고르기(결정 사항 1의 질의 수 m): 풀에서 judge가 실패로 판정한 단위가 많은 질의를 우선 고르되, 실패가 없는 질의도 약 1/3 넣어 TNR(맞는 것을 맞다고 본 비율)을 낼 수 있게 한다. 같은 회의는 한 질의만 넣는다. 순서는 seed로 섞고 고르는 규칙과 seed는 `configs/config.yaml`(`gen_eval.blind`)에 둔다
- 검수 문서에 judge의 판정·이유·점수는 넣지 않는다. 정답 키(질의·단위별 judge 판정)는 따로 `data/gen_eval/blind/s25_key.jsonl`에 쓰고, 집계 전까지 메인도 검수 문서와 함께 열지 않는다
- 뽑은 질의의 qid는 `configs/gen_eval/dev_queries.yaml`의 새 목록(`blind`)에 더한다. 판정용 순서의 331번 이후라 앞 330은 바뀌지 않고, 나중에 n을 늘려도 판정용에 들어가지 않는다(D-44 지켜야 할 것 3)
- 출력은 덮어쓰지 않는다(`refuse_existing`, 사람이 채우는 검수 파일)

### (c) 검수 문서 (`data/gen_eval/blind/s25_blind.md`, 커밋하지 않음)

- 질의마다 한 절: 질문 → 답변 → 근거 5개(접어 둠) → 판정 목록
- 판정마다 선택지를 `- [ ]` 체크 상자로 두고 하나를 `[x]`로 바꾼다. 아래에 `이유:` 빈 줄을 두고, 사용자가 필요할 때만 쓴다
- 찾을 곳 표시(②): 충실성 진술과 정보 상태 항목마다, 근거 5개를 문장으로 나눠 rapidfuzz `partial_ratio`가 가장 높은 문장 하나를 `> 찾을 곳 [근거 번호]: …`로 판정 바로 위에 보인다. 표시는 읽을 곳을 줄이는 용도이고, 판정은 근거 전체를 보고 한다. 이 점을 문서 맨 위 안내에 적는다
- 판정 순서는 질의 안에서 정보 상태 → 충실성 → 처리 → 포함도 → 관련성이다. 근거를 읽는 판정을 먼저 두어 근거를 한 번 읽고 끝내게 한다

### (d) 집계 (`rag.gen_eval.blind --score`, 노트북 `notebooks/36_01_S25_블라인드확인.ipynb`)

- 검수 문서의 체크를 읽어 정답 키와 맞춘다. 체크가 없거나 둘 이상인 판정은 목록으로 내고 멈춘다(사람이 넣는 입력은 읽을 때 전제를 확인한다)
- 기준별로 퍼센트 일치, κ(Cohen. 정보 상태·처리처럼 값이 여럿이면 범주형 κ), 실패 클래스 TPR·TNR, 질의 단위 bootstrap 95% 구간을 낸다
- 결정 사항 4의 구간 표(대체 가능·판정 사용·보조 지표)에 기준마다 점추정을 넣는다
- 어긋난 판정 목록(사용자 판정, judge 판정·이유, 사용자 이유)을 낸다. 이 목록은 검수가 끝난 뒤 메인이 보고, 해석하기 어려운 곳을 사용자에게 묻는다. 동결이라 지시는 고치지 않는다(D-49)
- 두 설정 답변의 judge 오류율 차이(초안 judge 검증)는 이 표본이 기준 설정 답변뿐이라 낼 수 없다. 생성 실험 판정 스킬에서 다시 본다

## 결정 사항

1. **질의 수 m(검수 작업량).** S24 100질의 기준 질의당 판정 수는 충실성 2.4, 포함도 1.6, 거부 항목 1.4(정보 상태와 처리 각각), 관련성 1이다. 질의 하나에 약 7.8개 판정이다. 근거 5개를 읽는 판정(충실성·정보 상태)이 작업 시간의 대부분이고, 나머지는 질문과 답변만 본다
   - (a) m = 12: 판정 약 94개(충실성 약 28, 포함도 약 20, 정보 상태·처리 각 약 17, 관련성 12). 근거 읽기 12회. 실패가 많은 질의를 골라 충실성·포함도는 실패 사례가 10개 넘게 모일 것으로 본다. 관련성·거부는 판정 수가 적어 구간이 넓다
   - (b) m = 15: 판정 약 117개(충실성 약 35, 포함도 약 24, 정보 상태·처리 각 약 21, 관련성 15). 근거 읽기 15회
   - (c) m = 8: 판정 약 62개. 기준마다 판정이 20개 아래라 κ 0.6 관문 판단이 어렵다(실패 10개로 잰 TPR의 95% 구간 반폭 약 ±0.25, `docs/research/llm-judge-evidence.md:133`)
   - 추천은 (a)다. 근거 읽기를 PLAN의 30\~40개 판정 수준 작업량에 가깝게 두면서 충실성·포함도는 관문 판단이 가능하다. 판정이 적은 기준(관련성, 거부)은 구간이 결정 사항 4의 경계를 걸치면 "판정 불충분"으로 보고하고, 추가 표본을 할지 그때 정한다
2. **답변 관련성을 블라인드 대상에 넣을지.** 질문과 답변만 보면 되어 작업량이 작지만, S24에서 judge가 실패(일부·답하지 않음)로 본 답변이 100개 중 15개라 m = 12에서 실패 사례가 몇 개뿐이다
   - (a) 넣는다(추천): 추가 작업이 질의당 판정 1개다. TPR은 못 내더라도 퍼센트 일치와 κ는 낸다
   - (b) 뺀다: 관련성은 블라인드 확인 전 상태로 남아, 판정에 쓸지 정할 근거가 없다

### 실행 비용·시간 추정 (판정 세트 230 + 풀 100 = 새 330질의)

| 항목 | 호출 | 비용 | 근거 |
| --- | ---: | ---: | --- |
| 생성 330질의 | 330 | 약 $0.08 | S24 질의당 약 $0.000245(D-37 CoreWeave 요율) |
| judge `mixed` 330질의 | 약 2,430 | 비피크 약 $1.7, 피크 약 $3.4 | S24 측정: 100질의를 모두 새로 채점하면 호출 약 735회, 비피크 약 $0.51 |
| 합계 | 약 2,760 | 비피크 약 $1.8, 피크 약 $3.5 | opencode Go 월 한도 $80의 약 2\~4% |

- PLAN의 옛 추정(judge 약 5,500회)은 S14 dev-small 기록과 반복 없는 전체 채점을 가정한 값이다. 위는 S24 실측 호출 수로 다시 낸 것이다
- 시간: 생성은 동시 4로 약 4분(2.5초 × 330 / 4, 검색은 차례로). judge는 동시 4에서 330질의 약 45분(D-50 어림)이고, 동시 8이 얼마나 줄이는지는 이 실행에서 잰다
- 보내는 데이터: dev-full 질의 330개와 근거(D-31 허용 범위). test 분할은 쓰지 않는다
- 사용자 검수 시간은 재지 않았다. m = 12 기준 근거 읽기 12회와 체크 약 94개다

## 완료 기준

1. `uv run pytest -q`, `uv run ruff check .` 통과
2. 실행: 430질의 모두 생성 기록과 judge 결과가 있다. 앞 100질의는 S24 기록을 이어 써 생성·judge 새 호출이 없다(report의 새 호출 수로 확인)
3. 베이스라인 보고: `gen_eval.n=330` report가 기준별 점수·구간, 참조 사용 불가 비율, 형식 오류·잘림 수, judge 지연·429 수를 낸다. 결과를 이 문서 결과 절에 적는다
4. 표본 도구: 같은 입력·seed로 두 번 돌리면 같은 질의·같은 판정 목록이 나온다(테스트). 검수 문서에 judge의 판정·이유·점수 문자열이 없다(테스트). 판정용 330 안의 qid가 표본에 없다(테스트)
5. 집계: 체크가 없거나 둘 이상인 판정이 있으면 멈추고 목록을 낸다(테스트). 노트북이 위 (d)의 표를 낸다
6. 사용자 결정(기준별 판정 사용·보조 지표)을 DECISIONS에 기록하고, 이에 따라 PLAN의 거부 정확도 "참고값" 줄 등을 고친다
7. test 분할은 쓰지 않는다. 외부 API는 승인받은 실행만 한다
