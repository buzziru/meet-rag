# S14b 부분 거부 처리와 거부 이유 분류

S14 생성 평가 모듈의 거부 처리를 고친다. 지금은 답변 어딘가에 거부 문구가 있으면 답변 전체를 거부로 보고 충실성·답변 관련성·핵심 답변 포함도를 채점하지 않는다(`judge.py`의 `judge_record`). 사용자 지적(PR #106 코멘트, 2026-10-20): "A 위원은 B를 제안했습니다[1]. C의 시행 시기는 제공된 회의록에서 답을 찾지 못했습니다."에서 첫 문장은 평가해야 하고, C의 시행 시기를 거부한 것도 이유에 따라 달리 평가해야 한다. 근거 문서에 정보가 부족한 경우(청크가 잘렸거나 잘못된 문서), 근거가 "예정이다", "정해지지 않았다"처럼 모호하게 답한 경우, 답변자가 답을 거부한 경우가 서로 다르다.

점수로 무엇을 정하는 조각은 아니다. S14 표본 20질의는 거부가 0건이라 이미 기록한 점수는 바뀌지 않는다.

## 만드는 것

### 거부 판정 (코드)

- 답변을 인용 검사와 같은 `sentences()`로 나누고, 프롬프트의 거부 문구(`gen_eval.refusal`)를 담은 문장(공백 차이 무시)을 거부 문장으로 본다. 거부 문장도 아니고 내용 없는 문장(`gen_eval.filler_phrases`)도 아닌 문장이 내용 문장이다
- 전체 거부: 거부 문장이 있고 내용 문장이 없다. 부분 거부: 거부 문장과 내용 문장이 함께 있다
- judge 기록의 `refusal`을 `"full"`, `"partial"`, `null`로 바꾸고 거부 문장 목록을 남긴다. 이전 judge 기록은 그 커밋의 코드로 집계한다(구현 원칙: 과거 코드와 병용하지 않는다)
- 지정 문구를 따르지 않은 거부("근거에 나와 있지 않습니다")는 이 조각에서 잡지 않는다(초안 "코드로 판정하는 항목", 보정 표본에서 비율을 본다)

### 부분 거부 답변의 채점

- 충실성, 답변 관련성, 인용 검사, 메타데이터 일치는 거부 문장을 뺀 내용 문장으로 한다(결정 사항 1). 거부 문장에는 진술이 없어 충실성이 정의되지 않고, 관련성에서 거부를 깎으면 아래 거부 평가와 같은 일을 두 번 센다(초안 "거부 답변의 처리"와 같은 이유)
- 핵심 답변 포함도는 답변 전체로 본다. 거부한 부분의 핵심 진술은 답변에 없어 0으로 잡힌다
- 전체 거부 답변은 지금처럼 위 기준을 채점하지 않는다
- 예: "A 위원은 B를 제안했습니다[1]. C의 시행 시기는 제공된 회의록에서 답을 찾지 못했습니다." → 부분 거부. 충실성·관련성·인용 검사는 첫 문장 하나로 하고, 둘째 문장은 거부 이유 분류로 간다

### 거부 이유 분류 (judge)

- 새 judge 단계 `refusal_reason`을 거부 문장이 있는 답변(전체·부분)마다 한 번 부른다. 입력은 질의, 거부 문장 목록, 근거 5개 전체(`format_contexts`, 결정 사항 3), 참조 발언(`answer.comment`)이다
- 출력은 거부 문장마다 거부한 내용(그 문장이 답하지 못했다고 한 것), 판정 이유 한 문장, 이유, 참조 포함 여부다. 형식이 틀리면 실패로 기록하고 다시 묻지 않는다(S14 규칙)

| 이유 | judge 판정 기준 | 평가 |
| --- | --- | --- |
| `answerable` 근거에 답 있음 | 근거 5개 중 어딘가에 그 내용이 분명히 있다 | 잘못된 거부 |
| `ambiguous` 근거가 모호함 | 근거가 그 내용을 예정·검토 중·정해지지 않음으로만 말한다 | 상황 미전달(별도 유형, 결정 사항 2) |
| `declined` 답변자 회피·거부 | 근거에서 답변자가 그 내용에 답하지 않았거나 답을 피하거나 거부했다 | 상황 미전달(별도 유형, 결정 사항 2) |
| `missing` 근거 부족 | 근거 5개에 그 내용이 없다 | 적절한 거부 |

- 근거 부족(`missing`)의 원인은 코드가 나눈다. 정답 문서가 근거에 없으면 `gold_missing`(검색 누락), 정답 문서는 있는데 judge가 참조 발언에는 그 내용이 있다고 판정하면 `chunk_cut`(청크 잘림 추정, 근거는 문서마다 청크 하나, D-05), 그 밖은 `other`다. 검색·청킹 개선 근거로 보고한다
- 지시는 `j_v6`(`j_v5`에 `refusal_reason` 단계를 더한 것)으로 만들고 judge 기본 지시로 바꾼다. 다른 단계 문구는 그대로라 저장된 응답(요청 본문 해시)을 다시 쓴다. 예시는 지어낸 회의록 문단으로 쓴다(AI Hub 데이터를 넣지 않는다)

### 집계

- `rag.gen_eval.report`
  - 거부: 전체 거부와 부분 거부 수를 따로 낸다. 기준별 평균 표에 부분 거부 답변이 몇 개 들어갔는지 적는다
  - 거부 이유 표: 이유별 거부 문장 수를 전체·부분 거부로 나눠 내고, 근거 부족은 원인(`gold_missing`, `chunk_cut`, `other`)별로 나눈다
  - 잘못된 거부율: `answerable` / (`answerable` + `missing`). 상황 미전달(`ambiguous`, `declined`)은 분모에 넣지 않고 따로 센다(결정 사항 2)
  - 기존 거부 교차 집계(근거 상태별)는 전체·부분 거부를 합친 거부로 그대로 둔다

## 결정 사항

모두 정했다(사용자 결정 2026-10-20). DECISIONS D-41로 기록한다.

1. 부분 거부 답변의 답변 관련성 입력: 거부 문장을 빼고 채점한다. 답하지 못한 부분은 포함도와 거부 이유 분류가 맡는다
2. 근거가 모호함·답변자 회피의 평가: 잘못된 거부와 적절한 거부 사이의 별도 유형(상황 미전달)으로 세고 거부 정확도에 넣지 않는다. 지금 생성 프롬프트(v1·v2)는 "답할 수 없으면 거부"만 지시하고 모호함·회피를 전하라고 하지 않아, 이 거부는 지시를 따른 결과다. 생성 프롬프트에서 모호함·회피를 전하게 하는 것은 생성 실험 아이디어(PLAN H18)로 둔다
3. 거부 이유 분류에 쓰는 근거: 근거 5개 전체. 다른 문서에 답이 있었는데 거부한 경우도 `answerable`로 잡는다

## 완료 기준

- `uv run pytest -q`, `uv run ruff check .` 통과
- 테스트
  - 거부 분리: 거부 없음, 전체 거부, 부분 거부(위 예시), 공백이 다른 거부 문구, 내용 없는 문장이 섞인 전체 거부("다음과 같습니다." + 거부 문장은 전체 거부)
  - 부분 거부의 judge 입력: 가짜 judge로 충실성·관련성에 거부 문장이 빠진 답변이, 포함도에 답변 전체가 가는지
  - 근거 부족 원인: 정답 문서 없음 → `gold_missing`, 정답 문서 있음·참조 포함 → `chunk_cut`, 그 밖 → `other`
  - `refusal_reason` 응답 파싱: 정상, 형식 오류, 거부 문장 수와 출력 수가 다름
  - 집계: 이유 표, 잘못된 거부율의 분모에서 상황 미전달 제외
- judge 동작 확인: S14 생성 기록의 dev 질의 중 4개를 골라, 실제 답변에 거부 문장을 붙인 합성 답변을 이유마다 하나씩 만들어(로컬 `data/` 아래, 커밋하지 않음) `refusal_reason`으로 판정한다. 의도한 이유와 judge 판정을 대조한 표를 결과 절에 적는다. 호출 4\~8회, opencode Go 구독이라 추가 과금 없음
- 회귀: S14 표본 20질의를 `rag.gen_eval.judge`·`report`로 다시 돌려 기준별 평균이 S14 결과 절과 같다(거부 0건, 저장된 응답 사용)
