# S51 후속 질문 답변 다듬기와 앞 근거 다시 쓰기

S40(대화 이어 가기) 병합 뒤 사용자가 production에서 본 대화에서 후속 답변이 만족스럽지 않았다(2026-11-06). 이 조각은 두 가지를 한다. 하나는 앞 대화를 넣는 형식을 고치는 것이고, 다른 하나는 직전 답변이 쓴 근거를 다시 쓰는 것이다(PLAN S51, 사용자 결정 2026-11-06으로 합침). 대화 이어 가기는 판정 지표로 재지 않으므로(D-76 결정 4), 지어낸 대화 표본과 기계 검사, 사용자 검수로 본다.

관찰된 문제(S40 결과 절 관찰, 사용자 대화 2026-11-06). 추적이 꺼져 있어 재작성 질의와 근거는 보지 못했다:

- **반복**: "자세히 알려줘"에 앞 답을 거의 그대로 되풀이했다. 근거에 세부가 없으면 일부 거부 문장을 써야 하는데 쓰지 않았다. 원인은 앞 답변을 assistant 차례로 넣어 모델이 근거 대신 그 답을 다시 쓴 것으로 추정한다
- **인용 누락**: 앞 답변이 두 개 쌓인 3번째 턴에서 `[n]`이 빠졌다(S40 확인 1번, 사용자 대화 1번). 원인은 인용 번호를 지운 앞 답변이 형식 예시가 된 것으로 추정한다
- **범위 좁힘**: "다른 안건은?"에 다시 같은 주제로 답했다. 재작성이 앞 주제로 좁혔는지, 근거에 다른 안건이 없었는지 모른다

## 만드는 것

- **대화 표본**: 메인이 코퍼스 문서 본문을 보고 대화 20개를 짓는다. 대화마다 첫 질문 1개와 후속 질문 2개다. 후속 질문은 지시어 풀기, 근거에 없는 세부 요청, 범위 넓히기, 주제 바꾸기를 고루 담는다. 후속 질문마다 기대 동작을 적는다(앞 근거가 필요한가, 답이 근거에 있을 것으로 보는가). 10개는 개발용, 10개는 확인용이다. 파일은 `data/multiturn/`에 두고 커밋하지 않는다. 경로는 config에 둔다
- **실행 도구**: 표본 대화를 로컬에서 차례로 돌려 턴마다 재작성 질의, 근거, 메시지, 답변, 검사 결과를 기록한다(`rag.multiturn_check`, 실행 config로 아래 방식을 고른다). 기록은 `refuse_existing`으로 덮어쓰지 않는다
- **기계 검사**: 후속 답변마다 다음을 본다
  - 인용: 문장마다 `[n]`이 있다(`rag.gen_eval.checks.citation_check`)
  - 반복: 앞 답변과 겹치는 정도. 겹침이 크면 일부 거부 문장이 있어야 한다(`refusal_split`)
  - 근거 범위: 인용 번호가 이번 근거 수 안이다
- **앞 대화 형식(A)**: config로 두 방식을 고른다. 하나는 지금처럼 assistant 차례로 넣는 방식(`turns`)이다. 다른 하나는 user 메시지 앞에 "[앞 대화]" 글 묶음으로 넣고, 앞 대화는 질문을 이해하는 데만 쓰며 답과 인용은 이번 [근거]로만 하라는 지시를 붙이는 방식(`block`)이다. 지시는 앞 대화가 있을 때만 붙고 첫 질문의 v19 메시지는 바꾸지 않는다
- **앞 근거 다시 쓰기(B)**: 마지막 조각에 근거마다 청크 번호를 더해 보낸다. 페이지는 답변이 인용한 근거의 청크 번호를 앞 대화와 함께 들고 다음 질문에 보낸다. 서버는 번호의 범위와 개수(최대 3개)를 확인하고 원문을 다시 읽어 근거 5칸 안에 넣는다. 남은 칸은 이번 검색 결과로 채우고 번호는 1부터 다시 매긴다. 근거 칸 수가 그대로라 프롬프트 길이가 늘지 않는다
- **넣을지 판단(B)**: config로 세 방식을 고른다
  - `rule`: 직전 인용 청크의 문서가 이번 재정렬 후보에 다시 나오면 넣는다. 호출이 없다
  - `rewrite`: 재작성 호출이 검색 질의와 함께 "앞 근거 필요"를 표시한다. 새 재작성 지시 버전이 필요하고 호출 수는 그대로다
  - `decision`: 판단 모델 `microsoft/microsoft-decision-1`(OpenRouter Decisions API, D-48 파일럿에서 항목 처리 38/41, 지연 p50 0.74초)을 재작성과 병렬로 부른다
- **앱·페이지**: 고른 방식을 `app.multiturn`에 두고, 페이지가 청크 번호를 들고 보낸다

## 결정 사항

1. **생성 단계를 다시 열지 않는다(메인 판단, 사용자 대화 2026-11-06)**: 바꾸는 것은 앞 대화가 있을 때의 경로뿐이다. 첫 질문의 메시지와 검색 질의는 지금과 같아(이미 있는 시험) 생성 test 1회 결과(D-90)는 그대로다. 해결책이 v19 system 지시 자체를 고쳐야 하면 생성 기준이 바뀌므로 멈추고 묻는다
2. **표본을 짓는 방법(승인 필요)**: 메인이 코퍼스 문서의 본문만 보고 짓는다. 문서의 `summary_q`, `summary_a`, 분할 정보와 평가 질의(dev·test·multi-doc)는 보지 않는다. 판단이 들어가는 일이라 opencode worker에 맡기지 않는다(ADR-0105). 기대 동작은 메인이 적고 사용자 검수는 받지 않는다(처음 지시는 애매한 칸만 사용자가 답하는 검수였다. 사용자는 질문과 답변만 보고 사용자 경험으로 판단한다고 정했다, 2026-11-06)
3. **방식 고르기(승인 필요)**: 개발용 10개로 고르고, 확인용 10개는 고른 뒤 한 번만 돌린다. 고르는 기준은 실행 전에 정한다
   - 형식(A): 기계 검사 위반(인용 누락, 거부 없는 반복) 수가 적은 쪽. 같으면 `turns`(지금 방식)다
   - 판단(B): 기대 동작의 "앞 근거 필요" 라벨과 맞는 수가 많은 쪽. 2개 차이 안이면 호출이 적은 쪽(`rule` > `rewrite` > `decision`)이다. 지연은 S41 재측정에서 본다
   - 확인용에서 위반이 개발용보다 크게 늘면 멈추고 보고한다
4. **노트북과 결정(사용자 결정 2026-11-06)**: 방식은 결정 3의 기준대로 메인이 고르고, 개발용 결과 노트북에 근거를 남겨 보인다. 사용자가 다르게 정하면 따른다(처음 지시는 노트북을 보고 사용자가 정하는 것이었다. 사용자가 권고대로 진행하라고 했다)
7. **사용자 판단의 범위(사용자 결정 2026-11-06)**: 사용자는 확인용 대화의 질문과 화면에 나가는 답변 글만 읽고 사용자 경험으로 판단한다. 근거의 정확성·충실성, 기계 검사 수치, 기대 동작 라벨은 보지 않는다. 그래서 확인용 결과는 대화마다 질문과 답변만 담은 읽기 문서로 따로 만든다. 입력→동작: 대화 하나는 "질문 1 → 답변 1 → 질문 2 → 답변 2 → 질문 3 → 답변 3"만 보이고, 근거 칸과 인용 대조는 메인이 기계 검사로 본다
5. **외부 호출과 재시작(승인 필요)**
   - OpenRouter, 개발용: 형식 2개 × 대화 10개 × 3턴에 재작성을 더해 약 80번이다. 판단 3방식은 재작성 표시 20번, 판단 모델 20번, 다시 쓰기 생성 약 40번이다. 지시를 고쳐 두세 번 다시 돌리는 것까지 넣어 약 400번 안쪽, $0.2 이하로 본다(생성 1,000질의당 약 $0.37, S39b. 판단 모델은 60요청 $0.0027, D-48)
   - OpenRouter, 확인용: 약 80번
   - Space 재시작 1번. 미리보기 화면 확인에 지어낸 대화 2개(약 10번)
   - 로컬에는 GPU가 없어 재정렬을 끄고 돌린다(`retriever.rerank.enabled=false`). 근거가 Space와 조금 다를 수 있다. 판단 `rule`이 쓰는 재정렬 후보는 로컬에서 RRF 후보로 대신한다
6. **판단 모델로 보내는 것**: 후속 질문과 앞 질문·답변이다(코퍼스 내용 포함). OpenRouter는 허용 처리처다. 평가 질의는 보내지 않는다

## 노트북과 결정의 순서

1. 표본 → 개발용 실행 → `notebooks/51_01_후속답변방식.ipynb`(방식별 기계 검사 위반, 판단 라벨 일치, 사례)
2. 메인이 결정 3의 기준대로 형식과 판단 방식을 고르고 노트북과 함께 보인다 → 이 문서 결정 사항에 기록하고 config 기본값을 바꾼다
3. 확인용을 한 번 돌리고, 질문과 답변만 담은 읽기 문서를 사용자가 읽는다(결정 사항 7)
4. 대화 이어 가기의 형식·판단 방식은 앞 결정에 없는 새 운영 설정이라 DECISIONS에 새 결정으로 적는다

## 감수하는 것

- 표본은 메인이 지은 20개라 실제 방문자 질문의 분포를 대표하지 않는다. 개발용과 확인용을 나눠 고른 대화에만 맞추는 것은 막지만, 표본 밖 유형의 실패는 production 확인에서만 드러난다
- 로컬은 재정렬을 끄고 돌려 근거가 Space와 다를 수 있다. 미리보기 확인(완료 기준 6)이 Space 경로를 본다
