# S20 시작 준비 시간 줄이기

S17 뒤에도 전체 인덱스 명령의 시작 준비가 약 50초 남았다(`docs/slices/17-load-speed.md` 결과). 검색과 생성은 실행할 때마다 이 준비를 다시 한다. 평가 반복 전 리뷰 항목과 생성 실험에서 확인 명령을 계속 돌리므로 지금 줄인다(사용자 지시 2026-10-22, 이슈 #133). 검색 순위와 생성 근거는 바뀌지 않아야 한다.

## 측정 (2026-10-22, `main` 6c06e13, exp017 full, 로컬 CPU, RAM 8GB)

S17과 같은 방식으로 쟀다. 함수를 시간 측정 래퍼로 감싸 실제 경로를 한 프로세스에서 재고, 같은 측정을 두 번 했다. 조건 색인과 추출기는 cProfile로 함수별로 나눴다. 측정 스크립트는 저장소 밖에 두었다.

- 프로파일 수치는 측정 부담이 붙어 실제보다 크다. 비율만 근거로 쓴다
- 임베딩을 메모리 매핑으로 바꿔도(S17 안 (3)) 디스크 읽기는 줄지 않는다. dense 검색은 질의 묶음마다 청크 행렬 전체와 내적하므로 결국 모든 행을 읽는다. 따로 잰 값으로는 첫 인덱스(461MiB)의 이어 붙이기가 0.2\~0.4초로, 매핑이 줄일 수 있는 것은 이어 붙이기 시간과 사본 메모리뿐이다

## 만드는 것

### (a) 안건 법률명 기억

- `agenda_laws`에 `functools.cache`(크기 제한 없는 `lru_cache`)를 달아 같은 (안건, 최소 글자 수)는 한 번만 계산한다. 반환은 `frozenset`으로 바꾼다. 같은 집합을 여러 호출부가 받으므로, 한 곳에서 고치면 다른 곳에 번지지 않게 한다. 지금 호출부는 둘(`doc_values`, `build_extractor`)이고 둘 다 읽기만 한다
- 크기 제한 없이 둔다. 안건 문자열 5,822개와 그 법률명 집합이라 메모리가 작다(재지 않음, 결과 절에 적는다)

### (b) 추출기의 설정 읽기를 반복문 밖으로

- `build_extractor`의 `docs()`가 문서마다 읽는 `c.get("agenda_law")`와 `c.law_min_chars`를 반복문 전에 지역 변수로 한 번 읽는다

### (c) doc_id 읽기

- 줄마다 본문까지 파싱하는 대신 줄 앞부분에서 doc_id만 꺼낸다(결정 사항 1 (a)). 줄이 `{"chunk_id": <줄 번호>, "doc_id": "`로 시작하는지 보고, 그 뒤 문자열을 `json.decoder.scanstring`으로 읽는다. 이스케이프가 든 값도 `json.loads`와 같게 읽는다. 시작이 다르면 파일 경로·줄 번호와 함께 멈춘다
  - 본문의 같은 문자열을 잘못 읽지 않는다. 본문(`text`)은 줄 끝에 있고 `json.dumps`가 본문의 따옴표를 `\"`로 쓰므로, 본문 안에 `"doc_id": "`가 그대로 나오지 않는다
  - 지시서 확인 때 잰 값(2026-10-22): 인덱스 9개(dev-small 6, full 3, 476,651줄) 모두 키 순서가 `chunk_id`, `doc_id`였고, 이 방법으로 읽은 값과 `json.loads` 값이 다른 줄은 0개였다. doc_id 문자는 영숫자와 `_`·`-`·`.`뿐이다
- BM25용으로 기본 인덱스를 한 번 더 읽는 것은 그대로 둔다. 부분 파싱 뒤 한 번에 0.4초 안팎이라 `load_dense` 결과를 나눠 쓰는 연결을 만들 만큼 크지 않다

### (d) 임베딩 이어 붙이기

- 부분 파일을 모두 읽은 뒤 두 번 이어 붙이는 대신, 전체 크기의 배열 하나를 먼저 만들고 부분 파일을 차례로 그 안에 읽어 넣는다. 사본이 생기지 않아 순간 메모리가 약 1.3GB 준다. 디스크 읽기는 그대로다
- `load_embeddings`(인덱스 하나)와 `load_dense`(여러 인덱스)의 반환 값은 지금과 같다(같은 값, `float32`, 같은 순서)

### (e) 확인 명령 한 프로세스 실행 (S17 안 (4))

이 조각에서 하지 않는다(결정 사항 2 (a)). (a)\~(d) 뒤 결과 절의 시간으로 다시 정한다.

### 테스트

- `agenda_laws`: 같은 입력을 두 번 부르면 같은 `frozenset`을 돌려준다. 기존 법률명 테스트는 그대로 통과한다
- doc_id: 합성 `chunks.jsonl`(본문에 따옴표·역슬래시·`"doc_id"` 문자열이 든 줄 포함)에서 새 읽기와 `json.loads` 읽기가 같다
- 임베딩: 합성 부분 파일 여러 개에서 새 읽기가 `np.concatenate` 결과와 같다(값, dtype, 행 순서). 인덱스마다 청크 수와 행 수가 다를 때 멈추는 기존 확인은 그대로 둔다
- 기존 조건 색인·추출기·검색 테스트가 그대로 통과한다

## 결정 사항

1. **doc_id만 꺼내는 방법.**
   - (a) 줄 앞부분만 파싱한다: 청크 파일은 `rag.index`가 `chunk_id`, `doc_id`, `start`, … 순서로 쓴다(`src/rag/index.py:257`). 줄 앞에서 `"doc_id"` 값까지만 읽는다. 새 산출물이 없다. 측정에서 정규식 추출이 인덱스 하나에 2.1초 → 0.4초였고 결과가 같았다. 쓰는 순서가 바뀌면 틀리므로 첫 키가 `chunk_id`, 둘째가 `doc_id`가 아닌 줄을 만나면 멈춘다
   - (b) 인덱스를 만들 때 doc_id를 따로 저장한다(S17 안 (3) 원안): 읽기는 가장 빠르다. 다만 `data/`에 새 산출물이 생겨 지문(`basis.json`)과 덮어쓰기 방지가 필요하다. 기존 인덱스 8개에는 파일이 없으니 만드는 명령(adopt)도 필요하다
   - 추천은 (a)다. 남는 차이가 인덱스 하나에 0.4초 안쪽이고, (b)는 산출물과 장치가 늘어난다
   - 결정: (a)(사용자 결정 2026-10-22). 사용자가 부분 파싱의 위험을 물어 위 "(c)"의 대조를 먼저 했다
2. **확인 명령을 한 프로세스로 돌릴지 (S17 안 (4)).** 완료 기준의 결과 불변 확인은 dev-small, dev-full, multi-doc 세 명령이다. 그중 dev-full과 multi-doc은 같은 전체 인덱스를 쓴다
   - (a) 하지 않는다: (a)\~(d)를 마친 뒤 준비 시간을 다시 재고, 남는 시간을 보고 정한다
   - (b) 한다: `rag.search`가 질의 세트 여러 개(`search.queries=[summary_q,multidoc]`)를 받아 `Retriever`를 한 번만 만들고 세트마다 순위 파일을 쓴다. 확인 한 번에 전체 인덱스 준비 한 번이 준다. 순위 파일 경로·내용은 세트마다 따로 실행할 때와 같다
   - 추천은 (a)다. (a)\~(d)로 준비 시간이 얼마나 남는지 모르는 채로 실행 방식을 바꾸면, 줄어든 폭에 비해 설정 형식이 복잡해질 수 있다
   - 결정: (a)(사용자 결정 2026-10-22)
3. **임베딩 메모리 매핑 (S17 안 (3) 앞부분).** 위 측정으로 줄일 수 있는 시간이 이어 붙이기 1.3초뿐이라 이 조각에서 하지 않는다. (d)가 같은 몫을 줄이고 메모리 사본도 없앤다

1. `uv run pytest -q`, `uv run ruff check .` 통과
2. 결과 불변(검색): `uv run python -m rag.search +exp=exp017 index.scope=dev-small`, `… index.scope=full`, `… index.scope=full search.queries=multidoc`가 기존 순위 파일과 "같은 내용, 그대로 둠"으로 끝난다. full 후보 쌍(`search.mode=rerank-pairs`)도 "같은 내용"
3. 결과 불변(조건): 조건 색인(필드 → 값 → 문서 번호)과 추출기(값 사전, 법률명)가 `main`의 것과 같다. 한 번 저장해 대조하고, 저장 파일은 `data/` 밖 임시 경로에 둔다
4. 결과 불변(생성 근거): 기존 생성 기록 `data/gen_eval/runs/hybrid-cond-filter-law-ms256-k20-ce-v1-dev-small.jsonl` 20건의 qid로 `Pipeline.retrieve`만 불러(생성 API 호출 없음, `LANGSMITH_TRACING=false`) 근거 dict 전체가 기록과 같다
5. 시간: 위 "측정"과 같은 방법으로 단계별 시간과 `rag.search` 세 명령, `Pipeline` 준비의 벽시계를 다시 재 결과 절에 전후 표로 적는다. 목표 수치는 두지 않는다
6. test 분할 질의를 읽는 명령은 돌리지 않는다. 외부 API는 호출하지 않는다
