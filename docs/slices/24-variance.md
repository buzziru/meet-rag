# S24 변동 폭 측정과 생성 평가 질의 규모 결정

기준 설정을 반복 실행해 생성 API 비결정성과 judge 잡음의 변동 폭을 재고, 그 값으로 생성 평가 판정용 질의 수 n과 judge 실행 설정을 정한다(PLAN "변동 폭 측정과 질의 규모 결정", D-44, 기준 문서 P7). 실행 설정(단계별 사고 과정, 다수결, `max_tokens`)은 사람 라벨 없이 일관성 수치로만 골라 고정한다(D-49에서 미룬 두 번째 동결). 생성 실험 1회가 dev-small 전체 기준 비피크 약 $4.1·피크 약 $8.0이라 규모를 줄일 근거가 필요하다(D-44).

함께 하는 것(사용자 지시 2026-10-26):

- 생성 평가의 질의 생성을 동시에 한다. 방식은 아래 결정 사항 1에서 고른다
- 생성·judge 응답마다 시간과 토큰을 기록해 나중에 참고할 수 있게 한다. 동시 생성이 지연에 영향을 주는지 이전 기록(S14 v1·v2, 차례로 생성)과 비교한다

결정 순서: 측정 코드 → 측정 실행(비용 승인) → 근거 노트북 → 사용자 결정(n, 실행 설정) → DECISIONS 기록 → PR. 결정이 걸린 조각이라 노트북을 결정 전에 보인다.

## 만드는 것

### (a) 반복 실행 (생성·judge)

- 생성 반복: `gen_eval.gen_rep`(정수, 기본 0)를 생성 기록 경로(`paths.gen_runs`)와 judge 결과 경로에 넣는다. 0이면 지금 경로와 같다. 같은 질의를 같은 설정으로 다시 생성해 생성 잡음을 잰다
- judge 반복: `judge.rep`(정수, 기본 0)를 judge 캐시 키(요청 본문 해시)와 judge 결과 경로에 넣는다. 0이면 지금 키·경로와 같아 저장된 응답을 그대로 쓴다(D-49 캐시 키). 같은 답변을 같은 지시로 다시 채점해 judge 잡음을 잰다
- 레시피에 두 값을 남긴다

### (b) 동시 생성 (`rag.gen_eval.generate`, 결정 사항 1)

- 추천안 (b)로 쓰면: 질의마다 검색·프롬프트를 지금처럼 차례로 만들고, 생성 호출(`Pipeline.generate`)만 워커 풀로 동시에 보낸다. 동시 수는 `gen_eval.concurrency`(결정 사항 2). 기록은 표본 순서대로 쓰고, 중간에 멈춰도 이어 쓸 수 있게 끝난 것부터 쓴다
- 생성 기록 형식(`contexts`, `answer`, `usage`, `provider`, `first_token_s`, `total_s`, `recipe`)은 바꾸지 않는다. 검색 근거는 지금과 같아야 한다

### (c) 시간·토큰 기록

- 생성: 지금 기록하는 `usage`, `first_token_s`, `total_s`, `provider`에 검색 시간 `retrieve_s`와 동시 수 `concurrency`를 더한다
- judge: 호출마다 `usage`에 지연 `latency_s`, 저장 응답 사용 여부 `cached`, 끝난 이유 `finish_reason`을 더한다. 새로 부른 응답은 캐시 파일에도 지연과 끝난 이유를 저장하고, 저장 응답을 쓸 때는 그 값을 읽는다(이 조각 전 캐시에는 없어 비어 있다)
- report: 생성 지연(첫 토큰, 전체, 검색)의 중앙값·p95와 동시 수, judge 단계별 지연 중앙값·p95, 새로 부른 호출 수와 토큰, 끝나지 않은 응답(`finish_reason`이 `stop`이 아님) 수를 낸다

### (d) 측정 실행 (결정 사항 3·4, 비용 승인 후)

- 표본: dev-full 판정용 순서(개발 질의 제외, D-47 결정 5)의 앞 n0개
- 생성: 기준 설정(EXP-017 검색, 프롬프트 v2)으로 G회. 반복 0은 차례로(동시 수 1), 나머지는 동시로 생성해 같은 시간대에서 지연을 비교한다
- judge: 지금 실행 설정(`deepseek_go_mixed`)으로 생성 반복마다 채점하고, 생성 반복 0에는 J회 반복 채점한다. 비교할 실행 설정도 생성 반복 0에 J회 채점한다
- 다수결: judge 반복 J회의 판정을 단계별로 다수결한 값의 일관성도 같은 기록에서 계산한다(추가 호출 없음)

### (e) 근거 노트북 (`notebooks/35_01_S24_변동폭.ipynb`)

- 기준별(충실성, 관련성, 포함도, 거부 정확도 참고값) 질의 단위 값으로 잡음을 나눈다. judge 잡음은 같은 답변의 judge 반복 사이 차이, 생성 잡음은 생성 반복 사이 차이에서 judge 잡음을 뺀 나머지로 본다
- n 결정 근거(결정 사항 5): 같은 설정 두 실행의 평균 차이에 대한 회의 단위 paired bootstrap 95% 구간 반폭 h를 n0에서 재고, n에 따라 h(n) ≈ h(n0)·√(n0/n)로 늘려 표로 낸다. 짝지은 제외(D-47 결정 6)로 버려지는 질의 비율을 함께 낸다
- 실행 설정 비교: 설정마다 judge 반복 사이 일치(판정 단위 일치율, 질의 점수 차이), 끝나지 않은 응답 수, 비용·지연
- 동시 생성 영향: 반복 0(차례로)과 동시 반복의 첫 토큰·전체 시간 분포, 이전 S14 v1·v2 기록(차례로, 20질의)과 비교

## 결정 사항

1. **동시 생성 방식.** 생성 1건은 검색(로컬 CPU, Kiwi 형태소 분석·조건 추출) 다음 생성 API 호출(네트워크, S14 v2 전체 시간 중앙값 2.5초)이다. Kiwi와 조건 추출기가 여러 스레드에서 동시에 써도 안전한지는 확인하지 않았다
   - (a) 워커 풀로 `Pipeline.run` 전체를 동시에: 코드가 가장 적다(judge의 `ThreadPoolExecutor` + `concurrency`와 같은 방식). 검색 단계가 스레드 안전하지 않으면 근거가 조용히 달라질 수 있고, 검색 CPU 시간이 겹쳐 지연 측정에 섞인다
   - (b) 검색은 차례로, 생성 호출만 워커 풀로(추천): 예: 질의 500개를 동시 수 4로 생성하면 검색을 먼저 차례로 끝내고(질의당 검색 시간은 구현 때 잰다) 생성 500건을 4개씩 보낸다. 근거는 차례로 만들 때와 같다. 생성 지연(`first_token_s`·`total_s`)에는 로컬 검색 CPU가 섞이지 않는다. LangSmith 추적에서 검색과 생성이 한 `rag` 부모 아래 묶이지 않고 따로 남는다
   - (c) 프로세스 병렬(질의를 나눠 명령 여러 개나 병렬 에이전트로): 프로세스마다 인덱스를 읽어 시작 준비와 메모리(S20 기준 임베딩 읽기 때 순간 약 2.6GB)가 프로세스 수만큼 든다. 출력 파일을 나눠 합쳐야 하고 이어 쓰기 규칙이 복잡해진다
   - (d) asyncio(`AsyncOpenAI`): `Pipeline.generate`의 비동기판을 따로 만들어야 한다. 동시 수가 수 개 수준이면 스레드와 차이가 없고 코드가 겹친다
   - 추천은 (b)다. 근거 동일성을 지키고 지연 측정을 깨끗하게 둘 수 있는 방식 중 코드가 가장 적다
2. **동시 수 `gen_eval.concurrency`.**
   - (a) 4: judge와 같다. 질의 500개의 생성 시간 추정 약 5분(2.5초 × 500 / 4)
   - (b) 8: 약 3분. 제공자를 CoreWeave 하나로 고정해(D-37) 요청 제한(429)에 걸릴 가능성이 4보다 크다. 걸리면 그 질의는 오류로 남고 다시 실행해 이어 쓴다
   - 추천은 (a)다. 차례로 하면 약 21분이라 4로도 충분히 줄고, 지연 영향도 작게 시작해 측정한다
3. **측정 규모 n0·G·J.**
   - (a) n0 = 100, G = 3, J = 3(추천): 질의당 잡음을 추정하기에 질의 수가 충분하고(질의 단위 표준편차 추정), 반복 3회로 다수결도 계산할 수 있다
   - (b) n0 = 50, G = 3, J = 3: 비용이 절반이지만 h(n) 외삽의 불확실성이 커진다
   - (c) n0 = 200, G = 2, J = 2: 다수결(3회)을 계산할 수 없다
4. **비교할 judge 실행 설정.**
   - (a) `deepseek_go_mixed`(지금, 기본 끔 + 세 단계 low)와 `deepseek_go_nothink`(모두 끔) 두 개(추천): 둘 다 설정 파일이 있다. 다수결은 반복 기록에서 계산한다. `max_tokens`는 끝나지 않은 응답 수로 본다(16384에서 잘림이 없으면 그대로 둔다)
   - (b) (a) + `deepseek_go`(모두 사고 과정 켬): 모든 단계에 사고 과정 토큰이 붙어 judge 비용이 가장 클 것으로 추정한다(재지 않음). 2026-10-20에 20질의 검수로 끔·low 혼합을 기본으로 정했다(D-40)
5. **n 결정 규칙.** 최소 개선 폭 δ는 오라클 진단 뒤 정하므로(PLAN), 이 조각에서는 규칙만 정하고 값은 노트북 표를 보고 정한다
   - (a) 기준마다 h(n) ≤ δ가 되는 n을 δ 후보(0.02, 0.03, 0.05)별로 표로 내고, 짝지은 제외 비율로 나눠 키운 값을 사용자가 고른다(추천): 예: 충실성의 h(100)이 0.06이면 δ = 0.03에 n ≈ 400, 제외 비율 10%면 약 445
   - (b) 비용 상한으로 n을 먼저 정하고 그 n의 h를 보고한다: 생성 실험 1회 비용을 정할 수 있지만 그 n이 기준 차이를 가려낼 수 있는지는 사후에 본다

## 완료 기준

1. `uv run pytest -q`, `uv run ruff check .` 통과
2. 반복 0 동일성: `gen_eval.gen_rep=0`·`judge.rep=0`의 생성 기록 경로, judge 결과 경로, judge 캐시 키가 이 조각 전과 같다(S14 v2 기록을 j_v8로 다시 채점하면 API 호출 0회, 결과가 기존 j_v8 기록과 시간·지연 필드를 빼고 같다)
3. 동시 생성의 근거 동일성: 같은 질의를 동시 수 1과 4로 생성하면 `contexts`가 같다(생성 API 호출 없이 검색 단계만 비교하는 테스트, 실행 확인은 측정 실행의 반복 0과 1 비교)
4. 시간·토큰 기록: 측정 실행의 모든 생성 기록에 `retrieve_s`·`concurrency`, 새로 부른 judge 호출마다 `latency_s`·`cached`·`finish_reason`이 있고 report가 지연·토큰 요약을 낸다
5. 측정 실행이 끝나고 근거 노트북이 위 (e)의 표를 낸다
6. 사용자 결정(n, 실행 설정)을 DECISIONS에 기록하고, 기본 설정(`gen_eval` n·`queries`, judge 설정)에 반영한다
7. test 분할은 쓰지 않는다. 외부 API는 결정 사항 3·4로 승인받은 측정 실행만 한다
