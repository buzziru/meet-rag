## 만드는 것

### 청크 묶음 키우기 (1)

- 원인: `rank_with_pool`은 점수 상위 `retriever.chunk_pool`(200)개 청크만 정렬하고, 그 안에 서로 다른 문서가 k개 없으면 청크 전체를 정렬한다. 200은 D-08에서 dense 단독 top_k 10을 기준으로 정했고 그때는 전체 정렬이 0건이었다. 지금 hybrid는 dense 목록에서 `fusion.depth` 100개 문서를 고르므로 dev-full 3,016건 중 1,301건, dev-small 1,039건 중 1,022건이 전체 정렬로 넘어간다(실행 출력 "전체 정렬 N건")
- 바꾸는 것: 문서가 모자라면 묶음을 두 배로 키워 `argpartition`으로 다시 고르고, 묶음이 청크 수 이상이 될 때만 전체 정렬한다. 시작 크기는 지금처럼 `chunk_pool`이다. 고른 묶음은 지금처럼 (점수 내림차순, 청크 번호) 순으로 정렬하므로 결과는 전체 정렬과 같다(경계의 동점 제외, 기존 함수 설명과 같은 조건)
- 키우는 배수 2는 결과를 바꾸지 않고 속도에만 닿는 구현 상수라 config에 두지 않는다. `chunk_pool`의 뜻(첫 묶음 크기, 속도에만 영향, D-08)은 그대로다
- 반환하는 "전체 정렬 여부"와 실행 출력 "전체 정렬 N건"은 마지막에 전체 정렬까지 간 질의 수로 뜻이 같다. 이 조각 뒤에는 거의 0건이 된다
- BM25 문서 순위(`rank_docs`)도 같은 함수를 쓰므로 함께 빨라진다

### 코퍼스 한 번 읽기 (2)

- `rag.index`에 코퍼스를 읽어 문서 목록을 돌려주는 함수를 하나 두고, 한 프로세스 안에서 같은 파일은 한 번만 읽는다(파일 경로·수정 시각·크기로 캐시). 본문(`context`)은 이 세 곳이 쓰지 않으므로 빼고 담는다
- `Retriever._condition_index`, `conditions.build_extractor`, `generate.Pipeline`의 회의 정보가 이 함수를 쓴다. 각 결과(조건 색인, 값 사전·법률명, 회의 정보)는 지금과 같아야 한다
- 다른 코퍼스 읽기(`bm25.doc_meta`는 인덱스를 처음 만들 때만, `judge`, `g2`, `multidoc`, `ingest`·`splits`·`index`의 생성 경로)는 이 조각에서 바꾸지 않는다. 확인 명령의 시간에 닿지 않는다

### 테스트

- `rank_with_pool`: 문서당 청크가 많아 첫 묶음에 문서가 모자라는 합성 점수에서 결과가 전체 정렬과 같고, 전체 정렬로 넘어가지 않는다. 묶음이 청크 수에 닿으면 전체 정렬로 넘어간다
- 코퍼스 읽기: 같은 파일을 두 번 읽으면 파일을 한 번만 연다. 파일 내용이 바뀌면 다시 읽는다. 본문 필드가 없다
- 기존 조건 색인·추출기·생성 테스트가 그대로 통과한다
