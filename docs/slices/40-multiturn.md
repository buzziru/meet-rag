# S40 대화 이어 가기

지금 앱은 질문마다 따로 답한다. 한 대화 안의 앞 질문과 답변을 다음 질문 처리에 넘겨, 후속 질문("그건 언제 논의됐어?")에도 답하게 한다(H21, D-76 결정 4). 판정 지표로 재지 않는다(D-76 결정 4).

## 만드는 것

- **페이지**: `deploy/web/app.js`가 앞 대화를 메모리에 들고 있다가 `/chat`에 함께 보낸다. 브라우저 저장소에 넣지 않아 새로 고치면 대화가 지워진다. 질문마다 따로 답한다는 안내 문구는 지운다
- **새 채팅**: 페이지에 "새 채팅" 버튼을 두어 새로 고치지 않고 대화를 비운다(사용자 요청 2026-11-05). 답변 중에는 누를 수 없고, 대화 칸과 앞 대화 메모리를 함께 비운다. 문서 탭과 사이드바 선택은 그대로 둔다. Space 호출은 없다
- **API**: `chat(message, history)`. `history`는 기본값이 빈 목록이다. 첫 질문은 재작성 호출 없이 지금과 같은 프롬프트로 처리한다
- **검색 질의 재작성**: `search_query`가 앞 대화가 있을 때만 후속 질문을 혼자 읽히는 검색 질의 한 줄로 고친다. 지시는 `configs/rewriter/prompt/`에 새 버전으로 두고, 모델과 제공자는 생성과 같게 한다. 실패하거나 시간 제한을 넘으면 질문 그대로 검색한다. 재작성 결과는 추적에 남긴다(`src/CLAUDE.md`)
- **생성**: 메시지에 앞 질문과 답변을 넣고 근거는 이번 검색 결과만 넣는다. 앞 대화가 없으면 메시지는 지금과 한 글자도 다르지 않다. 값은 config(`app.multiturn`)에 둔다 이후 변경: S51(D-91)부터 앞 대화는 assistant 차례가 아니라 글 묶음(`block`)으로 넣고, 직전 답변이 인용한 청크의 문서가 이번 검색 상위 top_k에 다시 나오면 그 청크를 근거 칸에 다시 넣는다(`rule`). S40 병합 뒤 후속 답변이 앞 답을 되풀이하고 인용을 빠뜨려 지어낸 대화로 비교해 정했다
- **입력 상한**: 페이지가 보낸 `history`는 믿지 않는다. 형식이 어긋나면 버리고, 턴 수와 길이를 config 상한으로 자른다

## 결정 사항

1. **앞 대화 보관(사용자 결정 2026-11-05)**: 페이지 메모리에 둔다. 지난 방문자의 대화를 저장하지 않는다. 서버에 저장하지 않아 "방문자 질의는 `data/`에 저장하지 않는다"(S35)가 유지되고 동시 처리 수에도 영향이 없다. 서버 세션은 Space 재시작 때 사라지고 코드가 늘어 고르지 않는다. 입력→동작: 새로 고치면 첫 질문처럼 처리한다
2. **생성에 넣는 앞 답변(사용자 결정 2026-11-05)**: 변환 전 원문에서 인용 번호를 지워 넣고, 최근 3턴까지 넣는다. 화면 글을 넣으면 모델이 문장 끝 괄호 형식을 따라 써서 S45 변환이 맞지 않을 수 있고, 인용 번호를 남기면 지난 근거의 `[1]`과 이번 근거의 `[1]`이 섞인다. API 마지막 조각에 원문을 함께 보낸다. 입력→동작: 앞 답변 "2018년 … 회의에서 A는 찬성했습니다 [1]."은 "2018년 … 회의에서 A는 찬성했습니다."로 들어간다
3. **첫 토큰 3초(사용자 결정 2026-11-05)**: 후속 질문은 재작성 호출만큼 첫 토큰이 늦는다. 얼마나 늦는지는 아직 재지 않았다(EXP-013의 Google 경로 평균 46초는 다른 경로라 근거로 쓰지 않는다). D-30 기준은 첫 질문에만 적용하고 D-30에 표시를 붙인다. 후속 질문 시간은 이 조각에서 기록만 하고, 3초 재측정은 계획대로 S41에서 1회 한다
4. **앱 쪽 점검 4건의 위치(사용자 결정 2026-11-05)**: 전체 파이프라인 점검이 넘긴 R1-1, R3-2, R3-9, R3-12는 S40에 넣지 않고 앞에 별도 조각 S49로 한다. R1-1은 검색 경로라 순위가 달라지면 기준 변경 결정으로 멈추는데, 멀티턴과 묶으면 함께 멈춘다. 브랜치 하나에 목적 하나다(`git.md`). S40은 S49의 질문 길이 상한(R3-9)에 `history` 상한만 더한다. 입력→동작: S49 병합 → Space 반영 → S40 구현 순서다
5. **외부 호출과 재시작(승인 필요)**
   - OpenRouter: 지어낸 대화 3개, 생성 약 7번과 재작성 약 4번, 합쳐 11번 안쪽. $0.01 이하로 본다(1,000질의당 약 $0.37, S39b). 재작성은 생성보다 짧아 이 어림 안에 든다고 보지만 재지 않았다
   - Space 재시작 1번. `history`에 기본값을 두어 지금 production 페이지가 그대로 동작하는지 먼저 본다. 동작하지 않으면 멈추고 묻는다
6. **Aside(ADR-0099, ADR-0101)**: 미리보기 주소의 토큰은 스크립트로 옮긴다. 답변 경로가 바뀌므로 질의를 보낸다

## 감수하는 것

- 앞 대화에 든 내용을 근거 없이 답할 수 있다. 근거는 이번 검색 결과만 넣지만 모델이 앞 답변을 그대로 쓰는 것은 막지 않는다. 앞 답변이 틀렸으면 잘못이 이어지고, 화면 근거 칸에는 이번 근거만 보여 알아채기 어렵다. 지표로 재지 않아 빈도는 모른다 이후 변경: S51(D-91)부터 앞 대화는 assistant 차례가 아니라 글 묶음(`block`)으로 넣고, 직전 답변이 인용한 청크의 문서가 이번 검색 상위 top_k에 다시 나오면 그 청크를 근거 칸에 다시 넣는다(`rule`). S40 병합 뒤 후속 답변이 앞 답을 되풀이하고 인용을 빠뜨려 지어낸 대화로 비교해 정했다
- 페이지가 보내는 `history`는 방문자가 고칠 수 있어 형식 검사와 상한만 둔다. 지어낸 앞 대화로 모델을 유도할 수 있지만 결과는 그 방문자 화면에만 보이고, 서버 데이터는 바뀌지 않는다. 상한 안의 호출 비용은 S41의 크레딧 한도가 막는다

### 지시서와 다르게 하거나 더한 것

- 재작성은 기존 `rag.rewrite`에 `FollowUpRewriter`로 두고, 지시는 `configs/rewriter/prompt/rwmt_v1.yaml`, 값(시간 제한 10초, 재시도 없음, `max_tokens` 256, 질의 상한 300자)은 `app.multiturn.rewrite`에 둔다. 모델·제공자·파라미터는 `generator`를 따른다
- 앞 답변의 인용 번호는 페이지가 아니라 서버가 지운다. 페이지가 보내는 값은 믿지 않으므로 상한과 같은 곳에서 처리한다. 앞 답변 길이 상한은 3,000자(생성 `max_tokens` 1024의 답변이 든다), 앞 질문은 `app.max_query_chars`를 같이 쓴다
- `chat`의 `history` 기본값으로 지금 페이지가 그대로 동작하는지는 Space 재시작 전에 로컬 gradio 6.31과 `@gradio/client` 2.7.2로 먼저 봤다. 인자 하나만 보내면 클라이언트가 `null`을 채운다

### 관찰

- 후속 질문 하나(대화 A의 3번)는 답변에 `[n]`이 없었다. 앞 답변을 인용 번호 없이 넣어(결정 사항 2) 모델이 그 형식을 따랐을 수 있지만 한 건이라 원인은 모른다. 다른 후속 질문 3개에는 있었다
- 대화 C의 첫 질문(코로나19 백신 접종)은 관련 근거를 찾지 못해 일부 거부로 답했다. 첫 질문이라 S40 변경과 상관없다
- 페이지가 보내는 턴 수(`deploy/web/app.js`의 `HISTORY_TURNS`)는 `app.multiturn.max_turns`와 같은 3을 따로 적는다. 페이지는 config를 받는 경로가 없다(S49의 `maxlength`와 같은 경우). config만 올리면 페이지가 3턴까지만 보내 실제 상한은 늘지 않는다
- 생성 첫 토큰 시간은 생성 호출 시작부터 잰 값이라 검색·재작성 시간이 빠져 있다. 3초 판정(D-30)은 S41에서 입력부터 잰다
