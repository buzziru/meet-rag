# S26 오라클 진단과 정답 문서를 뺀 거부 세트

생성 평가 베이스라인(S25, D-51)과 같은 설정에서 근거만 바꾼 두 조건을 한 번 만들어 생성·채점한다(PLAN 생성 평가 "오라클 진단과 최소 개선 폭", D-38, 초안 "오라클 진단"). 검색 기준 근거와 오라클 근거의 점수 차이로 생성 실패와 검색 실패를 가르고, 정답 문서를 뺀 입력은 거부 정확도 세트로 쓴다. 최소 개선 폭(초안 결정 사항 3)은 이 결과와 S24 변동 폭으로 사용자와 따로 논의한다. 이 조각은 판단 재료만 만들고 값을 정하지 않는다.

흐름: A. 사용자는 이 조각의 진행과 API 사용(OpenRouter 생성, opencode Go judge)을 승인했다(2026-10-27, "오라클 진단에 필요한 api 사용도 승인하니 진행해"). 사용자 부재 중 진행하라는 지시라 지시서 확인을 받지 않고 구현한다. 아래 "메인이 정한 것"은 PR에서 확인받는다.

## 메인이 정한 것 (PR에서 확인)

1. 근거 수는 베이스라인과 같은 5개(`generator.context_docs`)로 두고 근거만 바꾼다. 비교가 근거 내용 차이만 보게 하려는 것이다
2. 오라클 조건(`gen_eval.contexts=oracle`): 정답 문서가 검색 상위 5개에 있으면 근거를 바꾸지 않는다. 없으면 5번째 자리를 정답 문서로 바꾼다. 정답 문서의 근거 청크는 검색과 같은 규칙(문서 안 dense 점수가 가장 높은 청크, `best_chunks`)으로 고른다. 정답 문서를 1위로 옮기지 않는 것은 순서 효과를 섞지 않으려는 것이다(베이스라인에서 정답 문서가 있는 319질의 중 302질의가 이미 1위)
3. 거부 세트(`gen_eval.contexts=no_gold`): 정답 문서를 근거에서 빼고 검색 6번째 문서로 채운다. 정답 문서가 원래 없던 질의는 근거가 바뀌지 않는다
4. 근거가 베이스라인과 같아지는 질의는 새로 생성하지 않는다. 같은 입력을 다시 생성하면 생성 잡음만 더하고 비용이 든다. 비교할 때는 그 질의의 베이스라인 결과를 쓴다. S25 판정용 330질의 기준으로 오라클은 11질의, 거부 세트는 319질의를 새로 생성한다
5. 거부 세트의 "거부해야 함" 라벨에는 잡음이 있다. 정답 문서 밖에도 답을 담은 문서가 있을 수 있다(SPEC 해석의 한계 2항, D-34의 "다른 정답" 9개). 이 세트의 판정은 judge 항목 평가(정보 상태)를 그대로 쓰고, 근거에 정보가 "있음"으로 판정된 항목을 따로 센다

## 만드는 것

- `configs/config.yaml`: `gen_eval.contexts`(`retrieved` 기본, `oracle`, `no_gold`). `paths.gen_runs`·`paths.gen_judge`에 `retrieved`가 아닐 때만 `-oracle`·`-no_gold`가 붙는다. 기본값의 경로와 생성 레시피는 바뀌지 않는다
- `rag.generate.Pipeline.retrieve`: 정답 문서와 조건을 받아 근거를 바꾼다. 근거가 기본 검색과 같으면 `None`을 돌려준다. 기본 호출(`rag.generate` CLI, 베이스라인)은 동작이 같다
- `rag.gen_eval.generate`: 조건이 `retrieved`가 아니면 정답 문서를 읽어 넘기고, `None`인 질의는 건너뛰고 수를 출력한다. 생성 레시피에 `contexts`를 더한다(기본값이면 넣지 않아 S25 레시피 해시가 같다)
- 노트북 `notebooks/36_01_오라클진단.ipynb`: 조건별 기준 점수, 거부 수, 정보 상태별 처리 표, 오라클로 바뀐 11질의의 점수 차이. 판단 재료만 두고 결정은 적지 않는다
