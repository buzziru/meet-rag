# S39 실시간 재정렬

S38의 Space는 재정렬을 끈 구성이라 평가한 기준 설정(EXP-017, D-36)과 검색 순서가 다르다. 자유 질의를 같은 Space의 ZeroGPU에서 재정렬해 기준 구성으로 맞춘다. 재정렬이 실패해도 방문자는 재정렬 없는 답변을 받는다. 콜드 스타트를 줄이기 위해 시작 시간을 단계별로 재고 병렬 읽기를 시험한다. 공개는 하지 않는다(S41).

배포의 목표 사용자는 HF 계정이 없는 인사담당자다. 로그인 없이 5\~10개 질의를 할 수 있어야 한다(사용자 2026-11-04). 방문자별 비로그인 할당량 대신 소유자 계정의 할당량(무료 계정 하루 5분, HF 문서)을 모든 방문자가 나눠 쓴다.

## 만드는 것

- **실시간 재정렬 경로**: `Pipeline.rank`가 점수 파일이 없는 자유 질의에서 RRF 상위 `retriever.rerank.depth`개의 질의·근거 청크 쌍을 만들어 점수를 받는다. 후보와 청크 선택은 `rag.search` 후보 쌍과 같은 함수(`candidates`, `best_chunks`)를 쓰고, 순서 규칙은 `final_order`를 그대로 쓴다. 점수 파일 경로(`rag.generate`, 생성 평가)는 바꾸지 않는다
- **Space 진입점**: `deploy/space/app.py`가 시작할 때 모듈 수준에서 리랭커를 `cuda`, `float16`으로 올리고(HF 문서 권장, EXP-017과 같은 dtype), `@spaces.GPU`로 감싼 점수 함수를 둔다. S38의 부르지 않는 함수를 대신한다
- **소유자 할당량 호출**: 채팅 처리 함수가 Space 시크릿의 소유자 토큰으로 `gradio_client.Client`를 열어 같은 Space의 점수 함수를 부른다. 토큰으로 인증한 호출은 그 계정의 할당량을 쓴다(HF 문서). 점수 함수는 `api_visibility="undocumented"`로 두어 공개 API 목록을 그대로 비운다(D-74). 토큰 값은 명령과 로그에 남기지 않는다
- **실패 뒤 일시 중단**: 점수 함수가 실패하면 그 질의는 RRF 순서로 답하고 답변 아래에 안내를 한 줄 보인다. 실패 후 일정 시간은 모든 방문자의 재정렬을 부르지 않고 RRF 순서로 답한 뒤, 시간이 지나면 다시 부른다. 할당량 초과면 오류 메시지의 대기 시간을, 그 밖의 실패나 대기 시간을 읽지 못한 경우는 config의 기본값을 쓴다. 실패와 건너뛴 사실, 오류 종류를 추적 메타데이터와 로그에 남긴다
- **시작 시간 측정과 병렬 읽기**: 시작 로그를 단계별(모듈 불러오기, 임베딩, BM25·조건 색인, 청크 위치, 코퍼스, 구간, 임베딩 모델, 리랭커)로 나눈다. 임베딩 조각, BM25, 코퍼스 읽기를 스레드로 동시에 돌리는 경로를 `deploy` 설정으로 켜고, Space에서 켠 경우와 끈 경우의 콜드 스타트를 잰다. 이어 붙이는 순서는 지금과 같게 둔다
- **설정**: 켜는 값, GPU 예약 시간(`duration`), 일시 중단 기본값, 병렬 읽기 값은 `configs/config.yaml`의 `deploy` 키, 안내 문구는 `app` 키에 둔다. 생성 레시피가 `retriever` 전체를 기록하므로 `retriever`에 키를 더하지 않는다. 앱의 재정렬 시작 거부(`src/rag/app.py:178`)는 점수 함수가 없을 때만 멈추게 바꾼다
- **후속 조각 기록**: PLAN에서 S40 앞에 화면 분리 조각(Vercel 정적 프론트, 브라우저가 Space API를 직접 호출, 하루 1회 cron, 공개 후 3일 관찰)을 더한다. 공개 후 재시작이 잦으면 백엔드 이전을 다시 본다는 줄을 함께 적는다(사용자 결정 2026-11-05). 조각 지시서는 S39 뒤에 쓴다
- **결정 기록**: 잰 값을 보이고 채택을 받은 뒤 DECISIONS에 적는다. PLAN S39 줄, SPEC 자원 제약의 "리랭커는 GPU 추론 서버" 문장, D-26·D-36의 서버 비용과 남은 일에 표시를 붙인다

## 결정 사항

1. **방안**: 같은 Space의 ZeroGPU에서 재정렬한다. 할당량이 떨어지면 재정렬을 뺀 검색을 쓴다(사용자 결정 2026-11-04). 처음 비교한 다른 안(CPU, HF Endpoint, 리랭커 없음)은 시험하지 않는다
2. **건너뛰는 범위(메인 적용)**: 할당량 오류만이 아니라 GPU 대기 시간 초과 같은 점수 함수 실패도 건너뛴다. 사용자 결정의 의도가 방문자 테스트가 막히지 않는 것이기 때문이다. 입력→동작: GPU 할당이 실패하면 오류 창 대신 재정렬 없는 답변과 안내가 나온다. 앱의 다른 오류(생성 API 실패 등)는 지금 그대로다
3. **OpenRouter 호출**: 약 25번, $0.02 이하로 본다(S38 추정과 같은 단가). 시작 시간 측정은 첫 답변까지 재지 않아 호출을 더하지 않는다. 재정렬은 무료 할당량 안이고 Colab과 유료 HF 하드웨어는 쓰지 않는다
4. **실패 뒤 재시도(사용자 채택 2026-11-05)**: 처음에는 요청마다 건너뛰었고, 이후 사용자가 실패를 기록하고 이후 요청을 재정렬 없이 처리하자고 정했다. 프로세스가 끝날 때까지 끄면 cron으로 깨워 둔 Space에서 일시적 실패 한 번으로 재정렬이 계속 꺼지므로, 일정 시간 뒤 다시 시도한다. 입력→동작: 할당량 초과로 "Try again in 3:00:00"이 오면 3시간 동안 부르지 않고, 대기 시간 초과면 기본값(1시간) 뒤 다시 부른다
5. **할당량 공유(사용자 결정 2026-11-05)**: 재정렬은 프로젝트 성능을 보이는 데 필수가 아니므로(재정렬 없는 검색 성능도 충분하다, 사용자) 소유자 할당량 하나를 나눠 쓴다. 입력→동작: 한 방문자가 할당량을 소진하면 초기화까지 모든 방문자가 재정렬 없는 답변과 안내를 받는다
6. **바꾸지 않는 것(사용자 결정 2026-11-05)**: 벡터 스토어를 도입하지 않고(D-80 유지), 문서 열람 규칙을 바꾸지 않는다(D-74, 직접 다운로드만 막고 열람은 막지 않는다)

## 노트북과 결정의 순서

지연·할당량 실측 몇 개로 정하는 결정이라 노트북을 쓰지 않는다(S38과 같다). 결과 절에 표로 적어 사용자에게 보이고, 결정을 받은 뒤 기록한다.

### 회고·보고 참고: 첫 토큰 시간과 ZeroGPU 우선순위

사용자 경험을 기준으로 첫 토큰 시간(질의 입력부터 답변 출력 시작까지)을 운영 기준으로 삼았고 상한은 3초다(D-30, 중앙값 판정 D-37). 리랭커를 운영에 넣을 때의 근거는 검색 부분 약 0.84초였다(로컬 CPU 검색 0.40초에 Colab T4 재정렬 0.44초를 더한 값, EXP-017). 이 값으로 3초 안에 들어온다고 추론했는데, 추론 서버의 네트워크 왕복과 기동 지연은 들어 있지 않았다(EXP-017 결정 사항 2).

ZeroGPU 배포에서는 GPU를 호출마다 공유 자원에서 받으므로 지연이 고정 GPU 측정과 달라질 수 있다. 지어낸 질의 20개의 실측은 아래와 같다.

| 항목 | 값 |
| --- | --- |
| 첫 토큰 시간 | 중앙값 1.75초, 최소 1.55초, 최대 8.41초 |
| 3초를 넘은 질의 | 20개 중 3개(8.41초, 5.63초, 3.26초) |
| 재정렬 호출 | 보통 0.36\~0.48초, 위 3개는 각각 5.37초, 4.36초, 1.91초 |

중앙값으로는 상한 안이지만, 느린 질의는 재정렬 호출이 늘어난 질의와 일치한다. 첫 질의(5.37초)는 GPU 작업자를 처음 띄운 비용이 섞였을 수 있다.

- **사용자 추정**: 재정렬을 포함한 지연이 늘어나는 것은 ZeroGPU의 우선순위와 관련 있을 것이다
- **출처가 있는 사실**: HF 문서는 대기열 우선순위가 계정 등급(비로그인 낮음, 무료 중간, PRO 가장 높음)과 남은 할당량에 따라 달라진다고 적는다. 이 구성은 소유자 무료 계정으로 호출하므로 중간이다
- **확인하지 못한 것**: 늘어난 시간이 대기열 대기인지, GPU 작업자 시작인지, 모델 전송인지 나눠 재지 않았다. 호출 전체 시간만 쟀다

보고에는 고정 GPU에서 잰 지연으로 운영 가능성을 추론했고, 공유 GPU 배포에서는 중앙값은 유지돼도 일부 질의가 상한을 넘을 수 있다고 적는다. 최종 3초 판정은 S41이다.
