# SPEC 개정 초안: 생성 단계 평가

SPEC에 더할 생성 단계 평가의 초안이다(D-38). 초안은 SPEC 밖에 두어 고칠 때마다 승인을 받지 않는다(사용자 결정, PR #99 코멘트). 남은 결정 사항이 정해지면 이 내용을 SPEC에 옮기며 사용자 승인을 받고, 개정 사실을 DECISIONS.md에 적는다. 옮기기 전에는 생성 EXP 판정에 쓰지 않는다.

## 문제

- 입력: 평가 질의 1건과 검색 기준 설정(D-36)이 고른 근거 문서 5개(D-11 `generator.context_docs`)
- 출력: 근거 번호 `[n]`을 붙인 한국어 답변, 또는 근거에서 답을 찾지 못했다는 거부 답변
- 생성 조건: OpenRouter `google/gemma-4-31b-it`, 제공자 CoreWeave 고정, 사고 과정 끔(D-37). 실험 간 비교는 `temperature` 0과 고정 프롬프트(`configs/prompt/`의 버전)로 한다
- 평가 질의: dev 분할의 평가 질의(`summary_q`). multi-doc 질의는 아래 보조 관찰로 따로 본다. 보정 표본은 판정용 질의와 겹치지 않게 뗀다(아래 judge 보정)
- test: 검색 단계와 같이 생성 단계 마지막에 사용자 지시로 1회만 쓴다(D-38). 그 전에는 test 질의를 읽거나 보내지 않는다. 지금 SPEC은 test를 검색 단계 종료 1회로만 허용하므로, 이 규칙은 SPEC에 옮긴 뒤에 효력이 있다. CLAUDE.md 금지 절은 이 조건을 붙여 적었다. SPEC에 옮길 때 CLAUDE.md 외부 전송 줄을 함께 고친다. protocol-guard P1·P6과 pr-briefer R6의 단계별 1회 문구는 하네스에서 먼저 고쳤고(ADR-0051), 옮길 때는 거기 남은 "SPEC 개정 전/뒤" 조건만 정리한다

## 기준

지표 정의는 RAGAS(Es et al., EACL 2024 System Demonstrations, arXiv:2309.15217)와 RGB(Chen et al., AAAI 2024, arXiv:2309.01431)를 빌려 고쳐 직접 구현한다. ragas·deepeval 라이브러리는 쓰지 않는다(D-38).

| 기준 | 묻는 것 | 출처 | 판정 방법 | 참조 답변 |
| --- | --- | --- | --- | --- |
| 충실성 | 답변의 진술이 근거에서 나오는가 | RAGAS 논문 faithfulness | judge가 답변을 진술로 나누고 진술마다 근거로 뒷받침되는지 판정, 뒷받침된 진술 수 / 전체 진술 수 | 필요 없음 |
| 답변 관련성 | 답변이 질의에 답하는가 | RAGAS 논문 answer relevance | judge 판정. 계산 방식(논문의 역질문 생성과 임베딩 유사도, 또는 judge 직접 채점)은 생성 평가 SLICE에서 정한다 | 필요 없음 |
| 핵심 답변 포함도 | 질의가 묻는 핵심 답이 답변에 들어 있는가 | ragas 라이브러리 answer correctness(RAGAS 논문에는 없음)를 고쳤다. 원래 지표와 고친 이유는 "기준 설명" 절 | judge가 `answer.comment`에서 질의에 답하는 핵심 진술만 뽑고, 진술마다 답변에 그 내용이 있는지 판정한다. 답변에 담긴 핵심 진술 수 / 핵심 진술 수 | `answer.comment`(결정 사항 1) |
| 거부 정확도 | 답이 없는 근거에서 거부하고, 답이 있는 근거에서 거부하지 않는가 | RGB negative rejection | 거부 문장은 거부 문구로 코드가 판정하고, 거부한 내용이 근거에 있는지는 judge가 판정한다(D-41, 아래 "거부 답변의 처리"). 답이 없는 근거 세트는 오라클 진단에서 정답 문서를 뺀 입력으로 만든다 | 필요 없음(근거 부족의 원인을 나눌 때만 쓴다) |

RAGAS 논문의 세 번째 기준 context relevance는 쓰지 않는다. 검색 품질은 검색 단계 지표(Recall@k)가 본다.

## 기준 설명

기준을 고른 근거와 각 기준이 무엇을 재는지 적는다. 예는 모두 지어낸 것이다(AI Hub 데이터가 아니다).

### 세 judge 기준이 맡는 실패

생성 답변의 실패를 셋으로 나누고, judge 기준이 하나씩 맡는다.

| 실패 | 맡는 기준 |
| --- | --- |
| 근거에 없는 내용을 지어냄 | 충실성 |
| 질의와 다른 이야기를 함 | 답변 관련성 |
| 질의에 맞는 이야기를 했지만 핵심 답을 빠뜨림 | 핵심 답변 포함도 |

충실성과 답변 관련성은 중복이 아니다. 충실성은 답변 진술이 근거 안에 있는지를, 답변 관련성은 답변이 질의에 답하는지를 본다. RAGAS 논문도 답변 관련성이 사실 여부를 보지 않는다고 적는다. 한쪽만 실패하는 경우가 둘 다 있다.

| 답변 | 충실성 | 답변 관련성 |
| --- | --- | --- |
| 근거에 있는 문장을 옮겼지만 질의와 다른 쟁점을 말함 | 높음 | 낮음 |
| 질의에 정면으로 답했지만 근거에 없는 수치를 지어냄 | 낮음 | 높음 |

두 점수 사이에 상관이 나올 수는 있다. 이는 두 실패가 함께 나는 경우가 많다는 뜻이지 같은 것을 잰다는 뜻은 아니다(추론).

세 번째 실패는 앞의 두 기준으로 잡히지 않는다. 근거에 있는 말만 했고(충실성 높음) 주제도 맞는데(관련성 높음) 답의 절반을 빠뜨린 답변이 그렇다. 무엇이 핵심 답인지 알려면 기준이 되는 답이 필요하고, 답변 발언 원문 `answer.comment`가 그 역할을 한다.

### 핵심 답변 포함도

**정의:** 질의가 묻는 핵심 답이 생성 답변에 얼마나 들어 있는지의 비율이다. 핵심 답은 `answer.comment`에서 뽑는다. 점수는 답변에 담긴 핵심 진술 수 / 핵심 진술 수이고 0\~1이다.

**계산 순서.** 질의 "○○ 사업 예산을 줄인 이유는?"에 대한 `answer.comment`(장관 답변 발언)가 (가) 인사와 질의 경위, (나) 집행률이 낮았다, (다) 유사 사업과 통합했다, (라) 다른 위원 질의 언급, (마) 내년 계획을 담고 있다고 하자.

1. 핵심 진술 뽑기: judge가 `answer.comment`에서 이 질의에 답하는 진술만 뽑는다. (나)·(다) 2개다. (가)·(라)·(마)는 같은 발언에 있지만 질의가 묻지 않은 내용이라 뺀다
2. 포함 판정: judge가 핵심 진술마다 생성 답변에 그 내용이 있는지 판정한다. 답변이 "집행률이 낮아 줄였습니다[1]."이면 (나)는 있고 (다)는 없다
3. 점수: 1 / 2 = 0.5

**원래 지표와 고친 이유.** ragas 라이브러리의 answer correctness(RAGAS 논문에는 없음)는 참조 답변 전체와 답변을 진술 단위로 대조한 F1(TP / (TP + 0.5·(FP + FN)))과 의미 유사도를 가중 결합한다(v0.2.15 기본 0.75·0.25). 의미 유사도의 근거 문헌은 SAS(Risch et al., "Semantic Answer Similarity for Evaluating Question Answering Models", MRQA@EMNLP 2021, arXiv:2108.06130)다. 지금 ragas 문서는 이 지표 대신 factual correctness(진술 단위 정밀도·재현율·F1)와 semantic similarity를 따로 둔다. 두 가지를 고쳤다.

- 질의로 거른다: 위 예에 원래 F1을 쓰면 참조 진술 5개, 답변 진술 1개 중 (나)가 맞아 재현율 1/5, 정밀도 1/1, F1 = 2·(0.2·1) / (0.2 + 1) ≈ 0.33이다. 질의가 묻지 않은 (가)·(라)·(마)를 빠뜨린 것까지 감점되어, 질의에 맞게 간결히 답할수록 점수가 낮아진다. `answer.comment`가 질의자 질문 전체에 대한 응답이라 생기는 문제다
- 재현율만 쓴다: `answer.comment`는 거의 모두 정답 문서 `context` 안에 그대로 있다(`docs/data.md` §7, 39,633건 중 39,467건). 그래서 정밀도(답변 진술이 참조에 있는가)는 "답변이 근거에 있는 말만 했는가"와 거의 같아져 충실성과 겹친다(추론). 답변이 지어낸 내용은 충실성이 감점한다. 의미 유사도 항도 쓰지 않는다

**계산에서 빼는 질의.** 아래 경우는 점수 0으로 두지 않고 뺀다. 0으로 두면 생성 답변의 잘못이 아닌 것을 감점하게 된다.

- 참조 사용 불가: 1단계에서 핵심 진술이 하나도 뽑히지 않는 경우다. `answer.comment`가 "검토해 보겠습니다"처럼 답을 피한 발언이거나 질의와 범위가 맞지 않으면 기준이 될 답이 없다. 비율을 따로 보고한다
- 정답 문서가 근거 상위 5개에 없는 경우: 검색이 놓쳐 답변이 핵심 답을 담을 수 없다. 이 실패는 검색 지표가 맡는다
- 전체 거부 답변: 거부 정확도로만 평가한다. 부분 거부 답변은 거부 문장을 뺀 내용을 채점한다(아래 "거부 답변의 처리")

**짝지은 비교.** 빼는 질의가 실행마다 달라, 기준과 후보를 비교할 때는 두 실행 중 하나라도 빼는 조건에 해당한 질의를 양쪽에서 함께 뺀다. 그대로 두면 paired bootstrap의 짝이 맞지 않는다.

**정하는 방법.** dev-small에서 참조 사용 불가 비율과, 남은 질의의 점수가 사람 판단과 맞는지를 보고 종합 지표에 넣을지 보조 지표로 둘지 정한다(결정 사항 1). 관찰은 기준 설정 출력만으로 하고, 후보 설정끼리 비교한 결과를 보고 정하지 않는다(사용자 결정, PR #100). dev-small 질의는 dev-full 판정 질의에 들어 있어, 후보 비교를 보고 지표를 정하면 판정 질의로 지표를 고르는 셈이 되기 때문이다.

### 거부 답변의 처리

거부는 문장 단위로 본다(D-41). 거부 문구를 담은 문장이 거부 문장이고, 내용 문장이 없으면 전체 거부, 있으면 부분 거부다.

- 전체 거부 답변은 거부 정확도로만 평가하고 충실성·답변 관련성 계산에서도 뺀다. "근거에서 찾지 못했습니다"는 진술이 없어 충실성이 정의되지 않고, 답변 관련성은 거부를 낮게 매겨 거부 정확도와 같은 일을 두 번 세게 된다
- 부분 거부 답변은 거부 문장을 뺀 내용으로 충실성·답변 관련성·인용 검사를 하고, 핵심 답변 포함도는 답변 전체로 본다. 답하지 못한 부분은 포함도와 거부 평가가 맡는다(PR #106 코멘트)
- 거부 문장마다 judge가 근거 5개 전체를 보고 이유를 나눈다. 근거에 답이 있으면 잘못된 거부, 근거에 없으면 적절한 거부다. 근거가 "예정", "검토 중", "정해지지 않음"으로만 말하거나 답변자가 답을 피한 경우는 상황 미전달로 따로 세고 거부 정확도에 넣지 않는다. 지금 생성 프롬프트는 이런 경우를 전하라고 지시하지 않기 때문이다(생성 실험 아이디어 PLAN H18). 근거 부족은 원인(정답 문서 없음, 청크 잘림 추정, 기타)을 나눠 검색·청킹 개선 근거로 보고한다

어려운 질의에서 거부를 늘리면 세 judge 기준이 함께 오를 수 있다. 이를 막는 것은 거부 정확도의 "답이 있는 근거에서 거부하지 않는가"이므로, 거부 정확도를 종합 지표에 넣을지를 결정 사항 2에서 함께 정한다.

## 코드로 판정하는 항목

LLM 없이 처리하고 judge에 넘기지 않는다(PLAN "생성 평가" 절).

- 인용 번호 유효성: 답변의 `[n]`이 실제로 넣은 근거 번호(1\~5) 안에 있는가, 인용이 없는 진술 문장이 있는가
- 거부 문구: 프롬프트가 지정한 거부 문구가 답변에 있는가. RGB도 지정 문구 일치(Rej)를 쓰고, 문구를 따르지 않은 거부는 LLM 판정(Rej\*)으로 따로 셌다. 지정 문구를 따르지 않는 거부의 비율은 보정 표본에서 본다
- 메타데이터 일치: 답변에 나온 발언자·회의 일자가 인용한 문서의 메타데이터와 맞는가(대조 범위는 생성 평가 SLICE에서 정한다)

## judge

- 모델은 DeepSeek V4.1 Flash, 경로는 opencode Go 구독(`deepseek-v4.1-flash`)이다(D-38). 생성 모델(Gemma 4)과 다른 계열이다. opencode Go는 judge 용도로 D-31 허용 처리처에 들어 있다(D-38)
- 제공자, 모델, 파라미터(`temperature` 0 등), 프롬프트를 `configs/`에서 버전 관리한다. 실행 기록과 LangSmith 메타데이터에 레시피(git 커밋, 생성 레시피, judge 레시피, 프롬프트 SHA-256)를 남긴다
- opencode Go 이용 조건(https://opencode.ai/docs/go/, 2026-10-19 확인): OpenCode와 비슷한 요청을 내는 코딩 에이전트용으로 설계했고 남용을 감시한다. 사용량 한도는 월 금액이고 5시간에 20%, 주에 50%까지 쓸 수 있다. 학습 미사용, 보존 0일(ZDR)이고 ZDR 협약은 매달 갱신하며 지금 협약은 2026-10-31까지다. 배치 판정으로 의심받아 사용이 막히면 그때 경로를 다시 정한다(D-38). 대안은 같은 모델의 OpenRouter 경로(`deepseek/deepseek-v4.1-flash`, 2026-10-19 확인)다
- judge 보정: dev 표본 30\~50건을 사람이 기준별로 채점하고(G 게이트, meet-rag D 흐름), judge가 같은 표본을 채점해 기준별 일치율과 Cohen's kappa를 잰다. 일치가 낮은 기준은 기준 문구나 judge 모델을 바꾸고, 충분해진 뒤에 판정에 쓴다. 보정 표본은 판정용 질의에서 뺀다

## 오라클 진단

정답 문서를 근거에 직접 넣는 조건은 매 실험이 아니라 진단용으로 한 번 한다(D-38).

- 검색 기준 근거와 오라클 근거의 점수 차이로 생성 실패와 검색 실패를 가른다
- 근거에서 정답 문서를 뺀 입력은 거부 정확도 세트로 쓴다. 다만 정답 문서 밖에도 답을 담은 문서가 있을 수 있어(SPEC 해석의 한계 2항, D-34의 "다른 정답" 9개) 이 세트의 "거부해야 함" 라벨에는 잡음이 있다

- 재표본 단위는 검색 판정과 같은 회의, 반복 10,000회, seed 20260929로 기준과의 차이를 paired bootstrap 95% 구간으로 낸다
- 채택·기각·보류 규칙은 결정 사항 2·3이 정해진 뒤 적는다

## 보조 관찰: multi-doc 질의

검색 단계와 같이 multi-doc 질의로도 생성을 평가하되 판정에는 쓰지 않는다(사용자 결정, PR #99). 근거가 여러 문서에 나뉜 질의에서 답변이 문서들을 합쳐 답하는지를 single-doc 질의로는 볼 수 없기 때문이다.

- 질의 세트: G3 동결 세트 `queries_g3.jsonl` 600건(D-15). dev 전용이고 고치지 않는다
- 기준: 위 기준 표와 코드 판정 항목을 그대로 쓴다. 생성 EXP마다 single-doc 결과와 함께 보고한다
- 기준 실험과의 차이는 paired bootstrap 95% 구간으로 보고하고 판정 라벨을 붙이지 않는다. 재표본 단위는 SPEC multi-doc 보조 관찰과 같은 `pool_id`, 반복 횟수와 seed는 위 판정 절과 같다
- 핵심 답변 포함도의 참조 답변: 세트의 기대 답(`answer`)은 검수하지 않은 참고 자료이고, 표본 통과 47건 중 16건에 기대 답·요소 문제가 있었다(D-15 단서). 참조로 쓸지는 결정 사항 1과 함께 정한다
- 해석의 한계: 질의 수가 single-doc보다 적어 구간이 넓으므로 방향과 큰 변화만 읽는다(SPEC multi-doc 보조 관찰과 같다)

## 결정 사항

1. 핵심 답변 포함도의 위치: 참조 답변은 `answer.comment`로 한다. 답변 발언 원문이라 질의의 답 내용을 그대로 담고 있고, `summary_a`는 KoAlpaca(LLaMA 7B)가 그 내용을 요약한 생성물이라 쓰지 않는다(사용자 결정, PR #99). 다만 `answer.comment`는 질의자 질문 전체에 대한 응답이라 평가 질의와 범위가 다를 수 있고, 정치적 고려로 직접 답을 피하기도 한다. dev-small에서 핵심 답변 포함도를 재 보고, 참조 사용 불가 비율과 남은 질의의 점수가 사람 판단과 맞는지를 근거로 종합 지표(결정 사항 2)에 넣을지 보조 지표로 관찰할지 정한다. 관찰은 기준 설정 출력만으로 하고, 후보 설정끼리 비교한 결과를 보고 정하지 않는다(사용자 결정, PR #100). dev-small 질의는 dev-full 판정 질의에 들어 있어, 후보 비교를 보고 지표를 정하면 판정 질의로 지표를 고르는 셈이 되기 때문이다
2. 종합 지표 구성: 주지표는 RAGAS 기준을 결합한 종합 지표다(D-38). 결합할 기준과 방식(평균, 가중치)은 핵심 답변 포함도의 위치(결정 사항 1)와 judge 보정 결과를 보고 정한다
3. 최소 개선 폭: 추가 논의한다(사용자, PR #99 코멘트). 기준 설정을 반복 실행해 생성과 judge의 변동 폭을 재는 것이 근거가 된다(D-35, `docs/ML 프로젝트 문서 작성 원칙.md` EXP 원칙)
4. judge 보정의 통과 수준: 기준별 일치율·kappa가 얼마 이상이면 판정에 쓰는지
