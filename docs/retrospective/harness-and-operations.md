# 하네스와 ML 프로젝트 운영 회고 (meet-rag, 2026-11-06, 완료 시점 보강 2026-11-09)

## 결론

1. 프로젝트가 늘어진 원인은 둘이다. 최종 산출물(생성 답변)의 평가를 검색 단계 뒤로 미뤘고, 평가 모듈(LLM judge)을 언제 그만 고칠지 기준이 없었다 [사용자]. 병렬이 부족했던 것도 있지만 비중은 작다.
2. 11/4 회고 상담에서 정한 방향은 그 뒤 바뀌지 않았다. 빠져 있던 제안 둘(B4, C2)은 11/6에 원칙 문서에 넣었고 C3·C4는 전역 규칙으로 올렸다(아래 "원칙 문서에 반영한 것"). 그 뒤 늘어난 하네스(세션 병행, opencode worker, 디자인 스킬, 리뷰 범위)는 필요에 따라 더한 것이다 [사용자].
3. 다음 프로젝트에서 처음부터 둘 것: 넓은 자율 범위, 작성과 검증의 분리, 일일 코드 리뷰, opencode worker, 디자인 스킬, 평가기 수정을 멈추는 기준 [사용자].
4. 성과 주장의 약점: 외부 데이터·벤치마크와 비교하지 않았고, 직접 만든 평가기(judge)의 정확도를 검증하지 않은 채 그 점수를 결과로 썼다 [사용자, 2026-11-06]. 다음 프로젝트에서는 데이터의 과제 적합성 점검, 평가기의 변형 시험, 외부 비교를 계획 단계에 넣는다.
5. 하네스는 파일을 복사하지 않는다. 원칙 문서(`docs/ML 프로젝트 문서 작성 원칙.md`)와 이 문서를 `/harness`의 입력으로 쓰고, 그대로 쓸 수 있는 훅·에이전트·워크플로만 작은 묶음으로 가져간다.
6. Claude가 저지른 가장 큰 실수 둘(사용자 평가, 2026-11-06): 사용자가 검수 중이던 파일을 worktree 정리 중 지운 것, 비밀 값 출력을 막는 거부 규칙을 확인하지 않고 사용자에게 권한 완화를 요청한 것. 공통 원인은 되돌리기 어렵거나 보호 장치가 걸린 일 앞에서 대상과 그 장치가 지키는 것을 확인하지 않고 움직인 것이다

## 늘어진 원인

### 1. 최종 산출물의 평가를 미뤘다

RAG를 처음 하면서 생성 평가를 검색 단계 뒤로 미뤘고, 처음 만든 RAG에는 생성 평가가 없었다 [사용자]. 검색 EXP를 모두 마친 뒤 평가 모듈을 만드느라 6.5작업일이 들었다 [기록]. 생성 평가 도구는 검색 설정과 무관하게 만들 수 있어, 지금의 지식으로 다시 하면 검색 EXP와 나란히 만든다(2\~4일 절감 [추론]).

원칙 문서에 반영했다: 지표가 주어지지 않는 프로젝트는 최종 산출물을 채점하는 단계까지 먼저 연결하고, 평가 설계가 없으면 기성 도구를 고치지 않고 붙여 점수만 나오게 둔다(원칙 문서 PLAN 절 B1). 평가 미결이 앞 단계 실험까지 막지 않게 했다(B2).

Kaggle처럼 지표가 주어지는 프로젝트에서는 이 문제가 작아진다. 다만 대회 지표와 실제로 보고 싶은 성능이 다르면(예: 리더보드 점수와 보정된 확률) 같은 문제가 다시 생긴다 [추론].

### 2. 평가기 수정을 멈출 기준이 없었다

- judge 지시가 10/20 하루에 j_v2에서 j_v5까지 바뀌었고, 10/26에 j_v8로 동결한 뒤에도 11/3에 j_v13까지 갔다 [기록]
- 생성 EXP 6개의 기준선은 모두 재채점 결과였고, 서로 다른 기준선이 5개였다 [기록]
- ragas를 조금 고칠 예상이 빗나간 이유는 지표 수식이 아니라 회의록 고유의 판정 규칙(질의자 주장, 부분 거부)에 시간이 들어서였다 [추론]
- 오차 분석(S43)에서 세트 밖 100질의의 손실 몫은 답변 오류 47.6%, judge 적용 잡음 31.5%, 규칙과 지시의 충돌 10.5%였다 [기록, 서브에이전트 판독]. judge를 고치면 지금까지의 개선폭을 같은 지표로 설명할 수 없어 고치지 않았다(D-82) [사용자]

사람 검수는 개인 프로젝트에서 쓰기 어려운 수단이었다 [사용자]. 대신 쓸 멈춤 기준을 원칙 문서에 넣었다(SPEC 절 B3).

1. 같은 입력을 반복 실행해 흔들림을 재고, 그 폭 안의 차이는 노이즈로 본다
2. 실험 판정을 뒤집는 오류만 고치고 나머지는 기록만 한다
3. 답변을 일부러 망가뜨려 평가기가 잡는지 확인한다

한계: 알려진 유형의 오류를 잡는지만 보여 주고 평가기의 실제 정확도는 보여 주지 못한다.

### 3. 자율 범위를 좁게 시작했다

작은 판단까지 사용자에게 넘어가 PR 리뷰와 이슈 처리에 시간이 들었다 [사용자]. 병목은 PR 수가 아니라 PR마다 넘어간 판단의 개수였다 [사용자]. 10/14(ADR-0041)과 10/29(ADR-0077)에 묻는 범위를 줄였다. 11/3\~11/4에 처리량이 높았지만(커밋 89, 125개, 2026-11-09 기준) 세션 병행, 자율 범위 확대, 평가기 안정이 겹쳐 각각의 기여는 나눌 수 없다 [기록].

### 4. 성과를 바깥에서 확인할 장치가 없었다

[사용자, 2026-11-06 대화] 늘어진 원인과 별개로, 결과를 성과로 주장하기 어렵게 만든 약점이다.

- 데이터: RAG용 한국어 데이터를 찾지 못해 RAG 평가용이 아닌 데이터를 골랐다. 선택 자체는 무리가 아니었지만(실제 RAG의 흔한 조건이고 두 성과가 여기서 나왔다), 착수 전에 과제 적합성(정답 문서 수, 질의를 만든 방식, 답변 정답 유무)을 점검하지 않아 생성 평가를 미루게 됐다
- 외부 비교: 공개 벤치마크나 외부 데이터에 최종 설정을 돌려 보지 않아 모든 수치가 이 데이터 안의 결과다
- 평가기 검증: 직접 만든 judge로 채점한 결과를 성과로 쓰려면 judge의 신뢰성 검증이 먼저인데 하지 않았다. 블라인드 확인(S25)은 1질의에서 멈췄다(D-51)
- 개인 프로젝트의 제약: 사람 평가는 평가자가 한 명이라 신뢰성 근거가 되지 않는다. 복수 평가자가 필요한데 개인 프로젝트에서는 할 수 없다. 그래서 남는 수단은 변형 시험(답변을 일부러 망가뜨려 잡는지)과 주장 범위를 좁히는 것이다. 변형 시험은 회고 뒤 S53으로 했다. 뚜렷한 오류 세 유형(근거 없는 진술, 발언자 잘못 귀속, 무관한 답변)을 50건 중 하나도 놓치지 않았고, 미묘한 오류의 검출률은 재지 못했다(`project-rag.md` 3.4)

### 5. 첫 경험의 학습 비용

RAG·생성 평가 개념, PR로 에이전트와 일하는 방식에 적응하는 데 든 시간은 다음 프로젝트에서 대부분 다시 들지 않는다 [사용자]. git 기록에 따로 남지 않아 크기를 나누지 못했다.

## 사용자의 운영 방식

다음 프로젝트에서 같은 패턴을 알아보려고 적는다.

- 잘한 것 [사용자]: 작업을 SLICE와 EXP로 나눈 것, 폴더별 CLAUDE.md, GitHub Actions 일일 리뷰, 코드 품질 조치, 앞 결정에 비춰 다시 묻지 않게 한 것, 자율 범위 설정

- 판단 방식 [기록]: 비용·위험이 있는 일(Colab, 유료 API, test 1회, 외부 공개)은 직접 승인했고, 그 밖은 점점 메인에 맡겼다. 결정마다 이유와 감수하는 것을 적게 했다
- 리뷰 방식 [기록]: PR 화면에서 diff를 한 번 읽고 판단한다. 리뷰는 대화로 남기고 기록은 PR 댓글로 받는다. 같은 계정의 PR 코멘트는 세션이 받지 못해 대화가 주 경로가 됐다
- 작업 시간 [기록]: 커밋의 약 95%가 10시\~19시다
- 하네스 수정 [사용자]: 하네스 작업이 많았지만(chore PR 78개) 허들은 아니었다

### 측정으로 판정하는 ML 프로젝트에서만

- 평가 도구 보호와 test 단계별 1회: 경로와 지표만 바꾼다
- EXP 문서와 판정선을 실행 전에 쓴다(ADR-0037). 결정의 근거 노트북을 결정보다 먼저 쓴다(ADR-0009)
- 평가기를 직접 만들면 멈춤 기준 셋을 먼저 정하고, 변형 시험을 평가기 완성 조건에 넣는다. 사람 일치도는 평가자가 여럿일 때만 근거가 된다
- 데이터를 고를 때 과제 적합성(정답 수, 질의를 만든 방식, 답변 정답 유무)을 착수 전에 표로 점검한다
- 성과를 주장할 수치는 외부 기준(공개 벤치마크, 알려진 기준선)과 한 번은 비교하는 계획을 둔다. Kaggle은 리더보드가 이 역할을 한다
- 실험 판정은 회의 단위 paired bootstrap처럼 데이터의 묶음 단위로 구간을 낸다
- Colab 보조 스크립트와 복구 절차: Colab을 다시 쓸 때만

### autoresearch·Kaggle 구상에 비춰 [추론]

- Kaggle은 지표와 test(리더보드)가 주어져 "평가가 주어지지 않은 프로젝트"의 문제는 작다. 대신 CV 설계와 리더보드 과적합이 평가 보호의 대상이 된다. test 단계별 1회 규칙은 "공개 리더보드 제출 횟수와 최종 제출 선택 기준을 미리 정한다"로 옮긴다
- 실험 반복이 많아지면 실행 대기와 판정이 병목이 된다. EXP 판정선을 미리 쓰는 규칙과 판정 에이전트 분리가 더 중요해진다
- opencode worker는 판단 없는 일(문헌·노트북 조사, 결과 표 모으기)에 맞다. 실험 판정과 다음 실험 결정은 Claude에 둔다

## 남은 관찰 [기록]

하네스 대기 목록에서 `관찰`로 남은 11건 중 다음 프로젝트에도 해당하는 것:

- 지표가 나오는 실행 뒤 결과를 보고하고 멈추지 않고 PR로 넘어감(반복되면 흐름에 넣는다)
- 요청하지 않은 후속 측정을 남은 일에 넣음
- 에이전트가 검증하는 중에 메인이 대상 파일을 고쳐 어느 코드로 검증했는지 흐려짐
- Windows 기본 인코딩(cp949) 때문에 `PYTHONUTF8=1` 없이 테스트 1건이 실패함
- 파일 손상 검사 훅이 한 명령에 묶인 `sed -i`와 `git commit`을 보지 못함
- 판단 없는 공개 웹 조사를 worker에 맡기지 않고 메인이 직접 해 작업이 멈춤(규칙은 있었고 적용하지 않음)
